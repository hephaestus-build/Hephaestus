The number of reviews that run at once now follows the memory that your sandbox nodes give review Pods, instead of a fixed count per worker. The chart divides `worker.sandbox.reviewMemory` by one review Pod's request and its RuntimeClass overhead, sizes the reviews quota for that many reviews, and lets each worker run as many of them as its memory limit holds. When a review Pod requests less, more reviews run in the same memory, with no change to your values. The default of 3840 MiB keeps 10 reviews. A single node with `small.yaml` now runs five reviews at once instead of one, and keeps its 32 conversation turns. **Operators:** remove `worker.reviews` from your values file. To keep the same number of reviews, set `worker.sandbox.reviewMemory` to your old `worker.reviews` times your worker replicas times 384Mi plus `worker.runtime.podOverhead.memoryMi`. The check on the worker's memory limit now also counts the 128 MiB of direct memory that the JVM takes from the heap, which the old check left out. One review needs a limit of at least 1023 MiB, and 2 GiB holds 57 reviews. A worker memory limit that the old check passed can now hold fewer reviews, and a limit below 1023 MiB stops the render with that minimum. Such a worker never had the heap that the old check promised to its reviews. To keep a worker's reviews, raise `worker.resources.limits.memory` by 128 MiB.
