# Accessibility — the posture, and what axe cannot see

**The baseline is already at ceiling. Protect it. Do not propose work here.**
`webapp/.storybook/preview.tsx` sets `a11y: { test: "error" }` project-wide, and its one global
exclusion (`[data-base-ui-focus-guard]`) cites the upstream Base UI issue in a comment beside it. A
story that suppresses the check fails the build — `hephaestus/no-story-a11y-override` reads both
`parameters.a11y` and `globals.a11y`. If a rule genuinely misfires, the exclusion goes in
that file with the upstream link beside it, never in a story.

**A green axe panel is the floor, not the goal.** The addon is axe-core, which

*"automatically catches up to 57% of WCAG issues"*

(storybook.js.org/docs/writing-tests/accessibility-testing). Everything below is what it misses.

## The three things axe does not check for us

1. **A name that disambiguates two instances on one screen.** Axe sees "has an accessible name". It
   cannot see that both copies are called the same thing. A component with no visible label *requires*
   `aria-label`/`aria-labelledby` in its props type — see `props-state-shape.md` rule 5.

2. **A state conveyed by colour needs a second channel.** The registries make `icon` required for
   exactly this reason — see `vocabulary-registries.md` rule 1 (WCAG 2.2 SC 1.4.1).

3. **`aria-invalid` announces *that* a field is wrong and never *why*.** A field marked `aria-invalid` also points `aria-describedby` at the element carrying its message.
   Thus, a reader who tabs back hears the reason, not "invalid" alone.
   See WCAG 2.2 SC 3.3.1.
   Use `aria-describedby`, **not** a live region.
   A live region re-announces on every keystroke.

## Hover cards carry supplementary content only

A hover card must never hold the only copy of a fact or the only control that reaches one.
Hover is unavailable on touch and awkward on keyboard. Everything in the card must also be on the page its link
goes to.

WCAG 2.2 SC 1.4.13 is the normative rule.
Content shown on hover or focus must be **dismissible**:

<!-- vale STE.SentenceLength = NO -->
*"A mechanism is available to dismiss the additional content without moving pointer hover or keyboard
focus, unless the additional content communicates an input error or does not obscure or replace other
content"*
<!-- vale STE.SentenceLength = YES -->

It must be **hoverable**:

*"the pointer can be moved over the additional content without the additional
content disappearing"*

It must be **persistent**:

*"remains visible until the hover or focus trigger is
removed, the user dismisses it, or its information is no longer valid"*

The additional "destination is a superset of the card" clause is house policy.
<https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html>

## Hide rather than disable, for permissions specifically

Disabling is the better default for a control the user could still unlock. If their role will never unlock a control, hide it.
A native `disabled` button is unreachable by keyboard.
Thus, a tooltip that explains why can never be read. Details in `webapp/AGENTS.md` § Role-based gating.

## The A+ move

Assert the invariant that axe cannot see.
A disabled control must be genuinely out of the tab order (`expectGenuinelyDisabled`, `webapp/src/test/controls.ts`).
Or an error field's `aria-describedby` must point at the element carrying its message. A regression then fails the suite instead of silently degrading.
