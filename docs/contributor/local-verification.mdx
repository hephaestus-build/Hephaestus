# Local verification

| Command                 | What success proves                                           | Excludes                                                                                                                         |
| ----------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `vp run check:affected` | Selected gates passed, including any tests they contain       | Unselected scopes, verification-only suites and builds, and CI-only checks                                                       |
| `vp run check`          | Every gate the `quality` task in `vite.config.ts` runs passed | Distributable builds, browser and live-service tests, images, mutation analysis, and release security                            |
| `vp run verify`         | The local verification suites and builds passed               | Server integration and database tests, full-application E2E, live-service tests, images, mutation analysis, and release security |

Run `check:affected` while working, `check` before pushing, and `verify` before requesting review.
`vp run` with no task name lists every task, and `vite.config.ts` is where each one is defined.

## Affected selection

The command compares committed, staged, unstaged, untracked, and deleted paths with the merge base of
`origin/main`. For another target, run `vp run check:affected --base <revision>`.

| Changed path                                                                                                                                                                                         | Task                                  |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| `webapp/**`                                                                                                                                                                                          | `affected:webapp`                     |
| `server/**` outside the agent and precompute resources                                                                                                                                               | `affected:server`                     |
| `server/**/resources/{agent,practices/precompute}/**`, `docker/agents/**`                                                                                                                            | `affected:agents`                     |
| `docs/**`                                                                                                                                                                                            | `affected:docs`                       |
| `docs/images/readme/**`                                                                                                                                                                              | `affected:docs` and `affected:webapp` |
| `.github/**`, `.claude/**`, `.agents/**`, `.changeset/**`, `scripts/**`, `webapp/tools/oxlint/**`, root package and tsconfig files, generated artifacts, `AGENTS.md`, `CLAUDE.md`, or any other path | `quality`                             |

The tasks are defined in `vite.config.ts`. Selection uses `git diff --no-renames`, so both sides of a
rename are evaluated. Git documents the underlying change statuses in
[`git diff`](https://git-scm.com/docs/git-diff#Documentation/git-diff.txt---diff-filterACDMRTUXB).

## Pre-push hook

`vp install` configures the Vite+ hook dispatcher, which runs the project hooks in `.vite-hooks/`.
It preserves a custom `core.hooksPath` and the local preference set by `vp hooks disable`;
`vp hooks enable` re-enables the dispatcher. `vp hooks status` shows which hooks are active.
The pre-push hook runs `vp run check`; `git push --no-verify` skips it. With custom hooks, run
`vp run check` yourself before pushing.

## Complete local verification

`vp run verify` runs `quality`, then the webapp unit tests, the Storybook browser tests,
`test:server:selection` followed by `test:server:verification` (unit and architecture with coverage), the webapp build with a
`routeTree.gen.ts` comparison that restores the committed file before exiting, the Storybook build,
and the docs build.

Server integration and database tests, full-application E2E, live-service tests, image builds,
mutation analysis and release security are outside `verify`; see [CI/CD](./ci-cd.mdx).
Run affected server integration tests separately with `vp run test:server:integration`.

## Vite+ task cache

On Windows the runner's automatic input tracking misses a file you add, so run
`vp run --no-cache check` there.

`quality` is a group: its gates run in parallel, and a cacheable gate whose inputs are unchanged replays.
`vite.config.ts` states which gates are uncached and which name their inputs. Run
`vp run --last-details` to inspect the latest run and its miss reasons, or `vp cache clean` to
discard the local cache. In CI the cache restores per [CI/CD](./ci-cd.mdx#caches).

### Java checks and caching

`gate:server` invokes Gradle once for build-script formatting, Java formatting and PMD. Gradle owns
their inputs and cached outputs; Vite does not cache a second verdict over the Java build. The scoped
commands `format:java:check` and `lint:java` use the same native tasks. Test execution remains uncached.

`vp run --no-cache check` disables Vite's cache, not Gradle's. To inspect a Java check without task-output
or configuration-cache reuse, run:

```sh
./server/gradlew -p server :spotlessCheck :application:spotlessCheck :application:pmdMain \
  --rerun-tasks --no-build-cache --no-configuration-cache --profile
```

The generated HTML report is `server/build/reports/profile/profile-*.html`. Keep clean, warm and cache-restored
measurements separate; [Gradle's performance guide](https://docs.gradle.org/current/userguide/performance.html)
explains why a baseline is needed before changing the build.

PMD must analyze every selected source successfully: a report containing processing or configuration
errors fails the task, even when it contains no rule violations. `vp run gate:pmd-canary` proves this
with clean, rule-violating and unparseable sources in a temporary directory. It checks the production
task's source coverage and annotation policy without editing or compiling the application's source
files. CI runs it when its implementation or PMD wiring changes.

The facts the graph relies on are gates of their own: `gate:runner-contract` proves how `vp run`
executes commands, and `gate:lint-contract` proves every house rule still fires through `vp lint`.
