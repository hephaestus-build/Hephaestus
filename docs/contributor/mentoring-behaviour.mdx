Hephaestus reaches out only when it helps, at a moment that fits, and the person stays in control of every contact.
This page gives the rules for contact, notifications, check-ins, goals, help settings and tone.
Read it if you build a part that talks to a person, or if you review how Hephaestus behaves.
Each rule has an ID, such as `C3` or `N2`, so that an issue, a test or a review comment can cite it.

The **Decided in** column names the proposed ADR that owns each rule.
[Mentoring framework](./mentoring-framework.mdx) gives the whole design and the reasons.

:::note
This page describes an accepted design. The current release has the weekly digest and the conversation, but not the rest.
:::

## The constraint

When Hephaestus interrupts too often, people learn to ignore it.
Hephaestus must reach out to keep an agreement.
The design solves this with one distinction: an entry in the app does not interrupt, and a notification does.
So Hephaestus is present in the app at all times, and it limits only notifications.
Silence never changes what Hephaestus does. Only the person's explicit controls do.

## The contact policy

The [contact policy](./practice-review-glossary.mdx#mentoring-terms-planned) runs when a message is committed, and again before each send.

### Kinds of contact

| ID | Kind | In the app | As a notification | Decided in |
| --- | --- | --- | --- | --- |
| C1 | An answer | At once, streamed | One push if the answer is unread 30 seconds after its turn ends, unless the person is active in that workspace | [ADR 0116](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0116-a-push-is-one-web-push-message-from-the-instance.md), ADR 0139 |
| C2 | A result that the person asked for | At once | At once, at any hour, outside the daily limit. **Pause** removes only this notification. | ADR 0139 |
| C3 | An agreed contact: a check-in or a goal follow-up | At its time | At its slot, outside the daily limit. In quiet hours it waits, unless the person set the slot inside them. Under **Pause** the occurrence is skipped. | ADR 0139, ADR 0133 |
| C4 | An unprompted update | Only if it passes the eligibility check (C5) | Under the daily limit, never in quiet hours | ADR 0139 |

### When Hephaestus starts a message

| ID | Rule | Decided in |
| --- | --- | --- |
| C5 | An unprompted message carries a problem in a new admitted observation, a material change on an agreed goal, or an awaited result. A new problem counts only when its practice has a current agreement qualification (ADR 0142). | ADR 0139, ADR 0142 |
| C5a | A withheld copy on the work with a Critical or Major problem also qualifies. The reasons are the deadline, a second guardrail refusal and an expired approval. That message is unprompted contact, so **Pause** or a mute blocks it. The item card always shows the withheld state. Nothing else qualifies. | ADR 0122, ADR 0139 |
| C6 | Code decides whether a finished review or task starts a turn. The model decides nothing about it. | ADR 0120, ADR 0139 |
| C7 | A background turn writes at most one message, or none. Three results in one minute become one message. | ADR 0120 |
| C8 | The same problem on the same version is never sent twice. A new version can be sent. | ADR 0139 |
| C9 | The instance and the workspace can turn off messages that Hephaestus starts. The person's controls narrow further. Rules narrow, never widen. | ADR 0139 |
| C10 | Optional background items wait until two minutes after the person's last message. A requested result and an agreed check-in never wait. | ADR 0139 |
| C11 | Each decision to reach a person, except an answer to their message, writes one delivery decision. ADR 0149 (proposed in #4868) decides what a delivery experiment may draw. | ADR 0139, ADR 0149 |

### The order of checks

At each boundary the checks run in this order:

1. The authorization recheck: may Hephaestus still read and send this?
2. The route and its limits: which channel, and is that channel on?
3. The contact policy: Pause, the card mute, then the person's activity, quiet hours and the daily limit.

ADR 0134 (proposed in #4863) owns this order. A contact change never counts as a permission change.
**Pause**, quiet hours and **Not now** never stop an answer that streams, and never reset a cache.

## The notification budget

The [review glossary](./practice-review-glossary.mdx#mentoring-terms-planned) defines the notification budget.
A Slack direct message that Hephaestus starts is its one interrupting effect. These rules apply at its send, and its app entry commits either way (ADR 0139).

| ID | Rule | Decided in |
| --- | --- | --- |
| N1 | At most one notification for each committed message. Code decides it at commit, never the model. | ADR 0139 |
| N2 | The initiative level caps only unprompted notifications. **Sometimes**, the default, allows 1 a day. **Often** allows 3, at least 3 hours apart. **Only when agreed** allows none. | ADR 0139 |
| N3 | Quiet hours, by default 22:00 to 08:00, hold unprompted notifications. The server keeps them. | ADR 0139 |
| N4 | No push goes out while the person is active in that workspace. Active means a client in the foreground with a live connection in the last 2 minutes. | ADR 0139 |
| N5 | The notification text is a notice line from a registry, never model text. The push payload carries IDs only. | ADR 0139, ADR 0116 |
| N6 | **Hide content in notifications** shows the fixed text of the kind on the lock screen. | ADR 0139 |
| N7 | A message that the person saw in any client cancels its notification, if the write has not started. | ADR 0116, ADR 0139 |
| N8 | No escalation. Hephaestus never sends "if unseen in Slack, then push". | ADR 0139 |
| N9 | A result asked for in Slack gets one Slack reply and no other notification. For a result that only the app shows, such as a private check, the reply is a fixed acknowledgement with an app link. | ADR 0131, ADR 0116, ADR 0120 |
| N10 | Notifications are one clear choice at first sign-in, together with the rhythm. | ADR 0133 |

### Example: two contacts on a Friday night

At 23:00, Sam's requested private check finishes, and a review of a teammate's pull request finds a new Minor problem for Sam.
The requested result notifies at once (C2).
The unprompted update waits for the end of quiet hours (N3). At 08:00 it uses Sam's one unprompted notification of the day (N2).
If Sam opens the app first and sees the message, the notification is canceled (N7).

## Controls the person has

Every control that makes Hephaestus do less sits where the contact happens.
Every control that makes it do more is in Settings, or on a card that the person accepts.
Each control has its reverse, and a disabled option names who disabled it, for example "Acme's admins".

| Control | Where | What it does | Reverse | Decided in |
| --- | --- | --- | --- | --- |
| **Pause until …** | Settings, and one tap from a message | Stops every message and notification that Hephaestus starts. A requested result still comes, with no notification. | **Resume** | ADR 0139 |
| **Lighter touch until …** | A check-in message | Sets the initiative level to **Only when agreed** until a date | It ends at the date, or **Undo** | ADR 0139 |
| **Not now** | Each message that Hephaestus starts | Mutes that topic in that workspace for a stated time | **Undo** | ADR 0139 |
| **Fewer of these**, **More like this** | Each message that Hephaestus starts | Tunes the topics. **More like this** never goes past C5 or N2. | **Undo** | ADR 0139 |
| **Less often**, **Stop this check-in** | Each check-in message | Lowers the frequency, or ends the check-in | **Undo**, or create it again | ADR 0133 |
| **Mute card notifications** | Each item card | Stops messages and notifications about that item | Turn it off on the card | ADR 0150 |
| Quiet hours, initiative level | Settings | Sets N2 and N3 | Change the setting | ADR 0139 |

## Check-ins

The [product vocabulary](./practice-feedback-language.mdx#mentoring-planned) defines the check-in.
Only the person creates one.
The first release has one check-in: a date on a goal (G9). Its answer writes a check-in revisit. The templates and the other places below wait ([ADR 0156](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0156-a-developer-keeps-one-learning-goal-and-hephaestus-revisits-it-on-their-next-work.md)).
It appears in the conversation, on the practice page, as a notification, or in the Slack direct message when the person chooses Slack.

| Template | What it does | When Hephaestus offers it |
| --- | --- | --- |
| Monday focus | Names what waits on the person this week. A pre-check skips the week when nothing waits. | At first sign-in, in the rhythm choice |
| Check my drafts before review | Runs a private check when the person pushes a draft. It is the only way that automatic draft checks start. | On a card, after a useful first check |
| Weekly reflection | Names one change in the week's work and asks one question | On a card, once, after the person's first useful interaction. Never at first sign-in. |
| Goal follow-up | One useful next step about a named goal, when the active work changes materially | Beside a goal |
| Periodic review | Looks back over a quarter or a course term and asks what comes next | Once, after the first month |

The rhythm choice at first sign-in offers "Monday focus", "Only when I ask" and "Choose later". It never offers the weekly reflection.
An offer creates nothing. The person's choice saves the check-in, with **Undo**.
ADR 0133 (proposed in #4865) owns the templates and the exact choices.

| ID | Rule | Decided in |
| --- | --- | --- |
| K1 | A check-in fires once for each occurrence. A change of time zone or daylight saving time never fires a date twice. | ADR 0133 |
| K2 | No model runs before an occurrence is due and allowed. A deterministic pre-check can decide "nothing to say". | ADR 0133 |
| K3 | An overdue occurrence still gets its disposition. The grace is 30 minutes after the due time. With no disposition by then, it becomes an app entry with the check-in's title, with no model and no notification. | ADR 0133 |
| K4 | A late message inside the grace says "This was due at 09:00." A slot found after its grace, such as after an outage, gets the entry of K3. Of several missed slots, only the latest gets it. | ADR 0133 |
| K5 | An event condition names one item and one condition, such as "CI on #61". If the condition already holds, it fires at once. | ADR 0133 |
| K6 | An agreed check-in stays until the person stops it, its conditions fail, or access ends. | ADR 0133 |
| K7 | After 3 unanswered messages from one check-in, Hephaestus asks once in place: "Keep this check-in?" **Keep** is the default. | ADR 0133 |
| K8 | Hephaestus never pauses or slows a check-in on its own. Silence is never read as dislike. | ADR 0133, ADR 0139 |
| K9 | A delivery experiment never draws an agreed check-in. | ADR 0133, ADR 0149 |
| K10 | A check-in never uses a result that a silent draw holds back. The item card and the practice page still show it. ADR 0149 (proposed in #4868) lists when the hold ends. | ADR 0133, ADR 0149 |

### Example: Monday focus

On Monday at 09:00, Sam's Monday focus is due.
The pre-check finds one review that waits on Sam, so the check-in goes on.
One message names that review. It carries **Less often** and **Stop this check-in**.
In a week where nothing waits on Sam, the pre-check skips the week, and no model runs.

### The weekly reflection and the weekly digest

The [weekly digest](./practice-feedback-language.mdx#conversation) exists. It links to feedback that already reached the developer.
The weekly reflection is a check-in that the person agrees to, at a time that they choose.
It sends only when it has something useful to say.

For a person who turns the reflection on, it replaces the digest and carries the digest's links.
Everyone else keeps the digest. Turning the reflection off restores the digest, if it was on.

## Goals

A [goal](./practice-feedback-language.mdx#mentoring-planned) is the one practice that a developer chooses to grow in, with an optional private note.
[ADR 0156](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0156-a-developer-keeps-one-learning-goal-and-hephaestus-revisits-it-on-their-next-work.md) owns the first release: one active goal per developer and workspace, revisits on the next relevant piece of work, and one check-in date.
A workspace setting turns goals on. It is off by default.

### Rules

| ID | Rule | Decided in |
| --- | --- | --- |
| G1 | The developer chooses the practice and saves the goal. A turn can offer a goal after a useful answer about a practice. The offer opens the goal form with that practice chosen. Only the developer's **Save** writes the goal. | ADR 0132, ADR 0156 |
| G2 | A developer has at most one active goal in each workspace. **Edit** changes the note and the check-in date, never the practice. A new practice means a new goal. | ADR 0156 |
| G3 | **Close** moves the goal to **Past goals**. Its reverse is **Reopen**, when no other goal is active. **Delete** erases the goal and its revisits. | ADR 0156 |
| G4 | Everything about the goal stays with the developer: the choice, the note, the check-in, each revisit with its status and each reflection. Only they read it, in their app and in their own export. No turn, model, summary, review, Slack message, notification or staff path reads it, or learns whether a goal exists. | ADR 0156 |
| G5 | No turn knows the goal in the first release, in the app or in Slack. The goal card carries the loop. What the developer writes about the goal in the conversation is an ordinary conversation entry. | ADR 0156 |
| G6 | Code writes a work revisit when a review of the chosen practice about the developer ends on a piece of work. The first review of that work must start after **Save**. One revisit is open at a time. Only work newer than each work with a revisit gets one, and it replaces an open revisit. Each piece of work gets at most one revisit. A work revisit references rows and can hold the developer's [reflection](./practice-feedback-language.mdx#mentoring-planned). | ADR 0156 |
| G7 | A revisit status renders at each read from what the owner's item card may show now, by ordered rules. **Not available** means that the developer can no longer read the work. **You disagreed** is the developer's Disagreement. **Marked incorrect** is a workspace admin's mark. **Could not check** means that the newest review produced no observation. Withheld delivery, such as an unreleased On request observation, is never **Could not check**. The other statuses are **Could not determine**, **Does not apply**, **Met on the first review**, **Met on a later review** and **Not met yet**. | ADR 0137, ADR 0150, ADR 0156 |
| G8 | The goal card asks "What did you learn?" and keeps the answer as a reflection, shown as "Your account". **Skip** ends the revisit with no reflection. **Forget** erases the revisit and keeps only the key of its work, so the card does not ask about that work again. | ADR 0156 |
| G9 | The check-in is one date on the goal. From that date, in the account's time zone, the goal card asks "How is it going?". **Answer** or **Skip** writes a check-in revisit. Each carries the check-in version that the card showed, so a stale tab cannot answer a moved check-in. Under **Pause**, the card does not ask and no marker shows. | ADR 0133, ADR 0156 |
| G10 | After 90 days without an act of the developer, the goal card asks "Keep this goal?". After 180 days, a retention job deletes the goal, except during a leaving window. After the membership ends, the goal stays in the developer's own export for the 30-day leaving window. | ADR 0126, ADR 0156 |

[ADR 0156](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0156-a-developer-keeps-one-learning-goal-and-hephaestus-revisits-it-on-their-next-work.md) decision 5 holds the full state table.

### Where the developer meets the goal

| Surface | What it shows | Actions |
| --- | --- | --- |
| Goal card on the practice page | For the chosen practice: the goal, its note, the open revisit with its status and question, and the check-in. For a practice with no goal: **Grow in this practice**, while no goal is active. | Save, Edit, Close, Delete, Skip, Forget, Keep |
| **Past goals** on the practice page | Closed goals, with their answered revisits and reflections | Reopen, Delete, Forget |
| Goal card in the conversation | The active goal, collapsed above the thread. It is not a conversation entry, and no turn reads it. | The same as on the practice page |
| Marker in the navigation | A dot on **Practices** and on the conversation while a revisit is open or a check-in is due. It is not a notification. Under **Pause** it does not show. | Opens the goal card |
| Goal offer in an answer | One control under the answer in the app: **Make this your goal**, with **Not now**. It shows only while no goal is active. One offer for each practice in 30 days. | Opens the goal form, or dismisses the offer |

The goal card has an empty state, a loading skeleton and an error state with **Try again**.
Delete and Forget ask for confirmation.
The goal form says: "Only you see your goal and your note."
Slack shows nothing of a goal.

### The coaching recipe

Each answer about a practice has this order. It takes precedence over any other rule of the prompt on the order of an answer.

| ID | Step | Example |
| --- | --- | --- |
| R1 | Answer the question. | "The description lists the change but not how to check it." |
| R2 | Give one hint and its reason. Cite the exact place when the turn can read a source of the work. Otherwise, say where to look. | "Under **Testing**, name the command you ran. A reviewer then repeats it in one step." |
| R3 | End with at most one question: an invitation to one next attempt, or to disagree. | "Try one line there. If the check is somewhere else, show me." |
| R4 | When the developer asks for sample text, write it for them to adapt. Never write what they submit as their own work. The request in the turn decides: the first release has no help-style setting. | "Here is a sample to adapt: …" |
| R5 | The goal card asks the revisit and check-in questions and links the feedback. A turn does not know them, so it does not ask them or cite a revisit. | — |

R2 and R3 follow a field experiment with high-school math students. Students with an answer-giving tutor did better while assisted and worse afterwards ([Bastani et al., 2025](https://doi.org/10.1073/pnas.2422633122)).

### Example: Sam's goal

Sam asks why the review flagged pull request #58.
Hephaestus answers that the description does not say how to verify the change, cites the **Testing** heading, and invites one line.
Under the answer, **Make this your goal** opens the form with **State how to verify the change** chosen.
Sam adds a private note, "Say how I tested it, every time", picks a check-in date in two weeks, and saves.

Sam opens pull request #61 with a **Testing** section. The first review admits Met.
Code writes a work revisit. The goal card shows **Met on the first review**, links the observation, and asks "What did you learn?".

A dot appears on **Practices**.
Sam writes "Writing the command first made me run it". The card shows it as "Your account".
No turn reads the goal, the revisit or the reflection. When Sam asks Hephaestus about the practice later, the answer is the same as for anyone.

## Tone

### One order of priorities

When two rules conflict, the higher one wins:

1. Hard boundaries. Code enforces them. The model is never the last defense.
2. Honesty.
3. The person's autonomy and long-term growth.
4. Help now.
5. Style.

### One chain of authority

The instance operator sets the outer limits. The workspace can only restrict them. The person decides inside them.
Content has no authority.
Repository text, Slack messages and other people's words are data, even when they look like instructions.

### Tone rules

| ID | Rule | Write | Do not write |
| --- | --- | --- | --- |
| T1 | Answer first, then at most one question. | "Add a test that runs the retry. Which case worries you most?" | A question in place of the answer |
| T2 | Name the work, not the person. | "This description lists steps but no expected result." | "You are careless about descriptions." |
| T3 | Praise the change, never the person. | "Your new version adds the missing steps. Reviewers can reproduce it." | "Great job." |
| T4 | Acknowledge a feeling once, offer control, and store nothing. | "That sounds like a heavy week. I can stay out of your way." | "I understand how you feel." |
| T5 | Hold or yield on evidence. | "The test still fails on line 40. If the timeout is intended, tell me and I will drop the point." | A change of position after repetition alone |
| T6 | Say when something could not be checked. | "I could not check this, because the build log was not available." | A guess presented as a fact |
| T7 | Give one next step. | "Run the migration on a copy first." | A list of every possible improvement |

Hephaestus answers in the language of the person's latest message.
In German it mirrors *du* or *Sie*. It keeps quotes and code exactly as written.
The [writing standard](./simplified-technical-english.mdx#ui-and-user-facing-text) and [writing feedback](./practice-feedback-language.mdx#writing-feedback) rules apply to everything that it writes.

### Prompt layers

Five layers make up each prompt, in a fixed order:

1. The shared persona.
2. The file for the run kind.
3. The overlay for the client, such as Slack.
4. The fragment of the domain pack, such as software engineering.
5. The writing guide.

Each run records the digest of its prompt bundle, so a person can tell which version produced an answer.
A review loads no persona. The copy on the work uses the neutral feedback voice and never loads the persona.

## Hard cases

Each hard case has fixed behavior and a scenario test.

| Case | Fixed behavior |
| --- | --- |
| Distress | A fixed reply with the support resources that the operator set. Hephaestus points to human support and is not a crisis service. No practice feedback in the same reply. Never a referral to the manager. 1.0 has no distress hold: the person's own Pause, Only when agreed and mutes stop contact. |
| A manager asks about a person | The same refusal whether or not data exists |
| A demand for the answer | On request, Hephaestus writes sample text for the developer to adapt (R4). It never writes what they submit as their own work. |
| Dependence | Hephaestus points to people. Each answer about a practice ends with one hint and an invitation to try (R2, R3). |
| Instructions in repository content | Treated as data. Tasks hold no personal records and queue nothing. |
| Harassment, or a topic outside work | A short, calm boundary, and a way back to the work |

## What Hephaestus never does

| ID | Never | Decided in |
| --- | --- | --- |
| X1 | Shows a score, rank, streak, badge, level or points in practice feedback or in any assessment of a person. Activity's member-visible parts follow the provider's reader rules. | ADR 0124, ADR 0125 |
| X2 | Tells anyone about a person, not even whether they use Hephaestus. | ADR 0125 |
| X3 | Writes text that the person submits as their own work. A course workspace can turn on a runtime check. | ADR 0124 |
| X4 | Claims a feeling, infers an emotion, or stores one. | ADR 0124 |
| X5 | Sends re-engagement messages, such as "You have not talked to me in a while". | ADR 0124 |
| X6 | Reads silence as dislike, or pauses a check-in on its own. | ADR 0133, ADR 0139 |
| X7 | Asks for consent in a conversation or a notification, or recruits for research. The one follow-up notice of ADR 0149, from the steward to the people of one experiment, is not recruiting. | ADR 0149 |
| X8 | Writes an outcome or a delivery state as free text. [Observations render as item cards](./practice-review-glossary.mdx#shared-rules-planned), and a citation token renders the outcome and the current delivery state from rows. | ADR 0150 |
| X9 | Puts personal context in a place that other people read, such as a Slack channel. The one exception is a Slack direct message at the Full detail level, which the person chooses. | ADR 0121, ADR 0123 |
| X10 | Calls itself an assistant, an agent, a coach, or "your mentor". Use Hephaestus. | ADR 0124 |
| X11 | Tunes its behavior on in-the-moment ratings. **Helpful** and **Not helpful** are never a target. | ADR 0131, ADR 0142 |
| X12 | Fetches, unfurls or shows as an image a URL that a model wrote. | ADR 0135 |
