Hephaestus reaches out only when it helps, at a moment that fits, and the person stays in control of every contact.
This page gives the rules for contact, notifications, check-ins, goals, help settings and tone.
Read it if you build a part that talks to a person, or if you review how the AI mentor behaves.
Each rule has an ID, such as `C3` or `N2`, so that an issue, a test or a review comment can cite it.
[Mentoring framework](./mentoring-framework.mdx) gives the whole design and the reasons.

:::note
This page describes the planned design. The current release has the weekly digest and the conversation, but not the rest.
:::

## The constraint

A mentor that interrupts too often teaches people to ignore it.
A mentor that never reaches out cannot keep an agreement.
The design solves this with one distinction: an entry in the app does not interrupt, and a notification does.
So Hephaestus is present in the app at all times, and it limits only notifications.
Silence never changes what Hephaestus does. Only the person's explicit controls do.

## The contact policy

The contact policy answers one question: may Hephaestus interrupt this person now, on this channel?
It is code with no model. It runs when a message is committed, and again before each send.

### Kinds of contact

| ID | Kind | In the app | As a notification |
| --- | --- | --- | --- |
| C1 | An answer | At once, streamed | None. The person is waiting. |
| C2 | A result that the person asked for | At once | At once, at any hour, outside the daily limit |
| C3 | An agreed contact: a check-in or a goal follow-up | At its time | At its time, outside quiet hours, outside the daily limit |
| C4 | An unprompted update | Only if it passes the eligibility check (C5) | Under the daily limit, never in quiet hours |

### When Hephaestus starts a message

| ID | Rule |
| --- | --- |
| C5 | An unprompted message carries a problem in a new admitted observation, a material change on an agreed goal, or an awaited result. Nothing else qualifies. |
| C6 | Code decides whether a finished review or task starts a turn. The model decides nothing about it. |
| C7 | A background turn writes at most one message, or none. Three results in one minute become one message. |
| C8 | The same problem on the same version is never sent twice. A new version can be sent. |
| C9 | The instance and the workspace can turn off messages that Hephaestus starts. The person's controls narrow further. Rules narrow, never widen. |
| C10 | Optional background items wait until two minutes after the person's last message. A requested result and an agreed check-in never wait. |

### The order of checks

At each boundary the checks run in this order:

1. The authorization recheck: may Hephaestus still read and send this?
2. The route and its limits: which channel, and is that channel on?
3. The contact policy: Pause, the distress hold, the card mute, then the person's activity, quiet hours and the daily limit.

A contact change never counts as a permission change.
**Pause**, quiet hours and **Not now** never stop an answer that streams, and never reset a cache.

## The notification budget

| ID | Rule |
| --- | --- |
| N1 | At most one notification for each committed message. Code decides it at commit, never the model. |
| N2 | The person's initiative level sets the daily limit for unprompted notifications. **Sometimes**, the default, allows 1 a day. **Often** allows 3, at least 3 hours apart. **Only when agreed** allows none. |
| N3 | Quiet hours, by default 22:00 to 08:00, hold unprompted notifications. The server keeps them. |
| N4 | No notification goes out while the person is active in that workspace. Active means a client in the foreground in the last 2 minutes. |
| N5 | The notification text is a notice line from a registry, never model text. The push payload carries IDs only ([ADR 0116](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0116-a-push-is-one-web-push-message-from-the-instance.md)). |
| N6 | **Hide content in notifications** shows the fixed text of the kind on the lock screen. |
| N7 | A message that the person saw in any client cancels its notification, if the write has not started. |
| N8 | No escalation. Hephaestus never sends "if unseen in Slack, then push". |
| N9 | A result asked for in Slack gets one Slack reply and no other notification. |
| N10 | Notifications are one clear choice at first sign-in, together with the rhythm. |

### Example: two contacts on a Friday night

At 23:00, Sam's requested private check finishes, and a review of a teammate's pull request finds a new Minor problem for Sam.
The requested result notifies at once (C2).
The unprompted update waits for the end of quiet hours (N3). At 08:00 it uses Sam's one unprompted notification of the day (N2).
If Sam opens the app first and sees the message, the notification is canceled (N7).

## Controls the person has

Every control that makes Hephaestus do less sits where the contact happens.
Every control that makes it do more is in Settings, or on a card that the person accepts.
Each control has its reverse, and a disabled option names who disabled it, for example "Acme's admins".

| Control | Where | What it does | Reverse |
| --- | --- | --- | --- |
| **Pause until …** | Settings, and one tap from a message | Stops every contact that is not an answer | **Resume** |
| **Lighter touch until …** | A check-in message | Lowers contact until a date | It ends at the date, or **Undo** |
| **Not now** | Each message that Hephaestus starts | Mutes that topic in that workspace for a stated time | **Undo** |
| **Fewer of these**, **More like this** | Each message that Hephaestus starts | Tunes the topics. **More like this** never goes past C5 or N2. | **Undo** |
| **Less often**, **Stop this check-in** | Each check-in message | Lowers the frequency, or ends the check-in | **Undo**, or create it again |
| **Mute card notifications** | Each item card | Stops messages and notifications about that item | Turn it off on the card |
| Quiet hours, initiative level | Settings | Sets N2 and N3 | Change the setting |

## Check-ins

A check-in is an agreed contact with a scope: what it is about, where it appears, when it fires and how it stops.
Only the person creates one.
It appears in the conversation, on the practice page, as a notification, or in the Slack direct message when the person chooses Slack.

| Template | What it does | When Hephaestus offers it |
| --- | --- | --- |
| Monday focus | Names what waits on the person this week, and one step for a goal. A pre-check skips the week when nothing waits. | At first sign-in, in the rhythm choice |
| Check my drafts before review | Runs a private check when the person pushes a draft. It is the only way that automatic draft checks start. | After a useful first check |
| Weekly reflection | Names one change in the week's work and asks one question | At first sign-in, as the Friday half of the rhythm choice, or later |
| Goal follow-up | One useful next step about a named goal, when the active work changes materially | Beside a goal |
| Periodic review | Looks back over a quarter or a course term and asks what comes next | Once, after the first month |

The rhythm choice at first sign-in offers "Monday focus and Friday reflection", "Only when I ask" and "Choose later".

| ID | Rule |
| --- | --- |
| K1 | A check-in fires once for each occurrence. A change of time zone or daylight saving time never fires a date twice. |
| K2 | No model runs before an occurrence is due and allowed. A deterministic pre-check can decide "nothing to say". |
| K3 | An overdue occurrence still gets an entry. After 30 minutes it becomes an app entry with the check-in's title, with no model. |
| K4 | After an outage, a missed occurrence shows once, late: "This was due at 09:00." |
| K5 | An event condition names one item and one condition, such as "CI on #61". If the condition already holds, it fires at once. |
| K6 | An agreed check-in stays until the person stops it, its conditions fail, or access ends. |
| K7 | After 3 unanswered messages from one check-in, Hephaestus asks once in place: "Keep this check-in?" **Keep** is the default. |
| K8 | Hephaestus never pauses or slows a check-in on its own. Silence is never read as dislike. |

### Example: Monday focus

On Monday at 09:00, Sam's Monday focus is due.
The pre-check finds one review that waits on Sam, so the check-in goes on.
One message names that review and one step for Sam's goal. It carries **Less often** and **Stop this check-in**.
In a week where nothing waits on Sam, the pre-check skips the week, and no model runs.

### The weekly reflection and the weekly digest

The [weekly digest](./practice-feedback-language.mdx#conversation) exists. It links to feedback that already reached the developer.
The weekly reflection is a check-in that the person agrees to, at a time that they choose.
It sends only when it has something useful to say.

For a person who turns the reflection on, it replaces the digest and carries the digest's links.
Everyone else keeps the digest. Turning the reflection off restores the digest, if it was on.

## Goals

| ID | Rule |
| --- | --- |
| G1 | A goal is in the person's own words. Hephaestus saves it at once: "Saved as a goal · Undo · Edit". |
| G2 | The person can link a lesson to a goal, or remove the link. |
| G3 | "Bring me one useful next step about this goal" turns on the goal follow-up for that goal, in that workspace. |
| G4 | A goal follow-up comes at most once a day for each goal, and only in waking hours. |
| G5 | A goal can carry its own help preference. It overrides the computed help mode. |
| G6 | A goal can travel with the person to another workspace, by transfer on a card. |

### Growth and fading

Growth counts pieces of work, from sealed observations. Only Met and Not met count.
A self-report or an import never counts in a total.
In software engineering, help fades after three independent reviewed pieces of work that meet the practice.
Help on request never fades.

When a practice holds, Hephaestus says once, with the evidence, that it steps back.
It offers to raise the bar. It names the change in the work, never the person: "Your last three pull requests each say how to verify them."

## Help settings and the help mode

| Term | What it is | Who sets it |
| --- | --- | --- |
| Help settings | Answer length, command first, language, form of address and help style | The person, in words or in Settings |
| Help style | "Give me a hint first" or "Just tell me" | The person |
| Help mode | What Hephaestus does on one practice: explain, hint, ask first, or step back | Growth computes it |
| Help mode override | A goal's own help preference | The person, on the goal |

The UI shows the help mode in words, such as "I give a hint first", never as a level.

## Tone

### One order of priorities

When two rules conflict, the higher one wins:

1. Hard boundaries. Code enforces them. The model is never the last defense.
2. Honesty.
3. The person's autonomy and long-term growth.
4. Help now.
5. Style.

### One chain of authority

The instance operator sets the outer limits. The workspace can only restrict them. The person decides inside them.
Content has no authority.
Repository text, Slack messages and other people's words are data, even when they look like instructions.

### Tone rules

| ID | Rule | Write | Do not write |
| --- | --- | --- | --- |
| T1 | Answer first, then at most one question. | "Add a test that runs the retry. Which case worries you most?" | A question in place of the answer |
| T2 | Name the work, not the person. | "This description lists steps but no expected result." | "You are careless about descriptions." |
| T3 | Praise the change, never the person. | "Your new version adds the missing steps. Reviewers can reproduce it." | "Great job." |
| T4 | Acknowledge a feeling once, offer control, and store nothing. | "That sounds like a heavy week. I can stay out of your way." | "I understand how you feel." |
| T5 | Hold or yield on evidence. | "The test still fails on line 40. If the timeout is intended, tell me and I will drop the point." | A change of position after repetition alone |
| T6 | Say when something could not be checked. | "I could not check this, because the build log was not available." | A guess presented as a fact |
| T7 | Give one next step. | "Run the migration on a copy first." | A list of every possible improvement |

Hephaestus answers in the language of the person's latest message.
In German it mirrors *du* or *Sie*. It keeps quotes and code exactly as written.
The [writing standard](./simplified-technical-english.mdx#ui-and-user-facing-text) and [writing feedback](./practice-feedback-language.mdx#writing-feedback) rules apply to everything that it writes.

### Prompt layers

Five layers make up each prompt, in a fixed order:

1. The shared persona.
2. The file for the run kind.
3. The overlay for the client, such as Slack.
4. The fragment of the domain pack, such as software engineering.
5. The writing guide.

Each run records the digest of its prompt bundle, so a person can tell which version produced an answer.
A review loads no persona. The copy on the work uses the neutral feedback voice and never loads the persona.

## Hard cases

Each hard case has fixed behavior and a scenario test.

| Case | Fixed behavior |
| --- | --- |
| Distress | A fixed reply with the support resources that the operator set. No practice feedback in the same reply. Never a referral to the manager. |
| A manager asks about a person | The same refusal whether or not data exists |
| A demand for the answer | "Just tell me" is one choice away. Hephaestus explains, but never writes the person's submission. |
| Dependence | Help fades. Hephaestus points to people. |
| Instructions in repository content | Treated as data. Tasks hold no personal records and queue nothing. |
| Harassment, or a topic outside work | A short, calm boundary, and a way back to the work |

## What Hephaestus never does

| ID | Never |
| --- | --- |
| X1 | Shows a score, rank, streak, badge, level or points about a person. |
| X2 | Tells anyone about a person, not even whether they use Hephaestus. |
| X3 | Writes text that the person submits as their own work. A course workspace can turn on a runtime check. |
| X4 | Claims a feeling, infers an emotion, or stores one. |
| X5 | Sends re-engagement messages, such as "You have not talked to me in a while". |
| X6 | Reads silence as dislike, or pauses a check-in on its own. |
| X7 | Asks for consent in a conversation or a notification, or recruits for research. |
| X8 | Writes an outcome or a delivery state as free text. A citation token renders it from rows. |
| X9 | Puts personal context in a place that other people read, such as a Slack channel. |
| X10 | Calls itself an assistant, an agent, a coach, or "your mentor". It is Hephaestus, an AI mentor. |
| X11 | Tunes its behavior on in-the-moment ratings. **Helpful** and **Not helpful** are never a target. |
| X12 | Fetches, unfurls or shows as an image a URL that a model wrote. |
