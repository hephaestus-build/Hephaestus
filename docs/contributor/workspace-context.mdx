Every API endpoint that operates on workspace data must be scoped to a workspace slug. This keeps tenants isolated and enables per-workspace authorization.

## Quick Start

```java
@WorkspaceScopedController          // auto-prefixes routes with /workspaces/{workspaceSlug}
@RequestMapping("/teams")           // becomes /workspaces/{slug}/teams
@RequiredArgsConstructor
public class TeamController {

    private final TeamService teamService;

    @GetMapping
    public List<TeamDTO> list(WorkspaceContext ctx) {   // injected by framework
        return teamService.findByWorkspace(ctx.id());
    }

    @PostMapping
    @RequireAtLeastWorkspaceAdmin   // only ADMIN or OWNER can create
    public TeamDTO create(WorkspaceContext ctx, @RequestBody CreateTeamDTO dto) {
        return teamService.create(ctx.id(), dto);
    }
}
```

The filter resolves the slug and checks workspace access. Controllers and repository queries must still
scope their operations to the supplied workspace.

## What You Get

| Annotation                      | Effect                                                  |
| ------------------------------- | ------------------------------------------------------- |
| `@WorkspaceScopedController`    | Adds `/workspaces/{workspaceSlug}` prefix to all routes |
| `WorkspaceContext` parameter    | Auto-injected with workspace ID, slug, and user's roles |
| `@RequireAtLeastWorkspaceAdmin` | Requires ADMIN or OWNER role                            |
| `@RequireWorkspaceOwner`        | Requires OWNER role only                                |

## Authorization

Instance admins can access active workspaces as ADMIN without a membership or an SCM identity.
Elevation does not grant OWNER; an explicit OWNER membership still permits owner-only operations.
It does not make them a member either: what a workspace offers its own members, such as Heph, is
declared with `@PreAuthorize("@workspaceSecure.isMemberWithoutElevation()")`, which a user view
still satisfies as the viewed member.
`@PreAuthorize("@workspaceSecure.isMember()")` admits any effective role, elevation included, but never
a public read: the Activity endpoints use it, so a publicly viewable workspace does not open them to
non-members.
The privilege and audit policy lives in [Instance administration](./instance-admin.md#who-is-an-instance-admin).

Check roles via the context:

```java
if (ctx.hasRole(WorkspaceRole.OWNER)) {
    // owner-only logic
}

if (!ctx.hasMembership()) {
    // no effective workspace role (for example, a public read by a non-member)
}
```

Or use method-level annotations that fail fast with 403:

```java
@DeleteMapping("/{id}")
@RequireWorkspaceOwner
public void delete(WorkspaceContext ctx, @PathVariable Long id) { ... }

@PatchMapping("/settings")
@RequireAtLeastWorkspaceAdmin  // Also allows super admins
public void updateSettings(WorkspaceContext ctx, @RequestBody SettingsDTO dto) { ... }
```

## Where membership rows come from

A membership is created by workspace administration or by the provider granting access. Leaderboard, profile and
league-point paths only read memberships: a non-member's points are the default, and updating points never makes
anyone a member.

What a GitLab group grants is `WorkspaceMembershipService#entitledUserIds`: the group's effective roster
(`organization_membership`, listed with `relations: [DIRECT, INHERITED, SHARED_FROM_GROUPS]` so a workspace on a
subgroup keeps the people it inherits from a parent group or gets from an invited group, each at their highest grant)
and the members of its subgroup teams on the same instance. A subgroup team lists `DIRECT` and `SHARED_FROM_GROUPS`
members, not `INHERITED` ones, since the team hierarchy carries what it inherits, plus the WRITE/TRIAGE collaborators
of projects directly in it. `WorkspaceOrganizationMembershipAdapter#reconcileWorkspaceMembers` sets
`workspace_membership` to that set: the roster's ADMIN or MEMBER, MEMBER for someone only a team lists, and OWNER kept
for anyone who holds it. It runs after a complete roster listing and, once a roster has been reconciled, after a team
sync whose graph and every team's members were listed completely.

A member event changes one person only. On a connection route, whose credential authenticates the connection, the
handler replaces that person's stored grant with what GitLab's lookup reports now, read with the same relations as the
listing: the connected group's effective access, or a subgroup team's. The workspace member then gets the role the
stored roster or a subgroup team still grants them, or loses the membership if none does
(`WorkspaceMembershipService#applyProviderGrant`). A removal off a connection route names one direct grant, which does
not prove the person lost an inherited or invited-group one, so it changes nothing until the next complete roster
listing.

Every GitLab listing is read in full before any membership is written from it, and only a complete one is applied,
in one short transaction: a page with GraphQL errors, a page that is not whole
(`GitLabGraphQlResponseHandler#isWholePage`, which a `group: null` answer fails), an entry without a readable user or
access level, or a failed page changes no membership or role from that listing. The group roster upserts its users
before the role transaction, so a failure between the two can leave user rows, never a grant. Only the scope whose
reading of the group is authoritative writes it (`GitLabWorkspaceLinkService#mayWriteGroup`): its active connection is
on the group's instance and the workspace is linked to the group, or not linked yet while no other workspace is. A
shared project's collaborator rows are replaced only by the workspace that owns its group and monitors that project
(`GitLabWorkspaceLinkService#mayWriteRepository`), and only from a complete listing, so a failed or narrower reading
leaves the last complete answer in place.

Hiding a member only takes them off the leaderboard. A hidden member the roster no longer lists is removed like
anyone else; the preference is parked in `workspace_hidden_former_member` until a membership is created for the same
actor again, which takes it back, and purge clears it.

Practice-review eligibility is `WorkspaceMembershipService#practiceReviewEligibleUserIds`: human members on the
instance of the workspace's active connection (`WorkspaceActorSelector#connectedProviderId`), and, once a group is
linked, whom it still entitles. A workspace without an active connection reviews nobody, and a role kept only for administration,
such as an owner the roster dropped, grants no review. Coverage counts, person selection, widening and subject
admission all read it.

The GitLab deletion sweep lists with the scope's own credentials, so it tombstones only repositories on the scope's
connected instance, and checks again in the transaction that writes that the repository is still monitored, inside
the connected group this scope owns, and on that instance (`GitLabWorkspaceLinkService#mayWriteRepository`).

## Account identity resolution

Membership rows are keyed on SCM users, not accounts. The account-keyed schema in
[ADR 0019](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0019-workspace-membership-keyed-on-account.md) is proposed, not implemented.
`CurrentAccountUsers` resolves an account's non-disabled identity links to existing SCM actors by
provider id and immutable provider subject. It does not provision actors or fall back to usernames,
display names, or cached actor references. No resolvable links means no SCM actors, not a restriction
on public reads or instance-admin elevation.

`AccountWorkspaceMembershipQuery` uses that resolver for cross-module membership reads. The effective
role is the strongest role across the account's linked workspace members. The representative actor is
chosen by `WorkspaceActorSelector` among the actors that currently hold membership: the one on the
provider type and server URL the workspace's active SCM connection is configured for, because reviewed
work, observations and feedback name the account's actor on that instance. The account's actor on
another provider, or on another instance of the same provider, may still hold a membership, such as the
one that created the workspace. With no active SCM connection, or no member actor on its instance, the
first-linked member actor in identity-link id order is chosen. Until sync records actors against the
configured instance ([#2181](https://github.com/hephaestus-build/Hephaestus/issues/2181)); GitHub
Enterprise sync still records github.com), a workspace connected to a non-default instance falls back
to link order. This is a selection, not an aggregation: reads show the selected actor's observations
only. HTTP requests and provider attribution use that same selection. Role changes and newly added links
do not replace an eligible representative on the connected instance; losing or disabling its link or
membership, or reconnecting the workspace to another instance, can change it. Conversations with Heph
survive such a change: the request carries all of the account's member actor ids, a thread started
through any of them is listed and opened for the account, a new thread belongs to the selected actor,
and a continued one moves to it.
A failure in this cross-module query propagates rather than returning an empty membership list.

Slack and Outline attribution first resolve the provider subject and provider workspace identity
(Slack team or Outline team), then require membership in the target Hephaestus workspace. Account
status and link status are separate checks:

- Historical Slack/Outline attribution and account export queries require non-disabled links but do
  not require an ACTIVE account. They do not restore erased data or disabled links.
- Slack mentor admission, account-linked App Home reads, research preference changes, and outgoing
  feedback recipient resolution require an ACTIVE account as well as non-disabled links.

Account preference exports contain one actor's preferences: the first-linked actor that already
resolves through `CurrentAccountUsers`. If that actor has no preferences row, the export omits
preferences rather than trying another actor. Account settings instead select the first active
GitHub or GitLab link and may provision its missing actor, so the two paths can select different
actors before provisioning. Settings preserve an existing actor's provider-synced profile. If a
missing actor's saved signup username belongs to another native id on the same provider, provisioning
returns `409 Conflict` rather than reassigning the username. A non-numeric provider subject also
returns `409`; this path does not fetch fresh provider data.

Workspace creation resolves the authenticated account's verified actors directly because there is no
workspace context to pin yet. Workspace-scoped developer reads require the pinned actor; an elevated
instance administrator without membership has no developer identity and never inherits one from a
display login. GitHub installation attachment follows the immutable identity requirements documented
in [GitHub integration](../admin/github-integration#workspace-attachment).

## Async Work

`WorkspaceContextExecutor.wrap` captures the workspace context and MDC for a background task; it does
not propagate Spring authentication or `CurrentScmIdentityHolder`. Tasks that need the authenticated
actor must carry that identity separately. Mentor turns do this explicitly: they copy the verified
actor id and display login to the turn thread and clear them in `finally`.

For work that needs only workspace context:

```java
CompletableFuture.runAsync(
    WorkspaceContextExecutor.wrap(() -> heavyProcessing(ctx)),
    executor
);
```

## Global Routes

Routes that don't belong to a specific workspace (like `/workspaces` listing or creation) stay in a plain `@RestController`:

```java
@RestController
@RequestMapping("/workspaces")
public class WorkspaceRegistryController {

    @PostMapping
    public WorkspaceDTO create(@RequestBody CreateWorkspaceDTO dto) { ... }

    @GetMapping
    public List<WorkspaceListItemDTO> list() { ... }
}
```

## Testing

Integration tests must create a workspace and grant membership before hitting scoped endpoints:

```java
@Test
@WithMentorUser
void canListTeams() {
    User user = persistUser("mentor");
    Workspace ws = createWorkspace("test-ws", "Test", "org", AccountType.ORG, user);
    addMembership(ws, user, WorkspaceRole.ADMIN);

    webTestClient.get()
        .uri("/workspaces/{slug}/teams", ws.getWorkspaceSlug())
        .headers(TestAuthUtils.withCurrentUser())
        .exchange()
        .expectStatus().isOk();
}
```

See `AbstractWorkspaceIntegrationTest` for helper methods.
