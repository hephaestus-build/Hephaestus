Every API endpoint that operates on workspace data must be scoped to a workspace slug. This keeps tenants isolated and enables per-workspace authorization.

## Quick Start

```java
@WorkspaceScopedController          // auto-prefixes routes with /workspaces/{workspaceSlug}
@RequestMapping("/teams")           // becomes /workspaces/{slug}/teams
@RequiredArgsConstructor
public class TeamController {

    private final TeamService teamService;

    @GetMapping
    public List<TeamDTO> list(WorkspaceContext ctx) {   // injected by framework
        return teamService.findByWorkspace(ctx.id());
    }

    @PostMapping
    @RequireAtLeastWorkspaceAdmin   // only ADMIN or OWNER can create
    public TeamDTO create(WorkspaceContext ctx, @RequestBody CreateTeamDTO dto) {
        return teamService.create(ctx.id(), dto);
    }
}
```

The filter resolves the slug and checks workspace access. Controllers and repository queries must still
scope their operations to the supplied workspace.

## What You Get

| Annotation                      | Effect                                                  |
| ------------------------------- | ------------------------------------------------------- |
| `@WorkspaceScopedController`    | Adds `/workspaces/{workspaceSlug}` prefix to all routes |
| `WorkspaceContext` parameter    | Auto-injected with workspace ID, slug, and user's roles |
| `@RequireAtLeastWorkspaceAdmin` | Requires ADMIN or OWNER role                            |
| `@RequireWorkspaceOwner`        | Requires OWNER role only                                |

## Authorization

Instance admins can access active workspaces as ADMIN without a membership or an SCM identity.
Elevation does not grant OWNER; an explicit OWNER membership still permits owner-only operations.
The privilege and audit policy lives in [Instance administration](./instance-admin.md#who-is-an-instance-admin).

Check roles via the context:

```java
if (ctx.hasRole(WorkspaceRole.OWNER)) {
    // owner-only logic
}

if (!ctx.hasMembership()) {
    // no effective workspace role (for example, a public read by a non-member)
}
```

Or use method-level annotations that fail fast with 403:

```java
@DeleteMapping("/{id}")
@RequireWorkspaceOwner
public void delete(WorkspaceContext ctx, @PathVariable Long id) { ... }

@PatchMapping("/settings")
@RequireAtLeastWorkspaceAdmin  // Also allows super admins
public void updateSettings(WorkspaceContext ctx, @RequestBody SettingsDTO dto) { ... }
```

## Account identity resolution

Authorization comes from `workspace_account_membership`, uniquely keyed by workspace and account.
An account with no SCM identity is a valid member. Its role, source and sticky suspension belong to
that account membership, not to an upstream organization role. The retained `workspace_membership`
table contains SCM contributor and leaderboard facts; its legacy role is not an authorization input.
[ADR 0019](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0019-workspace-membership-keyed-on-account.md)
owns the split and migration decision.

`CurrentAccountUsers` resolves non-disabled identity links by provider ID and immutable subject.
It does not provision actors or fall back to usernames, display names, or cached actor references.
`AccountWorkspaceMembershipQuery` reads account membership directly and optionally selects the
first-linked SCM actor with a contributor row in that workspace. Changing roles or linking another
identity does not replace an existing eligible representative. Unlinking can remove attribution but
does not remove manually granted workspace access. Query failures propagate rather than pretending
that the account has no memberships.

Membership mutations lock the workspace and recheck the caller's current account role. Administrators
can manage non-owner access; only owners can change ownership or adopt directory-managed access as a
manual exception. Suspension survives sync. Removing the final active owner, including through
account deletion, requires an explicit ownership transfer. Instance administrators receive effective
ADMIN access, never synthetic ownership or an invented membership row.

Slack and Outline attribution first resolve the provider subject and provider workspace identity
(Slack team or Outline team), then require membership in the target Hephaestus workspace. Account
status and link status are separate checks:

- Historical Slack/Outline attribution and account export queries require non-disabled links but do
  not require an ACTIVE account. They do not restore erased data or disabled links.
- Slack mentor admission, account-linked App Home reads, research preference changes, and outgoing
  feedback recipient resolution require an ACTIVE account as well as non-disabled links.

Account preference exports contain one actor's preferences: the first-linked actor that already
resolves through `CurrentAccountUsers`. If that actor has no preferences row, the export omits
preferences rather than trying another actor. Account settings instead select the first active
GitHub or GitLab link and may provision its missing actor, so the two paths can select different
actors before provisioning. Settings preserve an existing actor's provider-synced profile. If a
missing actor's saved signup username belongs to another native id on the same provider, provisioning
returns `409 Conflict` rather than reassigning the username. A non-numeric provider subject also
returns `409`; this path does not fetch fresh provider data.

## Async Work

`WorkspaceContextExecutor.wrap` captures the workspace context and MDC for a background task; it does
not propagate Spring authentication or `CurrentScmIdentityHolder`. Tasks that need the authenticated
actor must carry that identity separately. Mentor turns do this explicitly: they copy the verified
actor id and display login to the turn thread and clear them in `finally`.

For work that needs only workspace context:

```java
CompletableFuture.runAsync(
    WorkspaceContextExecutor.wrap(() -> heavyProcessing(ctx)),
    executor
);
```

## Global Routes

Routes that don't belong to a specific workspace (like `/workspaces` listing or creation) stay in a plain `@RestController`:

```java
@RestController
@RequestMapping("/workspaces")
public class WorkspaceRegistryController {

    @PostMapping
    public WorkspaceDTO create(@RequestBody CreateWorkspaceDTO dto) { ... }

    @GetMapping
    public List<WorkspaceListItemDTO> list() { ... }
}
```

## Directory access boundary

Directory eligibility belongs to `workspace.directory`; the Keycloak adapter under
`integration.directory` only captures complete evidence. An operator-approved exact issuer and group
allowlist, a workspace owner's versioned approval, a healthy active connection and fresh evidence are
all required for a grant. `DirectorySnapshot` owns the freshness window. The
[operator runbook](../admin/directory-access) owns setup and recovery semantics.

A directory policy references its workspace and connection through a composite foreign key. HTTP
administration is a `@WorkspaceScopedController`; the directory sync adapter re-establishes and restores
workspace context inside the existing connection job infrastructure. Mutation transactions lock the
workspace, approved login-provider source and affected account, in that order, and recheck verified
identity links before granting. Provider approval changes lock the same source row. An in-flight
capture carries configuration and source versions and cannot overwrite newer policy decisions.

`/user/workspace-access` is deliberately outside workspace routing: a signed-in account may not yet
have any workspace. It returns only that current account's fresh, verified offers, not a searchable
directory of workspaces or identities. Joining rechecks all eligibility under locks and returns the
same unavailable result for an absent or ineligible offer. No account ID is accepted from the caller.

`IdentityUnlinkParticipant` lets directory membership removal participate in the identity unlink
transaction without coupling the account service to workspace implementation. It acquires no
workspace lock after the account lock, avoiding the reverse lock order of a grant. Workspace purging
removes policies before connections; account erasure clears approval attribution. Existing manual
access, owner roles and suspension records are not inferred from SCM or directory roster changes.

## GitHub access authority

`workspace.access` owns directory-backed external membership intent; `integration.access.github`
absorbs GitHub's identity, installation, invitation and permission semantics. It is separate from the
repository integration and reuses connection encryption, jobs, leases and audit ledgers. The
[operator runbook](../admin/github-access) owns App setup, supported scopes and recovery procedures.
GitLab, Slack and Outline have no external membership provisioning adapter.

Every target, membership and action carries its workspace. Composite foreign keys bind connections,
targets and action subjects to that same workspace. A PostgreSQL exclusion constraint arbitrates
cross-workspace organization-wide/team scope overlap, including concurrent claims. Authority remains
held until all managed access and unresolved actions are accounted for; deleting a connection or an
originating account cannot release that constraint.

Two separate approvals are required: a currently linked GitHub organization owner consumes an expiring,
single-use handoff, and a current workspace owner approves an exact inventory and directory capture.
The handoff endpoint is current-account scoped rather than workspace-member scoped, so an organization
owner need not join the requesting workspace. Its capability travels in a fragment and POST body,
never a query parameter. The recipient route remains outside the authenticated route subtree to avoid
copying the capability into a login return URL. Recent genuine authentication is enforced by the
existing step-up boundary; possession of an installation ID is not proof of organization ownership.

Reconciliation snapshots addresses, then locks workspace, directory provider, affected accounts in
ascending order and target before deciding a write. The provider-before-account order matches directory
capture even when the same account and provider appear in different workspaces. It commits an action's intent before provider I/O, reacquires locks and
revalidates policy, identity links, directory capture and organization-owner authority before executing.
A retry reads provider state first. Unknown grants require explicit adoption or an unmanaged exception;
a requested removal remains pending until absence is confirmed. Each target runs as an independent
connection job. Provider failures retain no response bodies or credentials in their exception causes.

Identity unlink and account erasure participate under the existing account lock without acquiring a
workspace lock in reverse order. Their minimal pending-removal records survive loss of attribution.
`DirectorySubjectRetention` keeps externally tracked subjects in subsequent directory captures, even
after directory-managed workspace membership is gone, so a provider outage cannot erase a departure.
Incomplete or stale captures are not departure evidence. All network and scheduling beans are server
role gated; lifecycle guards remain available wherever account or workspace data can be erased.

## Testing

Integration tests must create a workspace and grant membership before hitting scoped endpoints:

```java
@Test
@WithMentorUser
void canListTeams() {
    User user = persistUser("mentor");
    Workspace ws = createWorkspace("test-ws", "Test", "org", AccountType.ORG, user);
    addMembership(ws, user, WorkspaceRole.ADMIN);

    webTestClient.get()
        .uri("/workspaces/{slug}/teams", ws.getWorkspaceSlug())
        .headers(TestAuthUtils.withCurrentUser())
        .exchange()
        .expectStatus().isOk();
}
```

See `AbstractWorkspaceIntegrationTest` for helper methods.
