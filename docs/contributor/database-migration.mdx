Liquibase manages schema changes in the application server. This page is the procedure. The entity
conventions the drift gate reads are in `server/AGENTS.md` § Schema changes.

## Quick start

1. Modify the JPA entities.
2. Write the drift into this branch's changelog:

   ```bash
   vp run db:draft-changelog
   ```

   The command applies the whole chain to a disposable database.
   It compares the result with the JPA model.
   It writes the difference as change sets into `server/application/src/main/resources/db/changelog/<timestamp>_changelog.xml`.
   These use ids `<timestamp>-1`, `-2`, … and author `hephaestus`.

   A branch gets one such file: the first run
   creates it and appends its `<include>` to `master.xml`. Later runs add change sets to it. It then
   refreshes the ERD. With no drift it writes nothing.

3. **Review the change sets.** Keep the real deltas and remove what the diff only inferred. Prefer `renameColumn` to a drop-and-add pair.
   Unless there is a data migration plan, start new sequences at `1`.
   Follow the destructive-change policy below. Use preconditions to reject
   incompatible database states. Use `onFail="MARK_RAN"` only when failure proves the intended change
   is already present. Provide a tested rollback when reversal is safe. Otherwise document recovery
   through a verified backup in the operator instructions. If you edit the changelog, refresh the ERD:

   ```bash
   vp run db:generate-erd-docs
   ```

4. Add a release changeset: `vp exec changeset`, or hand-write `.changeset/<slug>.md`
   (`.changeset/README.md`). A Liquibase `<changeSet>` and a release changeset are different things
   and a schema change needs both. `verify-changesets` fails a PR that touches `db/changelog/`
   without one. Keep the summary user-facing. The release notes flag the migration automatically.
5. Commit the changelog, the `master.xml` edit, the changeset, and `docs/contributor/erd/schema.mmd`.

## Native objects the JPA diff does not cover

The JPA diff does not cover native `CHECK` constraints or triggers in this repository. For such a
change, write the change set as a draft in an ignored scratch directory, then promote it through the
same command:

```bash
node scripts/db-utils.ts draft-changelog --from-draft .context/<name>.xml
```

The draft is one `<databaseChangeLog>` with only change sets.
Promotion writes these into this branch's changelog with the usual ids and author.
It replays the whole chain on a disposable database and refreshes the ERD, as above.
It refuses a draft with any of these properties:

- Malformed XML.
- A DOCTYPE declaration.
- Content outside a change set.
- Root attributes other than the standard Liquibase and XML Schema namespaces and `xsi:schemaLocation`.
- Change-set attributes other than `id` and `author`.

Promotion would drop unsupported attributes.
State conditions as `preConditions` inside the change set.
Review the result as in step 3.
Add the database-level test required by the paragraph on populated tables below.

## Data corrections

If a fix leaves wrong rows, correct them in the code that writes them.
The next sync or event then repairs them.
Only rows that nothing will write again get a hand-written `<sql>` change set.
Merge requests that incremental sync never reads again are an example.
Put this change set in the branch's single changelog.
Include these safeguards:

- A comment that states which rows are wrong and why.
- A `HALT` precondition on the columns it reads.
- A `<rollback><stop>` that names the backup to restore.

A data correction needs maintainer approval in the pull request.

## Changelog immutability policy

The Liquibase changelog chain **is** the upgrade path: every production and self-hosted
instance upgrades by replaying exactly these files, in `master.xml` order. That works only
if history never changes underneath an instance that already ran part of it.

1. **Released changesets are never edited.** A changeset is *released* once it reaches
   `main` — from that moment it may already be applied to a production database. An edit causes checksum errors at boot on upgraded instances.
   Fresh installs silently get a different schema. Fix mistakes **forward** with a new changelog file. Liquibase [excludes preconditions, contexts and labels from checksums](https://www.liquibase.com/blog/what-affects-changeset-checksums).
   It ignores deleted changesets.
   Thus, those edits make installed instances inconsistent without an error.
2. **`master.xml` is append-only.** Never remove or reorder existing `<include>` entries.
   New changelogs go at the end. The maintainer-approved v0.77.4 cut-point guard is a
   changelog-level precondition at the head, not a change to released changesets. It protects
   both startup and `changeLogSyncToTag` without changing checksums or include order.
3. **Destructive changes follow deprecate-then-remove across two releases.** Renaming or
   dropping a released table or column happens in two steps.
   Release *N* stops reads and writes, and migrates data if necessary.
   Release *N+1* drops it. A single
   release must stay bootable against the schema left behind by the previous one.

CI enforces 1 and 2 mechanically (see below). 3 is a review responsibility. The sole archival
transition is the verified v0.77.4 baseline: archived files remain byte-identical and test-only.
The baseline and subsequent migrations follow the same immutability policy. Existing installations
must follow the [baseline synchronization runbook](../admin/liquibase-baseline-runbook).

## CI validation

1. **Migration-chain replay, schema drift and ERD** — Build workflow, job *App Server: Generated
   artifacts*. `vp run db:check-drift` applies the full `master.xml` chain to an empty database from the repository's PostgreSQL image (`docker/postgres`).
   It compares the result with the JPA entities. A changelog that does not parse or apply fails here. `vp run db:generate-erd-docs`
   then has to leave `docs/contributor/erd/schema.mmd` unchanged.
2. **Changelog immutability** — Security workflow, job *Dependencies, secrets, and policy*, step
   *Changelog immutability guard*. A git diff from the PR base commit checks two conditions.
   No file under `db/changelog/` can have a modification, rename, or deletion.
   No existing `<include>` in `master.xml` can have a removal, order change, or attribute change.
   Either prohibited change fails the check. The v0.77.4 transition also requires the
   pinned original master and byte-identical archives. It is not a general squash bypass.
3. **Seeded release upgrade** — `release-upgrade.yml` runs three independent paths.
   One upgrades the previous stable release.
   One follows pinned v0.77.4 → baseline synchronization → target release.
   One follows pinned v0.76.0 → expected refusal. Successful upgrades check readiness, seeded relationships, the practice
   catalog and authenticated reads. The refusal path checks both startup and `changeLogSyncToTag`.
   It checks the required v0.77.4 message, unchanged data and history, and a released lock. Release publication
   depends on every path. The same matrix also runs weekly.

The empty-database replay sets no context filter. It evaluates the full chain, but preconditions can
skip changesets. A successful replay does not prove that every change ran. It also does not reproduce
the context selection of a `dev` or `prod` boot (`spring.liquibase.contexts`).

Add focused migration tests for populated tables, rejected database states and any supported rollback.
Empty-database replay cannot prove that existing rows satisfy a new `NOT NULL` or `CHECK` constraint,
and it does not exercise rollback. Preconditions run during replay, but only against the states that
replay reaches. The JPA diff cannot establish equivalence for objects Hibernate does not model, such
as triggers, partitioning and partial-index predicates. Verify those through database-level tests.

## Baseline release gates

The v0.77.4 baseline remains the baseline for 1.0. **A future baseline requires both a major-version boundary and automated synchronization.** Released migrations and the
archived chain remain immutable.

A global Liquibase precondition checks the database cut-point before either update or synchronization.
Liquibase permits one global `preConditions` container, so the guard shares it with the PostgreSQL 18
check. Its failure message covers both prerequisites. Migration identities use id, author and logical
filename, not just id or row count. An empty history is permitted for fresh initialization. The
baseline's existing schema precondition still refuses a partially populated schema.

[Liquibase preconditions](https://docs.liquibase.com/concepts/changelogs/preconditions.html) use lazy
evaluation, so a missing history table never reaches the row query.
[Liquibase 5.0.4 validates the changelog](https://github.com/liquibase/liquibase/blob/v5.0.4/liquibase-standard/src/main/java/liquibase/command/core/helpers/DatabaseChangelogCommandStep.java)
before `changeLogSyncToTag`. Changeset-level preconditions cannot protect that command.
The baseline integration suite proves these properties in both `dev` and `prod`:

- Refusal without DDL.
- Fresh initialization.
- Native-object equivalence.
- Synchronization without DDL or data loss.
- Subsequent upgrades.
- Lock recovery.

- Record a seven-calendar-day staging soak against a restored production snapshot before production.
- Freeze new changelogs for at least 48 hours after production deployment.
- Keep `docs/db/archive/v0.77.4/` for at least two release cycles. Historical regression tests use it
  only as test resources. It must not enter the application JAR.
- Announce the cut-point and synchronization requirement before merging. Developer reset:
  `vp run dev:reset`, then `vp run dev`. This destroys local database data.

## Observation outcome transition before 1.0

The cutover stores one explicit outcome: `MET`, `NOT_MET`, `NOT_APPLICABLE` or `UNDETERMINED`.
Severity is required only for `NOT_MET`. The forward migration maps the previous behavior-level
outcomes for archival integrity and refuses inconsistent historical rows rather than inventing
certainty or severity. It does not reassess old evidence against the complete practice standard.

Historical revision fingerprints remain unchanged. Earlier fingerprint schemes and missing fingerprints are `UNVERIFIABLE` under the current standard.
These observations remain available in authorized history, but do not count as current evidence. A review-run summary counts their met or
not-met verdict as undecided. A new review receives a new immutable revision under the current
fingerprint scheme. Old observations retain their original revision.

The migration keeps criteria as written before cutover, including instructions for the presence and assessment matrix.
This applies to installed bundled workspace copies, instance overrides of bundled practices, and custom definitions.
Keep automated reviews paused until every active definition states its positive standard under the new outcome contract.
Update instance overrides first.
Then update workspace copies through audited catalog releases and custom practices in the editor.

Before upgrading, make and verify a database backup. Upgrade the server, sandbox runtime, webapp
and custom API consumers together. The migration removes the old assessment axes and nested
practice bindings. There are no compatibility readers. Consumers must use the explicit `outcome`
and the flat practice definition. Restore the verified backup to undo the destructive cutover.

Preserve schema versions on exported evaluation data. Frozen historical reports must not be silently
reinterpreted as assessments of the current standard.
