# Practice review runtime

The practices module owns reviews, assignments, results and feedback history.
The runtime owns job claims, attempts, preparation, scripts and transient evidence.
A review can outlive every execution job that produced it.

## Execution ownership

The server selects and persists a review before runtime execution.
A worker claims its job through the existing PostgreSQL queue and authenticated worker hub.
The webhook role receives provider input and does not execute reviews.
Only the worker owns sandbox access.

An ITEM review executes its assigned item.
A SCAN review can own many bounded file jobs, with one active job at a time.
Each job has an independent UUID and a workspace-scoped review reference.
A database index also permits only one active scan per workspace.

Claims carry an attempt fence.
Admission locks the review before its job and assignment rows.
Cancellation follows the same order and prevents later admission from publishing through the old attempt.
Classified preparation reasons describe work, source access, pinned versions and capture failures without raw exception text.

## Scripts and models

Each assigned practice runs its custom script or the built-in script.
The host stages one `<slug>.inputs.json` file under the script input directory.
The script returns one candidate result.
A custom child process has no provider credential.
It calls host capabilities through typed IPC.

The host owns the attempt credential, governed model requests, deadline and usage limits.
Its model assignment follows account-wide AI choice and source-person authorization.
The method snapshot retains all model slots and an epoch after job cleanup.
No second runtime serializer computes the method digest.

The [script runner](./practice-script-runner.mdx) owns the executable contract.
The [AI provider guide](/admin/ai-providers) owns model assignment, prices and ceilings.

## Admission and composition

The worker submits candidates and trusted receipts for its owned attempt.
The server returns allocated result and problem identities with verified citations.
Composition can refer only to those admitted records.
An ids-only admission response cannot authorize an invented problem reference.

An admitting attempt runs in two sandbox launches.
The review launch measures, admits the results and composes private feedback.
After it, a public review launch composes only the review on the work, from the admission that the server stages.
The sessions of the public review launch have no shell.
A continuing attempt runs the public review launch first and then composes private feedback.

Each later launch gets only the time that the attempt has left.
If the public review launch times out or exits with a failure, the attempt ends with that outcome.
If it cannot start, the attempt fails as for any other launch failure.

Each launch has a credential with one job scope: `review` or `public_review`.
The gateway refuses admission and practice script calls to a `public_review` credential.
It refuses public history to a `review` credential.
Each credential prepares only the feedback of its own launch.
A public package holds only the review on the work, and a private package holds none of it.

The [workspace ABI](./agent/workspace-abi.mdx) owns the exact result and history paths.
A history refusal is not an empty result list.
Source custody is checked before confirmed historical words enter the sandbox.

Preparation commits exact feedback and physical copy records before egress.
Runtime completion and feedback delivery have separate states.
A stopped private composition does not erase admitted results or a prepared public proposal.
The [pipeline](./practice-review-pipeline.mdx) owns these stage boundaries.

## Recovery

A failed attempt cannot overwrite its original admitted results.
A retry runs under a new fence and reuses durable assignment state.
Delivery recovery reads persisted copies rather than re-running a writer from raw result text.
Unknown visibility permits readback, not automatic reposting.

An upgrade to a different runtime contract cancels retained queued or running work with CONTRACT_CHANGED.
The migration keeps prior proof and physical write receipts.
A fresh review has new identity and current practice versions.
No decoder for the previous runtime contract remains.

## Retention

Transient job payloads expire after 14 days by default.
Terminal jobs expire after 90 days independently of reviews, results and feedback.
Unacknowledged physical erasure receipts cannot expire with their former job.
Usage keeps a durable review reference after job deletion.

The [operations reference](/admin/practice-review-operations) owns configurable limits and metrics.
The [data map](/admin/dsms/personal-data-map) owns personal-data retention and erasure.
