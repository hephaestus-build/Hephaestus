# Practice review runtime

Use this page when changing where practice-review work executes or extending an artifact handler. For the
review lifecycle and its product semantics, start with the
[practice review pipeline](./practice-review-pipeline.mdx).

## Execution sequence

```mermaid
sequenceDiagram
    accTitle: Practice review execution across server, worker, sandbox, and provider
    accDescr: The server queues a job, the worker captures evidence, Java admits sandbox observations, the same model session composes feedback, and eligible public feedback reaches the provider.
    participant S as Server
    participant DB as agent_job in Postgres
    participant W as Worker
    participant SB as Sandbox
    participant SCM as GitHub or GitLab
    S->>S: authorise, run the gate, record the occurrence
    S->>DB: INSERT one QUEUED row
    Note over S,DB: The row is the enqueue. The server never calls the worker.
    W->>DB: SELECT FOR UPDATE SKIP LOCKED, re-check budget and model
    W->>W: capture evidence, build the manifest, decide readiness
    W->>DB: write evidence_snapshot and review_readiness
    W->>SB: start the container, stage inputs
    SB->>SB: derive the change view, run precompute, build the brief
    SB->>W: model calls, through the worker's own LLM proxy (one session, one turn per practice group)
    SB->>W: submit observations for admission
    W->>DB: validate and persist admitted observations
    W-->>SB: return the durable observation projection and digest
    SB->>SB: resume the same model session and compose feedback
    SB->>W: out/ files and an exit code
    W->>W: verify the admission digest and apply delivery gates
    W->>DB: write the feedback ledger
    opt admitted IN_CONTEXT feedback
        W->>SCM: post or update provider feedback
        W->>DB: record whether delivery succeeded
    end
```

- **The `agent_job` table is the queue.** There is no broker between server and worker. Submission is one
  row containing metadata and an idempotency key. NATS carries webhook ingress upstream and is not part of
  the review queue.
- **Evidence capture runs on the claiming worker.** `ReviewRepositoryPreparer` authorizes the repository
  and clones or refreshes the worker-local mirror before pinning the review range. A missing mirror alone
  does not make the source unavailable. Disabled checkout records the tree as not collected; preparation
  failures are recorded in the capture result.
- **`evidence_snapshot` and `review_readiness` are written before the container starts**, in their own
  transaction, and a failed write fails the run before any model cost accrues. The result is a separate,
  later transaction.
- **One session per review, inside the sandbox.** `pi-runner.ts` builds a brief from the captured
  records and the derived change view, then supplies criteria, questions and each practice's
  precomputed leads one practice group per turn; a turn ends once each of its practices has a recorded
  result. The session carries every turn's reading of the work into the next, which keeps practices
  that share an occasion consistent and pays for that reading once. Once the context has grown past half the model's window, the next turn's end clears what the
  finished turns no longer need, as Pi context edits: each turn's prompt keeps its opening and heading,
  its long read outputs are cleared, and the model's own messages — what it read, concluded and recorded —
  stay. Below that the context only grows by appending, because an edit changes the prefix every later
  call starts with and a provider's prompt cache then serves none of what follows; one clearing of all
  finished turns at once buys the most room for that one break, well before compaction would summarize
  the session.
  The session's system prompt is the orchestrator alone (`pi-orchestrator.md`, staged as the Pi
  agent directory's `AGENTS.md`), with the task's real paths written in for its placeholders: a
  placeholder copied into a command is a shell error. Pi's coding-assistant preamble, edit rules and
  documentation pointers are not sent, and no repository instruction file is discovered. The first turn carries the task,
  the brief and three example observations that between them show every kind of answer once, a
  [skipped question](./practice-review-glossary.mdx#deriving-the-outcome) among them. When the context
  fills and is compacted, the next turn carries them again with what was recorded so far, so the model
  cites the captured lines rather than a summary of them. The brief numbers the lines of captured
  files only; the derived change files are shown as written and marked not citable, and `files.json`
  gives each file's lines in `diff.patch` so a large diff can be read a file at a time. A record the
  capture wrote empty is named as captured and empty; one it did not write is named as not captured,
  and an answer that depends on it stays open, since nothing is known about what it would hold.
  The rules that decide the outcome are never staged: the model answers what it observes, not toward
  an outcome. What is staged of them is each question's `skipWhen`, and the turn prints it under the
  question, for example "Skip it when `changes_behaviour` (Changes behaviour) is NO: it cannot change
  the outcome then." The model may leave such a question out exactly when its own answers meet that
  condition. A question whose answer can change only the severity is staged as `gradesSeverityOnly`, and
  the turn says it grades how serious a shortfall is; left out, it is read as open and the lower band
  holds. The runner refuses any other missing answer. Each observation opens with a `scan`, the model's
  working list of what it looked for and found, written before it cites or answers and never recorded. An observation lists the lines its answers rest on once, as
  evidence, and each answer cites them by number before giving its reason and then its answer; the
  model copies no text, and the runner records what the cited lines say. The [workspace ABI](agent/workspace-abi.mdx#practice-review-tools) owns the item shape, how a path
  resolves to a source, and how a call is put in shape before the SDK checks it.
  Recording tools validate each item separately so one invalid item does not discard valid siblings:
  their schemas are typed but carry no constraint keyword the SDK would apply to the whole call, so each
  item is answered on its own. What the run already knows is filled in rather than refused — the source
  and artifact a path names, a line written as `[L12]`, a line or range of `diff.patch` itself that
  holds lines of the cited file (a range from the file's header included), a checkout file named by its
  workspace path, an evidence entry naming the derived list of changed files (left out, since the
  change's own lines show what it lists), a range the change shows only in part (its shown lines are
  recorded), a reason over its bound (kept to its sentences that fit), a remark field such as
  `evidence_note` (left out), an answer nested inside another one, a range of `diff.patch` that holds
  one file's lines, an empty stray field, a WITHHOLD's own NOT_MET observations — and a fill
  that changes what was sent is reported. A refusal names every
  answer and field at fault in an item at once, with the value received and what would be accepted, and
  states facts rather than doubting an answer; a stored item echoes the answers recorded. A resend of what is already recorded is an error that names what is still owed, an
  identical resend of a refused item gets the same answer at once, and a third identical send ends the
  turn. An unreadable list shows where it breaks and is charged to no practice. A call cut off at the model's output limit reaches its tool incomplete: the model is told that the error is the cut, and a second cut in the turn ends it. Progress and repetition
  limits stop unproductive turns. Recorded results are saved under `work/notes/`.
  Each session is Pi's coding-agent `AgentSession`. Pi 1.0 also ships `pi-durable`, an experimental
  harness that checkpoints every model call and tool call so a crashed run can resume; it is not used.
  A review runs once in a sandbox that is discarded with its storage, a run that fails is retried by
  the server from the captured evidence, and `pi-durable` has no codemode.
- **Work, not time, bounds a turn.** Each turn gets its own budget of model calls and output tokens:
  `PRACTICE_REVIEW_PRACTICE_MODEL_CALLS` and `PRACTICE_REVIEW_PRACTICE_OUTPUT_TOKENS` per practice it
  carries, never less than three practices' worth, whatever earlier turns spent
  ([practice-review operations](/admin/practice-review-operations)). The turn text does not
  state the budget: told its call budget up front, an open model read less and missed more negatives.
  A turn is asked once to record when two calls are left, or when its tokens left only pay for
  the observations it still owes at the tokens per observation the session has shown. It ends at the
  first turn boundary after the call that spends the budget, so the tools of that call, a recording
  among them, have run; an aborted call records nothing. The budget is a cap on a turn that runs away,
  several times what a turn normally spends, not a pace. Composition gets one unit per NOT_MET
  practice, at most a full turn's worth. Time is used for liveness only: a turn with no session event for five minutes
  is aborted as stalled, two stalls in a row end measuring, and the binding's timeout is a safety
  ceiling, split so measuring stops early enough for admission and composition to land. An aborted turn
  must become idle before its session starts another turn. Practices still missing get the finishing
  turn with their criteria and their own budget; they are not treated as completed reviews. See
  [recorded-result coverage](./practice-review-pipeline.mdx#recorded-result-coverage).
- **Composition follows durable admission.** The same session composes feedback from the admitted
  projection and bounded history, making room by compaction first when the turn would not fit. The turn
  shows NOT_MET observations with their rationale and cited coordinates and the others by what they
  found; after a compaction it carries the task and the brief again, not the measuring examples. An
  earlier review of the same work is the same piece of work when a pattern is counted, as the server
  counts it. It cannot add observations during composition. There is no
  reconnaissance, per-practice or retry session.
- **The worker posts public feedback.** It validates sandbox output, persists observations and feedback,
  and applies delivery policy before calling the provider. Model composition runs in the sandbox.
- **Control never returns to the server between claim and completion.** The only server-to-worker push is
  the hub WebSocket, and it carries cancellation and drain, not work.

## Extension points

Artifact handlers assemble context and delivery constraints. Provider adapters own provider identifiers,
diff and comment APIs, and conversation storage; the practices module owns definitions, observations, and
the feedback ledger.

The extension boundaries are:

- **Occasion gate** — decides whether an occurrence may enqueue work.
- **Queue and execution** — `agent_job`, described by
  [ADR 0025](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0025-agent-job-queue-on-postgresql.md).
- **Workspace ABI** — the sandbox receives read-only `inputs/`, disposable `work/`, and returns only
  `out/`. [Agent workspace ABI](agent/workspace-abi.mdx) is the source of truth for paths and exit codes.
- **Observations** — the agent reports answers through `report_observation`; server admission validates
  them and derives the outcome from the practice revision's rules, and persistence assigns an occurrence
  identity and a separate evidence-location grouping key.
- **Feedback** — after admission, the same agent session reports through `report_feedback` in a closed
  intervention phase; the runner refuses a practice-page card unless the practice is NOT_MET on as many
  distinct pieces of work as the composition request's `minDistinctArtifacts`, counting this work and
  the staged history, so one occurrence stays a note on the work.
  Server admission validates the result without invalidating completed measurement. Admitted feedback,
  server suppressions, replacements, and placements enter the ledger; a model `WITHHOLD` remains only in
  the bounded job output. The seam itself is
  [ADR 0029](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0029-measurement-intervention-seam-and-channel-levels.md).

When changing sandbox inputs or outputs: update the owning runtime type or parser first; update the ABI
page only for a durable ABI change; add a behavioural test at the narrowest owning boundary; regenerate
OpenAPI and the web client when the HTTP contract changes. To extend the bundled catalogue, follow
[Practice catalogue curation](practice-catalogue.md).

Avoid copying file trees, enum inventories, defaults, or database columns into this guide. Those details
are owned by executable types, Liquibase, the generated database schema, and OpenAPI.
