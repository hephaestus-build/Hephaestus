Hephaestus supports full-stack development across Java and TypeScript. This guide focuses on the development environment. Production operations are covered in the Admin guide, starting with [Kubernetes](/admin/kubernetes).

## Prerequisites

Install and configure the following tools before you attempt a local build:

1. **Java JDK 21** – Required for the Spring Boot application server. Gradle reads the target JDK
   from `.java-version` and uses its Java toolchain support. The checked-in wrapper downloads the
   pinned Gradle distribution and verifies `server/gradle/wrapper/gradle-wrapper.properties`' checksum.
   CI also validates the wrapper JAR. No global Gradle installation is needed.
2. **Docker and Docker Compose** – Required for PostgreSQL. Verify both with `docker info`
   and `docker compose version`.
3. **Vite+ (`vp`)** – The command surface for every repository task, and how you get the pinned
   Node.js. Install the launcher:

   ```bash
   curl -fsSL https://vite.plus | bash
   ```

   On Windows: `irm https://vite.plus/ps1 | iex`. The launcher's own version does not matter: it
   runs the `vite-plus` this repository pins. Managed mode is on afterwards and provides the
   Node.js `devEngines.runtime` pins. Run `vp env off` if you manage Node.js yourself. `vp install`
   then installs dependencies through the pinned pnpm, which Vite+ downloads itself: no global
   pnpm, no Corepack.

   The installer adds `vp` to your login shell. Anything that does not start
   from one, an IDE task or a desktop app, needs `vp` on its PATH like `node` and `git`.

   After `vp install`, `vp --version` prints the pinned `vite-plus`.

4. **Helm CLI** – Required by `vp run check` and the pre-push hook: the tooling tests render the
   chart with the real `helm` on your PATH. Install the version that
   [`.github/actions/setup-helm/action.yml`](https://github.com/hephaestus-build/Hephaestus/blob/main/.github/actions/setup-helm/action.yml)
   pins. That file is the one home of the version and its checksums. CI installs the same version.
   Verify it with `helm version`.
5. **Kubernetes dev tools** – The host server runs its sandboxes in k3d. Install the tools in [Kubernetes](#kubernetes) before you start `vp run dev`.

If you push branches to the repository instead of a fork, also configure commit signing.
[CONTRIBUTING.md § Signed Commits](https://github.com/hephaestus-build/Hephaestus/blob/main/CONTRIBUTING.md#signed-commits) has the setup.
`vp install` warns while it is missing.

## Recommended IDE setup

Open the repository using the `project.code-workspace` file in VS Code and install the workspace recommendations (`@recommended` in the Extensions view). Key extensions include:

- Java Extension Pack
- Spring Boot tools
- TypeScript tooling
- oxlint (lint) and oxfmt (format)
- Tailwind CSS IntelliSense

The Oxc extension provides oxlint diagnostics. Workspace settings use it to format JavaScript,
TypeScript, and JSON files on save.

Run the same checks from the shell with:

```bash
vp run check:agents          # Format check, lint, and both typechecks outside the webapp
vp run fix:agents            # check:agents, applying every safe fix
vp run check:webapp          # The SPA's format and lint checks; the lint is type-aware and type-checks
vp run check                 # Complete local quality gate
```

Use the [local verification contract](./local-verification.mdx) for affected checks, the pre-push gate,
and CI exclusions.

IntelliJ and WebStorm are also supported.

### Java formatting

```bash
vp run format:java
vp run format:java:check
```

The repository commands are the source of truth. Optional editor integrations:

- [IntelliJ](https://plugins.jetbrains.com/plugin/13180-palantir-java-format)

## Application server

### Spring profiles and local configuration

For development stick to the `local` profile, which is the default. The other shipped profiles each
have their own `application-<name>.yml` under `server/application/src/main/resources/` — `prod` and `specs`, plus
the per-purpose overlays (`e2e`, `cds-training`, `migrate`, `playwright`) documented where
they are used.

These are Spring profiles, not build profiles. Gradle’s `bootRun` passes `-Pprofiles=…` through to
Spring. `vp run dev:server:e2e` uses that interface.

#### Build-only profiles

`specs` and `cds-training` generate artifacts. They are not deployment modes.
They load the application contract without runtime bootstrap, container-image validation or image pulls.
They supply no shared placeholder secrets.
If an authentication component needs a key to initialize, the build uses the non-production ephemeral-key behavior, without a runtime warning.

Startup rejects either profile together with `prod`, even when production secrets are configured.
Production encryption requirements apply to Spring's expanded profiles.
Thus, a production profile group requires the same keys as `prod` itself.

`vp run dev` runs the server role, with its sandboxes, in a host JVM against one shared k3d cluster.
Each worktree uses its own sandbox namespace, derived from its port set, with its own ResourceQuota.
Its review and conversation sandboxes stay in that namespace.
Five worktrees share the cluster. They do not each install a full chart release.

The sandboxes reach the host JVM through its sandbox gateway. Each sandbox receives its own subject-scoped token.

The cluster has one full chart release for cluster qualification and live suites.
Run that release on demand with `vp run dev:kubernetes`.
Production and `small` resource requests also apply when you qualify those profiles.
Changing the dev release's requests requires separate measurements of dev peaks.

Create `application-local.yml` in `server/application/src/main/resources` to override defaults. This file is gitignored.

The server encrypts stored secrets with `HEPHAESTUS_SECURITY_ENCRYPTION_KEY` and `HEPHAESTUS_SECURITY_CREDENTIAL_ENCRYPTION_KEY`.
For a new database, the first `vp run dev` writes both keys to `server/.env` ([Local settings](#local-settings)).
Keep these values across restarts.
For an existing database, keep its current keys and versions and follow the [stored secret conversion procedure](../admin/upgrade#convert-stored-secrets-for-10).
The server does not store plaintext credentials or JWT private keys.

:::caution[Keep it local]
Never commit `application-local.yml`. It may contain secrets and machine-specific configuration.
:::

### Running the stack

1. Check that the Docker daemon runs with `docker info`.
2. From the repo root, start everything with one command:

   ```bash
   vp run dev
   ```

   This launches an `mprocs` session with the server and webapp in separate panes (switch with the arrow keys). The PostgreSQL container is brought up automatically.

   Prefer plain terminals? Run the two sides yourself:

   ```bash
   vp run dev:server   # terminal 1 — brings up Postgres, then Spring Boot
   vp run dev:webapp   # terminal 2 — Vite dev server
   ```

3. Open the webapp on this worktree's `WEBAPP_PORT`. See the [port map](#port-map).
   The first worktree uses `http://localhost:4200`, with the server on `http://localhost:8080`.

   The OpenAPI description and Swagger UI are **off** by default. When enabled, these endpoints are
   unauthenticated and expose the route list, including admin routes. For a local session, set `SPRINGDOC_API_DOCS_ENABLED=true`
   (and `SPRINGDOC_SWAGGER_UI_ENABLED=true` for the browser UI) and Swagger UI appears at
   `http://localhost:<SERVER_PORT>/swagger-ui/index.html`. Committing a spec does not need either flag —
   `vp run generate:api:specs` boots under the `specs` profile, which turns them on
   itself.

To wipe the local database (e.g. after a bad migration or sync), run `vp run dev:reset`. The Postgres data is a bind-mounted folder (`server/postgres-data`), so `docker compose down -v` alone does not clear it — `dev:reset` removes the folder and recreates the stack.

### Local settings

`server/.env` holds the local settings of a checkout.
Docker Compose and Spring Boot both read it.
One command writes it: `vp run dev:env`.
`vp run dev`, `dev:server`, `dev:webapp`, `dev:compose`, `dev:reset` and every `db:*` command run it first, so you run it yourself only to edit the file before the first start.
It is safe to run again: it never replaces a value that is set.

1. If `server/.env` does not exist, the command creates it from `server/.env.example`.
2. It adds each of these values that the file and your shell do not set:

   | Value | Added | Why |
   |---|---|---|
   | `COMPOSE_PROJECT_NAME` | For a new database | The checkout's folder name and a hash of its path. A command in one checkout never acts on the containers of another. |
   | `POSTGRES_PASSWORD` | For a new database | Compose creates the database with it. Spring Boot and the database scripts read it. |
   | `HEPHAESTUS_SECURITY_ENCRYPTION_KEY`, `HEPHAESTUS_SECURITY_CREDENTIAL_ENCRYPTION_KEY` | For a new database | The server encrypts stored secrets with them. |
   | `WEBHOOK_SECRET` | Always | GitHub signs its webhooks with it ([Webhook receiver](#webhook-receiver)). |

Edit `server/.env` to add your own settings. Do not copy `server/.env.example` over it.
A copy removes the generated values that your database needs.
A value in your shell overrides the file.

PostgreSQL reads the password only when it creates a database, and the server reads stored secrets only with the keys that encrypted them.
Thus, a checkout whose `server/postgres-data` already has data gets no new password, project name or keys.
If its password or project name is missing, the command stops and tells you to set it. If a key is missing, it warns.
Run `vp run dev:reset` to start again with a new database. This deletes the local data.

### Port map

Each worktree of a clone has its own host ports, so several worktrees run at the same time.
`vp run dev:env` writes them to `server/.env` the first time, with the other [local settings](#local-settings).
It takes the first port set that no other worktree of the clone uses.
Set `n` adds `10 × n` to each default port. The first worktree gets the defaults.
A worktree keeps its ports: the command never changes a `SERVER_PORT` that is set.
Container-internal ports never change. Only the `localhost` binding moves.

| Service            | Default | Variable            |
| ------------------ | ------- | ------------------- |
| PostgreSQL         | 5432    | `POSTGRES_PORT`     |
| Application server | 8080    | `SERVER_PORT`       |
| Sandbox gateway    | 8081    | `SANDBOX_API_PORT`  |
| Management         | 9090    | `MANAGEMENT_PORT`   |
| Mailpit SMTP       | 1025    | `MAILPIT_SMTP_PORT` |
| Mailpit UI         | 8025    | `MAILPIT_UI_PORT`   |
| Webapp (Vite dev)  | 4200    | `WEBAPP_PORT`       |

Every set keeps the management port at `SERVER_PORT + 1010`.
Read your worktree's ports in `server/.env`.

Every consumer reads the same file:

- Docker Compose maps the PostgreSQL and Mailpit ports.
- Spring Boot listens on `SERVER_PORT`, `SANDBOX_API_PORT` and `MANAGEMENT_PORT`, and allows the webapp origin `http://localhost:<WEBAPP_PORT>`.
- `vp run dev:webapp` serves on `WEBAPP_PORT` and points the app at `http://localhost:<SERVER_PORT>`.
- `vp run check:ports` checks the ports before you start the stack.

A worktree that has no `SERVER_PORT` in `server/.env` uses the defaults.
Thus, a worktree from before this command counts as the first set until its next `dev*` or `db:*` command gives it its own ports.
That command can move its ports, and its sandbox namespace with them ([Kubernetes](#kubernetes)).
The command does not see other clones or other programs.
If a port is in use, set the port in `server/.env` yourself.
A port in your shell overrides the file.

### Email

The `local` profile sends every email to the Mailpit container from `server/compose.yaml`. Nothing
leaves your machine. Its SMTP and inbox ports bind to `127.0.0.1` only. Open `http://localhost:<MAILPIT_UI_PORT>` to read
what the server sent, with the HTML part, the plain-text alternative and the headers side by side.

The quickest end-to-end check is the **Send test email** button on the instance settings page
(`/admin/settings`). It goes through the same gateway as every notification, including silent mode.

Templates live in `server/application/src/main/resources/templates/email/` — `html/` and `text/`
hold the two parts of one message, and `messages.properties` holds the subjects.

#### The webapp's settings

`vp run dev:webapp` serves `/env-config.js` itself, with the server URL and the webapp URL of this worktree.
In production, the container entrypoint writes the same file.
Do not edit the committed stub `webapp/public/env-config.js`.

The app has no Vite-level environment variables: the config sets no `envPrefix`, and nothing in `src/` reads `import.meta.env` beyond `DEV`.
A `webapp/.env` file has no effect.

### GitHub configuration

Hephaestus supports two GitHub authentication modes. Pick the one that fits your workflow:

| Mode           | Best for                     | Workspace creation             | Repository monitors                  |
| -------------- | ---------------------------- | ------------------------------ | ------------------------------------ |
| **PAT**        | Quick local development      | Manual (from config)           | Manual (you list them)               |
| **GitHub App** | Testing webhooks, production | Automatic (from installations) | Automatic (from installation events) |

#### Option A: Personal Access Token (simpler)

1. [Create a Personal Access Token](https://github.com/settings/tokens) with scopes: `repo`, `read:org`, `read:user`.

2. Create `application-local.yml`:

   ```yaml
   hephaestus:
     workspace:
       init-default: true
       default:
         login: your-github-org # e.g., "ls1intum" or "HephaestusTest"
         token: ghp_your_token
         repositories-to-monitor:
           - your-github-org/repo1
           - your-github-org/repo2
   ```

3. Leave `hephaestus.integration.github.app.id` unset or set to `0`.

#### Option B: GitHub App

1. [Create a GitHub App](https://docs.github.com/en/apps/creating-github-apps) with appropriate permissions.

2. Create `application-local.yml`:

   ```yaml
   hephaestus:
     integration:
       github:
         app:
           id: 12345
           privateKey: |
             -----BEGIN RSA PRIVATE KEY-----
             ...
             -----END RSA PRIVATE KEY-----
     workspace:
       init-default: false # Workspaces created from installations
   ```

3. Install the app on your organization. Hephaestus creates workspaces and monitors automatically.

### Limiting sync scope (development filters)

When using GitHub App mode, your app might have access to hundreds of repositories. Use filters to focus on specific orgs/repos during development:

```yaml
hephaestus:
  sync:
    filters:
      allowed-organizations:
        - hephaestus-build
        - ls1intum
        - HephaestusTest
      allowed-repositories:
        - hephaestus-build/Hephaestus
        - ls1intum/Artemis
        - HephaestusTest/demo-repository
```

Empty lists = no filtering (production behavior). Non-empty = only sync matching items.

:::tip
Filters do not delete data – they just skip sync operations. Workspace and organization metadata is still created for all installations.
:::

### AI model (local)

Practice reviews and the mentor need at least one enabled model. Providers are registered at
runtime — either an instance-wide catalog entry (Instance administration → AI models) or a workspace's own
"bring your own AI provider" connection. Configure it through the same admin UI/API used in
production. There is deliberately no second env-var catalog or startup seeder that can drift from
the stored configuration.

New connections and models start inactive. Test the connection.
Declare its price or explicitly mark it as having no metered API cost.
Activate it.
Bind it to a purpose (`PRACTICE_REVIEW` or `MENTOR`) on the workspace's **AI models** page.

For an automated local end-to-end setup, use `vp run dev:e2e:setup`. It creates the connection, model, and agent binding through the application API.
It reads provider credentials from `E2E_*` environment variables.
Thus, they stay outside source control and command-line history.

Models always use the in-app LLM proxy: the upstream key is injected by the proxy and never reaches
the sandbox.

An SSRF egress guard (`EgressPolicy`) validates provider base URLs.
In production, it accepts only a public HTTPS host, or a private host that the operator lists in `hephaestus.llm.egress.private-hosts`.
It rejects plain-HTTP `localhost`/`127.0.0.1`/`::1` targets. To point a connection at a local OpenAI-compatible gateway during development,
set:

```yaml
# application-local.yml
hephaestus.llm.egress.allow-loopback: true
```

or `HEPHAESTUS_LLM_EGRESS_ALLOW_LOOPBACK=true` in `server/.env`. It is off by default and
`application-e2e.yml` is the only shipped profile that turns it on. Never enable it in a deployed
environment.

### Authentication (local)

Authentication is Hephaestus-native (no Keycloak — see [ADR 0017](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0017-replace-keycloak-with-spring-native-auth.md)). The server federates to GitHub (and optionally GitLab — gitlab.com or a self-hosted instance) through Spring Security `oauth2Login`, then issues its own short-lived ES256 cookie-session JWT. The webapp reads `GET /user` and redirects to `/auth/login` — there is no token in the browser.

#### Configure GitHub login

1. [Create a GitHub OAuth application](https://github.com/settings/developers) with the callback URL `http://localhost:8080/login/oauth2/code/github` (replace `8080` with your `SERVER_PORT`).
   The local auth issuer defaults to `http://localhost:${SERVER_PORT:8080}`.
   If you set `HEPHAESTUS_AUTH_ISSUER`, register its origin instead.
   Add `HEPHAESTUS_AUTH_API_BASE_PATH` before `/login` if you set an API prefix.
2. Create `server/.env` if it does not exist yet, and set the credentials in it:

   ```bash
   vp run dev:env
   # Edit server/.env and set:
   # GITHUB_OAUTH_CLIENT_ID=<github-client-id>
   # GITHUB_OAUTH_CLIENT_SECRET=<github-client-secret>
   ```

3. (Optional) To enable local GitLab login, register an OAuth application on your GitLab instance.
   Use callback `http://localhost:<SERVER_PORT>/login/oauth2/code/gitlab` and scope `read_user`.
   Apply the same issuer and API-prefix settings as for GitHub.
   Set `GITLAB_OAUTH_CLIENT_ID` / `GITLAB_OAUTH_CLIENT_SECRET`.
   Point `GITLAB_OAUTH_BASE_URL` at the instance.
   Its default is `https://gitlab.com`, but you can use, for example, `https://gitlab.lrz.de`.
   To hide the GitLab button, leave the client id blank.
4. Run the application server with `vp run dev:server`. It brings up the Compose services, installs
   the generated-clients module and starts the application module. Open the webapp and click
   **Continue with GitHub**.

GitLab workspaces are created only on `GITLAB_DEFAULT_SERVER_URL`, falling back to
`GITLAB_OAUTH_BASE_URL`. Set it consistently on every server. Additional GitLab login
providers permit sign-in and identity linking. They do not permit syncing another GitLab instance.

#### Super admin

App-level admin is the `APP_ADMIN` role on the `account` table, with authority `app_admin` in the JWT.
`admin` is the per-workspace role name, which instance tokens exclude.
An existing admin manages this role from the `/admin/users` UI.

Before first boot, list the first admin in `HEPHAESTUS_AUTH_BOOTSTRAP_ADMINS`, for example `github:@you`.
Promotion runs on their first login.
It is idempotent and promote-only.
Manual database edits are a last resort.

#### Troubleshooting auth

- **401 after login:** check that `GITHUB_OAUTH_CLIENT_ID/SECRET` are set.
  Check that the provider callback matches `HEPHAESTUS_AUTH_ISSUER`, or `http://localhost:<SERVER_PORT>` when it is unset, plus the configured API prefix.
- **Logins do not survive a server restart locally:** set `HEPHAESTUS_AUTH_STATE_COOKIE_KEY` (base64 32-byte. `openssl rand -base64 32`) in `server/.env` — otherwise an ephemeral per-boot key is used.
- **Reset everything:** `vp run dev:reset` (see Running the stack). On next login the account and identity link are recreated.

### Kubernetes

`vp run dev:kubernetes` installs the chart on a local [k3d](https://k3d.io) cluster with the images of this checkout.
It needs Docker with at least 10 GiB of memory, `k3d`, `kubectl`, Helm 4, the [`pack` CLI](https://github.com/buildpacks/pack/releases), `openssl` and `curl`.
The command checks the tools and memory budget first and names each missing item.
On macOS, `brew install k3d helm kubectl` installs three of the tools.
If the `buildpacks/tap/pack` formula fails, use the `pack` release archive.

The native stack (`vp run dev`) is the default inner loop.
It reloads the webapp at once.
The server stays on the host, where your IDE can debug it.
It runs its Pods in the shared cluster.

The dev launcher builds and pins the agent image, creates the worktree namespace, and applies the chart's sandbox quota, NetworkPolicy and server RBAC there.
It gives the JVM a namespace-scoped kubeconfig with short-lived credentials.
No cluster credential reaches a sandbox.

Each worktree has its own `SERVER_PORT` and `SANDBOX_API_PORT` ([Port map](#port-map)).
The namespace is `heph-dev-<SERVER_PORT>-<SANDBOX_API_PORT>`.
The host loop runs one review and one conversation turn at a time.
The Pod requests stay the same as the chart's.

`vp run dev:kubernetes:worktree:reset` deletes only this worktree's namespace and PriorityClasses.
Stop its JVM first.
A port set that belongs to another worktree stops startup instead of changing that namespace.

Use the cluster before you push a change to one of these:

- The Helm chart (`deploy/chart/`) or its script (`scripts/kubernetes-cluster.ts`).
- The Kubernetes sandbox backend or the sandbox gateway of the server.
- A runtime role, or a setting that a role binds at start.
- The agent or PostgreSQL image.

CI runs the cluster jobs for these paths, and `vp run check:affected` reminds you of them.
A cold `vp run dev:kubernetes` took about 5 minutes on an Apple silicon Mac, and a warm run about 3.
Debug a defect in the native stack when you can.
In the cluster, follow the logs of a role with the `kubectl` command that `dev:kubernetes` prints.

`vp run dev:kubernetes` does these steps:

1. It creates the k3d cluster `hephaestus` with two nodes and publishes HTTPS on the loopback address only.
   The Kubernetes API uses a free port on `127.0.0.1`.
   An older cluster with a non-loopback API binding requires `vp run dev:kubernetes:reset`.
   Port 443 must be free. The check stops the command when a program holds it.
   It also creates a local registry, which the nodes use as a mirror of `ghcr.io`.
2. It builds the server, webapp, agent and PostgreSQL images, and pushes them to that registry.
3. It creates the qualification namespaces, a Secret with generated values, and the certificates.
   It keeps them in `~/.hephaestus/kubernetes-cluster`, shared by the worktrees.
   Each worktree generates its private host-server kubeconfig at `.context/kubernetes-host/<namespace>/kubeconfig.json`.
4. It turns on the Gateway provider of the Traefik that k3s ships, and creates the Gateway `cluster`.
5. It installs the chart with the dev profile and sandboxes on.
   It runs the sandbox isolation gate against the installed templates.
6. It sends a request to the webapp and the API through the Gateway.
   Then it prints the URL, `https://hephaestus.localhost`, and how to sign in.

The local CA `ca.crt` in the `kubernetes-cluster` work folder signed the certificate.
The command prints its path and the commands that make your system trust it.
Below, `$WORK` is the work folder. On macOS:

```bash
security add-trusted-cert -r trustRoot -k ~/Library/Keychains/login.keychain-db "$WORK/ca.crt"
```

On Debian or Ubuntu:

```bash
sudo cp "$WORK/ca.crt" /usr/local/share/ca-certificates/hephaestus-dev.crt
sudo update-ca-certificates
```

Firefox, and Chrome on Linux, keep their own stores.
If you use [mkcert](https://github.com/FiloSottile/mkcert), `CAROOT="$WORK/mkcert" mkcert -install` adds the CA to those stores too.
A certificate lasts 397 days. A run issues it again when fewer than 30 days remain.

The chart runs the `prod` profile, so the passwordless dev sign-in is off.
To sign in, create a GitHub OAuth app for the cluster.
Use the homepage `https://hephaestus.localhost` and the callback `https://hephaestus.localhost/api/login/oauth2/code/github`.
Then give its values to the command:

```bash
GITHUB_OAUTH_CLIENT_ID=... GITHUB_OAUTH_CLIENT_SECRET=... \
  HEPHAESTUS_AUTH_BOOTSTRAP_ADMINS=github:@you vp run dev:kubernetes
```

Only one qualification release runs in the shared cluster.
Run it when you need chart or live-suite qualification. Then use `vp run dev:kubernetes:down` to release its compute resources.
Host edit loops keep their separate namespaces and keep running.
Five simultaneous full releases are outside the dev contract.

A second run reuses the cluster, the registry, the Secrets and the database.
It keeps every value of the Secrets, and adds only a key that a newer checkout needs.
It also keeps the OAuth app, so you give the variables only once.
Give both again to change the app, or `HEPHAESTUS_AUTH_BOOTSTRAP_ADMINS` alone to change the first admins.
`vp run dev:kubernetes:reset` removes the app with the cluster.
Every `kubectl` and `helm` call of the command uses the cluster `k3d-hephaestus`, whatever your current context is.

Each run applies the agent-sandbox controller of its checkout's `deploy/platform/k3s-agent-sandbox.yaml`.
The controller and its resource definitions are cluster-wide.
Thus, a checkout with an older pin downgrades them for every worktree.
They stay downgraded until a checkout with the newer pin runs again.

| Command | Does |
|---|---|
| `vp run dev:kubernetes:down` | Drains the qualification servers and removes that release and its sandbox namespace. Keeps the shared cluster, host-loop namespaces, database volumes, Secrets and CA. The next `dev:kubernetes` installs the release again. |
| `vp run dev:kubernetes:reset` | Deletes the shared cluster, its data, the registry and the work folder with the CA. Refuses while host-loop namespaces exist: stop those JVMs and reset each worktree namespace first. The next run makes a new CA, so trust it again. |

If Docker has no free address pool for the cluster network, the command stops before k3d starts.
Stopped Compose stacks of other worktrees keep their networks.
The command then tells you to run `docker network prune`, which removes the networks that no container uses.

The CI cluster jobs run the same script (`scripts/kubernetes-cluster.ts`) with the images of their run.
The k3d job also serves the release through the same Gateway, and sends the same HTTPS requests.

### Webhook receiver

The webhook receiver lives in the Java server (`integration.core.webhook` package).
`vp run dev:server` exposes the unified `/webhooks/{kind}` endpoint (kinds: `github` and
`slack`) alongside the rest of the API. GitLab and Outline post to their connection routes.

Production runs the receiver in the server too — [Server runtime](../admin/runtime-roles#reception-during-a-restart).

GitHub signature checks need the webhook secret.
In the native stack, `vp run dev:env` writes a random `WEBHOOK_SECRET` to `server/.env` ([Local settings](#local-settings)).
To use a secret of your own, replace the value in the file.

`vp run dev:kubernetes` generates it in the release Secret.

The value must match the secret configured on your GitHub webhooks, which `X-Hub-Signature-256` validates.
GitLab group hooks use `WEBHOOK_ROUTING_SECRET` instead — see [`WEBHOOK_ROUTING_SECRET`](../admin/production-setup#gitlab-rollout-bundle).

Before enabling GitLab or Outline registration with a routing secret, set `HEPHAESTUS_AUTH_ISSUER` to your public HTTPS tunnel's root origin.
Forward `/webhooks/` to the local receiver.

## Web client (`webapp`)

1. Install dependencies:

   ```bash
   vp install
   ```

2. Start Vite on this worktree's `WEBAPP_PORT`:

   ```bash
   vp run dev:webapp
   ```

3. Visit `http://localhost:<WEBAPP_PORT>`, with the port from `server/.env`.

### UI foundations

- We ship Tailwind CSS 4 in JIT mode. Keep utility classes in JSX and rely on design tokens defined in `src/styles/theme-tokens.css`.
- Enable Tailwind IntelliSense in your IDE. Typeahead prevents typos and invalid compositions.
- Avoid premature abstractions with `@apply`. Duplication is fine when it keeps components readable.

### Component workflow (Storybook + Chromatic)

Storybook is the source of truth for presentational components.

```bash
vp run --filter webapp storybook:dev           # Local playground on http://localhost:6006
vp run --filter webapp build-storybook     # Static bundle for Chromatic
vp run --filter webapp chromatic:ci        # Visual regression in CI
```

- Every new UI component ships with at least one story covering empty, loading, and error states.
- CI runs Chromatic for same-repository pull requests that change the webapp – review visual diffs before merging.
- Reference [ui.shadcn.com](https://ui.shadcn.com/) for composition patterns. A new widget builds on the Base UI primitives already wrapped under `src/components/ui/**`.

### OpenAPI client

`webapp/src/api/**` is generated from `server/openapi.yaml` and is the only way the webapp talks to
the server. After an API change, from the repository root:

```bash
vp run generate:api   # regenerates server/openapi.yaml from the packaged JAR, then the client
```

`vp run generate:api:client` regenerates the clients alone from the committed
spec: this one and the Chrome extension's `extension/src/api/**`. Commit the spec and both clients
with the change.
CI fails a change that breaks a client of the previous release.
See [API compatibility](./ci-cd.mdx#api-compatibility).

Both clients use the generator in `scripts/api-generator/`.
That workspace supplies the TypeScript 6 compiler API required by the stable generator.
The applications and root tooling keep TypeScript 7.
The generator pin lives in `scripts/api-generator/package.json`.

Both configurations disable the generated root entry file.
The webapp's owned `src/api.ts` exports types without listing each schema.
Oxfmt runs on each generated directory with `scripts/api-generator/oxfmt.generated.json`,
so one API addition does not rewrite a single long import or export line.
All generated outputs stay committed. CI regenerates them and requires a clean tree.

- Schema names carry no `DTO` suffix. The server strips it when it publishes the spec.
- Pair every new endpoint with its generated TanStack Query options. Never hand-roll `fetch` — the
  generated client is configured once and carries the cookie session.

### Updating Java dependencies

Edit `server/gradle/libs.versions.toml` for library and plugin versions.
Edit `server/build.gradle.kts` for plugin-classpath BOMs and transitive constraints.
Then resolve the graphs and exercise the changed tools.
Strict dependency locking rejects missing lock state as well as version drift. Do not delete a
lockfile or disable verification to make an update pass.

The root `dependencies` report covers both projects, including PMD's auxiliary classpath.
The `buildEnvironment` report covers the separately locked plugin classpath in
`server/buildscript-gradle.lockfile`. Renovate's standard lock and checksum commands refresh the
same graphs used by source builds.

Set `GRADLE_USER_HOME` to an empty temporary directory and disable configuration caching when
generating metadata, so cached resolution cannot omit parent POM or module-descriptor checksums:

```sh
./server/gradlew -p server --no-configuration-cache \
  dependencies buildEnvironment \
  --write-locks --write-verification-metadata sha256
./server/gradlew -p server --no-configuration-cache \
  :application:check :application:bootJar --write-locks --write-verification-metadata sha256
```

Review the dependency-lock diffs and independently verify newly trusted artifacts against their
publisher before committing `server/gradle/verification-metadata.xml`. Metadata generation records
what was downloaded. It does not establish trust. Run the checks again without metadata-writing
flags, still without configuration caching and with another empty Gradle user home, to verify fresh
downloads. Exercise changed generators, formatters, Liquibase or mutation tooling as well: their
classpaths are separate from the application runtime. Restore your usual Gradle user home afterward.

Gradle does not remove the verification entry of a version that no build downloads any more.
OSV Scanner reports such an entry as a dependency — [Gradle dependency inventory](./supply-chain-security.md#gradle-dependency-inventory-and-the-vulnerabilities-exclusion).
After an update that replaces versions, run:

```sh
node scripts/check-gradle-verification-metadata.ts --write
```

It resolves every server dependency in an empty Gradle home with strict verification.
Then it deletes each component that the resolution did not download.
The deletion adds no checksum to trust.
If a CI task reads a reported component, add that task to the script instead of deleting the entry.
Without `--write`, the command fails on such a component, as Quality → App Server does on a pull request.

Run `--write` on Linux, as CI does.
Another operating system can resolve a different set of components.
The script compares whole components.
It does not report an unused artifact inside a component that the build still downloads, such as the native JAR of another platform.

For a Gradle wrapper update, also run the build with `--warning-mode all` and review plugin
compatibility before accepting a new major. Do not suppress upstream deprecations to make the
upgrade appear clean. A JDK-line change updates `.java-version` and Renovate's matching
`constraints.java`. `gate:toolchain` rejects drift between them.
