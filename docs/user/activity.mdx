Use Activity to find work that needs you or prepare a record of your recent work.
It lists GitHub or GitLab work without scoring it or ranking people.

1. Under **Dashboards**, select **Activity**.
2. For work that needs you now, read **Needs you**.
3. For a standup or work record, choose a time range and use [Copy as Markdown](#copy-as-markdown).

The sidebar has two pages under **Dashboards**:

- **Activity** is your own page. A workspace without practice reviews opens here. A workspace with practice reviews opens on your [Practice profile](./practice-profile.mdx).
- **Workspace activity** shows everyone in the workspace or one team.

Every workspace has both pages, without an activation setting.
They show work in the workspace's repositories.
Everyone with a workspace role sees it, regardless of their individual GitHub or GitLab access.
GitLab pages use *merge request* where this guide uses *pull request*.
Their icons and colors are GitLab's own.

Pull requests and issues open on GitHub or GitLab, where you act on them.
Hephaestus does not change work there from Activity.
Activity only lets you start a practice review of your own work, with [Review this now](#review-this-now).

## Needs you

**Needs you** lists open pull requests that wait for you, grouped by their needs:

| Group | What is in it |
| --- | --- |
| **Review requested** | Pull requests that ask for your review and that nobody has settled yet |
| **Returned to you** | Your pull requests with requested changes or failed checks |
| **Approved** | Your pull requests that reviewers approved |

Each pull request shows its reviewers.
A mark on each face shows the review state: approved, changes requested, commented, or still requested.
When no work waits for you, the section says **Nothing needs you**.

Below, **Waiting on others** starts collapsed.
It holds pull requests where someone else must act next:

- **Waiting for review**: your pull requests that reviewers have not reviewed yet.
- **Drafts**: your draft pull requests.
- **Covered by other reviewers**: requests for your review that another reviewer's decision settles for now.
- **Requested from your team**: requests for review from one of your teams, but not you.
- **Reviewed by you**: merge requests that still list you after you approved them or requested changes.

A request counts as **Covered by other reviewers** if another reviewer requested changes, so the author must act first.
It is also covered if another reviewer approved it and GitHub or GitLab counts the pull request as approved.
Your own review never covers your request.
If the author asks you again, it stays under **Review requested** until another reviewer settles it.

On GitHub, and GitLab before 16.11, your earlier approval still counts toward the pull request's decision.
On GitLab 16.11 and later, a new request for your review removes that approval.
Without a decision, only a request for changes covers a pull request.
GitHub gives no decision where a branch needs no review.
GitLab gives none until Hephaestus reads the merge request's approvals.
The request returns to **Review requested** when the covering approval or request for changes no longer stands.

**Requested from your team** names the team, such as a request through the payments team.
Someone on the team handles it, so it never counts as your request.
A request that also asks you appears under **Review requested**.
The group excludes work you opened, drafts, and work you already approved or requested changes on.
A review with comments only keeps it listed.
Only GitHub has team reviewers, so GitLab workspaces never show this group.

GitLab keeps reviewers listed after their decision, which causes **Reviewed by you**.
A review with comments only leaves the request under **Review requested**.
A new request from the author moves it back to **Review requested** automatically.
On GitLab before 18.6, this may wait until Hephaestus next reads the merge request.

1. Open **Waiting on others** to see these requests.

It closes again when you leave the page.
**Assigned issues** lists open issues assigned to you.
Each list includes only the most recently updated work.
When more work exists, a line below the list states how many it shows.

Requests for changes on merge requests require GitLab Premium.
Without it, GitLab work never shows changes requested, and change requests do not count.

### Review this now

In a workspace with practice reviews, your open pull requests and assigned issues have **Review this now**, in any group.
It requests an immediate review against the workspace's practices.
A pull request that only asks for your review has no button, because it is someone else's work.
While Hephaestus receives the request, the button reads **Asking…**.
A message then states that the review started or explains why it did not.

After the review records a result about your work, it appears under [Reviews of your work](./practice-profile.mdx#reviews-of-your-work).
[Ask for a review](./ai-code-review#ask-for-a-review) explains who may ask and how often.

## Your work over a time range

1. Choose the last 7 days, 30 days, 90 days, or 12 months.
2. Open a tile to see its work in detail.

The page shows one tile for each kind of work:

| Tile | Its number | Also shown |
| --- | --- | --- |
| **Pull requests** | Your merged pull requests | Pull requests you opened, and yours closed without a merge |
| **Reviews** | Your reviews of other people's pull requests | Approvals, requests for changes, and reviews with comments only |
| **Comments** | Your comments | Comments in pull request or issue conversations, and comments on code |
| **Issues** | Issues you opened | Your closed issues |

Below the number, each tile compares it with the previous period of the same length.
For example, *4 more than the previous 30 days*.
Bars then show the number over the range, from the first day to today, in your time zone.
Each bar represents a day for 7 or 30 days, a week for 90 days, or a month for 12 months.

Every day has a faint track, so a day without work reads as zero.
The busiest bar shows its number.
Each tile's bars use a separate scale, so comparisons apply only to that tile's past, not to adjacent tiles.
The first and last week or month can cover only part of that period.
A tile with no work in the range does not open.

Hover over a bar to see the days it covers.

The detail shows the total, average per day, week, or month, busiest period, and comparison with the previous period.
It then shows a row of bars for each kind of work.
For reviews, these are approved, changes requested, and commented.
Rows share one scale, so their heights are comparable.
The number above each row is the maximum value on its scale.
**Show as table** lists the same numbers for each day, week, or month.

When you change the range, the previous figures stay visible without their colors until the new figures arrive.
If this takes more than a moment, **Updating…** appears beside the range.

These criteria determine who receives a count:

- **A merge counts for the pull request's author**, regardless of who selected the button. Closure without a merge also counts for the author. Unknown authors receive no count.
- **A closed issue counts for the issue's author**, regardless of who closed it.
- **A review of your own pull request does not count.** A review concerns another person's work. Your comments on your own pull request do count as comments.
- **Bots do not count.**

A count states how much happened, not how good the work was.
Planning, pairing, and help in chat do not appear here.

## Timeline

**Timeline** lists your work in the range, newest first and grouped by day.
Each pull request or issue has one row.
The row shows its events, such as *Merged*, *Approved*, *Commented*, or your number of comments.
Forty comments on one pull request produce one row with *40*, not forty rows.
**Show more** loads older work.

Timeline counts and tile counts follow the same criteria, so the rows for a range add up to its tiles.
If GitHub or GitLab removes a pull request or issue, its row stays without a link.
This keeps the counts accurate.

### Copy as Markdown

**Copy as Markdown** copies the whole timeline for the range, not only visible rows.
It includes a heading with the range and one line per pull request or issue, with its link and events.
A rich editor pastes a formatted list.
A plain text field pastes Markdown.

1. Select **Copy as Markdown**.
2. Paste the result into a standup note, a 1:1 document, or a work record.

## Workspace activity

Workspace activity shows the same tiles and timeline for everyone.
**Team** filters to one team.
**Everyone** shows the whole workspace.
A team includes its sub-teams and counts activity in repositories included by its settings.
If a team filters reviews by label, it counts only reviews of pull requests with one of those labels.
Workspace totals count only current members.

The page includes:

- **The tiles** count workspace or team work in the range.
- **Members** lists members by name, with each person's pull requests, reviews, comments, and issues. Search finds a member by name or username. The table first shows 50 members. **Show all** shows the rest. Name order is fixed, without sorting by count: Activity never ranks people.
- **Timeline** lists the work and who did it, with a Markdown copy control.

1. Open a member to see what needs them, their tiles, and their timeline.

The member view includes a GitHub or GitLab profile link.
With a team selected, counts apply to that team and match the member's table row.

A workspace admin can hide a member or team from workspace activity.
Hidden members are excluded from the counts and lists on Workspace activity.
Hidden teams do not appear in **Team** and do not count toward their parent team.
This changes only Workspace activity.
The member's own Activity page stays unchanged.
Requests to a hidden team still appear under **Requested from your team** for its members.
