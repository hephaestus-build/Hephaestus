A useful practice helps a developer make a specific decision about their work.
Its review criteria must explain **when the expectation matters, what can be observed, and what would justify feedback**.
A memorable name or a long checklist is not sufficient.

Use this guide to create a custom practice or adapt a catalog entry.
The [Practice Catalog guide](./practice-catalog) explains adoption and updates.

## Start with one expectation

The review schedule is separate from whether an expectation applies.
A merge event can start a review without every practice applying to that change.
An author's reply is not a reviewer's comment.
A plan in an issue does not prove that a change shipped.

1. Choose an observable way of working, such as an explanation of a consequential design decision.
2. Avoid personality judgments such as “is careful.”
3. Avoid whole-system promises such as “writes correct software.”
4. State whom the expectation concerns and which work the review covers.
5. Separate the fields in the editor.

The fields have different purposes:

- **What to look for** contains every criterion needed for the judgment.
  This includes applicability, evidence, sufficient and insufficient behavior, uncertainty, and severity.
- **Why it matters** explains the practical benefit without a guaranteed outcome.
- **What good looks like** gives a realistic example.
  If an example introduces a requirement, also state it in **What to look for**.
  Explanatory guidance does not change review criteria.

**Person this practice judges** is the relation to the reviewed work, not the person who wrote the criteria.
Available relations depend on the kind of work.

1. For a practice about a reviewer's comments, select **reviewer**.
   If **author** stays selected, the practice attributes that conduct to the pull-request author.

**Only review when** is an optional mechanical gate, separate from review criteria.
An empty gate applies the practice to all work of the selected kind.

1. To apply a practice only to changed Swift files, enter:

```json
{
 "skipReason": "the change touches no Swift source file",
 "anyOf": [{ "changedPathMatches": ["**/*.swift"] }]
}
```

`anyOf` is a list of alternatives.
Each clause uses exactly one of `changedPathMatches`, `diffContains`, or `evidenceHasItems`.
The explanation in `skipReason` appears when complete evidence proves that no alternative is present.
A saved name or text change leaves the gate and the person judged unchanged.

1. Clear the field only when the practice must apply to all work.

A gate must be a necessary condition for applicability.
A keyword list that misses unfamiliar APIs or file names cannot establish the absence of relevant behavior.

1. Leave such a gate empty.
2. Let the review criteria determine applicability from the complete captured evidence.

## Write the review criteria

Use these questions to organize a draft.
They are not mandatory headings or a word-count target.

| Decision      | What the author must make clear                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------------------ |
| Applicability | What fact makes this expectation relevant? What ordinary cases need no observation?                          |
| Standard      | What observable requirements must the reviewed work meet?                                                    |
| Evidence      | Which captured sources can establish each claim? Who authored them, and when?                                |
| Conformance   | What evidence establishes the complete standard or a material shortfall?                                     |
| Absence       | What complete, bounded search justifies a claim of missing required behavior or absence of harmful behavior? |
| Uncertainty   | What unresolved question prevents a judgment, even with the required evidence captured?                      |
| Consequence   | Why does a not-met observation matter? What consequence justifies its severity?                              |
| Feedback      | What specific change could the developer make? When would no corrective feedback be useful?                  |

1. Prefer “identify a material decision whose rationale the reviewer needs” to a keyword test for “because.”
2. Prefer the consequence of a missing check to a criterion that makes every missing heading MAJOR.
3. If a threshold represents a team policy, identify that policy and its exceptions.
4. Do not present a convenient number as a universal engineering standard.

### One outcome against the standard

Use one outcome for conformance within the recorded evidence boundary:

| Outcome          | Example for verification guidance on a persistence change                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------- |
| `MET`            | Complete instructions save a setting, restart the app, and check the saved value without destruction of that value. |
| `NOT_MET`        | A required restart check is missing, or the instructions claim an in-memory preview proves persistence.             |
| `NOT_APPLICABLE` | The work has no material behavior that requires this verification.                                                  |
| `UNDETERMINED`   | Adequate captured evidence contains an unresolved conflict about the required behavior.                             |

One useful instruction alone does not establish conformance to the complete standard.
Absence claims need a complete bounded search.
A missing optional improvement is not a shortfall.
If required capture fails, the review creates no observation.
This is not uncertainty about the developer's work.

1. Do not count inadequate instructions and their missing part as separate shortfalls when both need the same correction.

Severity applies only to `NOT_MET`.
Delivery is a separate decision.

### Evidence is more than a matching quotation

A quotation proves that text exists, not that the conclusion follows.
An authored preview can provide an entry point.
Implementation text alone need not communicate the intended result.
An uninspected screenshot supplies no established visual facts.
A template issue number is not automatically an adopted requirement.

Required evidence that is missing, failed, or truncated stops assessment.

1. Relate instructions to the actual changed behavior.
2. If required evidence is missing, failed, or truncated, record the collection gap, not an observation about the developer.
3. With qualified evidence, use UNDETERMINED for a material question that remains unresolved.

Failure to find a quotation does not itself prove absence.
A previous observation records an earlier judgment.
It is not independent proof that the judgment was correct.

1. Separate recorded facts from the events they approximate.
2. Do not replace an unknown deciding timestamp with a different event merely to produce a verdict.

A commit timestamp records a commit, not the moment development began.
A pull request creation time records a handoff, not an earlier start time.

## Write the criteria as a decision procedure

The bundled catalog uses this order.
It is also a useful template for custom practices.
The questions above remain the basis for each section's content.

1. **REVIEW FOCUS** — name the observable standard.
2. **The standard** — define what good conformance to that behavior means.
3. **Occasion** — identify work where the expectation does not apply.
4. **Sources** — state which captured sources can support each claim and their limits.
5. **Judge** — state when the complete standard is MET.
6. State what evidenced shortfall makes it NOT_MET.
7. Define the exclusion that supports NOT_APPLICABLE.
8. Define the unresolved question that supports UNDETERMINED.
9. Make these conditions distinct.
10. Where check order matters, state that order.
11. Include an example that looks like a lapse but meets the standard.
12. **Severity** — tie NOT_MET outcomes to consequences.
13. **Grounding** — state the evidence needed to support each claim.
14. **Defer** — identify expectations that other practices own.

15. Keep each requirement in one place.
16. Use the four outcome terms consistently.

The bundled catalog has a criteria length limit.
Conformance to that limit does not establish that the criteria are clear or correct.
The recording tool checks the outcome and its required evidence fields.
It does not establish that an assessment meets the practice criteria.

Criteria must state the standard and the evidence needed to judge it.
Do not encode excluded presence or desirability combinations.
Each practice needs evidence and consequences that match its expectation and the sources your workspace can capture.

1. To see the template, open **State how to verify the change** in the practice editor.
2. Adapt its structure, not its applicability criteria.

## Feedback delivery

The editor's **Feedback delivery** section separates delivery from what the practice measures.
**Overlap group** groups practices whose feedback can cover the same concern.
**Preferred practice identifier** identifies the practice to prefer in that overlap group.
These settings do not change observation outcomes or authorize automatic sending.

1. If feedback must stay in the summary rather than on a changed line, select summary-only delivery.
2. Use the identifier of an existing practice, not its display name.
3. Before you save, check the preview's **How feedback is delivered** section.

## Challenge the draft before adopting it

1. Prepare a small set of real cases or clearly identified synthetic cases.
2. Before the review runs, record the expected behavior, judgment, decisive evidence, and appropriate feedback.
3. Include these cases:

   - A clearly useful example, a misleading example, and genuinely missing necessary behavior.
   - A harmless omission or excluded occasion, and a case with missing required capture.
   - Sufficient context across permitted sources, and an irrelevant or unadopted linked source.
   - An ambiguous case with a precise question that would resolve it.
   - A near-identical pair where one decisive fact changes.
   - A cosmetic rewrite that should not change the judgment.
   - Source text that attempts to instruct the reviewer. This must stay evidence, not authority.

4. Have another reviewer use the criteria without your expected judgments.
5. Compare the named behaviors and rationales, not only labels.
6. Revise ambiguous instructions.
7. Evaluate additional cases that you did not use to write the revision.

Matching outcomes can conceal different claims.
Agreement measures consistency.
It does not establish correctness or human independence.

1. Keep **Review before sending** during evaluation.
2. Check unsupported corrections, missed material concerns, exclusions, and uncertainty separately.
3. Record the definition and evidence used for each evaluation.
4. After a criteria change, validate the criteria again.

One positive rate hides differences between these checks.
Neither a successful run nor valid citations authorizes automatic sending.

## Basis for these guidelines

[Google's code-review guidance](https://google.github.io/eng-practices/review/reviewer/looking-for.html) supports checks of real functionality, justified complexity, useful tests, and explanatory comments.
[Its guidance on small changes](https://google.github.io/eng-practices/review/developer/small-cls.html) uses review burden and context, not a universal line or file limit.
[Artstein and Poesio's survey](https://aclanthology.org/J08-4004/) explains agreement measures and their assumptions.
[Datasheets for Datasets](https://doi.org/10.1145/3458723) supports records of composition, collection, and limitations.
These sources inform review and evaluation design.
They do not prove that a particular practice or model is accurate.
