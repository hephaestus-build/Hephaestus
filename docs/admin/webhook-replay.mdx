Replay a provider event after you fix the cause that made it a dead letter.
An event becomes a dead letter when its parser fails, or when an unknown failure repeats 10 times.
A temporary failure, such as a provider that is down, retries without a limit and does not become a dead letter.
A dead letter keeps its payload in the provider event inbox for 30 days ([How long the inbox keeps an event](./webhook-ingestion-operations#how-long-the-inbox-keeps-an-event)).

No web app screen lists dead letters. Use the API.

## Before you start

- For a workspace's events, you need the workspace admin role.
- For a GitHub App installation event that has no workspace, you need the instance admin role and a recent sign-in.
- You need the access token of that account, as [Call the API](./instance-admin#call-the-api) describes.
- Find the cause in the server log. Read `error.root_type` and the sanitized stack frames of the event's first attempt.

## List the dead letters

1. Fix the parser, or restore the connection that the handler needs.
2. List the dead letters of the workspace:

   ```bash
   curl --header "Authorization: Bearer <access token>" \
     "https://<host>/api/workspaces/<workspace slug>/integrations/dead-letters"
   ```

   Replace `<access token>` with the access token, `<host>` with the instance host name, and `<workspace slug>` with the slug of the workspace.
   For installation events, use the path `/api/admin/integration/dead-letters`.

3. Find the record of the event in `content`.
   Each record has its `id`, `provider`, `errorClass`, `receivedAt`, `failedAt`, `replayedAt` and `replayedBy`.
4. If the response has a `nextCursor`, add `?cursor=<nextCursor>` to the path to read the next page.

A page holds up to 100 records in ID order.
The API does not return payloads or headers.

## Replay a record

1. Replay the record:

   ```bash
   curl --request POST --header "Authorization: Bearer <access token>" \
     "https://<host>/api/workspaces/<workspace slug>/integrations/dead-letters/<id>/replays"
   ```

   Replace `<id>` with the `id` of the record.
   For an installation event, use the path `/api/admin/integration/dead-letters/<id>/replays`.

2. Check that the response has a `replayedAt` time.

The event goes back to the inbox as a first attempt, at the head of its resource's order.
A replay does not rewind the later events of that resource.
The authentication audit trail records each installation replay.

## Check that it worked

1. List the dead letters again.
2. Check that the replayed record is not in the list.

An event that fails again comes back with its `replayedAt` time.

## Troubleshooting

| Answer | Cause |
| --- | --- |
| `404` | The record is not a dead letter of that workspace. You replayed it already, or it belongs to another workspace. |
| `503` on an installation replay | The server could not write the audit record. It queued nothing. Try again. |
