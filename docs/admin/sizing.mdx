This page owns the resource budget of the self-hosted Compose stack.
The [Install guide](./install#requirements) gives the host requirements.

## Measured conversation baseline

The web conversation target is first answer text within 10 seconds for at least 95% of turns.
Time starts when the client sends the question and includes queue, startup, provider and tool time.
A stream snapshot or heartbeat is not answer text.

The table gives a controlled Kubernetes measurement on release 0.95.0, with 4 vCPUs and 15.61 GiB of memory.
Each case had 40 synthetic users, three turns each and 30 seconds between turns.
The users arrived over one second.
All 120 turns completed in each case, with no missing first-text samples.

The deterministic provider used assumed timings: first token at 3 seconds, 500 declared output tokens and 13 seconds per call.
Each turn made one call, with no tools, reviews or provider throttles.
These conditions do not represent the full course workload.

| Turn admission | First text p50 / p95 | Turn duration p50 / p95 | First text within 10 s | Cohort drain, turns/h |
| -------------- | -------------------- | ----------------------- | ---------------------- | --------------------- |
| 8              | 25.78 / 55.97 s      | 35.56 / 65.76 s         | 8/120 (6.67%)          | 2,164                 |
| 16             | 3.46 / 31.27 s       | 13.24 / 41.05 s         | 96/120 (80.00%)        | 3,332                 |
| 32             | 3.57 / 17.88 s       | 13.37 / 27.66 s         | 112/120 (93.33%)       | 3,721                 |

Each case misses the 95% target, which requires at least 114 of 120 turns within 10 seconds.
The drain rate divides completed turns by the whole case duration.
It is not a sustained arrival rate or a review-throughput measurement.
Admission 32 is a tested point, not a qualified default.
The [CSV results](/data/capacity-s3-0950.csv) include the measured commit, cohort and provider assumptions.
The [capacity procedure](/contributor/capacity-benchmark) describes the fixture and required evidence.

The following effects still need measurement with the same workload:

| Condition                   | Required comparison                                                                                               | Current result |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------- |
| PostgreSQL and NATS backups | Throughput, first text, completion latency and resource pressure during a backup versus an idle control           | Unmeasured     |
| Cold starts and image pulls | Startup delay, first text and memory peak with an empty image cache versus a warm cache                           | Unmeasured     |
| Server deployments          | Failed or slow authenticated reads, user-visible outage and error-budget use during Recreate                      | Unmeasured     |
| Provider throttles          | First text, call-grant waits and review throughput with deterministic 429 responses versus an unthrottled control | Unmeasured     |

### Deployment availability budget

The app target is 99.5% of eligible authenticated reads succeeding within 2 seconds.
Deployments consume this error budget.
For a window with `N` eligible reads, the budget permits at most `floor(N / 200)` failed or slow reads.
Measure deployment failures with an authenticated probe outside the server Pod that is replaced.
Pod readiness alone does not measure the outage that a user sees.

At a constant probe rate of one request per second, a 30-day window permits 12,960 bad probe results, equivalent to 216 minutes.
This time conversion applies to that probe schedule.
The app's request-based budget uses its actual eligible request count.
No deploy-outage measurement or error-budget qualification is available from the conversation cases above.

## Initial budget

**4 vCPUs, 24 GB RAM, 40 GB SSD** is a conservative initial budget for one concurrent review sandbox.
It is not a measured requirement.
It covers these memory limits, which are ceilings, not reservations:

| Container                      | Memory limit | Setting                                                                                     |
| ------------------------------ | ------------ | ------------------------------------------------------------------------------------------- |
| `application-server`           | 5 GiB        | `APPLICATION_SERVER_MEM_LIMIT`                                                              |
| `application-worker`           | 3 GiB        | `APPLICATION_WORKER_MEM_LIMIT`                                                              |
| `webhook-server`               | 2 GiB        | `WEBHOOK_SERVER_MEM_LIMIT`                                                                  |
| `postgres`                     | 4 GiB        | `POSTGRES_MEM_LIMIT`                                                                        |
| each concurrent review sandbox | 3 GiB        | `SANDBOX_MEMORY_BYTES`, `SANDBOX_MAX_CONCURRENT` (1 in the self-hosted Compose file)        |
| the conversation host, one per worker  | 2 GiB        | Fixed. [Runtime roles](./runtime-roles.mdx#the-conversation-host) gives the limits of the conversation host |

With the defaults of the self-hosted Compose file, these limits add up to 19 GiB, about 20.4 GB.
During an upgrade, the one-shot `database-migration` container runs beside the previous roles for a few minutes.
Keep 1 GiB free for it (`DATABASE_MIGRATION_MEM_LIMIT`).
NATS, Traefik, and the webapp have no limit.
The rest of the 24 GB is for them and the operating system.

A limit caps a container but reserves nothing.
Each JVM sizes its heap from its own limit and can grow toward it.
The host must hold simultaneous use by all containers and sandboxes, plus the operating system and spare capacity.
If demand exceeds memory, the host swaps where swap is configured.
The kernel can kill a container or sandbox.

To use a smaller memory budget, lower the limits in `.env` before the first start.

A worker runs no more review sandboxes at once than `SANDBOX_MAX_CONCURRENT` and its review capacity allow.
A review whose sandbox has ended writes its feedback without a sandbox, so it does not count against these limits.
The application default of `SANDBOX_MAX_CONCURRENT` is 5.
The self-hosted Compose file sets 1.
The review capacity (`HEPHAESTUS_WORKER_REVIEW_MAX`) defaults to `auto`: the number of CPUs minus 1.

Each worker also runs [turn sandboxes](./runtime-roles.mdx#turn-sandboxes) for Hephaestus, beside the review sandboxes and the conversation host.
Their limits are fixed and do not count against `SANDBOX_MAX_CONCURRENT`.

## PostgreSQL memory

The bundled image calculates starting settings from its container limit.
The chart's `postgresql.parameters` adds explicit `-c` arguments after that calculation.
The small profile uses these shared-node values:

| Setting | Value |
| --- | --- |
| `shared_buffers` | `256MB` |
| `work_mem` | `2MB` |
| `hash_mem_multiplier` | `1.0` |
| `max_connections` | `80` |
| `maintenance_work_mem` | `64MB` |
| `autovacuum_work_mem` | `32MB` |
| `autovacuum_max_workers` | `3` |
| `effective_cache_size` | `1GB` |
| `max_parallel_workers_per_gather` | `0` |
| `max_wal_size` | `1GB` |

`work_mem` applies to each sort or hash operation and can multiply across concurrent queries.
`effective_cache_size` is a planner estimate. It allocates no memory.
These settings retain autovacuum, statement statistics, fsync, and WAL durability.
See [PostgreSQL resource consumption](https://www.postgresql.org/docs/18/runtime-config-resource.html).

The small profile requests the PostgreSQL process's full 2 GiB memory limit.
Its resident pgBackRest sidecar also requests its full 512 MiB memory limit.
CPU can still burst. These Pods retain Burstable QoS.

A lower 1536 MiB limit is a qualification target, not an enabled setting.
Count the pgBackRest server sidecar separately, and count a backup or stanza Job in addition.
Do not add individual-container p95 values to claim a synchronized node peak.

Before lowering the process limit, run the reference load with the representative database, vacuum work, WAL archiving, and the permitted worker surge.
Read `pg_settings` to verify the effective values and their command-line source.
Require process charge within 1536 MiB, no OOM, no Hikari timeouts, and connection-acquire p95 below 50 ms.
For the initial trial, require WAL archive lag below 60 seconds during steady load and below five minutes during recovery.

Require autovacuum to reduce dead tuples after the peak, and investigate idle transactions older than one minute.
Record vacuum duration and archive catch-up with the workload. A successful startup does not prove these gates.
Keep the larger limit and lower concurrency if the trial fails.

## Review sandbox limits

Each review sandbox has a limit of 3 GiB of memory (`SANDBOX_MEMORY_BYTES`), 1 CPU (`SANDBOX_CPUS`), and 256 processes (`SANDBOX_PIDS_LIMIT`).
On Kubernetes, the worker sizes each sandbox Pod by its kind and ignores `SANDBOX_MEMORY_BYTES` ([Kubernetes § Sandbox sizes](./kubernetes#sandbox-sizes)).
The CPU limit is a share of CPU time that the sandbox can use, not a reserved core.
The memory limit holds the sandbox's temporary file systems, which can grow to 2.06 GiB, and its processes.
Hephaestus refuses to start if `SANDBOX_MEMORY_BYTES` leaves less than 512 MiB beside those file systems.

These limits come from one measurement on release 0.82.0.
Later releases are not re-measured.
On that release, a review of a small course repository reached a cgroup `memory.peak` of 194 MiB.
It used at most 19 processes and 0.2 CPU, in samples taken once per second.
The workspace initializer used less than 1 MiB of its own memory for a 437 MB workspace.
The rest of its memory was file cache, which the kernel reclaims under the limit.

A larger repository or a review that runs heavy commands can need more memory.
If the kernel stops a review sandbox at its memory limit, the review fails with exit code 137.
Then increase `SANDBOX_MEMORY_BYTES`.

## CPU and processes

The application server and worker each default to 4 CPUs / 512 PIDs.
The webhook server defaults to 2 CPUs / 256 PIDs. Override them with the corresponding `APPLICATION_SERVER_*`,
`APPLICATION_WORKER_*` or `WEBHOOK_SERVER_*` limit variables. Keep the worker's PID limit: it is the
role with Docker access.

## What you can scale

The self-hosted stack runs one container for each runtime role: one server, one worker, and one webhook server.
You scale the work of the worker, not the number of containers:

- **Practice reviews.** `SANDBOX_MAX_CONCURRENT` sets how many review sandboxes the worker runs at once.
  On Docker, each concurrent review sandbox may use up to `SANDBOX_MEMORY_BYTES` (default 3 GiB).
  The self-hosted Compose file allows 1 concurrent sandbox.
  Raise `SANDBOX_MAX_CONCURRENT` only with sufficient RAM.
  [Worker pod env vars](./runtime-roles#worker-pod-env-vars) explains how it caps the review capacity of the worker.
- **conversation turns.** `HEPHAESTUS_WORKER_MENTOR_MAX` sets how many conversation turns the worker runs at once.
  In the Helm chart, set `worker.conversationTurns`.
  The model provider usually sets the real limit.
  [Conversation turn capacity](./runtime-roles#conversation-turn-capacity) explains how to size it.

These are deployment limits, not a claim that all workloads fit. Before raising webhook volume,
Conversation turn capacity (`HEPHAESTUS_WORKER_MENTOR_MAX`), or `SANDBOX_MAX_CONCURRENT`, reproduce the release's
[Compose capacity qualification](https://github.com/hephaestus-build/Hephaestus/tree/main/load-tests) on
your host shape. A release baseline is valid only with the raw k6 and container-resource evidence described there.
Without that evidence, keep the conservative defaults above.

## Database connections

Each chart role has a typed `databasePool.maximumPoolSize` and `databasePool.minimumIdle`.
They set native Spring datasource properties for that role and override its profile defaults.
The small profile uses:

| Client | Maximum / minimum idle |
| --- | --- |
| Server | 16 / 2 |
| Each worker | 24 / 2 |
| Migration Job | 2 / 1 |
| Webhook receiver | 0 / 0: no DataSource |
| Sandboxes | 0 / 0: use their gateway |

Preparing code evidence can hold two connections.
Bound capture concurrency separately. A larger pool does not authorize more simultaneous captures.
The server's four scheduled workspace syncs can hold eight connections, leaving eight for foreground and control work.
Do not hold a database transaction while waiting for a model grant or provider response.

With one replacement worker beside one old worker, pooled sessions use `16 + 24 + 24 = 64` connections.
During that worker surge, budget three dedicated listeners outside Hikari, four migration/backup sessions, four operator/monitor sessions, and three superuser-reserved slots.
The total is 78 of 80.
The server retains `Recreate`. Do not double the whole release or overlap another worker rollout.

The chart rejects a bundled database configuration whose explicit `max_connections` cannot hold its role pools, worker surge, listeners, and maintenance reserves.
Inventory dedicated listeners after runtime changes and recompute this budget if more exist.

The independent mentor loop and tool Pods must use the gateway without a database pool.

The chart defaults outside the small profile keep server/worker pools of 20/32 with minimum idle five.
For more replicas, change the role pools and PostgreSQL budget together.
Measure pool waits at the actual workload. A rendered connection count does not prove query latency or memory use.

## Memory headroom

When the JVM starts, the buildpack's memory calculator sets the Java memory from the container's memory limit.
`BPL_JVM_HEAD_ROOM` is an optional percentage of that limit.
The calculator keeps this percentage out of the Java memory that it calculates.
The heap must also leave room for the worker's file cache and for other memory that the container uses outside the JVM.

The default headroom is 0 %.
Thus, if you increase the container memory limit, the heap can also increase at the next start.
Select the headroom for the actual workload of your worker.

The split Compose stack passes `BPL_JVM_HEAD_ROOM` to the worker only.
If you do not set it, the buildpack's default behavior applies.
The value applies only when the JVM starts.
To apply a change, drain and restart the worker, as [Graceful drain](./runtime-roles#graceful-drain) describes.
For the calculation, see the [Paketo memory calculator](https://paketo.io/docs/reference/java-reference/#memory-calculator).

## Disk

Docker's data directory holds the images, the containers and the volumes.
On a host with [pull-based deployment](./pull-based-deployment.mdx#images-and-free-space), plan for these parts:

| Part | Size | What bounds it |
| --- | --- | --- |
| The images of one release | About 1 GB to download for `linux/amd64`. The application server is about half of it | The reconciler keeps the running and the previous release. During an apply, it pulls a third set |
| PostgreSQL data (`app_postgresql-data`) | Grows with your workspaces and their history | Your data. Back it up as [Backup and restore](./backup-restore.mdx) describes |
| Git repositories (`app_git-repos`, `app_worker-git-repos`) | Grows with the repositories that reviews read | Not bounded yet |
| NATS JetStream (`core_nats-data`) | Grows with buffered provider events | Not bounded yet |
| A restore rehearsal | A full copy of the database volume | Remove the clone's containers and volumes when the rehearsal ends |
| Free space before a pull | 10 GiB, set by `HEPHAESTUS_MIN_FREE_GIB` | The reconciler refuses an apply below it |

On a small disk, lower `HEPHAESTUS_MIN_FREE_GIB`.
`docker system df -v` shows what each image, container and volume uses on disk.
