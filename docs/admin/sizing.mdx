The [Helm chart reference](./helm-chart#profiles) owns the deployment profiles and their resource budgets.
Use measured requests to plan capacity, and keep room for the operating system, the cluster and a rolling update.
A resource limit is a ceiling, not evidence that every workload fits.

## Measured conversation baseline

The web conversation target is first answer text within 10 seconds for at least 95% of turns.
Time starts when the client sends the question and includes queue, startup, provider and tool time.
A stream snapshot or heartbeat is not answer text.

The table gives a controlled Kubernetes measurement on release 0.95.0, with 4 vCPUs and 15.61 GiB of memory.
Each case had 40 synthetic users, three turns each and 30 seconds between turns.
The users arrived over one second.
All 120 turns completed in each case, with no missing first-text samples.

The deterministic provider used assumed timings: first token at 3 seconds, 500 declared output tokens and 13 seconds per call.
Each turn made one call, with no tools, reviews or provider throttles.
These conditions do not represent the full course workload.

| Turn admission | First text p50 / p95 | Turn duration p50 / p95 | First text within 10 s | Cohort drain, turns/h |
| -------------- | -------------------- | ----------------------- | ---------------------- | --------------------- |
| 8              | 25.78 / 55.97 s      | 35.56 / 65.76 s         | 8/120 (6.67%)          | 2,164                 |
| 16             | 3.46 / 31.27 s       | 13.24 / 41.05 s         | 96/120 (80.00%)        | 3,332                 |
| 32             | 3.57 / 17.88 s       | 13.37 / 27.66 s         | 112/120 (93.33%)       | 3,721                 |

Each case misses the 95% target, which requires at least 114 of 120 turns within 10 seconds.
The drain rate divides completed turns by the whole case duration.
It is not a sustained arrival rate or a review-throughput measurement.
Admission 32 is a tested point, not a qualified default.
The [CSV results](/data/capacity-s3-0950.csv) include the measured commit, cohort and provider assumptions.
The [capacity procedure](/contributor/capacity-benchmark) describes the fixture and required evidence.

The following effects still need measurement with the same workload:

| Condition                   | Required comparison                                                                                               | Current result |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------- |
| PostgreSQL and NATS backups | Throughput, first text, completion latency and resource pressure during a backup versus an idle control           | Unmeasured     |
| Cold starts and image pulls | Startup delay, first text and memory peak with an empty image cache versus a warm cache                           | Unmeasured     |
| Server deployments          | Failed or slow authenticated reads, user-visible outage and error-budget use during server updates                      | Unmeasured     |
| Provider throttles          | First text, call-grant waits and review throughput with deterministic 429 responses versus an unthrottled control | Unmeasured     |

### Deployment availability budget

The app target is 99.5% of eligible authenticated reads succeeding within 2 seconds.
Deployments consume this error budget.
For a window with `N` eligible reads, the budget permits at most `floor(N / 200)` failed or slow reads.
Measure deployment failures with an authenticated probe outside the server Pod that is replaced.
Pod readiness alone does not measure the outage that a user sees.

At a constant probe rate of one request per second, a 30-day window permits 12,960 bad probe results, equivalent to 216 minutes.
This time conversion applies to that probe schedule.
The app's request-based budget uses its actual eligible request count.
No deploy-outage measurement or error-budget qualification is available from the conversation cases above.

## PostgreSQL memory

The bundled image calculates starting settings from its container limit.
The chart's `postgresql.parameters` adds explicit `-c` arguments after that calculation.
The small profile uses these shared-node values:

| Setting | Value |
| --- | --- |
| `shared_buffers` | `256MB` |
| `work_mem` | `2MB` |
| `hash_mem_multiplier` | `1.0` |
| `max_connections` | `120`, derived from the client budget |
| `maintenance_work_mem` | `64MB` |
| `autovacuum_work_mem` | `32MB` |
| `autovacuum_max_workers` | `3` |
| `effective_cache_size` | `1GB` |
| `max_parallel_workers_per_gather` | `0` |
| `max_wal_size` | `1GB` |

`work_mem` applies to each sort or hash operation and can multiply across concurrent queries.
`effective_cache_size` is a planner estimate. It allocates no memory.
These settings retain autovacuum, statement statistics, fsync, and WAL durability.
See [PostgreSQL resource consumption](https://www.postgresql.org/docs/18/runtime-config-resource.html).

The small profile requests the PostgreSQL process's full 2 GiB memory limit.
Its resident pgBackRest sidecar also requests its full 512 MiB memory limit.
CPU can still burst. These Pods retain Burstable QoS.

At 120 connection slots, a planning allowance of 5 MiB per backend totals 600 MiB.
Add 256 MiB of shared buffers, 96 MiB for three autovacuum workers, 64 MiB of maintenance memory, and 256 MiB for other memory and cache.
One 2 MiB work operation per slot brings that estimate to 1512 MiB. Two such operations per slot bring it to 1752 MiB.
Both estimates fit the unchanged 2 GiB request and limit.

These are planning estimates, not measured peaks or hard bounds.
`work_mem` applies per operation. Temporary buffers and cache can add memory.
The loaded qualification must check total container charge and OOM events at the permitted connection count.

A lower 1536 MiB limit is a qualification target, not an enabled setting.
Count the pgBackRest server sidecar separately, and count a backup or stanza Job in addition.
Do not add individual-container p95 values to claim a synchronized node peak.

### Measure stateful memory

The queries take each container's maximum over the window, then the maximum across its replacement containers.
They exclude Pod-level cgroups and infrastructure containers.
The working-set and charge maxima need not occur at the same time.
Working set excludes some reclaimable file cache. The container's limit also covers that cache.
Thus, working set alone does not justify a lower limit.

For example, query the working set with this PromQL expression:

```promql
max by (container) (max_over_time(container_memory_working_set_bytes{namespace="hephaestus",container=~"postgresql|nats"}[14d]))
```

Use `container_memory_usage_bytes` for total charge and `tfirst_over_time` to check the actual sample window in VictoriaMetrics.
A 14-day range selector does not prove that 14 days of samples exist.

Compare total charge with inactive file cache, memory pressure and OOM counters before attributing a peak to reclaimable cache.
Keep the existing ceilings until a controlled workload qualifies a lower limit.
The [stateful observations](/contributor/capacity-benchmark#stateful-resource-observations) record the available evidence and its limits.

Before lowering the process limit, run the reference load with the representative database, vacuum work, WAL archiving, and the permitted server surge.
Read `pg_settings` to verify the effective values and their command-line source.
Require process charge within 1536 MiB, no OOM, no Hikari timeouts, and connection-acquire p95 below 50 ms.
For the initial trial, require WAL archive lag below 60 seconds during steady load and below five minutes during recovery.

Require autovacuum to reduce dead tuples after the peak, and investigate idle transactions older than one minute.
Record vacuum duration and archive catch-up with the workload. A successful startup does not prove these gates.
Keep the larger limit and lower concurrency if the trial fails.

## Review sandbox limits

`sandbox.templates.review.resources` sets the memory, CPU and disk of a review sandbox ([Sandbox sizes](./sandboxes#sandbox-sizes)).
By default, it requests 100m and 512 MiB, and its limits are 2 CPUs and 2 GiB.
The Pod-kind table there owns the sizes of the other sandbox Pods.
The retired `SANDBOX_MEMORY_BYTES` and `SANDBOX_PIDS_LIMIT` settings do not configure Kubernetes.
The kubelet enforces the per-Pod process limit, which the server's isolation probe verifies.

## CPU and processes

CPU requests determine scheduling and CPU limits bound use.
Keep the node's process limit configured as the [Sandboxes](./sandboxes#server) requires.
A server that cannot prove isolation starts no sandbox work.

## What you can scale

The chart controls server replicas, review capacity and conversation capacity.
Each server replica also needs its JVM and database connections. The conversation loop has its own replicas and resources.
Before raising capacity, qualify the workload on the target host shape.
Keep the workload, logs and before/after measurements with the qualification result.

## Database connections

Each chart role has a typed `databasePool.maximumPoolSize` and `databasePool.minimumIdle`.
They set native Spring datasource properties for that role and override its profile defaults.
The small profile uses:

| Client | Maximum / minimum idle |
| --- | --- |
| Server | `auto`: 36 / 2 with the small profile |
| Migration Job | 2 / 1 |
| Sandboxes | 0 / 0: use their gateway |

Preparing code evidence can hold two connections.
Bound capture concurrency separately. A larger pool does not authorize more simultaneous captures.
The server's four scheduled workspace syncs can hold eight connections. The rest serve reviews, foreground and control work.
Do not hold a database transaction while waiting for a model grant or provider response.

The chart derives the server pool from the caps it gives the runtime:

```text
pool = inbox handlers + 2 × review captures + 2 × long-load preparations
     + permit maintenance threads + sync reserve + HTTP/control reserve
small = 8 + 2 × 5 + 2 × 2 + 2 + (4 × 2) + 4 = 36
```

`server.inboxClaimers` sets the inbox handler count. The review cap comes from the sandbox template requests and review memory budget.
Long loads have two preparation slots. The permit gate has two maintenance threads.

The last twelve connections reserve eight for four syncs and four for HTTP and control requests.
A model stream holds no pooled connection while it waits for the model.
A review or turn at its sandbox cap does not hold a pooled connection for its full run.

The same helper derives the PostgreSQL budget for one rolling update:

| Client or reserve | Small-profile peak |
| --- | --- |
| Servers at overlap | 2 |
| Server pools | 2 × 36 = 72 |
| Four dedicated LISTEN sessions per server | 2 × 4 = 8 |
| New revision's migration Job | 2 |
| PostgreSQL metrics exporter | 2, the monitor role's cluster-wide connection limit |
| Backup sessions | 2 |
| PostgreSQL probes and role/monitor setup | 3 |
| Ordinary client total | 89 |
| `superuser_reserved_connections` | 3 |
| Operator margin outside the reserved slots | 4 |
| Required slots, including reserves | 96 |
| Derived `max_connections` | 120 |
| Extra slots after all clients and reserves | 24 |

The owning helper is `hephaestus.databaseConnectionCapacity` in the chart. It reserves optional monitoring and backup clients even when they are off.
The chart rounds the derived limit up to twenty slots, with a floor of 120. An explicit limit must hold the complete budget.

The bundled database pins three superuser-reserved slots. An external database must also subtract its configured reserved slots.
See [PostgreSQL connection settings](https://www.postgresql.org/docs/18/runtime-config-connection.html#GUC-SUPERUSER-RESERVED-CONNECTIONS).

An explicit `server.databasePool.maximumPoolSize` must hold the derived holder count and reserve.
When all pooled connections are busy, Hikari waits up to the configured `connection-timeout`, 45000 ms, then throws an SQL exception.
This queue does not raise the connection limit. See [Hikari pool settings](https://github.com/brettwooldridge/HikariCP#frequently-used).

The load qualification must measure `hikaricp_connections_pending`, acquisition timeouts and acquisition latency with inbox, capture, conversation and HTTP work together.
That measurement qualifies the twelve-connection reserve. It does not replace the holder floor.

Inventory dedicated listeners after runtime changes and recompute this budget if more exist.

Agent sandboxes use the gateway and have no database connection pool.

The other profiles derive their server pool from the same holder model, with minimum idle five.
Recalculate the PostgreSQL budget if the server pool changes.
Measure pool waits at the actual workload. A rendered connection count does not prove query latency or memory use.

## Memory headroom

When the JVM starts, the buildpack's memory calculator sets the Java memory from the container's memory limit.
`BPL_JVM_HEAD_ROOM` is an optional percentage of that limit.
The calculator keeps this percentage out of the Java memory that it calculates.
The heap must also leave room for the server's file cache and for other memory that the container uses outside the JVM.

The default headroom is 0 %.
Thus, if you increase the container memory limit, the heap can also increase at the next start.
Measure the server's total memory use before changing its memory limit.

The Helm chart exposes no value for JVM headroom.
The release uses the buildpack's default behavior.
The value applies only when the JVM starts.
To apply a change, drain and restart the server, as [Graceful drain](./runtime-roles#graceful-drain) describes.
For the calculation, see the [Paketo memory calculator](https://paketo.io/docs/reference/java-reference/#memory-calculator).

## Disk

Budget the node's images, logs and sandbox scratch space separately from persistent database and Git-cache storage.
The chart bounds sandbox ephemeral-storage requests, limits and volumes.
The [Sandboxes](./sandboxes#sandbox-sizes) owns these bounds.
Back up persistent state as [Backup and restore](./backup-restore) describes.

## Conversation turn admission

[Sandbox capacity budget](./helm-chart#sandbox-capacity-budget) owns the budget values, formula and validation rules.
Automatic admission fits both steady-state and drained-upgrade requests.
A supplied budget also checks an explicit count.
The provider pool admits each physical model call separately.

The review request remains 512Mi, and the conversation request remains 384Mi, before RuntimeClass overhead.
These are current template values. No review or conversation workload peak has been measured.
Idle Pi SDK measurements do not qualify a workload request.
Qualification must sample each sandbox during reviews and conversation turns before proposing requests from p95 plus a margin.
