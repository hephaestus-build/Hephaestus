This page lists the work that the Helm chart runs at once, the resource budget of each part, and the evidence for each figure.
The [Kubernetes guide](./kubernetes#profiles) owns the chart profiles and the requests and limits of each role.
Each figure on this page comes from one of the sources in this table:

| Source | What it shows | What it does not show |
| --- | --- | --- |
| Chart derivation | The value that the chart renders from its values and its declaration files | That the work fits the node or meets a latency target |
| Chart test arithmetic | The requests and limits that a chart test adds up against a node | The memory and CPU that running work uses. It is not a load measurement |
| Load measurement | Use and latency under one stated workload, model, release and node | Any other workload, model, release or node |

## Reviews at once

`worker.sandbox.reviewMemory` sets the memory that the sandbox nodes give review Pods.
The chart derives the reviews at once from it. No value sets a review count.
The chart derives three counts:

| Count | Derivation |
| --- | --- |
| Reviews of the sandbox nodes | `reviewMemory` divided by the memory request of one review Pod, rounded down. That request is 384 MiB plus `worker.runtime.podOverhead.memoryMi` |
| Reviews of one worker, `SANDBOX_MAX_CONCURRENT` | The smaller of the reviews of the sandbox nodes and (worker memory limit − 1005 MiB) / 18 MiB, rounded down |
| Reviews of all workers, which the reviews quota holds | The smaller of the reviews of the sandbox nodes and `worker.replicas` times the reviews of one worker |

The 1005 MiB is the worker JVM at rest.
It has 501 MiB of code cache and metaspace, 128 MiB of direct memory, 120 MiB of thread stacks, and 256 MiB of heap.
Each review adds 8 threads and 10 MiB of heap.
The render stops if `reviewMemory` holds no review Pod, or if the worker memory limit is less than 1023 MiB.
A chart test checks these counts for `small.yaml` and for other values of `reviewMemory`.

| Profile | `reviewMemory` | Worker replicas | Worker memory limit | Reviews of one worker | Reviews of all workers |
| --- | --- | --- | --- | --- | --- |
| Chart default, with the worker on | 3840Mi | 2 | 2 GiB | 10 | 10 |
| `dev.yaml`, `preview.yaml` | — | No worker | — | — | — |
| `small.yaml` | 1920Mi | 1 | 2 GiB | 5 | 5 |
| `small-16gib.yaml`, on top of `small.yaml` | 1920Mi | 1 | 2 GiB | 5 | 5 |

The time that a review takes with a real model at these counts is [not yet measured](#not-yet-measured).

## Conversation turn admission

`worker.conversationTurns` sets the resident conversation turns of one worker, `HEPHAESTUS_WORKER_CAPACITY_MENTOR_MAX`.
The chart default is 8. `small.yaml` sets `auto`, and `small-16gib.yaml` keeps it.
The server's turn capacity is `worker.replicas` times the turns of one worker.

`auto` reads the CPU budget in the chart's `turn-admission.json`: 3500m of allocatable CPU, 50m for each turn, and 32 turns in total at most.
It subtracts these CPU requests from the 3500m:

- The server, the webhook role, the webapp and the worker, each times its replicas. The bundled PostgreSQL and NATS. The pgBackRest sidecar, when backups are on.
- For each running worker: the conversation host at 50m and 10 tools Pods at 25m each, plus the Pod overhead. With `RollingUpdate`, the chart counts two running workers for each replica.
- The review tier: 50m for each review, and 100m for the isolation probe of each running worker.

The remaining CPU divided by 50m, at most 32, is the total.
The total divided by `worker.replicas`, rounded down, is the count of one worker.
The render stops if that count is less than 1.
`auto` uses the 3500m budget on every node, so a node with more CPU does not get more turns.

For `small.yaml`, a chart test renders 32 turns. `small-16gib.yaml` changes none of these terms:

| Term | Millicores |
| --- | ---: |
| Allocatable CPU | 3,500 |
| Server 250, webhook role 250, webapp 50, worker 250, PostgreSQL 250, NATS 100 | −1,150 |
| Conversation host 50, and 10 tools Pods at 25 | −300 |
| 5 reviews at 50, and the isolation probe at 100 | −350 |
| pgBackRest, when backups are on | −100 |
| Remaining CPU | 1,700, or 1,600 with backups |
| Turns: the remaining CPU divided by 50, at most 32 | 32 |

Tools memory is a separate resource.
The conversations quota holds ten tools Pods for each worker, including a warm pool of up to two.
A turn requests a tools Pod only when it calls a tool. When the quota is full, that turn waits with visible progress.
The resident-turn count does not change this quota or the request of a Pod.
The provider pool admits each model call independently.

The 50m for each turn and the ceiling of 32 come from an admission sweep on release 0.95.0 with a scripted fake model.
[ADR 0068 G](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0068-reviews-and-heph-run-on-one-agent-runtime.md#g-review-pod-admission-checks-quota-and-provider-demand) owns that evidence and the qualification that a higher ceiling needs.
The [CSV results](/data/capacity-s3-0950.csv) give the measured commit, cohort and fake-model timings.
The [capacity procedure](/contributor/capacity-benchmark) describes the fixture.

## Measured conversation latency

The web conversation target is first answer text within 10 seconds for at least 95% of turns.
Time starts when the client sends the question, and includes queue, startup, model and tool time.
A stream snapshot or heartbeat is not answer text.

The latest first-text measurement ran for two hours on 2026-10-31, on commit `624a5836`.
Release 1.0.0-rc.1 contains that commit. No later release has a first-text measurement.
The model was a scripted fake model, not a real model. Its setup:

| Part | Setup |
| --- | --- |
| Node | One Kubernetes node with 4 vCPU and 15.61 GiB of allocatable memory, and no swap |
| Profile | `small.yaml` with `small-16gib.yaml`: one worker and 32 resident turns from `auto`. The run had one review slot, not the five that the profile now derives |
| Model | A scripted fake model. Each call gave its first token after 3 seconds and ended after 13 seconds, with 500 declared output tokens. It used no tools and refused no call |
| Call pool | 32 calls in flight, with a reserve of 8 for conversations |
| Load | 80 users with 3 turns each at 0, 30, 60 and 90 minutes. Between these bursts, cohorts of 40 users with 3 turns each started 60 seconds apart |
| Reviews | No review ran. One Pod in the review tier held 1,152 MiB for the whole run, in place of the memory of one review |
| Other workloads | PostgreSQL, NATS and monitoring of another release used about 1.4 GiB on the same node |

| Result | Value |
| --- | --- |
| Turns that ended with an answer | 5,880 of 5,880. No turn failed or was refused |
| First text p50 / p95 / p99 | 3.416 / 17.521 / 34.807 s |
| First text within 10 seconds | 4,679 of 5,880 turns (79.6%) |
| Lowest available node memory | 8,390.31 MiB |
| Highest memory charge of the server / worker / PostgreSQL | 1,437.24 / 1,375.60 / 442.30 MiB |
| OOM kills, evictions and swap use | 0 |

The run misses the 95% target.
In the 80-user bursts, turns wait for one of the 32 resident turns.
The values apply only to this fake model, workload and node.
A real model has other first-token and output times.

## Model capacity

Each model has a call pool with a learned limit of calls in flight.
[Runtime roles § The learned limit](./runtime-roles#the-learned-limit) gives each event that changes it.
The limit falls when the provider refuses a call, and when even the fastest first token of a window of calls waits too long.
The pool does not read the output rate of a stream.

A model server that batches calls, such as vLLM or Logos, starts a new call at once while its batch has room.
The first token of that call is not late, but each stream in the batch gets slower.
Thus, the pool can learn a limit past the throughput knee: the calls in flight at which the total output rate stops rising.
The `maxConcurrentCalls` ceiling caps the learned limit ([AI providers § Set a ceiling or a rate](./ai-providers#set-a-ceiling-or-a-rate)).

For Qwen3.8-27B served through Logos, one stream gives about 40 tokens per second.
[ADR 0074](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0074-a-reviews-width-and-count-follow-the-provider.md#context) records 40.5 tokens per second for each stream, in five reviews.
The knee of this model is not yet measured:

| Fact at the knee | Result |
| --- | --- |
| Calls in flight at which the total output rate stops rising | Not yet measured |
| Output rate of each stream at that point | Not yet measured |
| Time to the first chunk at that point | Not yet measured |
| Ceiling that the defaults use | Not yet measured |

## Deployment availability budget

The app target is 99.5% of eligible authenticated reads that succeed within 2 seconds.
Deployments consume this error budget.
For a window with `N` eligible reads, the budget permits at most `floor(N / 200)` failed or slow reads.
An authenticated probe outside the replaced server Pod measures deployment failures.
Pod readiness alone does not show the outage that a user sees.

At a constant probe rate of one request each second, a 30-day window permits 12,960 bad probe results, or 216 minutes.
This time conversion applies only to that probe schedule.
The app's budget uses its actual count of eligible requests.

Both single-node profiles update the worker and the server with `Recreate`.
Reviews and conversation turns stop while the old worker drains and the new worker starts.
This outage counts against the budget. A measurement of it is [not yet available](#not-yet-measured).

## CPU and processes

CPU requests decide scheduling, and CPU limits bound use.
A kubelet `podPidsLimit` on the sandbox nodes is optional.
The isolation probe records the process limit that a sandbox Pod meets ([Kubernetes § Sandbox prerequisites](./kubernetes#sandbox-prerequisites)).
A worker whose isolation probe fails starts no sandbox.

## Memory headroom

When the JVM starts, the buildpack's memory calculator sizes Java memory from the container's memory limit.
`BPL_JVM_HEAD_ROOM` is a percentage of that limit that the calculator keeps out of Java memory.
The chart does not set it, so the headroom is 0%.
Thus, a larger container memory limit gives a larger heap at the next start.
The worker's file cache and other memory outside the JVM use the rest of the limit.

The chart sets `BPL_JVM_THREAD_COUNT` for the worker: 120 threads, plus 8 for each review of one worker.
A changed value applies at the next start of the JVM, after a [graceful drain](./runtime-roles#graceful-drain).
The [Paketo memory calculator](https://paketo.io/docs/reference/java-reference/#memory-calculator) gives the calculation.

## PostgreSQL memory

The bundled image calculates starting settings from its container limit.
The chart's `postgresql.parameters` adds explicit `-c` arguments after that calculation.
The small profile uses these shared-node values:

| Setting | Value |
| --- | --- |
| `shared_buffers` | `256MB` |
| `work_mem` | `2MB` |
| `hash_mem_multiplier` | `1.0` |
| `max_connections` | `80` |
| `maintenance_work_mem` | `64MB` |
| `autovacuum_work_mem` | `32MB` |
| `autovacuum_max_workers` | `3` |
| `effective_cache_size` | `1GB` |
| `max_parallel_workers_per_gather` | `0` |
| `max_wal_size` | `1GB` |

`work_mem` applies to each sort or hash operation and can multiply across concurrent queries.
`effective_cache_size` is a planner estimate. It allocates no memory.
These settings keep autovacuum, statement statistics, fsync and WAL durability.
See [PostgreSQL resource consumption](https://www.postgresql.org/docs/18/runtime-config-resource.html).

The small profile requests the full 2 GiB memory limit of the PostgreSQL process.
Its resident pgBackRest sidecar also requests its full 512 MiB memory limit.
CPU can still burst, so these Pods keep the Burstable quality-of-service class.

A limit of 1536 MiB is a qualification target, not a setting.
The qualification counts the pgBackRest sidecar separately, and a backup or stanza Job in addition.
The p95 values of separate containers do not add up to a node peak at one time.
The qualification runs the reference load with a representative database, vacuum work, WAL archiving and the permitted worker surge.
`pg_settings` shows the effective values and their command-line source.

The qualification passes when all of these are true:

- The process charge stays within 1536 MiB, with no OOM kill and no Hikari timeout.
- The connection-acquire p95 is less than 50 ms.
- WAL archive lag is less than 60 seconds in steady load, and less than five minutes in recovery.
- Autovacuum reduces dead tuples after the peak.

The qualification also records vacuum duration, archive catch-up and each idle transaction older than one minute.
A successful start does not prove these gates. Until the qualification passes, the profile keeps the 2 GiB limit.

## Database connections

Each chart role has `databasePool.maximumPoolSize` and `databasePool.minimumIdle`.
They set the Spring datasource pool of that role and override its profile defaults.
The chart default is 20 / 5 for the server, 32 / 5 for each worker and 2 / 1 for the migration Job.
The small profile uses:

| Client | Maximum / minimum idle |
| --- | --- |
| Server | 16 / 2 |
| Each worker | 24 / 2 |
| Migration Job | 2 / 1 |
| Webhook role | 0 / 0: no DataSource |
| Sandboxes | 0 / 0: they use the worker's gateway |

The preparation of code evidence can hold two connections for each running review.
A larger pool does not admit more captures at once.
The server's four scheduled workspace syncs can hold eight connections, which leaves eight for foreground and control work.
No worker holds a database connection while its call waits for a model grant or for the provider.

The chart adds up the connections that PostgreSQL must hold.
With `RollingUpdate`, it counts each worker replica twice. `small.yaml` uses `Recreate`:

| Part | `small.yaml`, `Recreate` | `small.yaml` with `RollingUpdate` |
| --- | ---: | ---: |
| Server pool | 16 | 16 |
| Worker pools | 24 | 48 |
| Listeners, one for each server and worker replica | 2 | 3 |
| Migration pool | 2 | 2 |
| Backup sessions | 2 | 2 |
| Operator sessions | 4 | 4 |
| Superuser slots | 3 | 3 |
| Total, against `max_connections` of 80 | 53 | 78 |

The render stops if an explicit `max_connections` is less than the total.
Without an explicit value, the chart sets the total on a bundled database, and at least 100.
A rendered connection count does not show pool waits, query latency or memory use.

## Review sandbox limits

The [Pod-kind table](./kubernetes#sandbox-sizes) owns the memory, CPU request and disk sizes of each sandbox.
The reviews quota and the conversations quota bound sandbox requests separately from the worker JVM.

## Disk

The node's images, logs and sandbox scratch space are a budget separate from the persistent database and Git-cache volumes.
The chart bounds the ephemeral-storage requests, limits and volumes of sandboxes.
The [Kubernetes guide](./kubernetes#sandbox-sizes) owns these bounds.
[Backup and restore](./backup-restore) owns persistent state.
