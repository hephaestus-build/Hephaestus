This page gives the capacity of each [chart profile](./helm-chart#profiles), the values that change it, and the database connection budget.
The numbers come from the profiles and `values.yaml` of the chart.
They are scheduling requests, not measured peaks. Keep room for the operating system, the cluster and a rolling update.

## Profiles at a glance

| Profile | Nodes | Servers | Requests of each server | PostgreSQL requests and volume | Reviews at once | Conversation turns at once |
| --- | --- | --- | --- | --- | --- | --- |
| `dev.yaml` | One workstation node | 2 | 250m CPU, 3 GiB memory, 5 GiB Git cache | 100m CPU, 4020 MiB memory, 5 GiB volume | 0: sandboxes are off | 0 |
| `small.yaml` | One node of 4 vCPU, at least 16 GiB of memory and 150 GiB of disk | 1 | 500m CPU, 3 GiB memory, 20 GiB Git cache | 250m CPU, 4020 MiB memory, 20 GiB volume | 5 | 3, or 2 with backups on (`auto`) |
| [One host](./k3s): `small.yaml` with `k3s-values.yaml` | The node of `small.yaml` | 1 | As `small.yaml` | As `small.yaml` | 4 | 3, or 2 with backups on (`auto`) |
| `cluster.yaml` | Several nodes, with sandbox nodes that hold the review and conversation quotas | 2 | 500m CPU, 3 GiB memory, 70 GiB Git cache | 250m CPU, 9251 MiB memory, 20 GiB volume | 12 | 8 |

Turn swap off on each node.
With swap on, the kernel can move the memory of a Pod to disk, and the Pod slows down with no OOM kill.

Each server's memory request equals its limit, because the JVM sizes its heap from the limit.
The server's CPU limit is 4 cores, and 2 with `dev.yaml`.
The Git cache is node storage of each server ([Storage and retention](./helm-chart#storage-and-retention)).

The one host has fewer reviews than `small.yaml` alone, because each gVisor sandbox Pod also takes 48 MiB and 10m CPU of RuntimeClass overhead.
With backups, database metrics and the bundled monitoring stack all on, `small.yaml` and the one host each run 1 turn ([Node reserve](#node-reserve)).

The sandbox quotas hold these requests at full load, with any RuntimeClass overhead:

| Profile | Review quota | Conversation quota |
| --- | --- | --- |
| `small.yaml` | 5 Pods: 500m CPU, 2560 MiB memory | 3 Pods: 300m CPU, 1152 MiB memory |
| One host | 4 Pods: 440m CPU, 2240 MiB memory | 3 Pods: 330m CPU, 1296 MiB memory |
| `cluster.yaml` | 12 Pods: 1200m CPU, 6144 MiB memory | 8 Pods: 800m CPU, 3072 MiB memory |

Add the agent image DaemonSet (1m CPU and 16 MiB on each sandbox node).
With `cluster.yaml`, also add the agent-sandbox controller (10m CPU, 64 MiB).
During an install or an upgrade, the migration Job requests 250m CPU and 1536 MiB more.
Check the rendered requests against the allocatable resources of your nodes before you install.

## Measured throughput and latency

These measurements used the `small.yaml` cell of that time: one server with a CPU limit of 4 cores, 5 reviews and 11 conversation turns at once.
The sandboxes ran without gVisor. The one host with `k3s-values.yaml` uses gVisor, so it runs fewer reviews and turns at once.
Your model provider sets most of the time. Measure with your own model before you promise a time to your users.

### Reviews

A node with about 16 GiB of allocatable memory ran 5 reviews at once, with an open-weight model of 27 billion parameters.
Each round started the same five pull requests at the same time.
The server had a 2,304 MiB memory limit in both rounds ([Memory headroom](#memory-headroom)).

| Round | Review time, p50 and p95 | Model calls | Mean model call | Mean wait for a model permit | Reviews each hour |
| --- | --- | --- | --- | --- | --- |
| First | 14.2 and 14.3 min | 107 | 72 s | 44 s | About 21 |
| Second | 8.5 and 10.5 min | 57 | 41 s | 33 s | About 29 |

Reviews each hour is 5 reviews divided by the time until the last review ended.
In the first round, the reviews sent almost twice as many model calls, and each call took 76 % longer.
Thus, the same node finished fewer reviews each hour.
`gen_ai_client_operation_duration_seconds` shows the model call time on your installation.
`llm_pool_permit_wait_seconds` with `reason="capacity"` shows the wait for a model permit ([Metrics](./metrics.mdx)).

### Conversation turns

A test cluster on a shared host of 20 cores ran the `small.yaml` server with its 3 GiB memory limit.
A replay model sent its first token after 300 ms, and then 50 tokens each second.
Its answers had 100, 600 or 2,000 tokens.
In each run, all users arrived within about one second.
Each user asked three questions, 30 seconds apart.
The first answer text is the time from a question to the first text that the user sees.

| Users at once | First answer text, p50 | First answer text, p95 | Questions answered within 10 seconds | Runs |
| --- | --- | --- | --- | --- |
| 5 | 4.3 s | 31.6 s | 10 of 15 | 1 |
| 11 | 3.3 to 7.3 s | 7.6 to 32.9 s | 19 to 33 of 33 | 6 |
| 40 | 36 to 49 s | 77 to 86 s | 3 to 11 of 120 | 3 |

With 40 users, the node completed 1,250 to 1,570 turns each hour while the queue drained.

After a turn started, its first answer text came 0.7 to 1.1 seconds later.
The rest of the time is the wait for the turn to start.
Above 11 users, questions wait for a free turn.
Right after a server start, the first turns waited 13 to 21 seconds at the p50.
The host ran other work, so the p95 values changed from run to run.

Add your model's time to first token to these numbers.
`conversation_turn_queue_wait_seconds` shows the wait before a turn starts on your installation.
It also counts the wait behind an earlier question of the same conversation.

### What these measurements qualify

Hephaestus 1.0 is qualified at the caps of `small.yaml` on one node of 4 vCPU and 16 GiB.
The caps are 5 reviews and 11 conversation turns at once.
The server keeps its 3 GiB memory limit ([Memory headroom](#memory-headroom)).

These measurements leave some loads out.
Reviews and conversation turns did not run at full load in the same server at the same time.
No round ran more than 5 reviews at once, or looked for the load at which a model provider slows down.
Each round lasted less than one hour, so no peak of two hours and no soak of one day ran.
The one host with gVisor was not measured.

If you raise a cap, measure your installation with the signals in [Raise capacity](#raise-capacity).

## Raise capacity

| To get | Change | Also needs |
| --- | --- | --- |
| More reviews at once | `sandbox.reviewMemory`: 512 MiB more for each review, plus the RuntimeClass overhead | That memory on the sandbox nodes. Each review also takes three database connections of the server's pool. |
| More conversation turns at once | `sandbox.conversationTurns`, or with `auto` a larger `sandbox.budget` | 384 MiB and 100m CPU on the sandbox nodes for each turn ([Sandbox capacity budget](./helm-chart#sandbox-capacity-budget)) |
| More API capacity, and reception during a restart | `server.replicas` | A server request for each replica, and its database connections. More servers do not add reviews or turns. |
| Larger repositories | `server.gitCache.snapshotLimit` for one repository, and `server.gitCache.sizeLimit` for the volume | That much free ephemeral storage on each server's node ([Storage and retention](./helm-chart#storage-and-retention)) |
| More database space | `postgresql.persistence.size` | [Change a volume size](./upgrade#change-a-volume-size) |
| A larger review or conversation sandbox | `sandbox.templates.<kind>.resources` | The quotas follow the requests ([Sandbox sizes](./sandboxes#sandbox-sizes)) |

These signals show that a capacity limit holds work back:

| Signal | Meaning |
| --- | --- |
| `agent_run_oldest_due_age_seconds`, `HephaestusAgentQueueStalled` | Reviews wait for a review sandbox. |
| `conversation_turn_queued`, `conversation_turn_queue_wait_seconds` | Questions wait for a conversation turn. |
| `hikaricp_connections_pending`, `HephaestusDatabaseConnectionTimeouts` | Server threads wait for a database connection. |
| `HephaestusSandboxGatewayConnectionsHigh` | The sandbox gateway is near `sandbox.gateway.maxConnections`. |
| `HephaestusGitCacheNearlyFull` | The Git cache is near `server.gitCache.sizeLimit`. |
| `llm_pool_permit_wait_seconds` | Calls wait for the model provider, not for the cluster ([Call pool metrics](./metrics.mdx#call-pool-metrics)). |

## PostgreSQL memory

The chart sizes the memory of the bundled PostgreSQL from its memory settings and `max_connections`.
With `memory: auto` in `postgresql.resources`, the default, the request and the limit both take that size.
The chart refuses an explicit limit below it, and names each part in the error.
An explicit request stays as you set it, up to the limit.
A request below the derived size lets the node hold more sandboxes than the database can then use.

```text
memory          = shared memory + max_connections × each connection + maintenance + processes
shared memory   = shared_buffers + shared_buffers / 16 + 20 MiB + max_connections / 16 MiB
each connection = 26 MiB + shared_buffers / 512 + work_mem × hash_mem_multiplier
maintenance     = maintenance_work_mem + autovacuum_max_workers × autovacuum_work_mem
processes       = 80 MiB
```

The chart rounds each part up to a whole MiB.
With `max_parallel_workers_per_gather` above 0, it also adds 8 parallel workers as connections.

| Part | Value | Source |
| --- | --- | --- |
| Shared memory | The formula above | `postgres -C shared_memory_size` on the release image, PostgreSQL 18.6, for `shared_buffers` from 128MB to 1GB and 120 to 480 connections. The formula is at or above each result. |
| Private memory of each connection | 26 MiB | The 90th percentile of the private memory (`RssAnon`) that a backend of the server's role kept between statements. See the measurement below. |
| Page tables of each connection | `shared_buffers` / 512 | The kernel's page tables for a backend that has touched all of the shared buffers. |
| Postmaster and background processes | 80 MiB | The largest sum of the background processes' private memory in the same measurement: 78 MiB. |

The formula counts every connection at once, each with one sort or hash of `work_mem` in flight.

The measurement ran the server's integration tests against the release image with `jit = off`, on 2026-11-21.
A sampler read each backend's private memory every 5 seconds.
The run ended after 66 minutes, when one test process stopped, and it gave 61 minutes of samples.

93 backends of the server's role ran statements. Between statements, they kept a mean of 18.6 MiB.
Their 90th percentile was 26 MiB, and the largest kept 40 MiB.
A session that plans every table and index and holds 256 prepared statements keeps 16 MiB.

The chart uses the 90th percentile, not the mean.
A server connection lives up to 30 minutes, six times longer than these backends.
It sees every statement of the server, so it can keep more.
A size that is too large costs conversation turns. A size that is too small costs an outage of the database.

The figure of 26 MiB is provisional. A measurement on a production installation with `jit = off` replaces it:

- These backends lived at most 5 minutes.
- The tests also did work that production does not do, such as emptying every table.
- `RssAnon` counts pages that a backend still shares with the postmaster. It does not count kernel stacks and socket buffers.

To check the figure on your installation, sample the `RssAnon` line of each backend's `/proc/<pid>/status` while the server is busy.
Compare the server's backends with 26 MiB.
If they keep more, set `postgresql.resources.limits.memory` above the derived size. The chart accepts a larger limit.

The chart starts PostgreSQL with `jit = off`.
JIT compiles a query plan whose estimated cost passes `jit_above_cost`.
The server's queries are short, so the compilation buys no time, and each backend keeps the compiler's memory until it ends.
In production, the backends used about 37 MiB each with JIT on.
On 2026-11-14, 47 backends and 282 MiB of shared memory filled the 2 GiB limit of 1.0.0-rc.8.
The kernel then ended two backends.

An [external PostgreSQL](./external-database) keeps its own settings. Set `jit = off` there for the same reason.

The bundled image derives some settings from its container limit.
`postgresql.parameters` adds explicit `-c` arguments after that calculation, so these defaults of `values.yaml` replace it.
The chart refuses to render without one of the first seven, which the formula reads.
The last two keep the image from deriving them from the limit, which follows `max_connections`:

| Setting | Value |
| --- | --- |
| `shared_buffers` | `256MB` |
| `work_mem` | `2MB` |
| `hash_mem_multiplier` | `1.0` |
| `maintenance_work_mem` | `64MB` |
| `autovacuum_work_mem` | `32MB` |
| `autovacuum_max_workers` | `3` |
| `max_parallel_workers_per_gather` | `0` |
| `effective_cache_size` | `1GB` |
| `max_wal_size` | `1GB` |

`work_mem` applies to each sort or hash operation and can multiply across concurrent queries.
`effective_cache_size` is a planner estimate. It allocates no memory.
See [PostgreSQL resource consumption](https://www.postgresql.org/docs/18/runtime-config-resource.html).

These are the sizes for each profile. A chart test computes them again from this page and compares them with the rendered chart:

| Profile | `max_connections` | Memory |
| --- | --- | --- |
| `dev` | 120 | 4020 MiB |
| `small` | 120 | 4020 MiB |
| `cluster` | 300 | 9251 MiB |

`max_connections` follows the [connection budget](#database-connections), so more servers or a larger pool also raise the memory.
With backups on, the pgBackRest sidecar also requests its full 512 MiB limit.

## Node reserve

The single-node profiles state `sandbox.budget` as the node's allocatable resources, read from the node.
Before the chart derives the turns, it keeps a reserve out of the budget:

- The requests of the workloads outside the release on the same node, `sandbox.budget.outsideRelease`.
- 5 % of the budget as headroom, for memory that no request names, such as cert-manager and the kernel.

The turns come from what remains, at steady state and at the upgrade peak.
For `small.yaml`, the workloads outside the release are those of the [one-host platform](./k3s), at the pinned k3s version:

| Workload | Requests | Source |
| --- | --- | --- |
| Traefik | 100m CPU, 128Mi | `deploy/platform/k3s-platform.yaml` |
| The agent-sandbox controller | 10m CPU, 64Mi | `deploy/platform/k3s-agent-sandbox.yaml` |
| CoreDNS | 100m CPU, 70Mi | k3s's `manifests/coredns.yaml` at the version that `k3s-platform.yaml` pins |

cert-manager and the local-path provisioner set no requests, and the headroom covers them.
`small.yaml` states 210m CPU and 262Mi, and a chart test compares that sum with these files and this table.
Of the 14196 MiB of a 16 GiB node, the reserve keeps 972 MiB, and the release can use 13224 MiB.

A backup never takes room from the upgrade or from a sandbox.

Its Pods, a scheduled backup and the stanza Job of each upgrade, take the lowest priority, which never preempts.
A backup that starts during an upgrade waits for room. An upgrade that needs the room preempts a running backup, and its Job runs it again.
PostgreSQL archives its WAL from its own Pod also meanwhile, so no change is lost.
Thus, the upgrade peak does not count a backup. The steady state counts one backup, so that a backup gets its room when no upgrade runs.

`postgresql.backup.resources` sizes pgBackRest's TLS server beside PostgreSQL and the backup Jobs, with 256 MiB each.
On 2026-11-21, a full encrypted backup of a 2.25 GB database was measured.
It used at most 31 MiB of private memory in the server and 18 MiB in the Job.
With a 256 MiB limit, it took 22 seconds, as long as with no limit. With 128 MiB, it took 291 seconds, because the kernel reclaimed its page cache.
The S3 upload adds a buffer of a few MiB that this measurement, to a local repository, did not include.

A restore writes every data file, and the kernel charges the written pages to its limit until they reach the disk.
It failed with 256 MiB and passed with 512 MiB, so `postgresql.backup.restore.resources` keeps 512 MiB.

On a 16 GiB node, the upgrade peak binds. The free memory is what the node keeps free at that peak with every turn in use, the reserve included:

| Install | Release requests at the upgrade peak, before turns | Conversation turns | Free memory at the peak |
| --- | --- | --- | --- |
| `small.yaml` | 11844 MiB | 3 | 1200 MiB |
| `small.yaml`, backups on | 12100 MiB | 2 | 1328 MiB |
| `small.yaml`, backups, database metrics and the monitoring stack | 12516 MiB | 1 | 1296 MiB |
| One host | 11892 MiB | 3 | 1008 MiB |
| One host, backups on | 12148 MiB | 2 | 1184 MiB |
| One host, backups, database metrics and the monitoring stack | 12564 MiB | 1 | 1200 MiB |

## Database connections

Each chart role has `databasePool.maximumPoolSize` and `databasePool.minimumIdle`.
With `maximumPoolSize: auto`, the chart derives the server pool from the caps that it gives the server:

```text
pool = inbox handlers + 3 × reviews at once + 2 × long-load preparations
     + permit maintenance threads + boot + sync reserve + HTTP/control reserve
```

| Part | Connections | Source |
| --- | --- | --- |
| Inbox handlers | 8 | `server.inboxClaimers` |
| Review captures | 3 for each review at once | `sandbox.reviewMemory` |
| Long-load preparations | 4, with sandboxes on | Fixed |
| Permit maintenance | 2, with sandboxes on | Fixed |
| Boot work | 1 | Inside the pool |
| Sync reserve | 8, for four syncs | Fixed |
| HTTP and control reserve | 4 | Fixed |

The three connections of a review capture are its capture lease, a session lock and a transaction.
A composition that withholds what is open holds the lock while it records the withholding.

The result is 21 for `dev.yaml`, 42 for `small.yaml`, 39 on one host, and 63 for `cluster.yaml`.
An explicit `server.databasePool.maximumPoolSize` must hold the derived count. The chart refuses a smaller one.
A model stream and a sandbox hold no pooled connection. Sandboxes reach the server through the gateway and have no database pool.

The chart derives `max_connections` for one rolling update, in which every old server can still drain beside its replacement:

| Client or reserve | `small.yaml` |
| --- | --- |
| Servers at overlap: twice `server.replicas` | 2 |
| Server pools | 2 × 42 = 84 |
| Five dedicated `LISTEN` sessions for each server | 2 × 5 = 10 |
| Migration Job | 2 |
| PostgreSQL metrics exporter, the monitor role's connection limit | 2 |
| Backup sessions | 2 |
| PostgreSQL probes and role setup | 3 |
| Client total | 103 |
| `superuser_reserved_connections` | 3 |
| Operator margin | 4 |
| Required slots | 110 |
| `max_connections`: rounded up to a multiple of 20, at least 120 | 120 |

The chart reserves the exporter and backup sessions also when they are off.
Boot work uses the one connection included in each server pool. It has no separate connection term.

With `cluster.yaml`, four servers at overlap with pools of 63 give `max_connections` of 300.
An explicit `postgresql.parameters.max_connections` must hold the required slots. The chart refuses a smaller one.
An external database must hold the same budget beside its own reserved slots ([PostgreSQL connection settings](https://www.postgresql.org/docs/18/runtime-config-connection.html#GUC-SUPERUSER-RESERVED-CONNECTIONS)).
Helm does not check its limit. Add your operator margin and the clients of any other tenant that shares it.

When all pooled connections are busy, a caller waits up to 45 seconds for one, then gets an error.
`HephaestusDatabaseConnectionTimeouts` fires on such errors.

## Memory headroom

When the JVM starts, the buildpack's memory calculator sets the Java memory from the container's memory limit.
It subtracts the headroom, one 1 MiB stack per thread, metaspace, the code cache, and 128 MiB of direct memory.
The heap gets the rest.
See the [Paketo memory calculator](https://paketo.io/docs/reference/java-reference/#memory-calculator).

| Value | Calculator input | Default | Why |
| --- | --- | --- | --- |
| `server.jvm.headRoomPercent` | `BPL_JVM_HEAD_ROOM` | `15` | Native memory that the calculator does not count, such as the garbage collector's structures, grows with the heap. Under load it held about 290 MiB beside a 1 GiB heap. `0` restores the calculator's default. |
| `server.jvm.threadCount` | `BPL_JVM_THREAD_COUNT` | `200` | A server under five reviews and a sync burst ran at most 153 platform threads. Its virtual threads ran on 7 to 13 carrier threads. |

With the defaults and the 3 GiB limit, the server's heap maximum is about 1,796 MiB.
A higher memory limit also gives the heap more memory at the next start.
With no headroom, the garbage collector grows the heap until the container exceeds its limit, and the kernel kills it with no Java error.
`HephaestusContainerMemoryHigh` fires before that point ([Alert rules](./alert-rules)).
Measure the server's total memory use before you lower its memory limit or its headroom.

The calculator sets the Metaspace maximum from the number of classes that the JVM loads, `BPL_JVM_LOADED_CLASS_COUNT`.
The image sets this count, and the start log line `Calculated JVM Memory Configuration` shows it as `Loaded Class Count`.
A higher memory limit does not raise the Metaspace maximum.

Classes that the JVM reads from the image's AOT cache, `application.aot`, do not use Metaspace.
If the JVM refuses the AOT cache, it loads each class into Metaspace, and the start log shows why.
At the maximum, the server stops with `OutOfMemoryError: Metaspace`.
`HephaestusMetaspaceNearLimit` warns when Metaspace grows slowly toward the maximum ([Alert rules](./alert-rules)).

A socket call that blocks does not pin its carrier.
An ordinary file read or write holds its carrier and adds no carrier.
A synchronous, direct or `force` file operation lets the scheduler compensate. It can reactivate an idle carrier or add a carrier.
The JVM allows 256 carriers in total, or one for each CPU if the CPUs are more.
At that limit, such an operation holds its carrier and gets no replacement.

`jvm_threads_live_threads` shows the count. If it comes near `server.jvm.threadCount`, raise the value.

The 3 GiB default limit also applies to `small.yaml` and the one host.
A smaller limit did not pass a measured round.
On one host, under five reviews and a sync burst, a server with a 2,304 MiB limit and the default headroom gave these results:

| Measure | Result |
| --- | --- |
| Peak anonymous and kernel memory | 1,759 MiB, 76 % of the limit |
| Heap in use, of its maximum | 1,102 of 1,143 MiB, 96 % |
| Garbage collections | 5.7 each minute, 27 % more than at the same limit with no headroom |
| OOM kills and evictions | None |

The server was not killed. But its heap was almost full, and garbage collection rose by more than the 25 % that the round allowed.
Thus, `small.yaml` and the one host keep the 3 GiB limit.

## Disk

Budget the node's images, logs and sandbox scratch space separately from the PostgreSQL volume and the Git cache.
The sandbox templates bound their ephemeral storage ([Sandbox sizes](./sandboxes#sandbox-sizes)).
The `small` profile needs 150 GiB of disk on its node.
