This model applies to the Helm deployment on Kubernetes.
It covers the four application trust boundaries below.
These separate control planes are outside its scope:

- Browser and identity-provider internals.
- Host and database administration.
- Backup custody.
- The CI/release supply chain.
- Edge DDoS protection.

The [Security Policy](https://github.com/hephaestus-build/Hephaestus/blob/main/SECURITY.md), [Integration settings](./production-setup), [Backup & Restore](./backup-restore), and [Release Image Lock](./release-image-lock) own those control planes.

## Security objectives and protected assets

Hephaestus must meet these security objectives:

1. Prevent one workspace from reading or changing another workspace's data.
2. Keep reusable integration, session, encryption, and model-provider credentials out of untrusted content and sandbox environments.
3. Contain execution influenced by repositories and models without trusting their instructions or output.
4. Authenticate public ingress.
5. Bound public ingress.
6. Restrict outbound destinations and side effects.

| Asset                       | Examples                                                                           |
| --------------------------- | ---------------------------------------------------------------------------------- |
| Reusable credentials        | Provider keys, OAuth secrets, integration tokens, webhook secrets, encryption keys |
| Workspace-confidential data | Repository content, issues, messages, documents, feedback, membership              |
| Untrusted content           | Webhook bodies, diffs, files, comments, chat, documents, model output              |
| Operational data            | Job and delivery identifiers, metrics, sanitized error categories                  |

Arrows show permitted logical flows, not network-level reachability.
The [chart topology](./overview#architecture-and-network) shows the Pods and their connections.

Only the server role creates sandbox Jobs and Pods in the release's restricted sandbox namespace, and only with `sandbox.enabled`.
The webhook role has no sandbox RBAC.
No application role mounts a container daemon socket.

A deny-all NetworkPolicy covers that namespace.
Review sandboxes can reach the server's sandbox gateway.
Only the conversation loop, in the release namespace, can reach the conversation's tools Pods on TCP port 7100.
Review sandboxes reach nothing else, and tools Pods have no egress (SB-3).

Each server checks enforcement with real Pods before it starts a sandbox and at its configured probe interval (SB-7).
Its API serves meanwhile.
The native k3s CI and release smokes require every server to pass this probe.

Sandbox inputs arrive and results leave through the server's sandbox gateway, which also hosts the LLM proxy.
No server disk paths mount into a sandbox.
Runtime-role separation reduces reachable surface but is not authorization.
See [Runtime Roles](./runtime-roles).

## Attacker assumptions

An attacker can be any of these actors:

- An unauthenticated internet client that calls all routes exposed by the reverse proxy.
- A legitimate member who attempts horizontal or vertical privilege escalation.
- A compromised integration account that sends correctly signed malicious content.
- A repository contributor who puts prompt injection, malicious source, symlinks, or resource-exhaustion inputs in synchronized artifacts.
- A malicious or compromised model endpoint that returns crafted output.
- Code inside a sandbox, with full knowledge of the image and application design.

The model trusts these principals:

- Kubernetes control plane, container runtime and node root.
- Running application processes.
- PostgreSQL administrator.
- Instance encryption key.
- Configured instance admins.

Their compromise is outside the isolation guarantees described here.

### Boundary 2: LLM agent sandbox

Repository, chat, and model content is untrusted and can influence tool use.
A practice review's agent has `bash` among its tools.
The image includes Bash and Git.

1. Treat a sandbox as capable of running any shell command that untrusted content can cause.

Conversation turns run in the conversation loop, a Deployment in the release namespace.
The loop serves the turns of many developers and workspaces at the same time.
It is trusted as the roles are, and it runs no shell, file, or code tool itself.

Node runs the loop under its permission model, without child processes. It reads its code and its own directory, `/tmp/heph-loop`, and writes only that directory.
The permission model limits mistakes. It is not a sandbox.
The loop has no service account token and no ingress. It reaches only the servers' gateway port and the tools port of tools Pods (SB-3).

The loop has fewer controls than a sandbox Pod. It runs in the release namespace, without a user namespace or the sandbox RuntimeClass, and the isolation probe does not check its policy.
It holds the credential for turn pulls and the token of each turn that it runs.
It parses model output and the output of commands in tools Pods. A flaw in that parsing could expose those tokens until their turns end.

Its credential for turn pulls reaches only the assignment path. Each turn attempt then has its own attempt token (SB-2).

The loop's tools are `search_conversation`, `link_result`, `link_problem`, and `show_feedback`.
When the server can start tools Pods, the loop also has `read`, `bash` and `load_context`.
The server answers each tool call for that turn only.

#### Conversation tools Pod

`bash`, `load_context`, and a `read` of a file other than the turn's documents run in a [tools Pod](/contributor/practice-review-glossary#runtime-terms) in the sandbox namespace, not in the loop.
The server serves `INDEX.md`, `FIELDS.md` and the context documents from the memory of the attempt.
Treat each `bash` command as untrusted code that the model wrote.
The tools Pod's container is the security boundary, as it is for the shell of a review.

- **Boundary.** One Job for each turn attempt, from the agent image, under the restricted container policy of a review sandbox.
  Its one container, `tools`, runs only the tools program of [tool protocol v1](/contributor/practice-review-glossary#runtime-terms), as user 1001.
  The program listens on TCP, so it runs without the socket filter of a review's tools side. It starts each command under that filter, so a command cannot open a network socket.
- **Lifetime.** PostgreSQL binds the Pod to one attempt. A server deletes the Job when the attempt ends or loses its lease. The Pod's files go with it. No server gives the Pod to another attempt.
- **Contents.** The [context folder](/contributor/practice-review-glossary#runtime-terms) of one developer in one workspace, in the tools workspace `/tmp/tools/workspace`.
  It holds the context documents under `inputs/` and the repositories that Hephaestus loaded under `repos/`.
- **Write access.** The tools program writes each put read-only. Commands write only to `/tmp`, which the Pod removes with it.
  `/tmp` is a volume on the node's disk with a size limit ([Sandboxes § Sandbox prerequisites](./sandboxes#sandbox-prerequisites)).
- **Network.** Only the conversation loop can connect to the Pod, on TCP port 7100. The Pod has no egress and no DNS.
  The server writes a fresh nonce into the Pod spec. The tools program's `hello` returns it, and the loop checks it.
  The loop puts each file into the Pod. The server prepares each load as an archive for the loop.
- **Credentials.** None: no service account token, no Git token, and no turn token. A command gets a fixed environment and Git's hardening settings.
- **Limits.** The [Pod-kind resource table](./sandboxes#sandbox-sizes) sets CPU, memory and disk bounds. The node sets the process limit. Each command has a 60-second deadline.

A load checks the workspace, the account and the purpose of the turn.
It loads only a repository that the workspace monitors on an active connection and that no team hides.
An unknown, hidden, or other workspace's repository gets the same error.
An erasure, a hidden repository, a change of monitored repositories, or a changed AI choice revokes every tools Pod of that workspace.

These risks remain:

- **Prompt injection.** Repository files, Git history, Slack messages and documents can carry instructions. Hephaestus treats them as data, but a model can still follow them. The injected content can change Hephaestus's answer to the developer. It cannot reach another workspace or the network.
- **Shared kernel.** Without an isolating RuntimeClass, the tools Pod shares the node kernel with other containers. A review sandbox has the same limit (SB-1).
- **One user ID.** Each command runs as user 1001, the user of the tools program. A command can stop or read the processes of its own Pod. It cannot reach another attempt.

The [Conversation runtime](/contributor/unified-pi-runtime#context-folder) gives the endpoints and the limits.

`show_feedback` is the only tool that delivers feedback.
The server accepts it only for ready conversation feedback about the developer of the running turn.
It refuses it after an erasure of that developer's person data is requested.

Model output remains untrusted.
Any operation that stores it or creates an external write must apply that operation's validation and authorization.

A link in model-written text stays a link only when it points to Hephaestus or to a host of the workspace's connections ([OWASP LLM05](https://genai.owasp.org/llmrisk/llm052025-improper-output-handling/)).
Any other link, image or bare address shows as inline code, and Slack mention or link syntax shows as code too.
The server applies this rule to Slack replies in [`ModelLinks`](https://github.com/hephaestus-build/Hephaestus/blob/main/server/application/src/main/java/de/tum/cit/aet/hephaestus/core/ModelLinks.java).
The web app applies it in `UntrustedMarkdown`, with the hosts of `linkHosts` on the workspace list.
A bare domain without a scheme or `www.` stays plain text, and a client could still turn it into a link.
