# Runtime Roles

Hephaestus ships **one JAR** that boots in any of three runtime roles.
The same artifact can run as an application server, worker pod, or webhook receiver.
It can also run all three together as a monolith.
Three boolean properties control the roles:

| Role | Property | Default |
| --- | --- | --- |
| Server | `hephaestus.runtime.server.enabled` | `true` |
| Worker | `hephaestus.runtime.worker.enabled` | `true` |
| Webhook | `hephaestus.runtime.webhook.enabled` | `true` |

All three properties default to on, which starts the monolith role set. Heph also requires a connected worker control channel, even when server and worker roles share that JVM. It has no direct Docker fallback.

## Boot log

On startup, the JVM logs the enabled roles:

```text
INFO  RuntimeRoleStartupLogger : Runtime roles enabled: [SERVER, WORKER, WEBHOOK]
```

Under `prod`, disabling all roles prevents startup. Disabling NATS for a server or webhook role
also prevents startup. A worker-only process must disable NATS. The warning for a JVM with no roles
is a non-production diagnostic, not a production recovery mode. The startup event also records
`event.name=runtime.roles.configured` and the three `runtime.*.enabled` booleans.

## Monolith vs split-pod

Use the monolith when:

- You are a single contributor who runs locally.
- You have one app server and no horizontal scale yet.
- LLM capacity limits your worker, not Docker capacity.

Split the worker out when:

- LLM reviews and HTTP traffic compete for the same JVM heap / sandbox quota.
- You want to scale practice-review throughput independently of webhook ingestion.

The shipped Compose stacks use separate containers in both the reference deployment and the single-host install.
`application-server` turns off the worker role and has no Docker socket.
`application-worker` runs all sandboxes and is the only container with the socket.
The `gate:env` check fails a container that mounts the socket without the worker role.

Split the webhook receiver out when:

- You want to deploy app-server changes without dropping inbound GitHub/GitLab events. The webhook pod runs the JetStream publisher in isolation. Redeploys of the app pod do not touch the inbound HTTP surface.

## Per-role overlays

Each role has a Spring profile YAML that turns off the other two flags and removes their beans:

- `application-worker.yml`: `runtime.server=false` and `runtime.webhook=false`.
  It excludes OAuth2 autoconfigure but keeps JPA enabled.
  Its HTTP connector also serves management endpoints.
  It binds to loopback for in-container health checks.
  A separate sandbox gateway listens on `SANDBOX_API_PORT` (default `8081`).
- `application-webhook.yml`: `runtime.server=false` and `runtime.worker=false`.
  It enables sync NATS and disables the agent job queue.
  Webhook pods never claim jobs.
- No `application-server.yml` exists.
  The monolith default *is* the server profile.

The worker gateway's connector-specific security chain accepts only job-token-authenticated sandbox capabilities.
Other paths on that port return an empty `404`.
Capability calls receive these responses:

- Over `SANDBOX_API_MAX_REQUEST_BYTES`: `413`.
- No declared body length: `411`.
- Past `SANDBOX_API_REQUESTS_PER_MINUTE`: `429` with a `Retry-After`.

If the gateway cannot reach the store for rate-limit counts, it serves the call without a limit.
It counts that failure under `sandbox.gateway.limiter.errors`.
Thus, a limiter outage never stops a review.
Traefik never routes to this port.

To deploy a worker pod:

1. Set `SPRING_PROFILES_ACTIVE=prod,worker`.
2. Point `HEPHAESTUS_HUB_URL` at the app pod's WSS endpoint.

`docker/compose.app.yaml` contains a functional Compose template.

## Build-only profiles

`specs` and `cds-training` generate artifacts. They are not deployment modes. They load the
application contract without runtime bootstrap, container-image validation or image pulls. They
supply no shared placeholder secrets. If an authentication component needs a key to initialize,
the build uses the existing non-production ephemeral-key behavior, without a runtime warning.

Never combine either profile with `prod`, including through the `worker-node` or `webhook-server`
profile groups. Startup rejects that combination even when production secrets are configured.
Production encryption requirements apply to Spring's expanded profiles, so selecting a production
profile group requires the same keys as selecting `prod` directly.

## Configuration cheatsheet

Each cell shows the value a pod uses when the operator sets **no** environment variable for it.
It uses the profile overlay's value if the overlay specifies one.
Otherwise, it uses the base default.

| Property | Server | Worker | Webhook | Set by |
| --- | --- | --- | --- | --- |
| `hephaestus.runtime.server.enabled` | true | **false** | **false** | profile overlay |
| `hephaestus.runtime.worker.enabled` | true | true | **false** | profile overlay |
| `hephaestus.runtime.webhook.enabled` | true | **false** | true | profile overlay |
| `hephaestus.workspace.init-default` | false | false | false | `prod` profile |
| `hephaestus.git.enabled` | false | false | false | env default |
| `hephaestus.sync.nats.enabled` | false | **false** | **true** | env default / profile overlay |
| `hephaestus.agent.enabled` | false | false | false | env default |
| `hephaestus.integration.outline.allowed-origins` | empty | empty | empty | env default |
| `hephaestus.sandbox.gateway.port` | 8081 | 8081 | — | env default (`SANDBOX_API_PORT`) |
| `hephaestus.sandbox.gateway.requests-per-minute` | 120 | 120 | — | env default (`SANDBOX_API_REQUESTS_PER_MINUTE`) |
| `hephaestus.sandbox.gateway.max-request-bytes` | 4194304 | 4194304 | — | env default (`SANDBOX_API_MAX_REQUEST_BYTES`) |
| Needs user-auth wiring | yes | no | no | role gating |

Bold cells show values that the role's profile overlay specifies, not the base defaults.
The three `runtime.*` rows in a column show the pod's role set:

- The `worker` overlay turns off the server and webhook roles.
- The `webhook` overlay turns off the server and worker roles.
- The monolith, with no overlay, runs all three.

All three roles independently enforce Outline origin approval.
The server controls connections and sync.
The worker projects evidence.
The webhook role accepts change events.

1. Supply the same allowlist to all roles.
2. After a change, restart all three roles.

The reference Compose files supply the allowlist automatically.

Identical rows across the columns are **not** role-specific.
They are instance-wide defaults, shown per role because operators ask per role.
`init-default` is `false` in the `prod` profile for all roles.
These properties do not change with the active overlay:

- `git.enabled` (`GIT_CHECKOUT_ENABLED`).
- `agent.enabled` (`AGENT_ENABLED`).
- `integration.outline.allowed-origins`.

The two environment-variable flags default to `false` on **all** roles until the operator sets them.
No profile turns on work automatically.

`Needs user-auth wiring` is **not** in that group.
Its cells show `yes | no | no` because it differs by role.
User authentication exists only with the server role.
`hephaestus.runtime.server.enabled=false` removes it.
The `worker` overlay also excludes Spring's OAuth2 resource-server autoconfiguration.
A worker-only pod therefore never depends on user-auth wiring at boot.

The `webhook` overlay has no such exclusion.
It uses only the role gate.

No `hephaestus.sandbox.enabled` exists, and an architecture test forbids one.
The Docker sandbox *is* the worker capability, controlled by `hephaestus.runtime.worker.enabled`.
A server pod that keeps the worker role, such as a monolith, opens the sandbox gateway on the same port.
It needs the same firewall controls as a separate worker.
The webhook role turns off the worker role and opens no gateway.
Its three `sandbox.gateway` cells therefore show `—`.

Git needs no such row.
It runs in-process through JGit in the role that does the work.
It uses that container's mirrors under `hephaestus.fabric.root`.
The server role handles commit ingestion.
The worker role handles review preparation.
A server pod with the worker role enabled uses one root for both.

The webhook role has no Git.

Sandbox maintenance follows the worker role in both split-out and single-container deployments.
Idle mentor sessions and orphaned resources are cleaned periodically without enabling server-wide
scheduled jobs on the worker. Stalled writes are checked on a separate thread so a slow Docker cleanup
cannot delay their timeout. API-contract generation and CDS training do not run sandbox maintenance, server scheduled jobs or
startup sync-job recovery.

The worker application HTTP endpoint binds to loopback. Every role has a separate private
management listener on port **9090**, including a single-JVM topology. Management does not run on
`SERVER_PORT`. See [Observability](./observability#scrape-metrics) for network restrictions.

One row reads differently from what a bare `docker compose up` produces, because the shipped compose
file sets the env var the base default leaves off:

- `sync.nats.enabled` is `${NATS_ENABLED:false}` in `application-prod.yml`, but `docker/compose.app.yaml`
  passes `NATS_ENABLED: ${NATS_ENABLED:-true}` to `application-server` — so the compose server pod runs
  with NATS **on**. The `webhook` overlay pins it `true` regardless (it needs the shared `Connection`
  bean). The `worker` overlay pins it `false` (the job queue is PostgreSQL, ADR 0025).

`hephaestus.agent.enabled` (`AGENT_ENABLED`) gates three things that must agree, or a split
deployment silently does half its job. They do **not** share a gate:

- **Submission** (turning pull request, issue and bot-command events into queued jobs) needs
  this flag **and** the server role. A worker-only container executes jobs. It does not submit these reviews.
- **Orphan recovery** reclaims a dead worker's stuck jobs.
  It needs this flag **and** the server role.
  It therefore does not run twice on a dedicated worker pod.
- **Execution** (the poll loop that claims and runs jobs) needs this flag **and** the worker role.

`AGENT_ENABLED` is `false` on all roles until you set it, regardless of how the pod starts.

1. Set it to `true` on **each** pod that needs submission, orphan recovery, or execution.

In a split-pod topology, both pods need it:

- `application-server`: submission and recovery.
- `application-worker`: execution.

A pod without this setting claims nothing and spends nothing.

## Interactive mentor turns

Interactive mentor turns run their sandboxes on **connected workers**, for both web chat and Slack DMs.
The application server keeps these functions:

- HTTP/SSE and Slack delivery.
- Admission and budget checks.
- Thread persistence and `fetch_context`.

It needs no Docker client when `hephaestus.runtime.worker.enabled=false`.
A worker with spare mentor capacity owns each live session.
No in-process fallback exists.
`AGENT_ENABLED` controls queued practice reviews, not Heph.
The authenticated worker hub relays session commands and runner frames.

The server sends a session's proxy route and turn billing binding to its worker.
The worker resolves provider keys and never sends them to the sandbox.
PostgreSQL remains the billing record.

When no worker can admit a new session, Heph says **“Heph is busy. Try again.”** A drain rejects
new sessions and ends existing streams. After idle eviction, a drain or a worker restart, the next
turn opens a session on an available worker and restores the saved `session_jsonl`. Sticky server
affinity retains the live placement. Changing the model, route, image, runtime inputs or limits
replaces the session instead of reusing an incompatible runtime.

Each developer has at most one live Heph sandbox per workspace on its selected worker.
Startup takes several seconds because it requires these resources and actions:

- A job network and volumes.
- The workspace initializer.
- The runtime container.
- The runner's SDK load.

Where Hephaestus can anticipate a message, it starts the sandbox **before** the first message:

- **Opening Heph** in the webapp, or coming back to its browser tab, calls
  `POST /api/workspaces/{slug}/mentor/sandbox`. The server answers `202` at once and starts the sandbox
  in the background. It sends no prompt, calls no model and writes no thread.
- **Opening the Hephaestus app in Slack** (`app_home_opened`, either tab) does the same for a linked
  developer.

Preparation has no effect in these cases:

- The sandbox is already warm.
- A turn uses the sandbox.
- The developer has no Heph model.
- The developer's budget is spent.
- `hephaestus.mentor.max-sessions-per-user` or `hephaestus.mentor.max-sessions-total` has been reached.

A turn that arrives during preparation waits for that sandbox instead of starting another.

A sandbox stays warm for `hephaestus.mentor.idle-ttl-seconds` (default `900`) after its last frame.
Each idle runner holds about 165 MB, so a longer TTL keeps more memory in use between messages. The
session caps, not the TTL, bound the total. The Traefik sticky cookie's `maxAge` in
`docker/compose.app.yaml` follows the TTL.
Change both together.

A worker restart or deploy ends its
Heph sessions. The next message restores the saved thread on an available worker.
`mentor_turn_first_token_seconds{sandbox="cold"}` counts the turns that waited
([Observability](./observability.mdx#heph-turn-metrics)).

Attachment and a prepare `202` indicate transport or acceptance, not SDK readiness.
`mentor_turn_runtime_ready_seconds` measures from turn acceptance until `open_thread` confirms that
the runtime is usable. First-token and whole-turn timers measure different boundaries.

## Worker pod env vars

The bare minimum to boot a worker against a remote hub:

```sh
SPRING_PROFILES_ACTIVE=prod,worker
HEPHAESTUS_HUB_URL=wss://app.example.com/api/workers/connect
HEPHAESTUS_WORKER_REGISTRATION_TOKEN=<shared bootstrap secret>
HEPHAESTUS_WORKER_DRAIN_TIMEOUT=5m
AGENT_ENABLED=true
```

Without the last line, the worker boots and registers but claims no practice-review jobs.
It can still serve Heph: `AGENT_ENABLED` does not gate interactive sessions.

No LLM environment variables are necessary.
The LLM proxy runs in-process on this pod.
It follows the worker/sandbox capability, not `AGENT_ENABLED`.
It reads providers from the same instance/workspace catalog as the app pod.

1. Register providers at runtime under Instance admin → AI models, or under the workspace's AI models page.
2. Never register providers through an environment variable.

Capacity defaults to `auto` and auto-sizes from `Runtime.availableProcessors()`. Override only if the
host is noisy — and mind the name: the JVM binds
`HEPHAESTUS_WORKER_CAPACITY_REVIEW_MAX` / `HEPHAESTUS_WORKER_CAPACITY_MENTOR_MAX`. The shorter
`HEPHAESTUS_WORKER_REVIEW_MAX` / `_MENTOR_MAX` are **compose-file aliases only**
(`docker/compose.app.yaml` translates them). Set them on a K8s or systemd deployment and they are
silently ignored.

`SANDBOX_MAX_CONCURRENT` also caps review capacity.
A worker never claims more concurrent reviews than the host permits concurrent sandboxes.
The single-host self-hosted Compose file sets this limit to 1.
A higher review capacity there has no effect until you also raise the sandbox limit.

1. Raise the sandbox limit only with sufficient RAM, as the [Install guide](./install) describes.

The app pod signs worker tokens from a key *ring*, not a single value:
`hephaestus.worker.hub.token.keys[0].kid` + `.private-key` and
`hephaestus.worker.hub.token.active-kid`. Indexed list binding has no single env-var form, so
configure it through a mounted YAML/config-tree rather than a flat variable. Unset, the app logs a
warning and generates an ephemeral key that invalidates every worker token on restart.

## Graceful drain

On SIGTERM, the worker does these actions in order:

1. It sends `Heartbeat{draining=true}` to the hub.
   The dispatcher stops claiming new jobs for it.
2. It waits up to `hephaestus.worker.drain.timeout` (default 5 min) for active jobs to finish.
3. It stops containers that still run.
4. It returns each job to the queue with a worker-fenced requeue (`RUNNING → QUEUED`, retry-capped).

This is not a plain cancel.
Another worker's poll claims the job again, within `AGENT_MAX_RETRIES`.
Only jobs with an exhausted retry budget or a lost fence to concurrent user-cancel become terminally canceled/failed instead.
`timeout=0` skips step 2 and immediately applies the same requeue-first behavior.

The compose template pins `stop_grace_period: 6m` to give the JVM 60s of headroom before Docker SIGKILLs.
