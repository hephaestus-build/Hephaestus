1.0 starts the [1.x upgrade guarantee](./compatibility-policy#upgrade-guarantee).
Release candidates can require manual steps, including a stopped schema upgrade.
The target release's [migration guide](https://github.com/hephaestus-build/Hephaestus/blob/main/MIGRATION.md) owns each required action.

## Before you start

1. Find the installed release in **Instance administration → Overview**.
2. Select the required path in [Database baseline prerequisites](./compatibility-policy#database-baseline-prerequisites).
3. Read every migration entry between the installed release and the target release.
4. Preserve the current signed release lock, chart package, site values, and required keys.
5. Verify a restorable database backup with its matching keys and broker recovery material before upgrading.

[Backup policy for 1.0](./backup-restore#backup-policy-for-10) states the release scope.
Each upgrade still requires a verified recovery point.
If you have no verified recovery point, stop before the migration.

## Upgrade a release candidate

1. Complete [Validate the actual production data](./upgrade#validate-the-actual-production-data) on an isolated copy.
2. Pause [pull-based deployment](./pull-based-deployment#operating-it), if enabled.
3. Verify the target's [signed release assets](./release-image-lock#independent-verification).
4. If a migration entry requires every role stopped, use [Stopped schema upgrades](./kubernetes#stopped-schema-upgrades).
5. Otherwise, use the normal [Upgrade the host](./upgrade#upgrade-the-host) procedure.
6. Keep all roles on the target's signed image set.
7. Before resuming reconciliation, make its channel name the installed release.

:::caution[CAUTION: Changed schema]
Do not use automatic Helm rollback for a stopped schema upgrade.
An older role can corrupt data or fail against the changed schema.
Keep every role stopped after a migration failure.
Use [Failed-migration recovery](./upgrade#if-migration-fails).
:::

## Reach the database baseline from 0.x

A release before 1.0.0-rc.1 must first reach that database baseline.
Use its [versioned upgrade instructions](https://github.com/hephaestus-build/Hephaestus/blob/v1.0.0-rc.1/docs/admin/upgrade-to-1-0.mdx).

For a Compose installation, first upgrade to `0.95.0`.
Use [Move from Compose to the Helm chart](./compose-to-kubernetes) to move that version.
Apply `0.95.1` and install its reconciler tooling before the chart-only upgrade.
The versioned instructions own the stopped cutover to the database baseline.
Then follow the release-candidate procedure above.
1.0 supports only the [Helm chart](./compatibility-policy#supported-deployment).

## Check that it worked

1. Check the migration Job's log and the readiness of each enabled role.
2. Open **Instance administration → Overview** and read **Configuration readiness**.
3. Resolve each item under **Action required**.
4. Verify an authenticated read through the public gateway.
5. Run one practice review in **Approve first** mode, as [First steps § 7](./first-steps#7-first-practice-review) describes.
6. Ask one question in Hephaestus and verify that the answer completes.
7. Check the [metrics and alerts](./observability#scrape-metrics) for the enabled roles.

Check [Sizing and scaling](./sizing) before increasing capacity.
Its measurements state their workload and limits.
A successful upgrade does not qualify throughput or recovery time.
