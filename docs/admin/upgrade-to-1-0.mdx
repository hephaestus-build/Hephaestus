Cut over an installation from a release candidate of 1.0, from 1.0.0-rc.1 on, to 1.0.0.
The cutover is a [stopped upgrade](./upgrade#stopped-schema-upgrades): no server of the previous release runs beside a 1.0 server or on the 1.0 schema.
Plan one outage, from the first stopped server to the last passed check.
[ADR 0096](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0096-1-0-is-one-stopped-cutover-from-1-0-0-rc-1-and-keeps-nothing-for-0-x.md) records why.

1.0.0 carries the source and images of the last qualified release candidate.
A host that already runs that candidate changes only its release metadata.
It still stops the server, and it still needs the verified recovery point and the checks below.

## Before you start

1. Find the installed release in **Instance administration → Overview**.
2. Is the installed release older than 1.0.0-rc.1?
   Then install 1.0.0-rc.1 first ([Database baseline prerequisites](./compatibility-policy#database-baseline-prerequisites)).
3. Read every entry of the [migration guide](https://github.com/hephaestus-build/Hephaestus/blob/main/MIGRATION.md) between the installed release and the target.
   Each release candidate has its own `### v1.0.0-rc.N` section.
   This page orders the entries of § v1.0.0-rc.6 and of the target release.
   A host on 1.0.0-rc.5 or earlier also crosses the sections up to § v1.0.0-rc.6.
4. Preserve the current signed release lock, chart package, site values, and required keys.
5. Verify a restorable database backup with its matching keys, as [Back up the database](./backup-restore#back-up-the-database) describes.
   If you have no verified recovery point, stop.

## Prepare before the maintenance window

Complete these items before the maintenance window.
The window then holds only the cutover.

### The sandbox platform

The chart installs a sandbox template and a warm pool for each kind of sandbox.
They need the agent-sandbox controller and its resource definitions.
Thus, the controller must exist before the chart.

1. **Controller.**
   The platform bundle of the release pins the agent-sandbox controller in `k3s-agent-sandbox.yaml`.
   The one-host installer applies it.
   On another cluster, apply it for each release with cluster-admin rights.
   The migration entry *Install the agent-sandbox controller before the chart* gives the commands.
   Without it, `helm upgrade` stops because it cannot find the kind `SandboxTemplate`.
2. **Sandbox runtime.**
   Review and conversation Pods use `sandbox.templates.runtimeClassName`, or the default runtime of the cluster.
   [Sandbox prerequisites](./sandboxes#sandbox-prerequisites) states the requirements for each runtime.
   The one-host platform installs [gVisor](./k3s#the-platform-files) for the sandbox templates of the chart.
   The installer downloads the pinned gVisor release from `storage.googleapis.com`, so the host must reach that address.
   The first run with gVisor restarts k3s once, which stops the running Pods for a short time.
   Do this during the window, as the cutover steps below describe.
3. **NetworkPolicy enforcement.**
   The network plugin must enforce NetworkPolicy for egress and ingress.
   The [sandbox isolation gate](./sandboxes#sandbox-templates) qualifies that boundary before work starts. It is a script of the repository.
   Run it from a checkout of the release tag.
   It starts two sandboxes from a template, and it fails when a sandbox reaches more than the gateway.

A one-host installation that another tool deploys, such as [pull-based deployment](./pull-based-deployment), updates its platform with the installer's `--platform-only` mode.
[Install only the platform](./k3s#install-only-the-platform) gives what it installs, its checks and the procedure.

### Hosts with reconciler tooling of 1.0.0-rc.4

Do this procedure once, on a host with [pull-based deployment](./pull-based-deployment) whose tooling is that of 1.0.0-rc.4.
The `tooling` link names the release whose tooling runs.

1.0.0-rc.8 removes the `nats` image with the sync broker.
The verifier of 1.0.0-rc.4 compares a fixed list of chart images, so it refuses a release that removes one.
The verifiers from 1.0.0-rc.5 on read the images from the signed release lock and accept it.

1. Promote the channel to `v1.0.0-rc.5`, and complete its migration instructions.
2. Wait until the reconciler logs `Applied v1.0.0-rc.5`.
   Then `/var/lib/hephaestus/tooling` names `/var/lib/hephaestus/releases/v1.0.0-rc.5`.
3. Promote the target release.

A host whose tooling is 1.0.0-rc.5 or later needs no step.

### Hosts with reconciler tooling from before 1.0.0-rc.4

Do this procedure once, on a host with [pull-based deployment](./pull-based-deployment) that runs 1.0.0-rc.3 or earlier.

The reconciler verifies a release with the installed tooling before it adopts newer tooling.
Tooling from before 1.0.0-rc.4 expects five chart images, and 1.0.0-rc.4 has nine.
Thus, the old verifier stops each run with `does not pin the v1.0.0-rc.4 images`.
The running release is not affected.

Do not move the `tooling` link by hand. Each run sets it again from `applied.json`.

1. Make the channel name `v1.0.0-rc.4`, without `freeze`. A frozen channel adopts the tooling, but it never verifies the release.
2. If the host runs an earlier release, complete the migration instructions of each release first. The second run below applies 1.0.0-rc.4.
3. Stop the timer: `sudo systemctl stop hephaestus-reconcile.timer`. Confirm that `hephaestus-reconcile.service` does not run.
4. Authenticate the release lock and record the release that it names. The script stops at the first failure and keeps `applied.json` unchanged:

   ```bash
   sudo bash -s <<'SCRIPT'
   set -euo pipefail
   VERSION=1.0.0-rc.4
   STATE=/var/lib/hephaestus
   LOCK="release-v$VERSION.chart.json"
   BASE="https://github.com/hephaestus-build/Hephaestus/releases/download/v$VERSION"
   WORK=$(mktemp -d)
   if systemctl is-active --quiet hephaestus-reconcile.timer; then
     echo "Stop the timer first" >&2
     exit 1
   fi
   if [ "$(jq -er .release "$STATE/applied.json")" = "v$VERSION" ]; then
     echo "applied.json already names v$VERSION" >&2
     exit 1
   fi
   curl -fsSL "$BASE/$LOCK" -o "$WORK/$LOCK"
   curl -fsSL "$BASE/$LOCK.sigstore.json" -o "$WORK/$LOCK.sigstore.json"
   cosign verify-blob --bundle "$WORK/$LOCK.sigstore.json" \
     --certificate-identity 'https://github.com/hephaestus-build/Hephaestus/.github/workflows/release.yml@refs/heads/main' \
     --certificate-oidc-issuer https://token.actions.githubusercontent.com "$WORK/$LOCK"
   commit=$(jq -er --arg release "v$VERSION" \
     'select(.schemaVersion == 2 and .release == $release) | .commit | select(test("^[a-f0-9]{40}$"))' "$WORK/$LOCK")
   git -C "$STATE/checkout" fetch --quiet origin "$commit"
   cp -p "$STATE/applied.json" "$STATE/applied-before-tooling.json"
   cp -p "$STATE/applied.json" "$STATE/applied.json.new"
   jq --tab --arg release "v$VERSION" --arg commit "$commit" \
     '.previous = .release | .release = $release | .commit = $commit
      | .appliedAt = (now | strftime("%Y-%m-%dT%H:%M:%S.000Z"))' \
     "$STATE/applied-before-tooling.json" > "$STATE/applied.json.new"
   mv "$STATE/applied.json.new" "$STATE/applied.json"
   SCRIPT
   ```

5. Read `/var/lib/hephaestus/applied.json`. To undo, restore `applied-before-tooling.json` to `applied.json` now, while the timer is stopped.
6. Start the timer: `sudo systemctl start hephaestus-reconcile.timer`.

The next run logs `Adopted the tooling of v1.0.0-rc.4`.
The run after it logs `Applied v1.0.0-rc.4`: the new verifier checks the release, and a host that already runs it restarts no Pod.
After the timer starts, do not restore the record: the older tooling would then apply the older chart. Use [Rollback](./upgrade#rollback).

### Drain legacy reviews before removing gateway affinity

Before this first upgrade, stop the old servers and let their [graceful drain](./runtime-roles#graceful-drain) finish.
Follow the server stop procedure in [Planned node maintenance](./maintenance#planned-node-maintenance). Keep PostgreSQL running.
Do not start the target servers beside old servers with an active review during this first upgrade.
An old server held each composition's claim decision in its own memory, and an older review attempt has no published preparation checkpoint.
A target server cannot continue either of them.

Before you start the target servers, check that no review run has a live lease:

```sql
SELECT count(*) FROM agent_run
WHERE state = 'LEASED' AND kind IN ('REVIEW', 'REVIEW_COMPOSE')
  AND leased_until > clock_timestamp();
```

The count must be zero. If the drain deadline expired, keep the target stopped until the remaining leases expire.
Queued work can stay queued. The target claims it and records its own decision and preparation checkpoint in PostgreSQL.
After this first upgrade, the sandbox gateway Service has no client-IP affinity.
Each ready server reads the same run, lease, decision and checkpoint, so later rolling upgrades keep all active work.

## Cut over to 1.0.0

The migration entry *Stop every role to cut over to 1.0.0* points to this section.

:::caution[CAUTION: Changed schema]
Do not use automatic Helm rollback for a stopped schema upgrade.
An older server can corrupt data or fail against the changed schema.
Keep the server stopped after a migration failure.
Use [If migration fails](./upgrade#if-migration-fails).
:::

1. Complete [Validate the actual production data](./upgrade#validate-the-actual-production-data) on an isolated copy.
2. Pause [pull-based deployment](./pull-based-deployment#operating-it), if enabled.
   Wait for an active run to finish.
3. Verify the target's [signed release assets](./release-image-lock#independent-verification) and [chart](./kubernetes#verify-the-release-chart).
   Record the current chart, profile, site values and replica counts.
4. On a host on 1.0.0-rc.5 or earlier, drain the webhook streams just before you stop the roles.
   Wait until `webhook_stream_consumer_pending` and `webhook_stream_consumer_ack_pending` are 0 for each stream.
   The upgrade does not read the streams.
   Hephaestus does not handle an event that is still in a stream when the roles stop.
5. Stop every role.
   Do phase 1 of [Stopped schema upgrades](./upgrade#stopped-schema-upgrades) with the source release: `server.replicas` is 0.
   On a host on 1.0.0-rc.5 or earlier, also set `worker.replicas` and `webhook.replicas` to 0.
   Wait until every role Pod is gone.
   In the sandbox namespace, foreground-delete the claims with `hephaestus.build/sandbox-id` and the Jobs with `app.kubernetes.io/part-of=hephaestus`.
   Wait until every sandbox Pod is gone.
   The first reaper pass of the target servers takes back each ready sandbox whose claim you deleted.
6. Back up the database.
   Verify that the backup restores, as [Backup and restore](./backup-restore#back-up-the-database) describes.
   Export the keys and keep them with the backup and the current signed release lock.
   You need this recovery point to roll back.
7. Install the sandbox platform of the target release.
   On a one-host installation, run `--check-platform` and then `--platform-only` from the target bundle, as [Install only the platform](./k3s#install-only-the-platform) describes.
   On another cluster, apply `k3s-agent-sandbox.yaml` and wait for the controller:

   ```bash
   kubectl apply --server-side -f k3s-agent-sandbox.yaml
   kubectl -n agent-sandbox-system rollout status deployment/agent-sandbox-controller
   ```

   If this step restarts k3s, wait until PostgreSQL is ready before the next step.
   On a one-host installation, the platform files also renew the internal PostgreSQL certificate: do *Refresh the internal PostgreSQL certificate* before you continue.
8. Change the Secret.
   First move the database logins, as step 3 of *Give each database purpose its own login* describes.
   `hephaestus-keys.sh` stops while the Secret still holds `DATABASE_USERNAME` or `DATABASE_PASSWORD`.
   Then run the target release's `hephaestus-keys.sh` so that the Secret holds every new key.
   Export the keys again and keep that copy with the restore point.
9. Migrate.
   Do phase 2 of [Stopped schema upgrades](./upgrade#stopped-schema-upgrades) with the target chart and your changed site values.
   Save the log of the migration Job.
   Require its `Complete` condition and no `ERROR` line in the log.
   If the Job fails, keep the server stopped and go to [Roll back](#roll-back).
10. Check the sandbox prerequisites on the migrated release:
    - The controller is ready, and the chart's `SandboxTemplate` and `SandboxWarmPool` objects exist in the sandbox namespace.
    - The pre-pull DaemonSet is ready on every sandbox node: `kubectl --namespace hephaestus rollout status daemonset/hephaestus-agent-image`.
      It keeps the agent image on each node, because a cold pull takes longer than the start of a sandbox.
11. Start the server.
    Do phase 3 of [Stopped schema upgrades](./upgrade#stopped-schema-upgrades) with the recorded server count.
12. Run the sandbox isolation gate for each template, as [Sandbox templates](./sandboxes#sandbox-templates) describes.
    The gate needs a running server, because a sandbox must reach the gateway.
    If a check fails, scale the servers to 0 before work resumes.
    Then fix the policy enforcement of the network plugin before you continue.
13. On a one-host installation, run the target release's installer with `--version`, as [Upgrade the host](./k3s#upgrade-the-host) describes.
    Keep deployment automation paused until it finishes.
14. If pull-based deployment is enabled, make its channel name the installed release, then resume reconciliation.
    [Stopped major upgrades](./pull-based-deployment#stopped-major-upgrades) gives the reconciler's rules for a cutover.
15. Load the alert rules of the target release into your Prometheus or vmalert.
    A chart upgrade brings them, but your own Prometheus does not read them until you load them ([Alert rules](./alert-rules)).
16. Do [Check that it worked](#check-that-it-worked).

A review that a stopped server held goes back to the queue.
The entry *Stop every role before moving review leases to agent runs* gives the details.

No server receives provider deliveries during the window.
[Reception during a restart](./runtime-roles#reception-during-a-restart) says how each provider delivers them again.
Keep the window short.

## Roll back

1.0 has no mixed-version window.
An older image or `helm rollback` does not undo the migration.

1. Keep the server stopped.
2. Restore the verified backup from step 6 into the database.
   Restore its keys into the Secret.
   [If migration fails](./upgrade#if-migration-fails) gives the procedure.
   Use the previous release's signed lock.
3. Install the previous release.
   For a pull-based host, [Recover a stopped cutover](./pull-based-deployment#recover-a-stopped-cutover) gives the Helm and applied-record steps.
4. Start the roles of the previous release only on the restored database.
5. Report the recovery point and any lost writes.

The migration entry of a stopped change can give its own rollback notes.

## Check that it worked

1. Check the log of the migration Job and the readiness of the server.
2. Open **Instance administration → Overview** and read **Configuration readiness**.
3. Resolve each item under **Action required**.
4. Verify an authenticated read through the public gateway.
5. Run the sandbox isolation gate against each template and require every check to pass.
6. Run one practice review in **Approve first** mode, as [First steps § 7](./first-steps#7-run-the-first-practice-review) describes.
   Watch it end with a result.
7. Ask one question in Hephaestus and verify that the answer completes.
8. Read the dashboards **Overview** and **Reviews and feedback**, as [Dashboards](./monitoring#open-the-dashboards) describes.
   Reviews leave the queue, and no server is missing from the scrape.
9. Watch these alerts for the first hours: `HephaestusAgentQueueStalled`, `HephaestusAgentRunReaperFailing`, `HephaestusAgentSandboxReaperFailing`, `HephaestusReviewSandboxFailing`, `HephaestusSandboxGatewayRefusing`.
   [Alert response](./production-operations-runbook#alert-response) gives the action for each.
10. Do the actions that [The other migration entries](#the-other-migration-entries) lists for after the upgrade.

[Sizing and scaling](./sizing) states the workload and limits of its measurements.
A successful upgrade does not qualify throughput or recovery time.
