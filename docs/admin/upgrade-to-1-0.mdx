1.0 starts the [1.x upgrade guarantee](./compatibility-policy#upgrade-guarantee).
The cutover to 1.0.0 is a stopped upgrade: [ADR 0070](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0070-1-0-is-a-cutover-release.md) records why.
No role of the previous release runs beside a 1.0 role.
No role of the previous release runs on the 1.0 schema.
Plan for one outage, from the first stopped role to the last passed check.

1.0.0 carries the source and images of the last qualified release candidate.
A host that already runs that candidate changes only its release metadata.
It still stops every role, and it still needs the verified recovery point and the checks below.

The target release's [migration guide](https://github.com/hephaestus-build/Hephaestus/blob/main/MIGRATION.md) owns each required action.
This page orders the actions of the migration entries after `1.0.0-rc.5` and names the entry of each.

[Sizing and scaling](./sizing) has no measurement of the sandbox load of 1.0 yet.
Do not size nodes for 1.0 from this page.
:::

## Before you start

1. Find the installed release in **Instance administration → Overview**.
2. Select the required path in [Database baseline prerequisites](./compatibility-policy#database-baseline-prerequisites).
3. Read every migration entry between the installed release and the target release.
   Each release candidate has its own `### v1.0.0-rc.N` section in the migration guide.
4. Preserve the current signed release lock, chart package, site values, and required keys.
5. Verify a restorable database backup with its matching keys and broker recovery material before you upgrade.

[Backup policy for 1.0](./backup-restore#backup-policy-for-10) states the release scope.
Each upgrade still requires a verified recovery point.
If you have no verified recovery point, stop before the migration.

## Prepare before the maintenance window

Complete these items before the maintenance window.
The window then holds only the cutover.

### The sandbox platform

The chart installs a sandbox template and a warm pool for each kind of sandbox.
They need the agent-sandbox controller and its resource definitions.
Thus, the controller must exist before the chart.

1. **Controller.**
   The platform bundle of the release pins the agent-sandbox controller in `k3s-agent-sandbox.yaml`.
   The one-host installer applies it.
   On another cluster, apply it for each release with cluster-admin rights.
   The migration entry *Install the agent-sandbox controller before the chart* gives the commands.
   Without it, `helm upgrade` stops because it cannot find the kind `SandboxTemplate`.
2. **Sandbox runtime.**
   Review and probe Pods run on `sandbox.runtime.runtimeClassName`, or on the cluster's default runtime.
   They always need [user namespace support](./sandboxes#sandbox-prerequisites): a RuntimeClass does not replace it.
   The one-host platform installs [gVisor](./k3s#the-platform-files) for the chart's sandbox templates (`sandbox.templates.runtimeClassName`).
   No component claims a sandbox from those templates in this release.
   The installer downloads the pinned gVisor release from `storage.googleapis.com`, so the host must reach that address.
   The first run with gVisor restarts k3s once, which stops the running Pods for a short time.
   Do this during the window, as the cutover steps below describe.
3. **NetworkPolicy enforcement.**
   The network plugin must enforce NetworkPolicy for egress and ingress.
   Each server proves it with its isolation probe, and it starts no sandbox while the probe fails.
   [Sandbox prerequisites](./sandboxes#sandbox-prerequisites) lists the probe's checks.
   The [sandbox isolation gate](./sandboxes#sandbox-templates) is a script of the repository.
   Run it from a checkout of the release tag.
   It starts two sandboxes from a template, and it fails when a sandbox reaches more than the gateway.
   Thus, it fails on a network plugin that does not enforce NetworkPolicy.
4. **NATS 2.11 or later.**
   An external broker (`nats.bundled=false`) must run NATS Server 2.11 or later.
   The bundled broker already does.
   Check the version with `nats server info`.
   See the migration entry *External NATS broker: NATS Server 2.11 or later*.
5. **Broker certificate names.**
   A TLS broker address needs a matching subject alternative name.
   See the migration entry *NATS broker certificate names*.

A one-host installation that another tool deploys, such as [pull-based deployment](./pull-based-deployment), updates its platform with the installer's `--platform-only` mode.
[Install only the platform](./k3s#install-only-the-platform) gives what it installs, its checks and the procedure.

### Values and keys to move

The chart refuses an old name.
Phase 1 of the window still runs the current release with your current site file and Secret, so change neither before the window.
Before the window, prepare a copy of your site file for the target release, as step 1 of [Upgrade the host](./k3s#upgrade-the-host) describes.
Change the Secret in step 7, after phase 1.
The migration guide owns each change. This table gives the names.

| Where | Before | After | Migration entry |
| --- | --- | --- | --- |
| Site file | `config.monitoring` | `config.sync`, with the same four child settings | *Rename scheduled sync settings* |
| Site file | `config.auth.bootstrapAdmins`, `config.auth.browserExtensionIds`, `config.auth.passkeys.allowedOrigins`, `config.outline.allowedOrigins` as strings | The same keys as YAML arrays | *Convert chart list values to arrays* |
| Site file | `server.conversationTurns` | `conversationLoop.turns`, a count for the whole installation | *Stop every role for the conversation loop* |
| Site file | `sandbox.enabled`, `sandbox.*`, `sandbox.runtime.*`, `sandbox.gateway.maxConnections`, `networkPolicy.workerGatewayPorts`, and the server's rollout, drain, pool, git cache and resources | `sandbox.*`, and the same settings under `server` | *Move the server values to the server and the sandboxes* |
| Profile | `small-16gib` in `HEPHAESTUS_CHART_PROFILE` and `profiles/small-16gib.yaml` | `small` and `profiles/small.yaml` | *Use the small profile on every single-node install* |
| Server settings | `hephaestus.agent.max-retries` | `hephaestus.agent.capacity.review-retries`. `AGENT_MAX_RETRIES` still works. | *Stop every role before moving review leases to agent runs* |
| Secret | `DATABASE_USERNAME`, `DATABASE_PASSWORD` | `DATABASE_ADMIN_USERNAME` and `DATABASE_ADMIN_PASSWORD` for the bundled PostgreSQL, and the new `DATABASE_OWNER_PASSWORD` and `DATABASE_APP_PASSWORD` | *Give each database purpose its own login* |
| Secret | No key | `HEPHAESTUS_CONVERSATION_LOOP_SECRET`, added by the release's `hephaestus-keys.sh` | *Stop every role for the conversation loop* |
| Image outside the chart | `HEPHAESTUS_WORKER_CAPACITY_MENTOR_MAX` | `HEPHAESTUS_CONVERSATION_LOOP_SECRET` and `HEPHAESTUS_MENTOR_TURN_CAPACITY` on the server | *Stop every role for the conversation loop* |
| Image outside the chart | `HEPHAESTUS_RUNTIME_WORKER_ENABLED` and the `server` profile | `AGENT_ENABLED=true` and the sandbox settings on the server | *Move the server values to the server and the sandboxes* |
| Custom agent image | An image from an earlier release | An image that you rebuilt from this release | *Rebuild custom agent images* and *Rebuild a custom agent image* |

The table covers the changes after the release candidate `1.0.0-rc.5`.
A host on an earlier candidate also needs the entries of the later candidates.

Four more checks need a read before the window:

- API callers of the team routes move to the new contract: *Update team API callers*.
- Custom API clients read error responses in the problem format: *Read problem responses from the top level*.
- Duplicate repository monitor names stop the migration: run the query of *Stop every role before enforcing unique repository monitor names*.
- A practice identifier can collide with a reserved route name: run the preflight of *Check practice identifiers before upgrading*.

These migration entries also apply to a host that upgrades to 1.0:

- *Refresh the internal PostgreSQL certificate*: on one host, restart PostgreSQL after cert-manager issues the new certificate.
- *Stop every role before correcting unknown issue comment counts*: the migration changes stored issue comment counts of zero to unknown.
- *Use the stopped procedure for one-host release changes*: the one-host installer refuses a release change that does not follow it.
- *Let the one-host installer reach the gVisor download*: allow `storage.googleapis.com` in the host's egress rules.
- *Update custom practice script imports*: remove the imports that the release deletes from your custom scripts.
- *Remove broker consumer settings*: remove `config.durableConsumerName` and `config.consumerInactiveThreshold` from every values file.
- *Remove the Git checkout switch*: remove `config.gitCheckoutEnabled` from every values file.
- *Move the GitHub webhook byte bound into the stream map*: replace `webhook.stream.maxBytesGithub` with `webhook.stream.maxBytesByStream`.
- *GitHub synchronization is incremental*: remove `HEPHAESTUS_SYNC_INCREMENTAL_ENABLED` from your configuration.
- *Change the model call queries that read `class` or `queue`*: your own queries and alerts read the `band` label.
- *Decide whether GitHub App installations need an instance admin's approval*: by default, an instance admin adopts each new installation.

## Cut over to 1.0.0

The migration entry *Stop every role to cut over to 1.0.0* points to this section.

:::caution[CAUTION: Changed schema]
Do not use automatic Helm rollback for a stopped schema upgrade.
An older role can corrupt data or fail against the changed schema.
Keep every role stopped after a migration failure.
Use [Failed-migration recovery](./upgrade#if-migration-fails).
:::

Follow these steps in this order.
Each step names the page that owns it.

1. Complete [Validate the actual production data](./upgrade#validate-the-actual-production-data) on an isolated copy.
2. Pause [pull-based deployment](./pull-based-deployment#operating-it), if enabled.
   Wait for an active run to finish.
3. Verify the target's [signed release assets](./release-image-lock#independent-verification) and [chart](./kubernetes#verify-the-release-chart).
   Record the current chart, profile, site values and the three replica counts.
4. Stop every role.
   Do phase 1 of [Stopped schema upgrades](./upgrade#stopped-schema-upgrades) with the current release: `server.replicas`, `server.replicas` and `webhook.replicas` are 0.
   Wait until every role Pod, sandbox Pod and Job is gone.
   Then delete the conversation's tools Pods as that page describes.
5. Back up the database and the JetStream data.
   Verify that the backup restores, as [Backup and restore](./backup-restore#back-up-the-database) describes.
   Export the keys and keep them with the backup and the current signed release lock.
   You need this recovery point to roll back.
6. Install the sandbox platform of the target release.
   On a one-host installation, run `--check-platform` and then `--platform-only` from the target bundle, as [Install only the platform](./k3s#install-only-the-platform) describes.
   On another cluster, apply `k3s-agent-sandbox.yaml` and wait for the controller:

   ```bash
   kubectl apply --server-side -f k3s-agent-sandbox.yaml
   kubectl -n agent-sandbox-system rollout status deployment/agent-sandbox-controller
   ```

   If this step restarts k3s, wait until PostgreSQL and NATS are ready before the next step.
   On a one-host installation, the platform files also renew the internal PostgreSQL certificate: do *Refresh the internal PostgreSQL certificate* before you go on.
7. Change the Secret.
   First move the database logins, as step 3 of *Give each database purpose its own login* describes.
   `hephaestus-keys.sh` stops while the Secret still holds `DATABASE_USERNAME` or `DATABASE_PASSWORD`.
   Then run the target release's `hephaestus-keys.sh` so that the Secret holds every new key.
   Export the keys again and keep that copy with the restore point.
8. Migrate.
   Do phase 2 of [Stopped schema upgrades](./upgrade#stopped-schema-upgrades) with the target chart and your changed site values.
   Save the migration Job's log.
   Require its `Complete` condition and no `ERROR` line in the log.
   If the Job fails, keep every role stopped and go to [Roll back](#roll-back).
9. Check the sandbox prerequisites on the migrated release:
   - The controller is ready and the chart's `SandboxTemplate` and `SandboxWarmPool` objects exist in the sandbox namespace.
   - The pre-pull DaemonSet is ready on every sandbox node: `kubectl --namespace hephaestus rollout status daemonset/hephaestus-agent-image`.
     It keeps the agent image on each node, because a cold pull takes longer than the start of a sandbox.
10. Start the new roles.
    Do phase 3 of [Stopped schema upgrades](./upgrade#stopped-schema-upgrades) with the recorded replica counts.
    A server claims no work until its isolation probe passes.
    The gate needs a running server, because a sandbox must reach the gateway.
    Thus, run the gate for each template now, as [Sandbox templates](./sandboxes#sandbox-templates) describes.
    If it fails, fix the policy enforcement of the network plugin before you go on.
11. On a one-host installation, run the target release's installer with `--version`, as [Upgrade the host](./k3s#upgrade-the-host) describes.
    Keep deployment automation paused until it finishes.
12. If pull-based deployment is enabled, make its channel name the installed release, then resume reconciliation.
    [Stopped major upgrades](./pull-based-deployment#stopped-major-upgrades) gives the reconciler's rules for a cutover.
13. Load the alert rules of the target release into your Prometheus or vmalert.
    A chart upgrade brings them, but your own Prometheus does not read them until you load them ([Alert rules](./alert-rules)).
14. Do [Check that it worked](#check-that-it-worked).

What happens to a review that a server still held when it stopped is in *Stop every role before moving review leases to agent runs*.

The webhook role is stopped during the window, so provider deliveries in that time reach no receiver.
GitHub redelivers the failed deliveries of the last two hours.
For the other providers, the reconciliation sync recovers the effect.
[Webhook ingestion operations](./webhook-ingestion-operations) gives the details.
Keep the window short.

## Roll back

1.0 has no mixed-version window.
An older image or `helm rollback` does not undo the migration.

1. Keep every role stopped.
2. Restore the verified backup from step 5 into the database.
   Restore its keys into the Secret.
   [If migration fails](./upgrade#if-migration-fails) gives the procedure.
   Use the previous release's signed lock.
3. Install the previous release.
   For a pull-based host, [Recover a stopped cutover](./pull-based-deployment#recover-a-stopped-cutover) gives the Helm and applied-record steps.
4. Start the roles of the previous release only on the restored database.
5. Report the recovery point and any lost writes.

The migration entry of a stopped change can give its own rollback notes.

## Reach the database baseline from 0.x

A release before 1.0.0-rc.1 must first reach that database baseline, as [Prepare an older database for the current release](./liquibase-baseline-runbook) describes.
Then follow the cutover above.

## Check that it worked

1. Check the migration Job's log and the readiness of each enabled role.
2. Open **Instance administration → Overview** and read **Configuration readiness**.
3. Resolve each item under **Action required**.
4. Verify an authenticated read through the public gateway.
5. Check `sandbox_isolation_passed` of each server and that `HephaestusSandboxIsolationFailed` does not fire.
6. Run one practice review in **Approve first** mode, as [First steps § 6](./first-steps#6-run-the-first-practice-review) describes.
   Watch it end with a result.
7. Ask one question in Hephaestus and verify that the answer completes.
8. Read the dashboards **Overview** and **Reviews and feedback**, as [Dashboards](./monitoring#open-the-dashboards) describes.
   Reviews leave the queue, and no role is missing from the scrape.
9. Check these alerts for the first hours: `HephaestusAgentQueueStalled`, `HephaestusAgentRunReaperFailing`, `HephaestusAgentSandboxReaperFailing`, `HephaestusReviewSandboxFailing`, `HephaestusSandboxGatewayRefusing` and `HephaestusSandboxIsolationFailed`.
   [Alert response](./production-operations-runbook#alert-response) gives the action for each.
10. Did the upgrade cross *Stop every role before correcting unknown issue comment counts*?
    Then ask the administrators of each affected workspace to run its backfill.
    Until it finishes, those issues show an unknown comment count.

Check [Sizing and scaling](./sizing) before increasing capacity.
Its measurements state their workload and limits.
A successful upgrade does not qualify throughput or recovery time.
