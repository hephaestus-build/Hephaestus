This procedure installs the signed Helm chart of a release on a Kubernetes cluster that you operate.
For one Linux host, [Install on one host](./k3s) runs the same chart on k3s with one command.
For a cluster on which you are not a cluster-admin, use [Install on a managed cluster without cluster-admin](./managed-cluster).
The [Helm chart reference](./helm-chart) describes what the chart runs and each value.

## Before you start

- The cluster meets the [supported cluster](./helm-chart#supported-clusters) requirements.
- The sandbox nodes meet the [sandbox prerequisites](./sandboxes#sandbox-prerequisites).
- You selected a [profile](./helm-chart#profiles) for the size of the cluster.
- You have the tools that [Verify the release chart](#verify-the-release-chart) names.

## Verify the release chart

The chart package of a release names the release version, the source commit, and the release's images by digest.
Thus, you give Helm only your own values.
The chart version and its `appVersion` equal the release version without the leading `v`.
A stable promotion keeps the candidate's images and packages the chart with stable release metadata.
The signed joint lock records the resulting chart digest.
The chart source in the repository names no image, tag, or registry.

You need [Cosign](https://docs.sigstore.dev/cosign/system_config/installation/) 3.1 or later, the Helm CLI, `curl`, and `jq`.
The release signs the chart with Cosign 3.1 in the Sigstore bundle format.
Cosign 2 reads that format only from version 2.6 and only with `--new-bundle-format`, and CI does not test it.
You do not need Node.js or a checkout of the repository.

Use the Helm version that [`.github/actions/setup-helm`](https://github.com/hephaestus-build/Hephaestus/blob/main/.github/actions/setup-helm/action.yml) pins.
CI and the release workflow install that version.
Contributors also need it: see the [local development prerequisites](/contributor/local-development#prerequisites).
The pin is a build tool, not a qualified Helm version for an installation.
No Helm plugin is necessary.

Run these commands in the directory of your `site.yaml`.
If one command fails, stop: do not install the chart.

```bash
VERSION=X.Y.Z
CHART=ghcr.io/hephaestus-build/charts/hephaestus
# 1. The chart digest, from the joint lock of the release.
DIGEST=$(curl -fsSL "https://github.com/hephaestus-build/Hephaestus/releases/download/v$VERSION/release-v$VERSION.chart.json" |
  jq -er .chart.digest)
# 2. The release workflow signed that digest.
cosign verify "$CHART@$DIGEST" \
  --certificate-identity 'https://github.com/hephaestus-build/Hephaestus/.github/workflows/release.yml@refs/heads/main' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
# 3. The one pull: Helm gets the chart by that digest, never by a tag.
helm pull "oci://$CHART@$DIGEST" --untar --untardir "chart-$VERSION"
# 4. The signed chart is the chart of this release.
helm show chart "chart-$VERSION/hephaestus" | grep -x "version: $VERSION" >/dev/null
```

The joint lock in step 1 is only a lookup for the chart digest.
You do not verify it.
Step 2 refuses every digest that the release workflow did not sign.
That identity is the same for every release, so step 4 binds the chart to the release that you asked for.
A version tag can move, and it is not a release signal.

The `chart-$VERSION/hephaestus` directory is the verified chart, with its `profiles/`.
Step 3 stops if that directory already exists.
[Install](#install) and [Upgrades](./upgrade#upgrade-a-schema-compatible-release) use it.
[Release assets](./release-image-lock#release-assets) gives the purpose of each signed asset of a release.

## Create the Secret

The chart reads secret values only from one Secret in the release namespace.
It never writes a secret value.
Set `secret.name` to the name of that Secret.
The chart reads fixed key names from it.

[Secret custody and rotation](./secret-custody#inventory) lists each key, the roles that read it, and the command that generates it.
That page also tells you which keys to keep outside the cluster for a restore, and how to replace each key.

A minimal install needs these keys:

- `HEPHAESTUS_SECURITY_ENCRYPTION_KEY` and `HEPHAESTUS_SECURITY_CREDENTIAL_ENCRYPTION_KEY`.
- `HEPHAESTUS_AUTH_STATE_COOKIE_KEY`.
- `WEBHOOK_SECRET` and `WEBHOOK_ROUTING_SECRET`.
- `HEPHAESTUS_CONVERSATION_LOOP_SECRET`, when the server runs.
- `DATABASE_OWNER_PASSWORD` and `DATABASE_APP_PASSWORD`, the passwords of the [database roles](./helm-chart#database-roles).
- With the bundled PostgreSQL, also `DATABASE_ADMIN_USERNAME` and `DATABASE_ADMIN_PASSWORD`, its administrator.
- `GITHUB_OAUTH_CLIENT_SECRET`, for sign-in with GitHub.

If a needed key is missing, the Pod that reads it stays in `CreateContainerConfigError`.
For a feature that you turn on later, for example backups or Slack, add the keys that the [inventory](./secret-custody#inventory) lists for it.

The release script `hephaestus-keys.sh` creates the Secret with these keys.
It generates each key that you do not choose, and it never changes a key that exists.
It prints key names, never a value.
It needs `kubectl` with access to the release namespace, `openssl` and `jq`.

1. Get the script from the signed bundle of the release.
   Download, verify and unpack the bundle as steps 2 and 3 of [Get the release files](./k3s#1-get-the-release-files) describe.
   You need only `hephaestus-keys.sh` from it.

2. Type the client secret of your GitHub OAuth app. The shell does not show it:

   ```bash
   read -rs GITHUB_OAUTH_CLIENT_SECRET && export GITHUB_OAUTH_CLIENT_SECRET
   ```

3. Run the script:

   ```bash
   sh hephaestus-keys.sh --namespace hephaestus --secret hephaestus-app
   ```

   Add these options when they apply:

   - `--external-database`: you use your own PostgreSQL. The script takes `DATABASE_OWNER_PASSWORD` and `DATABASE_APP_PASSWORD` from the environment. Use the passwords that you gave the [database roles](./helm-chart#database-roles).
   - `--new-keys`: with `--external-database`, for a database without Hephaestus data only. The script cannot see whether the database holds data. For a database with data, restore both keys from your backup first.
   - `--backups`: you turn on backups with a new, empty backup repository. The script generates `BACKUP_CIPHER_PASS`. For an existing repository, restore its passphrase into the Secret instead.
   - `--metrics`: you turn on the [database metrics](./monitoring#turn-on-database-metrics). The script generates `DATABASE_MONITOR_PASSWORD`.

4. Set `secret.name` to `hephaestus-app`.
5. Copy the keys off the cluster, as [Copy the keys from the Secret](./secret-custody#copy-the-keys-from-the-secret) describes.

Run the script again at any time, for example with `--backups` when you turn on backups.
It adds only the keys that the Secret lacks.
The script stops if the bundled PostgreSQL volume exists but the Secret lacks the administrator login or an encryption key.
Then restore the Secret from your backup.

If Git holds your release, for example with Argo CD or Flux, create the release namespace first.
Then run the script once from your workstation before the first sync.
Keep the Secret out of Git.
The chart never generates a key: a key in a rendered manifest would change at each render.
A new system key cannot read what the old key encrypted.

To write the Secret yourself instead, generate each value as [Generation and rotation](./secret-custody#generation-and-rotation) gives it, and do not write a newline into a value.

### PostgreSQL TLS Secret

Each role connects to PostgreSQL with `sslmode=verify-full`.
The role verifies the server certificate against a CA, and it checks that the certificate names the host that the role connects to.
Set `postgresql.tls.existingSecret` to an existing Secret in the release namespace.
The chart refuses to render without it.
The chart creates no certificate, no key, and no CA.

| Key | Bundled PostgreSQL | External PostgreSQL | Mounted in |
| --- | --- | --- | --- |
| `ca.crt` | Yes | Yes | Server, migration Job, PostgreSQL metrics |
| `tls.crt`, `tls.key` | Yes | No | Bundled PostgreSQL only |

These receive only `ca.crt`, read-only, at `/etc/hephaestus/postgresql-ca`.
No application role receives a private key.

Backup Jobs use a separate client Secret, `postgresql.backup.clientTlsSecret`.
It holds `ca.crt`, `tls.crt` and `tls.key` for the common name `hephaestus-backup`.
The PostgreSQL CA signs it.
The chart mounts its certificate and key as `backup.crt` and `backup.key`.
Do not put the private key of the CA in this Secret.

For the bundled PostgreSQL, the certificate in `tls.crt` must name `<release>-postgresql.<release namespace>.svc`.
`<release>-postgresql` follows the object name rule in [Install](#install).
The roles connect to exactly this name, without a cluster domain.
The chart mounts `tls.crt` and `tls.key` into the PostgreSQL pod with the mode `0440`.
The files belong to root and to the group 999, and PostgreSQL accepts a key with these permissions.

If you have no CA, make one with OpenSSL.
The server certificate needs the name above as a DNS subject alternative name, and the `serverAuth` extended key usage.
This example makes a CA that is valid for ten years, and a server certificate that is valid for one year.
Change `RELEASE` and `NAMESPACE` if your release differs.
If `<release>-postgresql` has more than 52 characters, the chart shortens the Service name, as [Install](#install) describes.
Then set `HOST` to that shortened name with `.<namespace>.svc`.

```bash
RELEASE=hephaestus NAMESPACE=hephaestus
HOST="$RELEASE-postgresql.$NAMESPACE.svc"
TLS_DIR=$(mktemp -d)
openssl req -x509 -newkey rsa:3072 -nodes -sha256 -days 3650 -subj '/CN=Hephaestus PostgreSQL CA' \
  -addext 'basicConstraints=critical,CA:TRUE' -addext 'keyUsage=critical,keyCertSign,cRLSign' \
  -keyout "$TLS_DIR/ca.key" -out "$TLS_DIR/ca.crt"
openssl req -newkey rsa:3072 -nodes -sha256 -subj "/CN=$HOST" \
  -keyout "$TLS_DIR/tls.key" -out "$TLS_DIR/server.csr"
openssl x509 -req -sha256 -days 365 -in "$TLS_DIR/server.csr" \
  -CA "$TLS_DIR/ca.crt" -CAkey "$TLS_DIR/ca.key" -CAcreateserial \
  -extfile <(printf 'subjectAltName=DNS:%s\nextendedKeyUsage=serverAuth\nkeyUsage=digitalSignature,keyEncipherment\nbasicConstraints=CA:FALSE\n' "$HOST") \
  -out "$TLS_DIR/tls.crt"
openssl verify -CAfile "$TLS_DIR/ca.crt" -verify_hostname "$HOST" -purpose sslserver "$TLS_DIR/tls.crt"
```

The last command prints `OK` when the certificate names the host.
Then create the Secret with the three keys, and set `postgresql.tls.existingSecret` to its name:

```bash
kubectl --namespace "$NAMESPACE" create secret generic hephaestus-postgresql-tls \
  --from-file=ca.crt="$TLS_DIR/ca.crt" \
  --from-file=tls.crt="$TLS_DIR/tls.crt" \
  --from-file=tls.key="$TLS_DIR/tls.key"
```

Keep `ca.key` outside the cluster, because you need it to renew the server certificate.
For an external PostgreSQL, the Secret holds only `ca.crt`.

[TLS certificates](./secret-custody#tls-certificates) gives the renewal of each certificate. A new CA needs the [database maintenance](./maintenance#database-maintenance) procedure.

## Prepare the Gateway

The Gateway API is a platform prerequisite of the chart.
The platform operator installs and operates these items:

- The Gateway API resource definitions and a Gateway controller.
- The Gateway, its TLS certificate, and its HTTP to HTTPS redirect.

The chart installs none of them.
It attaches one `HTTPRoute` to the Gateways in `route.parentRefs`.
`route.parentRefs` must name at least one Gateway.

On a k3s cluster that you set up yourself, the bundled Traefik does not serve the Gateway API until you turn on its Gateway provider.
Put this `HelmChartConfig` in `/var/lib/rancher/k3s/server/manifests/`.
Then run `kubectl get gateway --all-namespaces` to find the Gateway for `route.parentRefs`.

```yaml
apiVersion: helm.cattle.io/v1
kind: HelmChartConfig
metadata:
  name: traefik
  namespace: kube-system
spec:
  valuesContent: |-
    providers:
      kubernetesGateway:
        enabled: true
    gateway:
      enabled: true
      listeners:
        web:
          port: 8000
          protocol: HTTP
          namespacePolicy:
            from: Selector
            selector:
              matchLabels:
                kubernetes.io/metadata.name: hephaestus
        websecure:
          port: 8443
          protocol: HTTPS
          certificateRefs:
            - name: hephaestus-tls
          namespacePolicy:
            from: Selector
            selector:
              matchLabels:
                kubernetes.io/metadata.name: hephaestus
```

Traefik creates the HTTPS listener only when `certificateRefs` names a TLS Secret.
Create `hephaestus-tls` in `kube-system`, the namespace of this Gateway, from the certificate of your host name.
Change `hephaestus` in the selector if your release namespace differs.
The one-host install sets up its own Traefik, so it needs none of this.

A Gateway accepts a route from another namespace only if its listener allows that namespace.
If the Gateway is not in the release namespace, set `allowedRoutes.namespaces` on its listener.
This example allows only the release namespace:

```yaml
listeners:
  - name: websecure
    port: 443
    protocol: HTTPS
    allowedRoutes:
      namespaces:
        from: Selector
        selector:
          matchLabels:
            kubernetes.io/metadata.name: hephaestus
```

Traefik names this setting `namespacePolicy` in its chart values.
Without it, the Gateway rejects the route, and every request returns `404`.
Hephaestus reports nothing about it.
After the install, check that the Gateway accepted the route:

```bash
kubectl --namespace hephaestus get httproute -o jsonpath='{range .items[*].status.parents[*].conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'
```

Both conditions must be `True`: `Accepted=True` and `ResolvedRefs=True`.
`Accepted=False NotAllowedByListeners` means that the listener does not allow the release namespace.
`kubectl --namespace hephaestus describe httproute` shows the same conditions with a message.

Set `trustedProxies` to a Tomcat regular expression that matches only the Gateway data plane addresses.
The server does not start in production with a blank value.
The `IP` column of this command shows the addresses of the Gateway Pods:

```bash
kubectl get pods --namespace <Gateway namespace> --selector <Gateway pod label> --output wide
```

Write a regular expression for the Pod network that holds them, not for one address, because a Pod gets a new address when it restarts.
On a k3s cluster with the default Pod network `10.42.0.0/16`, use this value:

```yaml title="values.yaml"
trustedProxies: '10\.42\.\d{1,3}\.\d{1,3}'
```

Use single quotes, or no quotes, in YAML.
Double quotes read each backslash as the start of an escape sequence.

The Gateway API has no portable request body limit or idle timeout.
Configure these values on the Gateway:

- A request body limit of 25 MiB on `/webhooks` and `/api`.
- An idle timeout of at least 60 seconds for the Hephaestus live stream.

## Install

1. Create the release namespace and the sandbox namespace, and label both with the Restricted Pod Security level.
   Use the sandbox namespace for this release alone.

   ```bash
   kubectl create namespace hephaestus
   kubectl create namespace hephaestus-sandboxes
   kubectl label namespace hephaestus hephaestus-sandboxes pod-security.kubernetes.io/enforce=restricted
   ```

   With the server enabled, install the agent-sandbox controller of the release before the chart ([Sandbox templates](./sandboxes#sandbox-templates)).
   The file is `k3s-agent-sandbox.yaml` in the release's k3s bundle.
   Apply it again for each release.

   ```bash
   kubectl apply --server-side -f k3s-agent-sandbox.yaml
   kubectl -n agent-sandbox-system rollout status deployment/agent-sandbox-controller
   ```

2. Make the OAuth App of your login provider, as [First steps § 1](./first-steps#1-configure-a-login-provider) describes.
   Then create the [Secret](#create-the-secret) with its client secret, and the [PostgreSQL TLS Secret](#postgresql-tls-secret).
   The server copies the client secret into the database at its first start.
3. Write your values file, `site.yaml`, with `host`, `trustedProxies`, `secret.name`, `postgresql.tls.existingSecret`, `route.parentRefs`, and `networkPolicy.gateway` with its pod labels.
   Add `config.github.oauthClientId` and `config.auth.bootstrapAdmins`, as [First steps § 1 and § 2](./first-steps) describe.
   Do not set `release` or `images`: the release chart sets them.
   For a public instance, create the ConfigMap with your legal pages and name it in `webapp.legalOverrides`, as [Legal pages](./legal-pages#deployment-specific-overrides) describes.
   The webapp Pod waits for a ConfigMap that it names.
4. Enable reviews.
   `small.yaml` enables the sandboxes, and the chart does not render them without the sandbox namespace and the Kubernetes API endpoint.
   Find the endpoint that the network plugin sees:

   ```bash
   kubectl get endpointslices --namespace default --selector kubernetes.io/service-name=kubernetes
   ```

   On a single k3s node, `PORTS` is `6443` and `ENDPOINTS` is the node's internal address, for example `192.168.5.15`.
   Add both values to `site.yaml`:

   ```yaml
   sandbox:
     namespace: hephaestus-sandboxes
   networkPolicy:
     kubernetesApi:
       cidr: 192.168.5.15/32
       port: 6443
   ```

   Use `/128` for an IPv6 address.
   If `ENDPOINTS` lists more than one address, one for each control plane node, set a CIDR that holds all of them.

5. [Verify the release chart](#verify-the-release-chart).
6. Install the verified chart with a [profile](./helm-chart#profiles) and your values:

   ```bash
   helm upgrade --install hephaestus "chart-$VERSION/hephaestus" -n hephaestus \
     -f "chart-$VERSION/hephaestus/profiles/small.yaml" -f site.yaml \
     --wait=watcher --wait-for-jobs --timeout 45m
   ```

   The first install omits automatic rollback so a failure leaves its Jobs and Pods available for diagnosis.
   If it fails, use [A first install fails](#a-first-install-fails) before removing anything.

## Check that it worked

1. Find the successful install's revision with `helm history hephaestus --namespace hephaestus`.
   Follow its migration Job's log: `kubectl --namespace hephaestus logs job/hephaestus-migration-<revision>`.
   Replace `<revision>` with the successful install's revision number.
   The Job logs `Database migration completed` when it finishes.
   The JVM then prints a long native memory summary. It is not an error.
2. Wait until the server is ready, then run the [sandbox isolation gate](./sandboxes#the-agent-image-on-the-sandbox-nodes) for each template.

   ```bash
   kubectl --namespace hephaestus rollout status deployment/hephaestus-server
   ```

   The server's readiness does not run the old isolation probe. The platform gate must pass before work is enabled.

3. Continue with [First steps § 3. Sign in](./first-steps#3-sign-in).

## Undo

1. Delete the sandbox namespace first.
   This stops every sandbox at once.
   If you remove the release first, its network policies go.
   Then sandbox Pods that remain lose their policies.

   ```bash
   kubectl delete namespace hephaestus-sandboxes
   ```

2. Remove the release. Running reviews stop.

   ```bash
   helm uninstall hephaestus --namespace hephaestus
   ```

3. These items stay:
   - The PostgreSQL volumes.
   - The Secrets that you created.
   - The backups in the S3 bucket.
4. To remove the data too, delete the release namespace: `kubectl delete namespace hephaestus`.
   A PersistentVolume with the `Retain` reclaim policy stays until you delete it.

## Troubleshooting

### A first install fails

A failed first install keeps its Helm revision, Jobs and Pods when it runs without `--rollback-on-failure`.
The one-host installer does not use automatic rollback on a first install.
When the install fails, the installer stops and links to this section.
After the diagnosis, run the installer again with the same release. It retries the failed install.

For a one-host installation, first select the kubeconfig in the installer's release directory.
For the default directory:

```bash
export KUBECONFIG="$HOME/hephaestus/kubeconfig"
```

Use your chosen directory if it differs.
The installer exports this path only inside its own process.
If the file does not exist, inspect the saved installer output and k3s on the host.
Do not run the cluster checks below with another kubeconfig.

1. Preserve the installer's terminal output before retrying.
2. Check the Helm record with `helm list --namespace hephaestus`.
3. If the release remains, read its history with `helm history hephaestus --namespace hephaestus`.
4. List remaining Jobs and Pods with `kubectl --namespace hephaestus get jobs,pods -o wide`.
5. Read recent events with `kubectl --namespace hephaestus get events --sort-by=.metadata.creationTimestamp`.
6. If the migration Job remains, preserve its log with `kubectl --namespace hephaestus logs job/<migration-job>`.
   Replace `<migration-job>` with the Job name for the failed Helm revision from steps 3 and 4.
7. If a server Pod remains, read its log before the next install replaces it.

Events expire, and a removed Pod's log might no longer exist.
A failed install can still have changed the database.
Use [Failed-migration recovery](./upgrade#if-migration-fails) before starting an older release against it.
For durable logs, configure a [log collector](./monitoring#ship-logs-to-a-log-store) before the install.

### Other symptoms

| Symptom | Cause and check |
| --- | --- |
| A server log says that the network policy did not filter a sandbox Pod in time | The network plugin applied the policy of a new Pod more than 60 seconds after the Pod started. The attempt is tried again. |
| A sandbox Pod stays `Pending` with a quota error | Its tier's quota is full. The chart sizes each tier for its servers' capacity, so check a quota of your own, or `sandbox.reviewMemory` and `sandbox.conversationTurns`. |
| Every path returns `404`, and `kubectl get httproute` shows `Accepted=False NotAllowedByListeners` | The listener of the Gateway does not allow routes from the release namespace. Set `allowedRoutes.namespaces` on the listener, as [Gateway routes](./helm-chart#gateway-routes) shows. |
| A new Pod restarts during an upgrade, and its log names a pending change set | It waited 10 minutes for the schema. Check the migration Job's log. A longer migration needs the [database maintenance](./maintenance#database-maintenance) procedure. |
| A backup Job fails with `unable to find primary cluster` | The Job cannot reach pgBackRest's TLS server on port 8432 of the PostgreSQL Service, or its client certificate is not for `hephaestus-backup` from `ca.crt`. |
| PostgreSQL's volume fills | A failed WAL archive keeps the WAL on the volume. Check the latest backup Job's log and the bucket's credentials. |
| A practice review fails with "The sandbox could not prepare its workspace." | The sandbox's initializer failed before any model call. The job runs again within its retry limit, so a failure that repeats on every attempt uses all of them. The server log names the initializer's exit code. After the last attempt, read the exit code and the last lines of the initializer's log on the job: `kubectl --namespace hephaestus exec hephaestus-postgresql-0 -c postgresql -- psql -U "$DATABASE_USERNAME" -d hephaestus -c "SELECT capture->'initializationFailure' FROM review_job WHERE id='<job id>'"`. Known credential formats in those lines are masked. |

Run `node scripts/sandbox-isolation.ts` to verify each template and its network boundary.
The server's `/actuator/prometheus` on its management port shows the same tier in the `sandbox_isolation_*` metrics.
