---
title: Repair activity history
description: Run a backfill to restore missing activity of a GitHub or GitLab workspace, and check the result against the provider.
page_type: how-to
---

Run a backfill when a workspace shows no activity before a date, or fewer pull requests or merge requests than the provider.
The backfill rebuilds the missing activity events from the stored pull requests, merge requests, reviews, issues and comments.
It does not restore the work of an erased person, deleted work, or work with no author.
It does not invent edit, reopen, label or dismissal times.

## Before you start

- You need the workspace admin role.
- For the checks, you need read-only `psql` access to the application database.
- Keep public activity pages off until you verify the repair.

## Run the repair

1. Open **Administration → Integrations → GitHub** or **GitLab** in the workspace.
2. Open the menu next to **Sync now**.
3. Select **Run backfill**.
4. Wait until the job ends, and read its progress and repository warnings.

The API gives the same action to a signed-in workspace admin:

```http
POST /api/workspaces/{workspaceSlug}/connections/{connectionId}/sync/jobs
Content-Type: application/json

{"type":"BACKFILL"}
```

The connection must belong to the workspace.
If a backfill already runs, the server returns that job and starts no second one.

The backfill reads repository history again, within the provider rate limits.
It restarts the completed history of a repository in each of these conditions:

- At least 20 pull requests or merge requests are missing.
  The stored ones are also less than 80 % of the provider total.
- A pull request or merge request was not read whole: its threads, reviews or comments stopped at a page.
- A monitored issue has an unknown comment count.

After a row-count restart, the server does not restart the same gap again.
A repository that cannot be read or restarted adds a warning to the job, and the job continues with the other repositories.
A repeated backfill adds no duplicate activity.

Practices that need the whole discussion withhold their results on work that was not read whole.
After the backfill, request a new review of that work. Existing results do not change.

## Check that it worked

1. Find the workspace and repository IDs:

   ```sql
   SELECT id, slug FROM workspace WHERE slug = '<workspace slug>';

   SELECT r.id, r.name_with_owner, p.type, p.server_url
   FROM repository r JOIN identity_provider p ON p.id = r.provider_id
   WHERE r.name_with_owner = '<owner/repo>';
   ```

   If the repository name exists on more than one provider instance, use the row of the workspace's provider.

2. Run the read-only checks with those IDs:

   ```sql
   \set workspace_id <workspace id>
   \set repository_id <repository id>

   BEGIN READ ONLY;

   SELECT m.name_with_owner, m.pull_request_backfill_checkpoint,
          m.backfill_last_run_at, m.backfill_repair_provider_count,
          m.historical_backfill_sync_error
   FROM repository_to_monitor m
   WHERE m.workspace_id = :workspace_id;

   SELECT i.issue_type, count(*) AS stored_rows,
          count(*) FILTER (WHERE i.deleted_at IS NULL) AS live_rows,
          min(i.created_at) AS earliest_stored
   FROM issue i
   WHERE i.repository_id = :repository_id
   GROUP BY i.issue_type;

   SELECT discussion_read_whole, count(*)
   FROM issue
   WHERE repository_id = :repository_id
     AND issue_type = 'PULL_REQUEST' AND deleted_at IS NULL
   GROUP BY discussion_read_whole;

   SELECT event_type, count(*), min(occurred_at)
   FROM activity_event
   WHERE workspace_id = :workspace_id AND repository_id = :repository_id
   GROUP BY event_type
   ORDER BY event_type;

   COMMIT;
   ```

3. Compare `stored_rows` of `PULL_REQUEST` with the provider's total.
   Include deleted rows and erased work: the provider total counts them too.
   The counts match, or a job warning names the repository.
4. Check that `historical_backfill_sync_error` is empty.
5. Check that no pull request has `discussion_read_whole` null (unknown) or false (partial read).
6. Check that `activity_event` has events back to the date of the earliest stored row.
7. Optional: for GitHub, compare a sample, as [Compare a GitHub sample](#compare-a-github-sample) describes.

A `pull_request_backfill_checkpoint` of zero means that the scan finished. It does not prove that every provider row is stored.

### Compare a GitHub sample

Use a token that can read the same repository as the workspace connection.
Do not put the token in a command, log or support report.

```bash
gh api graphql -f query='query {
  repository(owner: "<owner>", name: "<repo>") {
    pullRequests(first: 1, orderBy: {field: CREATED_AT, direction: ASC}) {
      totalCount
      nodes { number createdAt }
    }
  }
}'

gh api --paginate repos/<owner>/<repo>/pulls/<number>/reviews \
  --jq '.[] | {id, state, submitted_at, user: .user.login}'
```

Replace `<owner>` and `<repo>` with the repository, and `<number>` with a pull request number.
For GitHub Enterprise, use the same GitHub instance as the connection.

1. Compare `totalCount` with `stored_rows` of `PULL_REQUEST`.
2. Compare the review IDs with `pull_request_review.native_id` of that pull request, not with its local `id`.

A review whose inline comments are all replies (`in_reply_to_id`) is not a separate review in the activity.
