Workspace subdomains give each workspace its own address, such as `https://acme.hephaestus.example.com` for the workspace `acme`.
Sign-in, the API and webhooks stay on the host of the instance, `https://hephaestus.example.com`.
The feature is off by default.

## Before you start

- A DNS name as `host`, not an IP address.
  The host must not be a [public suffix](https://publicsuffix.org/list/).
  Otherwise, the workspace hosts cannot use the session of the apex.
- A DNS provider that cert-manager can use for a [DNS-01 challenge](https://cert-manager.io/docs/configuration/acme/dns01/).
- A cert-manager ClusterIssuer with a DNS-01 solver for your zone.
  Keep its credential in a Secret in the namespace of cert-manager, never in `site.yaml`.
- A `host` of at most 189 characters, so that a full workspace label fits.

## Prepare DNS and the certificate {/*#configure-dns-and-the-edge*/}

1. Add a wildcard record `*.<host>` that points to the same address as the record of `<host>`.
   Keep the records of other services, such as `docs`, as separate records.
2. If your DNS provider proxies traffic, set both records to DNS only.
3. If the zone has CAA records, allow `letsencrypt.org` in `issue` for the host and in `issuewild` for the wildcard ([CAA](https://letsencrypt.org/docs/caa/)).
4. Get one certificate for `<host>` and `*.<host>` on the Gateway.

On one host with k3s, the installer requests that certificate.
On another cluster, issue it on the Gateway as you issue the certificate of the host.

## Turn on the Helm value {/*#helm-chart-and-k3s*/}

1. Add the value to `site.yaml`:

   ```yaml title="values.yaml"
   workspaceSubdomains:
     enabled: true
   ```

   The chart uses `host` as the base domain, and gives both settings to the server and the webapp.

2. Apply `site.yaml`.
   On a cluster, run the `helm upgrade` command of [Install](./kubernetes#install) again.
   On one host, run the installer again with the issuer of the wildcard certificate:

   ```bash
   sh k3s-install.sh --workspace-subdomains --dns01-issuer <issuer-name>
   ```

   Add the options of your first install.
   On a repeat run, the installer keeps `site.yaml`, so set the value in the file yourself.
   Without `--workspace-subdomains`, a repeat run stops instead of replacing the wildcard certificate, as [Run the installer](./k3s#2-run-the-installer) describes.

The chart adds a wildcard route to the webapp.
On a workspace host, the webapp refuses reserved or invalid labels and the API, sign-in and webhook paths.
On the apex, a `GET` or `HEAD` of a workspace path, such as `/w/acme/activity`, redirects to the workspace host with `308`.

## Register exact OAuth callbacks

Each login provider uses one callback on the apex, also with workspace subdomains.
A workspace host never receives a callback.

1. Open **Instance administration → Login providers**.
2. Select **Copy redirect URI** for each provider.
3. Make sure that the OAuth application of the provider registers that exact URI.
4. In the GitHub OAuth App, turn off **Enable wildcard matching in the callback URL**, and remove callbacks on workspace hosts.

The callbacks have this form, without a final slash or a wildcard:

| Provider | Callback |
| --- | --- |
| GitHub sign-in | `https://<host>/api/login/oauth2/code/github` |
| GitLab sign-in | `https://<host>/api/login/oauth2/code/gitlab` |
| Outline account linking | `https://<host>/api/login/oauth2/code/outline` |
| Slack account linking | `https://<host>/api/login/oauth2/code/slack` |
| Slack workspace connection | `https://<host>/api/oauth/callback/slack` |
| GitHub App | `https://<host>/api/oauth/callback/github` |

A provider that an instance admin added can have another registration ID in place of the provider name.
If the registered callbacks already use the apex, change nothing.

## Check that it worked

1. Open `https://<host>`.
   It serves the web app over HTTPS.
2. Ask the apex for a workspace path:

   ```bash
   curl -sI https://<host>/w/<workspace slug>/activity
   ```

   The answer is `308`, with `location: https://<workspace slug>.<host>/activity`.

3. Open `https://<workspace slug>.<host>`.
   It serves the web app over HTTPS, and you are signed in.

## Undo

1. Set `workspaceSubdomains.enabled` to `false` in `site.yaml`.
2. Apply `site.yaml`.
3. Keep the DNS records and the certificate while other services use them.

Workspace links on the apex then open the web app without a redirect.

## Workspace names

A workspace slug is a DNS label of 3 to 51 lowercase ASCII letters, digits and single hyphens.
It cannot start or end with a hyphen.
Infrastructure and application names are reserved, such as `www`, `api`, `docs`, `admin`, `auth`, `login`, `mail`, `status`, `staging`, `preview` and `pr` followed by digits.
The [RFC 2142 mailbox names](https://www.rfc-editor.org/rfc/rfc2142.html) are reserved too.
Reserve each label that another service uses before you turn on subdomains.

Serve only Hephaestus on workspace hosts.
A page on a workspace host can use the session of the apex.
Thus, never host uploaded HTML, another application, or scripts that a workspace controls there.

A renamed workspace keeps its old slug, which redirects to the new one.
A used slug cannot name another workspace, also after the workspace is deleted.
[ADR 0053](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0053-workspace-addresses-are-a-presentation-origin.md) explains the design, with the session and CSRF rules of the web app.
