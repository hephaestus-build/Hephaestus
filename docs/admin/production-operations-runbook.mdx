# Production operations runbook

This runbook is for the **instance operator**.

1. Before changing state, record the instance URL, Helm release, signed release lock, incident owner, and rollback point.
2. Keep credentials and feedback bodies out of tickets.

:::caution[CAUTION: Before broad or unattended delivery]
The operator must execute and sign off three drills on isolated, representative infrastructure.
The [failed-migration drill](./upgrade#if-migration-fails) is on the Upgrade page.
The broker and un-delivery drills are below.
An operator-owned silent run requires the silent deployment checklist first.
:::

## First response and kill-switch map

1. If external feedback is wrong, immediately turn on silent mode in **Instance administration → Instance settings**.
2. If the control plane is unavailable, block provider egress at the host/network boundary.
3. Apply the same block if a request already in progress may still write.
4. Under either condition, stop all application servers, workers, and active sandboxes.
5. To preserve a recovery point, also stop ingress.

A switch cannot recall a request that a provider already accepted.

### Turn silent mode on, verify it, and turn it off

The authenticated instance-admin API uses `GET /api/admin/settings` and `PATCH /api/admin/settings/silent-mode`.
The UI handles the preconditions below.

1. Turn on silent mode with `{"engaged":true,"reason":"incident reference"}`.
2. Read back `silentModeEngaged=true`.
3. Retain the audit event and current `ETag`.
4. To turn it off, use `{"engaged":false,"reason":"approved release reference"}` with **the current** `If-Match` ETag.
5. If the response is `412`, read again.
6. After a `412`, reassess turning it off.
7. Do not retry turning it off blindly.

`428` means the required precondition is missing.
**Restored settings can contain silent mode off**.
The default does not override an explicit decision to turn silent mode off.
Turning silent mode off affects all workspaces and never flushes suppressed feedback.

## Silent deployment checklist

1. **Contain**. For the running instance, turn on silent mode.
2. For the running instance, read back silent mode.
3. For a clone, use the pre-boot isolation below instead.
4. Record exceptions.
   Zero *content delivery* is not zero network traffic.

5. **Capture rollback**. Stop ingress.
6. Stop application writers, including remote workers and active sandboxes.
7. Save a restorable database backup with matching secrets, configuration, and signed release lock.
8. Verify the archive.
9. Verify the checksum.
10. Verify the off-host copy.
11. Record the recovery point and permitted outage/data loss.

12. **Validate then deploy**. Complete the [staging migration](./upgrade#validate-the-actual-production-data).
13. [Prepare the tested release](./upgrade#upgrade-the-host).
14. Keep `AGENT_ENABLED=false` on server and worker roles.
15. Keep Slack disabled and public ingress blocked.
16. Apply the verified chart with public routes disabled, reviews disabled and Slack disabled.
    If this is a restored database, follow the [restore startup sequence](./kubernetes#restore).

17. Verify migration completion.
18. Before starting `webhook-server` or enabling reviews, read back silent mode.

    Pod readiness alone does not verify the brake.

19. **Prove silence**. After readback, keep silent mode on.
20. Set `AGENT_ENABLED=true` on the submitting server and claiming worker roles.
21. Enable the intended review/Slack settings.
22. Upgrade the affected chart configuration.
23. Keep restore-clone network isolation.
24. Use controlled providers for clone drills.
25. Run bounded reviews on controlled GitHub/GitLab work and Slack conversations for each enabled lane.
26. Inspect practice results and `WITHHELD` / `INSTANCE_SILENCED` outcomes.
27. Correlate provider-side object inventories and egress observations, including retries and edits to existing feedback.
28. For Outline, verify no unplanned document writes or webhook registration.

    Outline is a source integration.

29. **Inspect and decide**. Inspect capture failures, withheld feedback, policy traces, queue age, and spend under small budgets.
30. Record known integration/readiness failures caused by isolation.
31. Remain silent if writes are unexplained, migrations fail, or spend is unaccounted for.
32. If necessary, use recovery below.

33. **Turn off silent mode deliberately**. Only after the rollout gates pass, review all workspace review scope, account consent, Hephaestus settings, and feedback mode.
34. After the rollout gates pass, turn silent mode off with the current ETag.
35. Prefer **Approve first** for a bounded pilot.
36. Prove that old suppressed work stays suppressed.
37. Prove that only a fresh eligible event can deliver.
38. If either check fails, turn silent mode on again immediately.

## Backup, restore and PostgreSQL × JetStream

[Backup & restore](./backup-restore) owns the data inventory and the backup and restore procedures. A dump restores
one snapshot, not an arbitrary point in time. Use **pgBackRest** for scheduled backups and WAL archiving
([backup tooling decision](https://github.com/hephaestus-build/Hephaestus/issues/1370)). Require off-host
backup freshness alerts and a verified restore before unattended delivery.

The chart backup implementation and its schedule are in [Backup and restore on Kubernetes](./kubernetes#backup-and-restore).
The shared redacted backup status required by [Readiness](https://github.com/hephaestus-build/Hephaestus/issues/1547),
[Operations](https://github.com/hephaestus-build/Hephaestus/issues/1387), and
[System Information](https://github.com/hephaestus-build/Hephaestus/issues/1548) does not exist yet.
Those consumers must show **unknown**.
They must not infer health from a configured timer or a passing `pgbackrest verify`.
A passing backup is not a restore result or release gate.
[Application metrics](./observability.mdx#scrape-metrics) do not report backup/WAL freshness or restore-rehearsal outcomes.

Until the status publisher and [operator alert service](https://github.com/hephaestus-build/Hephaestus/issues/1369) exist:

1. Monitor failed systemd units, WAL archive lag, and disk space.
2. Monitor pgBackRest `info`/`verify` and the last actual drill record.
3. Configure host or backup-tool alerts for stale backup/WAL, failed attempts, and expired or failed restore rehearsals.

For backup and recovery:

1. Set explicit RPO/RTO, backup schedule, retention, owner, off-host destination, and restore-test frequency.
2. Monitor the last successful backup/WAL archive and restore drill.
3. Test loss of the primary host.
   On the Helm chart, retrieve the required keys without that host, as [Secret custody](./secret-custody#keep-the-required-keys-outside-the-cluster) describes.
4. Test backup failure alerts.
5. For PITR, validate the base backup.
6. For PITR, validate continuous WAL coverage to the selected timestamp/timeline.
7. Where exact replay is required, include evidence storage.
8. If the backup overlaps a [key rotation](./credential-key-rotation), preserve active **and prior** credential-encryption keys and versions.
9. Disable rotation during recovery.

   :::caution[CAUTION: Broker snapshot consistency]
   Never treat a live filesystem copy as a consistent broker backup.
   Per-stream snapshots are not atomic with each other, PostgreSQL, or external provider writes.
   Preserve them for gap analysis, not automatic replay after PITR.
   :::

10. For incident forensics, take broker-supported snapshots or a cold copy of the stopped JetStream store.
11. Use an authenticated CLI on the isolated broker network.
12. For **each** stream, run the [NATS backup command](https://github.com/nats-io/natscli/blob/main/cli/backup_command.go):

    ```bash
    nats stream backup --check STREAM /restricted/incident/STREAM
    ```

13. Record start/end time, stream sequence, consumer ACK positions, CLI version, and each snapshot's checksum.
14. Encrypt the snapshots.
15. Move them off-host under the database's access and expiry policy.

Snapshots include message payloads and, by default, consumers.

### Pre-boot isolation — mandatory for every restore

The supported self-host clone needs a separate host.
A different Helm release name or namespace alone does not provide isolation.
Silent mode permits model calls and control-plane traffic.
A disabled Hephaestus row alone is never an isolation boundary.

1. Stop ingress, all server/worker replicas, and active sandboxes.
2. Suspend automatic restarts/reconcilers.
3. Use a separate host for the supported self-host clone.
4. Give it a separate database, NATS store, domain, and credentials.
5. Do not connect it to production volumes, NATS, or provider webhooks.
6. Before any application starts, deny external traffic from application **and sandbox** networks.
7. Allow only required isolated database/broker/admin access.
8. Set `AGENT_ENABLED=false` on server/worker roles.
9. Set `HEPHAESTUS_INTEGRATION_SLACK_ENABLED=false` on Slack-capable roles.
10. Withhold SCM write credentials, including app signing keys, PATs, and credentials encrypted **inside the restored database**.

    Removal of environment seeds does not remove database-backed credentials.

11. Keep network denial while inspecting those credentials.
12. Before interactive access, turn off all conversation model rows.
    The restore-clone lockdown does this.
13. Arrange admin authentication under isolation before the drill.
14. If admin authentication is unavailable, stop.
15. Review site values and Secret key names through a protected process. Do not print credential values.
16. Verify the chart renders each value for the role that reads it.
17. Boot only infrastructure.
18. Before any application role, run the [restore-clone lockdown](./kubernetes#isolated-restore-drill) against the recovered database.

    Keep migration and every application role disabled until lockdown completes.
    Application-health inspection needs an operator-owned isolated override.
    The server submits and recovers reviews.
    The worker runs them.

19. Keep `AGENT_ENABLED=false` on server and worker.
20. Before review execution, read back silent mode and the workspace delivery pause.
21. Record provider-readiness failures caused by isolation without restoring live write access.

    Releases before silent mode require the environment, mentor/Slack shutdown, credential withholding, and network barrier throughout.
    These controls permit restore inspection, **not** a full silent review run.

22. Before such a run, upgrade.
23. Before such a silent review run, validate the egress brake.

### Choose the broker recovery strategy before starting consumers

Restoring PostgreSQL to T-1 while JetStream retains T can replay work whose local processing/delivery
records disappeared. Broker publish deduplication and consumer ACKs are **not** external-delivery
idempotency. A provider comment written after T-1 can still exist with no restored ledger entry.

**Default: quarantine and recreate the instance's broker state.**
Accept and record event loss rather than silently replaying a divergent buffer.
The self-host broker publishes no host port.

1. Stop publishers and consumers.
2. Use an authenticated NATS CLI context for the intended instance on its isolated cluster network.
3. Record each stream and consumer's configuration, sequence/ACK positions, and pending counts.
4. Use these commands:

   ```bash
   nats stream report
   nats stream info STREAM
   nats consumer info STREAM CONSUMER
   ```

5. Stop NATS.
6. Identify the **exact** NATS PersistentVolumeClaim through its StatefulSet specification and Helm release labels.
7. Preserve a cold snapshot and configuration in restricted incident storage.

   :::caution[CAUTION: Remove only confirmed instance storage]
   Never delete storage by wildcard or by an unverified name suffix.
   On a shared broker, do not remove the broker volume.
   Have its owner export this instance's streams and consumers first.
   Have the owner delete/recreate only those streams and consumers.
   :::

8. For a dedicated self-host broker, remove only that instance's stopped NATS workload and confirmed PersistentVolumeClaim.
9. For a dedicated self-host broker, recreate NATS with an empty store.
10. Run the isolated database migration first, then start the application server.
11. Turn on silent mode and read it back.
12. Start the isolated webhook role to recreate streams.

    Start it only after the migration Job completes.

13. Keep public ingress blocked.
14. Verify that server consumers attach after streams exist.
15. If necessary, restart only the isolated server.
16. Before provider ingress returns, check fresh stream/consumer positions and no old pending deliveries.
17. Keep silent mode on during reconciliation.
18. Inventory the gap.
19. Run supported provider reconciliation within its configured monitoring window.
20. Observe that reconciliation.
21. Explicitly record unrecoverable intervals.

Reconciliation can restore current source state, **not all historical events or deleted sources**.
GitHub, GitLab, Slack, and Outline have different recovery limits.

**Replay is an exception requiring a separate drill.**
The [send recovery contract](./practice-review-operations#running-instance) covers interrupted writes.
It does not establish that identities derived from lost jobs survive a database rewind.

1. Preserve the retained stream.
2. Record the exact consumer start sequence/time.
3. Recreate only the chosen consumer under isolation.
4. Do not merely reset an ACK cursor and reconnect production writers.
5. Exercise provider-marker reconciliation with the specific target release and all enabled destinations.

   Do not release replay externally under any of these conditions:

   - A stable identity cannot be reconstructed.
   - Provider lookup is inconclusive.
   - Any live copy is unaccounted for.

6. Under those conditions, leave delivery suppressed.
7. Under those same conditions, reconcile manually.

**Drill**

1. Create a controlled delivery after the chosen restore point.
2. Retain newer broker events.
3. Restore PostgreSQL.
4. Exercise the chosen reset/replay strategy.
5. Include duplicate delivery and provider success with lost local acknowledgment.
6. Include a partially written summary/inline package and a provider lookup outage.
7. Verify no duplicate provider objects.
8. Verify no historical suppressed work was released.
9. Verify the recorded data-loss window.
10. Before release, also check restored PostgreSQL jobs/proposals and reviews created by source sync.

An empty broker does not remove those jobs/proposals or prevent source sync from creating new reviews.

## Access and erasure for one person

Use **Instance administration → Person data**.
Only an instance admin with a recent sign-in can create a preview, download an export, or start erasure.
Requests and replies go through the privacy contact in the instance notice.
This page is not a data-subject request portal.

1. Verify the requester's identity and authority under your privacy procedure.
2. Enter the account ID or exact provider instance and provider user ID.
3. For Slack, also enter the native Slack workspace ID.
4. Add all verified identities that belong to the request.
5. Do not match names, logins, or email addresses.

   A conflicting account link stops resolution.
   Cached Slack-to-SCM actor stamps are not identity proof.
   The page does not infer an identity from those stamps.

6. Before another preview, repair the verified link or correct the supplied exact IDs.
7. If collected work has a cached actor stamp, include verified exact keys for both providers.
8. If stamped work has a conflicting association, alternatively repair that association.
9. Select **Preview data**.
10. Check resolved identities and store counts.

    Stores with no rows appear under **stores hold no rows**.
    The preview expires after 48 hours.
    Export and erasure use its frozen row keys.
    Changed data needs a new preview, not an SQL supplement.

11. For an access request, select **Download JSON export**.
12. For an access request, transfer the file securely.
13. For an access request, handle the file as personal data.

    The export has a schema version and a `stores` object keyed by store name.
    It excludes credentials and session capabilities.
    The completed erasure receipt is not an export archive.

14. For erasure, follow [Un-deliver external feedback, then purge](#un-deliver-external-feedback-then-purge) for each provider locator in the preview.
15. For erasure of an unconfirmed write without a comment ID, inspect the linked reviewed work for summary and inline feedback.
16. For that erasure inspection, include preserved discussions.

    The application does not automatically delete provider comments already posted.

17. For erasure, select **Erase data…**.
18. For erasure, in the dialog, confirm removal of the listed provider copies.
19. For erasure, type **ERASE**.
20. For erasure, select **Erase data**.
21. For erasure, keep the request URL for access after a reload.

    The page follows the job until it finishes.
    The job records progress one store at a time.
    Worker evidence owners must acknowledge removal of each attempt and copy before database evidence clears.
    An unavailable owner is a failure, not proof of erasure.

22. For erasure, if the job stops, correct the operational failure.
23. For erasure, after correcting a stopped job's failure, select **Resume erasure…** on the same request.
24. For erasure, do not create a second request to bypass a failed job.
25. For erasure, before replying, check **Erasure complete** and the per-store receipt.

The receipt retains the acting instance admin, operational state, times, and counts.
It retains neither erased content nor selected subject keys.
Completion clears working request keys.
Expiry clears abandoned previews.
Failed jobs retain the working keys needed to resume.

Review-package provider requests hold capture admission until their outcomes have been recorded. Erasure cannot
pass an in-flight provider request. A queued call cannot recreate feedback after its review has
entered erasure or its job capability has been revoked.

The preview freezes delivery facts, not only row IDs.
If a provider write starts or its result changes after inspection, export and erasure reject the stale preview.
An unconfirmed write or a migrated comment without an exact inspection locator stops the request and identifies its send or review.
The system does not treat it as never delivered.

1. If the preview is stale, create a new preview before confirming removal again.
2. If the preview is stale, inspect the current locators before confirming removal again.

   Practice results and feedback belong to the developer they describe.
   The person's own results and feedback are exported and erased, including feedback copies in another person's conversation.
   Another developer's results and feedback remain, even when the person commented on that work.
   Instead, erasure removes the review's captured inputs and Hephaestus's hidden memory in affected workspaces.

   Exact provider-key suppression is separate from the audit receipt.
   It prevents further processing of the erased identity.
   It is not a reversible workspace consent choice.
   Provider sync can still mirror upstream records.

3. Tell the requester what remains outside the active application's control:
   - Original provider records.
   - Provider comments not yet removed.
   - Delivered mailbox copies.
   - Third-party retention and [backups](./backup-restore).
4. After a restore, follow isolation and reconciliation above before processing resumes.
5. Do not claim selective deletion in backups.

The [personal-data map](./dsms/personal-data-map) owns store-specific export, removal and residual
retention. The operator's [record of processing](./dsms/record-of-processing.md) owns the legal record, and [Data retention](./data-retention) the periods.

### Exact source bindings for person requests

Connected GitHub, GitLab, Slack, and Outline sources appear in the person-request provider list, even for a person without an account.
A connected source cannot change to a different provider instance.
Equivalent host case and default-port spellings remain the same instance and keep processing controls.
The upgrade registers existing source instances.
Names, logins, email addresses, and document text are not binding proof.

1. Use the source's exact native user ID.
2. For Slack, also use the native workspace ID.
3. To change the provider instance, create a new connection.
4. If upgrade reports mirrored Outline documents without a provider instance, restore verified state with that exact binding before upgrading.

Visible document content remains.

### An evidence store is offline

Person erasure records a deletion request for each mounted store that captured the person's data.
The owning worker cancels the affected attempt and removes the whole job folder, including failed
rendering folders and retries. It confirms deletion only after the runtime releases its folder.
A server that has no such folder cannot confirm deletion for another worker's volume.

If the mounted owner does not confirm deletion, the request fails and can resume.
The store identity stays on the volume across a worker restart.

1. Restore the same worker volume.
2. Let its deletion poll run.
3. Resume the request in instance administration.
4. Do not replace the volume with an empty one and report the old copy as erased.
5. Keep a disconnected old volume under access controls until removal of its copy and confirmation of deletion.

This does not change the normal job-folder contract:

- Admission removes the admitted folder.
- Ended attempts have a one-hour grace period.
- Restart cleanup removes old attempts.

### Git history and repository owners

The JSON export's `git_repository_history` section lists repositories whose history may contain the person's commits.
It uses exact stored provider identities and contributor references.
The list does not prove each author string in raw Git history.
Some Git attribution has no native provider person ID.

1. Do not infer ownership from names, logins, or email addresses.

   Raw Git objects in mirrors and job folders cache the upstream repository controlled by the workspace's organization.
   Hephaestus does not rewrite them or refuse capture.
   A rewrite changes commit IDs and breaks citations.
   A later fetch reverses the rewrite.
   Sync can mirror records that still exist upstream.

2. If Git authorship must be erased, ask the source repository's owner to remove it there.
3. Ask that owner to apply the repository retention procedure.

Hephaestus erases what it derives and records about the person.
The erasure job cancels affected active review attempts.
It removes their evidence folders through the evidence-erasure hook.
It must not report completion without proof of removal for affected copies.
No unfiltered Git object archive enters a person export.

Normal job-folder retention stays unchanged:

- Admission removes the verified folder.
- Ended attempts have a one-hour cleanup grace.
- Restart cleanup removes abandoned folders.

## Un-deliver external feedback, then purge

Deleting in-app data does not delete a provider comment. If external copies must be scrubbed,
**complete un-deliver before workspace purge, disconnect or person erasure removes their locator records**.

1. Turn on silent mode.
2. Stop active writers/sandboxes.
3. Preserve their send state.
4. Pause sending for the affected workspace.
   This prevents content recreation when silent mode is later turned off.
5. Locate the piece of feedback from the workspace review trace.
6. With authorized read-only database access, inventory **all** copies, not only the summary.
7. Run the query below with `psql` variables set to verified workspace and feedback IDs.

   The query deliberately omits bodies.

   ```sql
   SELECT f.id, f.review_id, f.item_id, f.destination,
          f.state, f.replaces_id, p.id AS copy_id,
          p.kind, p.state AS copy_state, p.write_started_at, p.write_marker,
          p.external_ref, p.external_url, p.mentor_entry_id, p.mentor_turn_id,
          p.path, p.start_line, p.end_line, p.side, p.posted_at
   FROM feedback f
   LEFT JOIN feedback_copy p
     ON p.feedback_id = f.id AND p.workspace_id = f.workspace_id
   WHERE f.workspace_id = :'workspace_id'::bigint
     AND f.id = :'feedback_id'::uuid;
   ```

8. For conversation copies, follow `mentor_entry_id` to the `mentor_entry` row of the Hephaestus message that showed the feedback.

   `mentor_turn_id` is the turn that claimed the feedback.
   A copy with `mentor_turn_id` and no `mentor_entry_id` has no stored Hephaestus message that showed it.
   For that copy, find the turn's question as described below.
   A copy from before the upgrade to one conversation per developer has neither value.

   Read the message's `conversation_id`, `turn_id`, and `surface`.
   A message with the surface `APP` has no Slack copy.
   For a thread, follow `mentor_conversation.parent_conversation_id` to the main conversation.
   The main conversation's `slack_team_id`, `slack_user_id`, and `slack_channel_id` identify the Slack DM.

   One Slack message shows all Hephaestus messages of a turn.
   The question of the turn records the state of that Slack reply: it is the `mentor_entry` row with the same `turn_id` and the kind `USER`.
   Read its `slack_delivery` and `slack_stream_ts`.
   Then read `slack_ts` of the last `HEPH` row of the turn.

   If `slack_delivery` is `DELIVERED`, that `slack_ts` is the `ts` of the Slack reply.
   A reply in a Slack thread is a stream, and its `ts` is also in `slack_stream_ts`.
   An `UNCERTAIN` or `PENDING` reply can have a Slack copy without a recorded `slack_ts`.
   A `FAILED` reply in a Slack thread can show part of a stream.
   Thus, the ledger query alone cannot establish complete Slack removal.

9. Use the provider's paginated [conversation replies](https://docs.slack.dev/reference/methods/conversations.replies/) API to find each exact bot-authored reply and its `ts`.
10. If provider inventory is inaccessible or ambiguous, record the gap.
11. If provider inventory is inaccessible or ambiguous, keep removal incomplete.
12. Follow replacement history.
13. Check the `feedback_send` row for the feedback: `action`, `state`, `attempts`, and `last_error`.
14. Treat each copy in `WRITE_STARTED` state and each `UNCERTAIN` send as a possible provider object, even without an `external_ref`.
    If the copy has a `write_marker`, search the provider for it. The application appends it to the posted body.
15. Before deletion, verify repository/project, item, provider account, author, and content against the provider.
16. Never infer an API object type from a numeric ID alone.
17. Use a separate authorized operator session to delete each confirmed provider object.
18. Do not turn off application silent mode for cleanup.
19. Select the endpoint for the actual copy:

    | Copy                                         | Provider API                                                                                                                                                                        |
    | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | GitHub issue or pull-request summary comment | `DELETE /repos/{owner}/{repo}/issues/comments/{comment_id}` — [issue comments](https://docs.github.com/en/rest/issues/comments#delete-an-issue-comment)                             |
    | GitHub inline review comment                 | `DELETE /repos/{owner}/{repo}/pulls/comments/{comment_id}` — [review comments](https://docs.github.com/en/rest/pulls/comments#delete-a-review-comment-for-a-pull-request)           |
    | GitLab issue or merge-request note           | `DELETE /projects/:id/issues/:issue_iid/notes/:note_id` or `DELETE /projects/:id/merge_requests/:merge_request_iid/notes/:note_id` — [notes](https://docs.gitlab.com/api/notes/)    |
    | GitLab discussion/diff note                  | Use its discussion and note IDs — [discussions](https://docs.gitlab.com/api/discussions/#delete-a-merge-request-discussion-note)                                                    |
    | Slack feedback or Hephaestus answer                | `chat.delete` with the exact channel and message `ts`, using a token permitted to delete that author's message — [Slack API](https://docs.slack.dev/reference/methods/chat.delete/) |
    | Outline                                      | No current external feedback destination. Do not delete source documents as a substitute for removing feedback                                                                      |

    A submitted GitHub review/approval is not an issue comment.
    A `404` can mean hidden/inaccessible, not deleted.
    A timeout is ambiguous.
    External deletion does **not** mark the immutable ledger as retracted.
    No admin removal API exists.
    Complete in-product retraction requires the [retraction workflow](https://github.com/hephaestus-build/Hephaestus/issues/1507).

20. For a submitted GitHub review/approval, use the provider-supported review dismissal/remediation flow.
21. Report any retained content.
22. For all providers, obey rate limits.
23. Verify the response.
    Slack requires `ok: true`.
24. Read back absence with credentials known to have access.
25. After a timeout, read before retrying.
26. Record each ledger ID/provider reference, deletion result, verification time, and operator in the restricted incident record.
27. Include partial failures.
28. Do not substitute `REPLACED`, `REJECTED`, recipient resolution, or edited write fences for retraction.
29. Before delivery resumes, verify no live copies or unresolved sends can recreate the content.
30. If you cannot prove this, keep the workspace paused.
31. Only then purge, if requested.
32. Retain minimal lawful removal evidence under the incident retention policy.

Deletion cannot recall email notifications, screenshots, or third-party archives.

**Drill**

1. Remove a summary, inline comments, and a Slack reply on controlled fixtures.
2. Include permission denial and timeout recovery.
3. Run the inventory again.
4. Exercise restart/retry under containment.
5. Verify that the incident record matches provider state.

## Alert response

Use [Scrape metrics](./observability.mdx#scrape-metrics) for the private endpoint.
[Alert rules](./observability.mdx#alert-rules) gives the shipped rules and their thresholds.
Use the instrumented metrics in [Practice review operations](./practice-review-operations#queue-health)
and [Webhook ingestion operations](./webhook-ingestion-operations). Configure thresholds against your
traffic and recovery objectives. Assign an owner and test the alert delivery route.
The signal names the alerts of the shipped rules that it answers.

| Poison events / repeated consumer failures (`HephaestusConsumerPoison`) | Preserve stream sequence, kind, reason and delivery count, not raw payloads in logs. Current poison handling **ACKs** at the retry limit. It does not move data to a durable DLQ. NATS maximum-delivery advisories are not a DLQ either. Recover the retained event before retention expires if authorized. Never raise the retry cap to hide a poison loop. | Reproduce with a sanitized fixture, fix the cause, replay one controlled event under silence, then reconcile the bounded gap. ## Model pricing update

Prices are runtime catalog data, not a source-code pricing table.
Instance prices are superseded with history.
Workspace-owned models use inline prices.
Missing cache rates can leave the entire call unpriced.

1. Follow [AI provider pricing](./ai-providers#4-pricing-a-model).
2. Record the vendor/contract rate source, upstream model ID, currency, effective date, and all token buckets.
3. Update the instance catalog or workspace-owned catalog as applicable.
4. Confirm **USD per million tokens**, including cache read/write rates.
5. Never mark an unknown model `NO_CHARGE` to bypass a refused call.
6. For a new/unpriced model, create it disabled.
7. For a new/unpriced model, price it.
8. For a new/unpriced model, enable it.
9. For a new/unpriced model, assign it to a purpose.
10. For repricing, use the catalog UI.
11. Verify that historical usage was not billed again.
12. Verify that a controlled new call uses the intended rate snapshot.
13. Compare a hand-calculated token-cost example and provider billing.
14. If the rate is wrong, correct the current catalog.
15. If the rate is wrong, keep affected models disabled.
16. If the rate is wrong, document the accounting gap instead of rewriting historical usage.

4. Take only final backups required by retention.
5. Deregister webhooks.

13. Verify that provider subscriptions and recurring AI or storage charges have stopped.
14. Record retained legal evidence and its deletion owner/date.

## Email delivery operations

`SENT` means relay acceptance, not inbox delivery.
SMTP health must not be a liveness or readiness dependency.
A broken email path cannot reliably report its own failure by email.
Sustained `unavailable`, `rate_limited`, `rejected`, or `expired` outcomes require investigation.

1. Use **Instance settings → Email → Send test email** to distinguish missing configuration, silent mode, exhausted capacity, and relay failures.
2. For application, database, NATS, scheduler, or SMTP outages, page the operator through an **external** monitoring channel.
3. Monitor the `notification.email.delivery` counter by bounded `kind` and `outcome`.
4. Inspect the publication backlog without selecting `serialized_event`:

   ```sql
   SELECT status, count(*) AS publications, min(publication_date) AS oldest_publication
   FROM event_publication
   GROUP BY status;
   ```

   Retry batches prioritize publications least recently retried.
   One failed batch therefore does not indefinitely block later work.
   This fairness does not promise delivery within five minutes.
   Capacity limits and backlog size still apply.
   Each listener rechecks current eligibility.
   silent mode completes withheld mail rather than retaining a flood for later.

5. Alert when pending/failed publications age beyond the expected five-minute retry interval.
6. Investigate before notification expiry.
7. Use a separate database-monitoring identity with least privilege.
8. Do not replay a backlog blindly.

Hephaestus records synchronous SMTP rejection.
It does **not** claim to ingest asynchronous delivery-status notifications or provider complaints.

Before inviting a large audience:

1. Confirm the relay's quota and SPF/DKIM/DMARC alignment.
2. Confirm the monitored reply address and bounce/complaint handling.
3. Use a relay that suppresses hard bounces and complaints.
4. Monitor that suppression list.
5. Keep optional bulk mail disabled until this operational path works.
6. Never re-enable a suppressed address without resolving the reason.

See [email configuration](./production-setup#email).

Unsubscribe URLs contain narrowly scoped bearer capabilities.
A local Mailpit MIME test alone cannot prove DNS or DKIM configuration.

1. Redact `/notifications/unsubscribe/*` in reverse-proxy access logs.
2. Never retain the public confirmation page's `token` query.
3. With a real message, validate the externally reachable HTTPS POST path.
4. Validate DKIM coverage of both unsubscribe headers.

Workspace connection alerts cover recorded Slack credential revocation and verified GitHub app
suspension, with paired recovery. Intentional disconnection, routine token refresh, and first-time
connection are not incidents. GitLab and Outline do not yet expose equivalent durable incident
signals. Monitor their existing health/configuration surfaces rather than assuming email coverage.
