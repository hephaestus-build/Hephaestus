Each alert that the chart ships links to this page.
Search the page for the name of the alert.
Before you act, collect the labels of the alert, the release version, and the server log from the time of the alert.
[Find the records of one request](./monitoring#find-the-records-of-one-request) shows how to read the log.
[Alert rules](./alert-rules.md) gives the threshold, the window and the severity of each alert.

Do not print Secret objects or credentials while you diagnose.
Do not change application rows in the database unless a row below tells you to.

If the alert shows wrong feedback or an incident in progress, first [contain the incident](./contain-an-incident).

## Alert response

### Monitoring and the server

| Alert | Cause | Action | Check |
| --- | --- | --- | --- |
| `HephaestusWatchdog` | This alert always fires while the monitoring works. | Route it to an outside dead-man check, not to a person. When that check reports silence, check Alertmanager and its receiver first. Then check vmalert and its rule file, then VictoriaMetrics and its scrape. | The outside check receives the alert again. |
| `HephaestusMetricsUnavailable` | The scraper cannot read a target. The Pod does not run or is not ready, or the network policy refuses the scraper. A server that stops during its startup also fires it. | Check that the Pod runs and is ready, and that `networkPolicy.metrics` names the scraper. For a server that stops during startup, read its log. `evidence.spool.cleanup.failed` means that the evidence volume needs access or space. `person_data.recovery.failed` means that the erasure manifest stops the start: see [Reapply erasures after a restore](./erasure-recovery). | The `up` series of the target is 1. While the target is down, its other alerts cannot fire. |
| `HephaestusServerDown` | No server replica is available. The API is down, and every provider delivery fails. It also fires during an [erasure recovery](./erasure-recovery) until the recovery Pod is ready. | Read the events, the readiness probe and the log of the server Pods. A Pod that waits for the schema needs its migration Job ([A server stays unready](./troubleshooting#a-server-stays-unready)). | The server Deployment has an available replica, and `webhook.publish` counts successes. The first redelivery run of a ready server recovers the failed GitHub deliveries of the past 71 hours. Other providers need the [reconciliation sync](./webhook-ingestion-operations#which-providers-deliver-again). |
| `HephaestusServerUnready` | One server replica stayed unavailable for 15 minutes. The other replicas serve. | Read the events and the log of the unavailable Pod. If it does not recover, delete the Pod. | The server Deployment has no unavailable replica. |
| `HephaestusContainerOomKilled` | The kernel killed a container at its memory limit. The `pod` and `container` labels name it. The alert reads every namespace. | Compare the limit with [Sizing](./sizing) and with the memory use before the kill. For the server or PostgreSQL, raise its `resources`. For a review sandbox, raise `sandbox.templates.review.resources`. The job lease and the inbox lease recover the lost work. | The container runs a full cycle of its work with no new kill. |
| `HephaestusSyncNotificationsFailing` | The server cannot publish or receive its sync notifications through PostgreSQL. Clients fall back to polling. | Check the PostgreSQL connection. Read the server log for `Sync notifications disconnected` or `Sync notification publish failed`. During a rolling upgrade, check the [connection budget](./sizing#database-connections). | No notification failure occurs for 15 minutes. |
| `HephaestusTenancyViolations` | A database statement did not stay in one workspace. On the chart, the check refuses the statement, so the request or job that ran it failed. | Read the server log line `Tenancy violation (throw)`. It names the tables and the start of the statement. If the violations started with an upgrade, [roll back](./upgrade#rollback). Report the statement and its stack trace to the maintainers. | `tenancy_violation_total` stops increasing, and the failed path answers again. |
| `HephaestusBrowserFaultsRising` | Browsers report failures of one kind. | In the log store, query `event.name` `browser.fault` with the `kind` of the alert. Group by `browser.page`, `error.type` and `browser.release`. A `browser.release` that differs from the server's `service.version` is a tab with an older build. Report `browser.fault.frames` and `browser.release` to the maintainers. Reports from readers who are not signed in can be forged. | The rate of that kind falls after the fix. |

### Database

| Alert | Cause | Action | Check |
| --- | --- | --- | --- |
| `HephaestusDatabaseConnectionTimeouts` | The server could not get a database connection in time, so requests or jobs failed. | Check PostgreSQL first: a restart or a maintenance phase closes connections. Compare `hikaricp_connections_active` with `hikaricp_connections_max`. A pool that stays full points to long transactions in `pg_stat_activity`. Raise `server.databasePool.maximumPoolSize` only within the [connection budget](./sizing#database-connections). | No timeout for 15 minutes. |
| `HephaestusDatabasePoolSlow` | Requests wait for a connection before they run. | Read `hikaricp_connections_pending`. Read the top statements by total time in `pg_stat_statements` ([Read database statement statistics](./monitoring#read-database-statement-statistics)). Look for long transactions in `pg_stat_activity`. | 95 % of the acquires take less than 50 ms for 30 minutes. |
| `HephaestusDatabaseDeadlocks` | PostgreSQL cancelled one transaction of a deadlock. Two code paths lock the same rows in a different order. | Find the PostgreSQL log line `deadlock detected`. It names the processes and the relation. Report the two statements, the time and the relation to the maintainers. | No deadlock in 15 minutes. |
| `HephaestusDatabaseTransactionOpenLong` | A transaction is open for more than 5 minutes. A migration during an upgrade can take this long. | Find it: `SELECT pid, state, now() - xact_start AS open_for, application_name FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 5`. An `idle in transaction` session that is not a migration is a leak. End it with `SELECT pg_terminate_backend(<pid>)`, and report its `application_name`. | No transaction is open for more than 5 minutes. |
| `HephaestusDatabaseDeadRowsHigh` | Autovacuum does not keep up with the table in `relname`. | First clear a long-open transaction, because it holds every vacuum back. Read `last_autovacuum` in `pg_stat_user_tables` for the table. Run `VACUUM (VERBOSE) <table>` once. | The dead rows of the table are below 20 % of its live rows. |
| `HephaestusDatabaseTransactionIdAgeHigh` | The oldest unfrozen transaction ID is more than 1 billion old. At about 2 billion, PostgreSQL stops all writes. | Act at once. Clear each long-open transaction and each prepared transaction (`pg_prepared_xacts`). Run `VACUUM (FREEZE, VERBOSE)` on the tables with the largest `age(relfrozenxid)` in `pg_class`. | `age(datfrozenxid)` of the database is below 1 billion. |
| `HephaestusPostgresVolumeFilling` | The PostgreSQL volume has less than 15 % free space (warning) or less than 5 % (critical). A failed WAL archive keeps the WAL on the volume. | Check the WAL archive first: read the PostgreSQL log for `archive-push` errors and the log of the latest backup Job. Do not delete files from the WAL directory. Expand the volume only after the archive works, and only if its storage class permits expansion. | The archive pushes again, free space rises, and a new backup succeeds. |
| `HephaestusWalArchiveFailing` | PostgreSQL cannot archive its WAL, or the server cannot read the state of the archiver. | Read the PostgreSQL log for `archive-push` errors. Check the credentials, the reachability and the free space of the bucket. After a change of the bucket credentials, restart PostgreSQL. If `database_wal_archive_sample_failures_total` increases, check the database connection of the server. Do not turn `archive_mode` off. | `database_wal_archive_failing` is 0, and a new backup succeeds. Point-in-time recovery has a gap from the first failure until the archive works again. |
| `HephaestusBackupStale` | No PostgreSQL backup completed in the last 30 hours. A failed WAL archive also stops the backups. | Read the log of the latest backup Job. Check the credentials of the destination, the disk and the WAL archive. Keep the last good backup. Escalate when the gap reaches your recovery point objective. | A new off-host backup completes, and an [isolated restore](./backup-restore#isolated-restore-drill) of it succeeds. |

### Provider events and webhooks

[Webhook ingestion operations](./webhook-ingestion-operations) gives the meters that these alerts read.

| Alert | Cause | Action | Check |
| --- | --- | --- | --- |
| `HephaestusWebhookPublishFailing` | The server cannot store deliveries in the provider event inbox in PostgreSQL. Each failure answers `503`. | Check PostgreSQL first: connections, locks and volume space. Read the server log records with `event.name=webhook.publish.failed`. The message names the exception class. Do not restart the server to clear the alert. | `webhook.publish` counts no new failure. Recover the failed deliveries, as [Which providers deliver again](./webhook-ingestion-operations#which-providers-deliver-again) describes. |
| `HephaestusWebhookReceiverBusy` | Large deliveries fill the memory that the receiver holds for bodies, so it answers `503` with `Retry-After`. | Check database latency first, because a slow inbox write holds each delivery longer. If the database is healthy, raise `server.resources`. | No new `busy` refusal. Redeliver the refused GitHub deliveries in the App settings. |
| `HephaestusWebhookEventsUnrecovered` | GitHub events failed all six delivery attempts, so Hephaestus did not receive them. | Fix the cause of the failed deliveries first, usually `HephaestusWebhookPublishFailing` or `HephaestusServerDown`. Redeliver older deliveries under **Advanced → Recent Deliveries** of the GitHub App, within three days. | `github.webhook.unrecovered` returns to 0. After three days, only the reconciliation sync recovers the effect. |
| `HephaestusWebhookRedeliveryNotRunning` | GitHub refuses the redelivery requests, or the server cannot read the deliveries of the GitHub App. | Check that the App ID and the private key of the GitHub App are current, and that the App can read its webhook deliveries. Read the server log for the refused requests. | `github.webhook.redelivery` reports no `refused` or `unavailable` outcome for 30 minutes ([Failed GitHub deliveries](./webhook-ingestion-operations#failed-github-deliveries)). |
| `HephaestusWebhookRedeliveryTruncated` | Redelivery runs read only part of the deliveries of the App, so older failed events can leave the three-day window. | Check `HephaestusWebhookEventsUnrecovered`. Fix the cause of the failed deliveries first. | Runs stop adding to `github.webhook.redelivery` with `outcome=truncated`, and `github.webhook.unrecovered` is 0. |
| `HephaestusWebhookRedeliveriesRequested` | GitHub recorded no successful delivery for more than 5 % of the deliveries. The cause can be before the server: the Gateway, its timeout, or a server that is not ready. | Read the status of the failed deliveries under **Advanced → Recent Deliveries** of the GitHub App. Check the readiness of the server and the `webhook.publish` failures. | `github.webhook.redelivery` with `outcome=requested` stops increasing. |
| `HephaestusProviderEventsWaiting` | The oldest due event of a provider waited more than 5 minutes. No server claims, or a handler holds the order of a resource. The events of a suspended workspace also wait. | Compare `integration_message_process_duration_seconds` with the event rate. Slow handling points to the database or the provider API. If handling is fast, check that the servers run and are ready, and that `server.inboxClaimers` is above 0. A long `LEASED` backlog points to a handler that holds the order of its resource. | `integration_consumer_oldest_due_seconds` falls below 5 minutes. |
| `HephaestusEventsDelayed` | More than 10 % of the events of a provider waited over 5 minutes. | Do the action of `HephaestusProviderEventsWaiting`. | Under 10 % of `integration_message_lag_seconds` is over 5 minutes. |
| `HephaestusConsumerRetryStalled` | Events retry for 15 minutes. A provider API or the database fails, or a workspace operation or a person erasure holds the lock that the handler needs. | If `integration_message_process_duration_seconds` with `outcome="retried"` rises, inspect the active database transactions and locks. Check for an active erasure before you change anything. Otherwise read the `kind`, the error class and the attempt count in the server log. Do not read raw payloads. | The retries stop, and `integration_consumer_oldest_due_seconds` falls. |
| `HephaestusConsumerPoison` | An event became a dead letter: a parsing failure, or an unknown failure after 10 attempts. It keeps its payload for replay. | Read the `kind`, the error class and `error.root_type` in the server log. Fix the cause. Then [replay one dead letter](./webhook-replay), and the rest after it succeeds. | The replayed events leave the dead-letter list. |
| `HephaestusConsumerHandlerTimedOut` | One event took longer than the handler timeout of 30 minutes. A provider or database call that never answers is the usual cause. | Read the `integration.message.timed_out` log record. It names the route, the workspace, the delivery and the timeout. If `integration.handler_stopped` is `false`, the server broke its liveness, so Kubernetes restarted the Pod. The event returns to the inbox and retries. | Fix the call that hangs. After the retry limit, the event is a dead letter with the error `HandlerTimeoutException`: [replay it](./webhook-replay) after the fix. |
| `HephaestusProviderEventBacklogUnsampled` | The server cannot read the inbox backlog. The backlog gauges show their last values. | Read the server log for `provider_event.backlog.sampler_failed` and its `error.type`. Check the database connection. | `integration_consumer_backlog_sampler_failures_total` stops increasing. |
| `HephaestusInboxRetentionFailing` | The hourly cleanup of handled events and dead letters failed more than once in 24 hours. Ingestion continues. | Read the server log for `provider_event.retention_failed` and its `error.type`. Check the database connection, locks and permissions. | The next hourly pass succeeds, and the counter stops increasing. |
| `HephaestusEventPublicationsOverdue` | Durable server work, such as an email or an account export, stayed incomplete for more than an hour. The server retries it every five minutes. The `listener` label names the work. | Search the server log for the error of that listener, and fix its cause, for example the mail server or a missing connection. For `GitLabConnectionStateListener.onDeactivated`, check the GitLab token. If the token cannot delete the hook, a GitLab group owner removes it. Then reconnect with a valid token, or disconnect. Do not delete rows from `event_publication`. | `event_publications_overdue` for that listener returns to 0. |
| `HephaestusCommitIdentityResolutionStalled` | Commit link correction made no progress for 6 hours. No provider answers. | Read `commit_identity_resolutions_total` by `outcome`. No `resolved` with a growing `retry` means no answer: check the connection that monitors the repository and the rate limit of the provider. To stop the job, set `config.commitIdentityResolutionEnabled` to `false`. | `resolved` or `no_account` outcomes increase again. |
| `HephaestusCommitIdentityResolutionUnanswered` | More emails used their 5 attempts than the provider answered in 6 hours. Near the end of a run, a few unanswered emails also fire it. | Read the `Commit identity correction failed` log for the queue ID and the cause. A missing answer changes no link. | After the fix, [ask again](./correct-commit-links#ask-again-after-a-provider-outage). |
| `HephaestusProviderRemovalNeedsConfirmation` | A provider removal or authorization stayed unresolved for an hour. An uncertain Slack exchange can also need it. | Open **Instance administration → Provider removals**. Restore the authorization, or confirm out of band that the old resource is gone. Then release the block, as [Confirm a provider removal](./integrations#confirm-a-provider-removal) describes. | The open count falls. |

### Practice reviews and sandboxes

| Alert | Cause | Action | Check |
| --- | --- | --- | --- |
| `HephaestusAgentQueueStalled` | A run that can start waited for more than one hour. The alert names the `band` that waits. | Read `agent_run_runs` by `state` and `hold_reason`: due, held (`budget`, `sandbox_room`) and leased runs have different causes. Check that `sandbox.enabled` is `true` and that the servers run. Check the sandbox quota, the model assignments, the database and the provider. Do not delete jobs or reset leases. | `agent_run_oldest_due_age_seconds` falls, and new work completes. |
| `HephaestusInteractiveRunWaiting` | A run of the interactive band, such as a conversation turn, can start and no server claimed it for more than a minute. A turn that no server starts within 3 minutes ends as not started, and the person sees that the system is busy. | Check that a server runs and has sandbox room: `agent_run_runs` with `band="interactive"` shows queued and leased runs, and `agent_run_due` shows how many wait. Check `agent_sandbox_dispatch_failure_total`, the sandbox quota and the model pool waits (`llm_pool_permit_wait_seconds`). A workspace that is suspended or on a hold does not count as due. | `agent_run_oldest_due_age_seconds{band="interactive"}` stays under a minute, and new turns start. |
| `HephaestusAgentRunsUnsampled` | A server cannot read the run gauges. They keep their last values, so a stalled queue does not fire `HephaestusAgentQueueStalled` or `HephaestusInteractiveRunWaiting`. | Read the server log for `agent.run.sampler_failed` and its `error.type`. Check the database connection. | `agent_run_sampler_failure_total` stops increasing. |
| `HephaestusAgentJobsFailing` | At least three agent jobs failed or timed out in one hour. | Read `agent.job.terminal` in the server log. Check the sandboxes, the model provider and the database. Do not delete jobs or reset leases. | New jobs complete. |
| `HephaestusReviewSandboxFailing` | Review sandboxes failed to start, initialize or finish. | Read the server log for the sandbox failure and the exit of the initializer. Check the quota and the events of the sandbox namespace, the image pull of the agent image, and the nodes. Do not raise the retry cap. | `agent.job.infra.retry.requeued` with `cause=sandbox` stops increasing. |
| `HephaestusReviewUnreachable` | Review sandboxes failed to reach the server, or every model call went unanswered. | For `server_unreachable`, check the network policies of the sandbox namespace and the sandbox gateway port of the server. For `provider_unreachable`, check the status of the provider and the egress of the server: `networkPolicy.externalEgress`, `networkPolicy.modelEndpoints` or `networkPolicy.modelGatewayPorts`. | The retries with that cause stop increasing, and reviews complete. |
| `HephaestusReviewPreparationFailing` | Review attempts fail before their sandbox starts. | Read the server log line `Review preparation failed`. It names the stage, the kind and the reason. Check the provider sync of the reviewed sources, and the database. | The retries with `cause=preparation` stop increasing. |
| `HephaestusReviewServerError` | The server answered the results of a review with its own error. | Read the server log line `The server refused a review's results` and the error log of the server at the same time. Report the exception to the maintainers. Do not raise the retry cap: another attempt meets the same error. | No new count of `agent_job_server_error_total`. |
| `HephaestusReviewHolderLost` | Servers stopped during each attempt of a review, so the review failed. | Find why servers stop during attempts: out-of-memory kills, evictions, lost nodes, or drains that end before the attempt. Compare the server restarts with the attempts of the review. | Servers run without restarts, and no review fails this way. |
| `HephaestusReviewFeedbackUnconfirmed` | Every attempt ended before it confirmed where the feedback went, so the review closed as Partial. It keeps its results. | Do the action of `HephaestusReviewHolderLost`. | No review closes with `COMPOSITION_UNCONFIRMED`. |
| `HephaestusReviewStageSlow` | One stage of review attempts ran past its bound: 30 minutes for `sandbox`, 10 minutes for the others. The `stage` label names it. | For `capture`, check the provider sync and its rate limits. For `sandbox`, check the model waits and the review width. For `composition`, check the model pool and the sandboxes that wait to start. | A review of the same size ends each stage inside its bound. |
| `HephaestusReviewsIncomplete` | More than a quarter of the item reviews of six hours did not end complete. The alert does not count `readiness_refused`, `budget` or `replaced`. | Find the stop reasons: `sum by (status, reason) (increase(practice_review_ended_total{kind="item"}[6h]))`. `execution_incomplete` and `execution_failed` point to the runtime: read `agent.job.terminal` and the sandbox exits. `deadline` points to slow model calls. `no_sandbox_room` points to the sandbox quota. Do not start the reviews again by hand. | Over six hours, at least three quarters of the counted item reviews end complete. |
| `HephaestusAgentRunReaperFailing` | The run reaper cannot take back an expired run, so its work waits. | Read the `agent.run.reaper.failed` log records: `run.id` names the run and `error.type` the error. Find its job with `SELECT id, status FROM review_job WHERE run_id = '<run id>'`. Report the error to the maintainers. | `agent_run_reaper_failure_total` stops increasing. |
| `HephaestusAgentSandboxReaperFailing` | The sandbox reaper cannot delete sandboxes that no work needs, so they hold cluster capacity. | Read `agent.sandbox.reaper.failed` and `agent.sandbox.claim_delete_failed`: they name the sandbox and the error. Check that the server's Role in the sandbox namespace grants `sandboxclaims`, and that the agent-sandbox controller runs. | `agent_sandbox_reaper_failure_total` stops increasing. |
| `HephaestusAgentSandboxDispatchFailing` | The server cannot request the sandboxes of due runs, so their work waits. | Read `agent.sandbox.dispatch.failed` and its `error.type`. Check that the server's Role in the sandbox namespace grants `sandboxclaims`, and that the agent-sandbox controller runs. | `agent_sandbox_dispatch_failure_total` stops increasing. |
| `HephaestusAgentSandboxUnisolated` | A sandbox could still reach the Kubernetes API 10 seconds after its start, so its network policy did not hold. The sandbox started none of its work. | Read `agent.sandbox.taken_back` with `sandbox.reason` `unisolated`. Check that the sandbox namespace has the NetworkPolicies of the chart: `kubectl --namespace <sandbox namespace> get networkpolicy`. Check that the network plugin of the node enforces them. | `agent_sandbox_revoked_total{reason="unisolated"}` stops increasing. |
| `HephaestusSandboxGatewayRefusing` | The sandbox gateway refused many requests for one reason. The `reason` label names it. | `unauthenticated`, `forbidden` and `unknown_route` mean that a sandbox calls what it may not call: find the review in the server log and cancel it. `source_limit` means that one connection peer sent too many requests. `principal_limit` can mean a wide review: read `Sandbox gateway rate limit exceeded`. `oversized` and `body_budget` mean large bodies. Do not raise a limit before you know the caller. | The rate of `sandbox_gateway_refused_total` for that reason falls. |
| `HephaestusSandboxGatewayConnectionsHigh` | The gateway holds more than 80 % of its connections. A review holds about 54 connections at normal width and 170 at most. | Compare `sandbox_gateway_connections` with the running reviews. If the reviews explain the count, raise `sandbox.gateway.maxConnections`. If not, find the Pod that holds them. | `sandbox_gateway_connections` falls below 80 % of the limit. |
| `HephaestusAttemptKeysNotSyncing` | A server cannot publish or load the keys that verify sandbox credentials. | Check the database connection of the server and its `Attempt key` log lines. To revoke a stolen key, read its `kid` from the start log line `Published this server's attempt key`. Restart that server, then delete that row from `attempt_public_key`. | `attempt_key_sync_failures_total` stops increasing. |
| `HephaestusEvidenceReconcileStalled` | Evidence cleanup failed for ten minutes, so erased evidence can remain in a folder, archive or sandbox. | Read `Evidence reconcile failed` and `Evidence reconcile left copies for the next pass`. Check the database connection and the space and permissions of the cache volume. For a failed sandbox, check the Kubernetes API, the `sandboxclaims` permission and the sandbox controller. A server restart does not prove that a sandbox is deleted. | `evidence_reconcile_last_success_seconds` is less than one minute old, and each failed SandboxClaim `agent-<sandboxId>` and its Pod are gone. |
| `HephaestusCheckoutUnverified` | A server could not build a captured checkout again, so an attempt ended as a capture failure. | Read the log line `Captured checkout cannot be built here`. `fetch_failed` means that the provider no longer has the commit, for example after a force-push. `unavailable` means that the workspace does not monitor the repository. `mismatch` means a different tree: report it with the job ID. | `evidence_checkout_copies_total` for these outcomes stops increasing. |
| `HephaestusGitCacheNearlyFull` | The Git cache volume stayed above 90 %, and eviction cannot free it. | Raise `server.gitCache.sizeLimit` and the matching `ephemeral-storage` limit in `server.resources` in one upgrade. Check that the node has the disk. Do not delete mirrors by hand. | `git_cache_bytes` stays below 80 % of `git_cache_limit_bytes`. |
| `HephaestusGitMirrorsEvicted` | At least five kept mirrors were evicted in one hour, so the volume is too small for the monitored repositories. | Do the action of `HephaestusGitCacheNearlyFull`. | `git_mirror_evictions_total` stops increasing. |
| `HephaestusNodeDiskFilling` | A node file system has less than 15 % free space. | Find what fills the node: Git mirrors (`server.gitCache.sizeLimit`), review sandboxes, or images. If a sandbox fills it, drain the node to move the server. | Free space stays above 15 %, and no Pod is evicted for disk pressure. |
| `HephaestusResultsMarkedIncorrect` | People marked more than 5 % of the judged results of a week incorrect. | Find the practices with the [outcome query](./metrics.md#feedback-trust). Read the reasons of the marks in the history of each result. One practice points to its criteria. Many practices point to a change of model, evidence capture or release. Do not delete marks. | The share of incorrect marks falls below 5 % in the next seven days. |

### Feedback delivery and the outbox

| Alert | Cause | Action | Check |
| --- | --- | --- | --- |
| `HephaestusFeedbackDeliveriesFailing` | At least three deliveries to one destination failed in one hour. The `destination` label names it. | For `on_work`, check the provider connection of the workspace, its rate limits and the server log for the failed send. For `conversation`, read `mentor_turn_completed_total` and the turn failures. Do not post the feedback by hand: a retry then shows it twice. | Fewer than three deliveries to each destination fail in one hour. |
| `HephaestusFeedbackDeliveryStalled` | Feedback on the work waited more than two hours for its first posted copy. | Find its send in `agent_action`: `lane_key` is `feedback:<feedback id>`, and `state` is `ADMITTED` or `EXECUTING`. Read the `action.*` log records. Check the provider connection for a revoked credential or a rate limit. | `practice_feedback_oldest_waiting_seconds` is below two hours. |
| `HephaestusFeedbackDeliverySlow` | More than 30 % of the reviews of six hours posted their first feedback later than 30 minutes. | Find the slow stage: the wait for a claim (`agent_run_claim_wait_seconds`, `agent_run_oldest_due_age_seconds`), attempt duration, model pool waits (`llm_pool_permit_wait_seconds`), and the quiet window of the occasion. | At most 30 % of the reviews in six hours post their first feedback later than 30 minutes. |
| `HephaestusFeedbackReadbackUnknown` | Readback could not tell whether feedback reached the work on a provider. | Check the credentials, the rate limit and the reachability of that provider. When the provider answers again, open the Unconfirmed feedback and select **Check delivery**. Never post the feedback again by hand. | **Check delivery** confirms each copy, or proves it absent. |
| `HephaestusFeedbackSendRetrying` | A feedback send used at least half of its readback attempts. | Find the open sends with high `attempts` in `agent_action`: `DELIVER_FEEDBACK`, `EDIT_FEEDBACK` and `RETRACT_FEEDBACK`. Read the provider and readback log records. Confirm the existing copy before any retry. | The send ends. |
| `HephaestusFeedbackSendMetricsUnavailable` | A server cannot read the attempts of feedback sends. | Read the server log for the failed read. Check the database. | Each server reports a finite `practice_feedback_send_attempts` value. |
| `HephaestusOutboxStalled` | An outbox action waited for more than 15 minutes after it became due. | Check that every server replica runs. Read `action.attempt.failed` and `action.batch.outlived` for the kind. List the waiting actions: `SELECT id, lane_key, state, attempts, next_attempt_at FROM agent_action WHERE kind = '<kind>' AND state IN ('ADMITTED','EXECUTING') ORDER BY next_attempt_at LIMIT 20`. An `EXECUTING` action at the head of a lane holds the others until its lease ends. Do not change the rows. | `action_oldest_due_seconds` for the kind falls below 900. |
| `HephaestusOutboxUnsampled` | A server cannot read the outbox backlog gauges. They keep their last values, so a stalled outbox does not fire `HephaestusOutboxStalled`. | Read the server log for `action.backlog.sampler_failed` and its `error.type`. Check the database connection. | `action_backlog_sampler_failures_total` stops increasing. |
| `HephaestusOutboxUncertain` | An outbox action ended uncertain, so its write can have reached the provider. Nothing retries it. | Read `action.ended.uncertain`: `action.id` names the action and `action.reason` the cause. Check at the provider whether the write arrived, for example in the mail log. If the message mattered, tell the person by another channel. | No new count of `action_ended_total{state="UNCERTAIN"}` in one hour. |
| `HephaestusOutboxRecordFailing` | The outbox could not record the result or the end of an action. | Find the action ID in the log line `Stale action could not end` or `Action result could not be recorded`. ### Models and budgets

| Alert | Cause | Action | Check |
| --- | --- | --- | --- |
| `HephaestusBudgetExhausted` | A workspace crossed the monthly budget cap of the instance-funded models. | Decide whether to raise the cap or pause the work. Compare the usage with the billing of the provider ([AI usage](./ai-providers#ai-usage)). Silent mode does not stop spending. | Usage stays inside the cap. Work that waits on the budget resumes on its own. |
| `HephaestusBudgetBlocked` | Budget admission refused work for 15 minutes. With `surface="model_call"`, the proxy refused calls of a running job at a cap. | Find the budget: shared or workspace-owned. Raise it, or pause the affected model. For runaway spend, [stop model spend](./contain-an-incident#stop-model-spend). | The refusals stop. |
| `HephaestusModelRefusalsReachCallers` | Callers saw the 429, 503 or 529 of the provider instead of waiting it out. | Read `llm_pool_upstream_throttled_total` by `status`. A spent account needs the quota or the plan of the provider. A 503 with no `Retry-After` can be an outage. A workspace credential in a shared pool also shows here. | `llm_pool_upstream_absorbed_total` grows as fast as `llm_pool_upstream_throttled_total`. |
| `HephaestusModelLimitAtFloor` | The provider refused, queued or did not answer even two calls for 30 minutes. | A rising `llm_pool_limit_decreases_total{cause="refusal"}` means refusals. `cause="unanswered"` means streams without content: check the provider and any gateway in front of it. A rising `llm_pool_first_token_baseline_resets_total` means a queue at the model server. | `llm_pool_limit` stays above 2 for 30 minutes. |
| `HephaestusConversationModelWaitLong` | Conversation calls wait for a free call of their pool. | Read `llm_pool_waiters`, `llm_pool_limit` and `llm_pool_cooldown_active`. A low limit means that the provider refuses or queues. A limit full of review calls means that the pool needs more calls, or reviews need their own pool. | Conversation calls wait under 5 seconds, and `llm_pool_waiters{band="interactive"}` returns to 0. |
| `HephaestusReviewModelWaitLong` | Review calls wait more than two minutes for a free call, while the sandbox and its deadline wait. | Compare `llm_pool_limit` with the review width. Raise the limit of the pool if the provider allows it, or lower the review width ([Sizing](./sizing)). | Under a quarter of the review calls wait over two minutes for one hour. |
| `HephaestusModelPermitsExpired` | A server stopped renewing a call in flight, usually because the server stopped. The pool frees that room one lease later. | Find why the server stopped: `HephaestusContainerOomKilled`, an eviction, or a lost database connection. | `llm_pool_permits_expired_total` stops increasing. |
| `HephaestusModelPermitRenewalFailing` | Servers failed to renew their call permits without a restart. The database is the usual cause. | Check `HephaestusDatabaseConnectionTimeouts` and the server log. | `llm_pool_lease_renewal_failures_total` stops increasing. |
