# Observability contract

Production logs are JSON records. `job.id` and `workspace.id` are fields, not metric labels.

## Agent-job lifecycle

Lifecycle records contain `event.name`, `job.id`, `workspace.id`, `job.type`, `job.phase`,
`job.outcome`, and `duration.ms`.

| `event.name` | Emitted when | `job.phase` | `job.outcome` | `duration.ms` |
| --- | --- | --- | --- | --- |
| `agent.job.queued` | A new job transaction commits | `queue` | `queued` | `0` |
| `agent.job.started` | A worker starts a claimed job | `queue` | `started` | Creation to start |
| `agent.job.delivery` | A delivery attempt finishes | `delivery` | `delivered`, `failed` | Delivery attempt |
| `agent.job.terminal` | A terminal transition commits | `total` | `completed`, `failed`, `timed_out`, `cancelled` | Creation to terminal emission |

Delivery is optional. Jobs that do not complete successfully may have no delivery event.

## Agent-job metrics

| Prometheus name | Type | Labels | Meaning |
| --- | --- | --- | --- |
| `agent_job_total` | Counter | `outcome` | Committed terminal transitions |
| `agent_job_duration_seconds` | Histogram | `phase` | Queue, execution-attempt, delivery-attempt, and total durations |

`outcome` is one of `completed`, `failed`, `timed_out`, or `cancelled`. `phase` is one of `queue`,
`execution`, `delivery`, or `total`. Identifiers, model and provider names, worker IDs, and exception text are not
labels. See [Practice Review Operations](./practice-review-operations.mdx) for queue health and the
existing execution metric.

## Privacy-job metrics

Account erasure, export generation, export expiry and LLM usage retention each report one terminal
outcome per run, published by the server role.

| Prometheus name | Type | Labels | Meaning |
| --- | --- | --- | --- |
| `privacy_job_completed_total` | Counter | `job`, `outcome` | Terminal privacy-job executions |
| `privacy_job_affected_total` | Counter | `job` | Rows or subjects the run removed or produced |

`job` is one of `account_erasure`, `export_generation`, `export_retention`, or
`llm_usage_retention`. `outcome` is `success`, `incomplete` or `failure`. An empty backlog is a
`success`, so silence on the success counter is itself alertable. `incomplete` means the run finished
without error but ran out of its time budget with work still eligible — the LLM usage retention sweep
deletes in batches for at most five minutes and reports `incomplete` when expired rows remain, so a
deployment that reports it every day never finishes deleting. Account, workspace, export and source
identifiers are not labels. The erasure and retention paths these cover are listed in the
[personal-data map](./dsms/personal-data-map.md).

For export generation, `success` and the affected count are published only after the export commits.
A failed attempt reports `failure` even if the database is unavailable and cannot save the failed
status; consult the server log when an export remains queued or processing after a reported failure.

## Correlating a request

Every HTTP response carries an `X-Request-Id` header whose value is the request's W3C trace ID — a
random 32-character hex string that is never derived from user attributes. The same value appears as
the `traceId` field in every JSON log line written while handling that request, and it follows the
work the request caused: a queued review job restores it when it executes, the sandbox and its LLM
proxy calls carry it, and Sentry events are tagged with it. Access logs stay off at every layer, so
this is the join key for "what happened to this request".

No collector or log aggregator is required. From a reference deployment, take the ID a user reports
(or the `X-Request-Id` of a failing response) and search the container logs:

```bash
docker compose logs --no-color | grep '"traceId":"<the-id>"'
```

That returns the request's own log lines, the lifecycle events of any job it enqueued (the
`agent.job.*` events above), and the proxy calls made on its behalf. A job triggered by the scheduler
rather than a request mints its own trace ID, so its lifecycle is still joinable even though no HTTP
response ever carried it.

## Private execution archives

Execution archives are **off by default**. On a dedicated evaluation instance, set
`PRACTICE_REVIEW_EXECUTION_CAPTURE_ENABLED=true` to retain the staged review inputs, collected
outputs, final provider request bodies and native Pi session transcripts for subsequent attempts.
This does not retroactively capture earlier reviews and does not enable OpenTelemetry export.

Treat these archives as sensitive source material: they can contain private repository content,
prompts, conversations and tool results. Transport headers and environment variables are not
archived, but source material itself can contain secrets. Restrict workspace administrator access,
protect the Context Fabric storage volume and apply its existing retention policy. Do not publish
raw archives as benchmark results or put their contents in telemetry attributes.

Workspace administrators can retrieve the manifest at
`GET /workspaces/{workspaceSlug}/agents/jobs/{jobId}/execution-archive` and manifest-listed content at
`GET /workspaces/{workspaceSlug}/agents/jobs/{jobId}/execution-archive/{attempt}/files/{sha256}`.
Verify both byte length and SHA-256 on download. Captures share Context Fabric retention; they are
not permanent backups. Missing attempts or expired files must be reported as unavailable.

An output archive means files were collected, not that every event was recorded. Inspect the native
`capture.json` and the authoritative job state as well. Cancellation or abrupt termination can
leave only the input archive. Disabling the setting stops new capture, but does not erase retained
archives; retention continues to govern existing files.

## Exporting OpenTelemetry traces

Hephaestus uses Spring Boot's OpenTelemetry starter and the OTLP HTTP exporter. Export is disabled
by default, independently of private execution capture. Configure these settings on the runtime
roles whose spans you want to collect:

| Variable | Default | Purpose |
| --- | --- | --- |
| `TRACING_OTLP_ENABLED` | `false` | Enable the OTLP trace exporter. |
| `TRACING_OTLP_ENDPOINT` | `http://localhost:4318/v1/traces` | Full OTLP HTTP receiver URL, reachable from the application container. |
| `TRACING_SAMPLING_PROBABILITY` | `0.0` | Fraction of new traces sampled; use `1.0` for a dedicated evaluation instance. |

The supported Compose stack forwards these settings to server, worker and webhook containers.
For authenticated collectors, configure Spring Boot's
`management.opentelemetry.tracing.export.otlp.headers` through protected deployment configuration.
Do not put collector credentials in a URL. OTLP log and metric export stay disabled: enabling traces does not
start exporting application logs, private transcripts or a second metrics stream. Prometheus metrics
remain available through the existing endpoint.

Each practice-review attempt starts a real `practice_review.execute` span. Its trace ID is retained
in the execution archive; it can differ from the job's submission correlation ID. The submission
ID is a separate span attribute, not an invented parent span. Sandbox proxy requests propagate the
execution trace's sampling decision. A `gen_ai.chat` span covers each authenticated model request,
including streaming, and records the model, HTTP outcome and observed streaming token usage when
available. Framework HTTP spans describe the transport. Prompts, tool results, headers and tokens
used for authentication are not span attributes.

For private capture, the actual outbound proxy request body is retained separately from the Pi
request: the proxy may replace a model identifier or add usage-reporting options. The private
request context links its Pi-request hash to the exported trace and span IDs. Both bodies are
content-addressed; neither body is copied into telemetry.

A trace ID is not proof of export. Verify that your collector received the execution root and model
request spans, then compare request hashes with the native event journal. Sampling, exporter errors,
collector retention and abrupt process termination can all leave partial coverage. Do not equate
successful feedback delivery or a nonempty trace file with complete execution evidence.
