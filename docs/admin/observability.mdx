Every runtime role writes one JSON record per event to standard output.
Spring Boot writes the records in its built-in [Elastic Common Schema (ECS) format](https://docs.spring.io/spring-boot/reference/features/logging.html#features.logging.structured).
`job.id` and `workspace.id` are fields, not metric labels.
The application exports no logs.
The container runtime keeps them on the host until an operator collects them ([Collecting logs](./monitoring#collect-logs)).

## Questions that the signals answer

Each row is a question that an operator asks to run an instance or to make it better.
The signal answers the question.
The alert or the objective tells the operator when the answer needs work.

A write failure stays queued and retries within minutes. Inspect its exception in server logs. A vanished or unmonitored source ends its pending fact without a write and also increments the failure counter. No workspace or person labels are emitted |

## Service level objectives

The group `hephaestus-slos` holds seven objectives.
The two API objectives, the Activity objective and the conversation objective each have an error budget for 30 days, and burn-rate alerts on that budget.
A fast burn spends 2 % of that budget in one hour, and a slow burn spends 5 % in six hours.
Each of these alerts checks a long window and a short window, so it ends soon after the cause ends ([Google SRE workbook](https://sre.google/workbook/alerting-on-slos/)).

The two API objectives also have a ticket window of three days, with six hours as the short window.
At a burn rate of 1, it spends 10 % of the budget.
It finds a slow leak that the fast and slow windows do not see, and it needs work on the next working day.
These ticket alerts need 1,000 requests in three days.

The review and feedback objectives each have one threshold over six hours, not a budget.
The page load objective has a threshold over six hours and a second threshold over seven days.
Each alert needs a minimum number of requests, page loads or reviews in its long window.
Thus, one failure on an idle instance does not page.

| Objective | Signal | Why this objective |
| --- | --- | --- |
| 99.5 % of API requests get no server error (`HephaestusApiErrorBudgetBurnFast`, `HephaestusApiErrorBudgetBurnSlow`, `HephaestusApiErrorBudgetBurnTicket`) | `http_server_requests_seconds_count` of the server role, without the `/internal/` routes | A reader sees every server error. The `/internal/` routes serve review sandboxes and the model proxy, which have their own alerts |
| 99.5 % of API reads finish within 2 seconds (`HephaestusApiLatencyBudgetBurnFast`, `HephaestusApiLatencyBudgetBurnSlow`, `HephaestusApiLatencyBudgetBurnTicket`) | `http_server_requests_seconds_bucket` with `le="2.0"` against `le="+Inf"`, for `GET` without server errors, event streams, downloads and exports | A page waits for its reads. An event stream stays open on purpose, and a download or an export takes as long as its size. A server from before the 2-second bucket counts on neither side |
| 95 % of Activity reads finish within 1 second (`HephaestusActivityLatencyBudgetBurnFast`, `HephaestusActivityLatencyBudgetBurnSlow`) | `http_server_requests_seconds_bucket` with `le="1.0"` against `le="+Inf"`, for `GET` without server errors on the workspace and public Activity routes | Activity is the page that a developer opens most. The alerts use the same windows as the API objectives. They need 20 reads in one hour or 60 in six hours, so that one slow read on a quiet instance does not fire |
| 95 % of conversation turns get their first token within 10 seconds (`HephaestusConversationFirstTokenBudgetBurnFast`, `HephaestusConversationFirstTokenBudgetBurnSlow`) | `agent_run_first_token_seconds_bucket` with `le="10.0"` against the count, for web and Slack turns | The first part of an answer is what a developer waits for. A turn that ends before any answer records no first token, so `HephaestusConversationTurnsFailing` covers it. An instance has few turns, so the alerts need 5 turns in one hour or 10 in six hours |
| 75 % of page loads show their main content within 2.5 seconds (`HephaestusPageExperiencePoor`, `HephaestusPageExperiencePoorWeekly`) | `web_vital_duration_seconds_bucket` for `lcp` with `le="2.5"`, over six hours, and over seven days | The Core Web Vitals threshold for a good Largest Contentful Paint ([web.dev](https://web.dev/articles/lcp)). It needs [page experience metrics](./metrics#page-experience-metrics) on. The six-hour alert needs 50 loads in six hours, which a small instance seldom has. The weekly alert needs 50 loads in seven days |
| 95 % of item reviews end complete (`HephaestusReviewsIncomplete`) | `practice_review_ended_total` with `kind="item"`, over six hours | A review that is not complete gives a developer no feedback on part of its practices. The alert fires when more than 25 % end incomplete, which spends the 5 % budget five times as fast. Readiness waits and budget stops are policy decisions with their own signals, so they count on neither side. A cancellation counts only when no sandbox room was left. The alert needs four reviews in six hours |
| 90 % of reviews post their first feedback within 30 minutes of their push or request (`HephaestusFeedbackDeliverySlow`) | `practice_review_first_delivery_seconds` with `trigger` `event` or `request` and `approval="none"`, over six hours | A developer waits for this feedback. The alert fires when more than 30 % come later than 30 minutes, which spends the 10 % budget three times as fast. Feedback that a person approves first, and scheduled or backfill reviews, count on neither side. The alert needs four reviews in six hours. Feedback that never arrives has no observation, so `HephaestusFeedbackDeliveryStalled` covers it: feedback on the work that waited more than two hours for its first copy |

## Health probes

Each probe group answers one question.
The probes read only state inside the process.
A slow or missing dependency therefore never restarts a Pod, and never takes every Pod out of rotation at once.

| Group | Members | Question |
| --- | --- | --- |
| Liveness (`/actuator/health/liveness`, `/livez`) | `livenessState` | Does the process run? |
| Readiness (`/actuator/health/readiness`, `/readyz`) | `readinessState` | Can this Pod serve now? |

`integrationConsumer`, `practiceReview` and `kubernetesSandbox` are in neither group.
A server serves its API whether or not it may start sandboxes, and its readiness does not qualify sandbox isolation. Run the platform isolation gate before enabling work.
They stay in `/actuator/health` and the metrics, which the alerts read.

One state inside the process breaks liveness: a provider event handler that ran past `hephaestus.integration.consumer.handler-timeout` and did not stop within 30 seconds of its interrupt.
Kubernetes then restarts the server Pod, so the stuck handler ends before another server handles its event.
