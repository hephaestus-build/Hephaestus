Upgrade a Helm installation to a later release, and recover when its migration fails.
The [compatibility policy](./compatibility-policy#upgrade-guarantee) states which releases you can upgrade from.
Read the release notes and the [migration guide](https://github.com/hephaestus-build/Hephaestus/blob/main/MIGRATION.md) entry of every release between yours and the target.
In-place downgrades are not supported.
For the cutover from a 1.0 release candidate to 1.0.0, follow [Upgrade to 1.0](./upgrade-to-1-0).

Expect a release candidate (`X.Y.Z-rc.N`) before major upgrades, [stopped cutovers](./pull-based-deployment#stopped-major-upgrades) and irreversible migrations.
See the [release policy](../contributor/release-management#release-candidate-policy).

## Choose a rolling or a stopped upgrade

Only the previous release can run on the schema of a new release.
A rolling upgrade keeps a ready server, and a stopped upgrade stops every server before the migration.

| Situation | Upgrade |
| --- | --- |
| The target is the next release on a cluster that is not a one-host installation. No entry between the two releases starts with **Stop every role**. | [Rolling](#upgrade-a-schema-compatible-release) |
| A migration guide entry between the two releases starts with **Stop every role** | [Stopped](#stopped-schema-upgrades) |
| The upgrade skips one or more releases | [Stopped](#stopped-schema-upgrades) |
| A one-host installation. Its installer refuses every other release change. | [Stopped](#stopped-schema-upgrades) |
| A 1.0 release candidate to 1.0.0 | Stopped, as [Upgrade to 1.0](./upgrade-to-1-0) describes |

During a stopped upgrade, no server receives provider deliveries.
[Reception during a restart](./runtime-roles#reception-during-a-restart) says how each provider delivers them again.

## Validate the actual production data

Run a restricted copy of production on the production host, so that the production data stays on that host.
Give the copy the access and retention rules of the backup.
Plan free disk on the host for the dump and the restored database.
Run the target release's [migrate run mode](./runtime-roles#database-migrations) with the production profile against the copy.
The update must use that exact release's changelog, contexts, PostgreSQL image and extensions, secrets, and role configuration.

Do these steps:

1. Set an outage budget.
2. Isolate the copy, as the [isolated restore drill](./backup-restore#isolated-restore-drill) describes, **before** you restore secrets or start application code.
   Keep ingress and sandboxes off, and external egress denied, for the whole rehearsal.
3. Check the [database prerequisites](./compatibility-policy#database-baseline-prerequisites) before the candidate starts.
4. If an intermediate release is required, rehearse that upgrade on the same copy first.
5. Run Liquibase **update**, not only `validate` or SQL generation.
   Do not use a test profile, Hibernate `ddl-auto`, or an empty database as this proof.
6. Verify application readiness and authenticated reads.
7. If the rehearsal exceeds the outage budget, stop.
8. After you fix a migration failure, repeat against a fresh copy.

Record these results:

- The migration duration, errors, free disk, WAL growth and locks.
- Before and after checks of representative workspace relationships and of the readability of encrypted credentials.
- Before and after checks of the practice catalog and the ledger row counts.
- The expected target changesets in `databasechangelog`, and a released lock in `databasechangeloglock`.

[CI migration checks](/contributor/database-migration#ci-validation) cover empty and seeded databases,
not your production data. They do not replace this update of the copy.

## Upgrade the release [#upgrade-the-host]

Check the [database prerequisites](./compatibility-policy#database-baseline-prerequisites) before you start.

1. On a pull-based one-host install, pause [reconciliation](./pull-based-deployment#operating-it), and wait for its active run to finish.
2. Take a verified [database backup](./backup-restore#back-up-the-database), and complete [Validate the actual production data](#validate-the-actual-production-data).
3. On the running instance, open **Instance administration → Instance settings**.
4. Select **Turn on silent mode…**, enter the upgrade as the reason, and select **Turn on silent mode**.
5. Read it back: the **Silent mode** card shows **On**.
   Do not continue until it does.
6. Read the target release's migration instructions, and update your protected `site.yaml` and Secret as they require.
7. Verify the target release's joint lock, as [Independent verification](./release-image-lock#independent-verification) describes.
8. Do the [rolling](#upgrade-a-schema-compatible-release) or the [stopped](#stopped-schema-upgrades) upgrade that [the table](#choose-a-rolling-or-a-stopped-upgrade) selects.
   During a rolling upgrade, reviews continue, and silent mode withholds their feedback on the work.
9. Check the migration Job and the readiness of the server, as [Check that it worked](#check-that-it-worked) describes.
10. If the migration fails, or Helm times out or reports a pending or failed release, follow [If migration fails](#if-migration-fails).
    A failed Helm status does not prove that the migration Job has stopped.
11. Follow [Prove silence, then turn off silent mode](./silent-deployment).
12. On a pull-based one-host install, make the channel name the installed release before you resume the timer.

## Upgrade a schema-compatible release

[Verify the release chart](./kubernetes#verify-the-release-chart).
Then apply the new chart, its profile, and your own values:

```bash
helm upgrade --install hephaestus "chart-$VERSION/hephaestus" -n hephaestus \
  -f "chart-$VERSION/hephaestus/profiles/small.yaml" -f site.yaml \
  --rollback-on-failure --wait=watcher --wait-for-jobs --timeout 45m
```

The migration Job of the new revision and the new Pods start together.
The new Pods wait up to 10 minutes for the migrated schema, and the previous release serves until they are ready.
`--wait-for-jobs` fails the upgrade when the migration fails, and `--rollback-on-failure` then returns the Deployments to the previous revision.

While the migration runs, a previous release later than 1.0.0-rc.14 starts no new work. Its running work finishes.
[Work during a migration](./runtime-roles#work-during-a-migration) gives the details.
A previous release of 1.0.0-rc.14 or earlier still claims work during the migration.

The server uses a rolling update: its replacement is ready before the old Pod stops serving.
An old server drains for up to `server.drainTimeoutSeconds`: 30 minutes by default, and 10 minutes in the `small` profile.
Any ready server serves the sandbox calls of running reviews. A connection that is open can finish on the old server during the drain.

Each release builds its PostgreSQL image again with the current security fixes of its distribution.
Thus, the upgrade usually restarts the bundled PostgreSQL once. While it restarts, requests that need the database fail.
Ready replacements accept new claims.

The Helm `--timeout` must cover the drain, 2 minutes of shutdown and up to 10 minutes of start.
After the timeout, Helm rolls the release back. If you set a longer drain, set a longer timeout.
Start the next upgrade only after the old server is gone: `kubectl --namespace hephaestus get pods -l app.kubernetes.io/component=server` shows no `Terminating` Pod.

To fix a failed upgrade, roll forward.
`helm rollback` and an older image do not undo a migration: restore the database from the backup taken before the upgrade ([Restore](./backup-restore#restore)).

### Sandbox capacity during upgrade

A rolling upgrade runs a draining server, its replacement, and the migration and stanza Jobs at the same time.
A supplied `sandbox.budget` must hold this peak, as [Sandbox capacity budget](./helm-chart#sandbox-capacity-budget) describes.
Let the review drain finish before the peak.
Do not resume review work while the Jobs or the replacement server still use the budget.
A drain timeout does not prove that the reviews ended: check the remaining runs before you continue.

## Stopped schema upgrades

Use this procedure when [the table](#choose-a-rolling-or-a-stopped-upgrade) selects a stopped upgrade.
Do not use `--rollback-on-failure`: a rollback can start the old server against a changed schema.
Pause deployment automation that can change the release until this procedure is complete.

Before phase 1, record the current chart, profile, site values and `server.replicas`.
Prepare a PostgreSQL backup or rehearse the [host-side restore](#restore-the-final-logical-archive).
Keep the matching signed release lock and encryption keys.
Verify the new release's chart before you use it.
Each phase is a separate `helm upgrade` with that phase's chart, profile and site values:

| Phase | Chart | `migration.enabled` | `server.stopped` | Before the next phase |
| --- | --- | --- | --- | --- |
| 1. Stop the server | Current release | `false` | `true` | Every old server Pod, including terminating Pods, and its sandbox Pods are gone. |
| 2. Migrate | New release | `true` | `true` | The migration Job of this revision completed successfully. |
| 3. Start the server | New release | `true` | `false` | Readiness, authenticated reads, a practice review and a conversation pass. |

1. Apply each phase's values after your profile and site values, so that they take precedence.
   Use `--wait=watcher --wait-for-jobs --timeout 45m`, without automatic rollback.
   Do not stop PostgreSQL yourself in these phases.
   Use `server.stopped=true` to stop the server, not `server.replicas=0` or `sandbox.enabled=false`.
   `server.stopped` keeps `server.replicas`, which sizes PostgreSQL's connections, so the stop does not restart PostgreSQL.
2. Do phase 1.
   A server can drain for up to its configured timeout. If phase 1 times out, keep `server.stopped=true` and wait for every old Pod to stop.
3. Remove the remaining sandbox workloads, as step 4 of [Planned node maintenance](./maintenance#planned-node-maintenance) describes.
4. Take and verify the final restore point while the server is stopped.
   Without `postgresql.backup.enabled`, take a [logical restore point](#take-a-logical-restore-point-without-backups) from the host.
5. Do phase 2.
   Expect one PostgreSQL restart: each release builds its PostgreSQL image again with current security fixes.
   Find the migration Job of the new Helm revision. For the release `hephaestus`, its name is `hephaestus-migration-<revision>`.
6. Save its log: `kubectl --namespace hephaestus logs job/<migration-job> -c migration > migration.log`.
7. Require its `Complete` condition: `kubectl --namespace hephaestus wait --for=condition=complete job/<migration-job> --timeout=20m`.
   If the Job fails or times out, do not do phase 3.
   Keep the server stopped. Save the log and the failed change set: the chart deletes the Job after 24 hours.
   Then follow [If migration fails](#if-migration-fails).
8. Do phase 3.
   Phase 3 runs another migration Job for the same release, which has no change to apply.
9. Resume deployment automation only after its release and replica counts match the verified installation.
   On one host, keep it paused through the final installer run of [Upgrade the host](./k3s#upgrade-the-host).

A current release from 1.0.0-rc.8 or earlier has no `server.stopped`.
In phase 1, set `server.replicas=0` instead. With the bundled PostgreSQL, also pin `postgresql.parameters.max_connections` for all three phases:

1. Read the current value with `SHOW max_connections` in PostgreSQL.
2. Read the value that the new chart derives for your site file:

   ```bash
   helm template hephaestus <new chart> --namespace <namespace> -f <profile> -f <site file> --set server.stopped=true \
     | grep -o 'max_connections=[0-9]*'
   ```

3. Set `postgresql.parameters.max_connections` to the larger of the two values in each phase.
   The new chart refuses a smaller value, and a reviewing server needs more connections in the new release.
   On a host with pull-based reconciliation, put it in `/etc/hephaestus/chart.yaml`, because the reconciler applies only that file.

If the new value is larger, PostgreSQL restarts once, in phase 1, while the servers stop.
The connection count does not restart it in a later phase.
Remove the setting at a later upgrade. The removal restarts PostgreSQL once.

A refused migration can follow changesets that it already committed.
An image or Helm rollback does not undo them.
Before you return to the old release, restore the matching pre-upgrade backup.

### Take a logical restore point without backups

Use this procedure on the host of the bundled PostgreSQL when `postgresql.backup.enabled` is off.
Keep the archive on the host with the matching signed release lock and encryption keys.
Confirm that the host and the database volume have room for the dump, the retained database and the restored copy.

Install the PostgreSQL client of the server's major version on the host before the window.
On Ubuntu 26.04 with PostgreSQL 18, run `sudo apt-get install -y --no-install-recommends postgresql-client-18`.
Hephaestus tested `postgresql-client-18` and `libpq5` 18.6-0ubuntu0.26.04.1 with `postgresql-client-common` 290ubuntu1.

#### Open the database tunnel

Run the commands on the host in Bash.

1. Choose an absolute path for the restore point.
   Create a private directory there on first use.
   Stop if the directory already exists on first use.

   ```bash
   work='/absolute/path/to/restore-point'
   (umask 077 && mkdir -m 700 -- "$work")
   ```

2. Set the namespace and Helm release name.
   Set the namespace from `sandbox.namespace`.
   With sandboxes disabled, set `sandbox_namespace=''`.
   Select the PostgreSQL Service of the release.
   Set the Secret name from `secret.name`.
   Set the database name from `postgresql.database`.

3. Define the tunnel and credential helpers.
   Use the same directory for each command of this restore point.
   The tunnel helper saves the PID when it opens the tunnel.
   It stops that PID after success or failure.

   ```bash
   set +x
   umask 077
   namespace='<release-namespace>'
   release='<helm-release>'
   sandbox_namespace='<sandbox-namespace>'
   postgres_service='<postgresql-service>'
   release_secret='<release-secret>'
   database='<database-name>'
   maintenance_database=postgres
   if [[ "$database" == "$maintenance_database" ]]; then maintenance_database=template1; fi
   pg_host='host=127.0.0.1 port=15432 sslmode=require connect_timeout=5'
   secret() { kubectl -n "$namespace" get secret "$release_secret" -o "jsonpath={.data.$1}" | base64 -d; }
   with_tunnel() (
     set +x
     set -euo pipefail
     local forward_pid command_pid command_input status=0
     exec {command_input}<&0
     kubectl -n "$namespace" port-forward --address 127.0.0.1 "svc/$postgres_service" 15432:5432 \
       > "$work/port-forward.log" 2>&1 &
     forward_pid=$!
     printf 'Port-forward PID: %s\n' "$forward_pid" >&2
     (
       for attempt in {1..50}; do
         grep -Fq 'Forwarding from 127.0.0.1:15432' "$work/port-forward.log" && break
         kill -0 "$forward_pid" 2>/dev/null || exit 1
         sleep 0.2
       done
       grep -Fq 'Forwarding from 127.0.0.1:15432' "$work/port-forward.log"
       "$@"
     ) <&"$command_input" &
     command_pid=$!
     exec {command_input}<&-
     wait "$command_pid" || status=$?
     kill "$forward_pid" 2>/dev/null || true
     wait "$forward_pid" 2>/dev/null || true
     exit "$status"
   )
   admin_pg() (
     set +x
     set -euo pipefail
     PGUSER="$(secret DATABASE_ADMIN_USERNAME)"
     PGPASSWORD="$(secret DATABASE_ADMIN_PASSWORD)"
     test -n "$PGUSER"
     test -n "$PGPASSWORD"
     export PGUSER PGPASSWORD
     "$@"
   )
   ```

Avoid `pg_isready`. Its disconnect can end this tunnel with `lost connection to pod`.
A client can also close a tunnel after the command succeeds.
The next call starts a new tunnel.

#### Check for erasure requests

Read the target release's migration guide.
If it requires zero requests in `ERASING` or `FAILED`, run this query before the window.
Run it again after the last server stops and before you take the final dump.

```bash
app_sql() (
  set +x
  set -euo pipefail
  PGPASSWORD="$(secret DATABASE_APP_PASSWORD)"
  test -n "$PGPASSWORD"
  export PGPASSWORD PGOPTIONS='-c default_transaction_read_only=on'
  psql -X -w -v ON_ERROR_STOP=1 "$pg_host dbname=$database user=hephaestus_app" "$@"
)
with_tunnel app_sql -c 'SHOW default_transaction_read_only' \
  -c "SELECT id, state, created_at FROM person_data_request WHERE state IN ('ERASING', 'FAILED');"
```

Require `on` from `SHOW`.
Require zero rows from the query.
If either check fails, stop before the dump or migration.

#### Take and verify the final archive

1. Confirm that the server has stopped.
   Confirm that its sandbox Pods and Jobs are gone.
   Both commands must print no resources.

   ```bash
   kubectl -n "$namespace" get pods \
     -l "app.kubernetes.io/instance=$release,app.kubernetes.io/component=server" -o name
   if [[ -n "$sandbox_namespace" ]]; then
     kubectl -n "$sandbox_namespace" get pods,jobs -o name
   fi
   ```

2. Run the applicable [erasure check](#check-for-erasure-requests) again.
   Define `app_sql` even if the target requires no erasure check.
   Record the quiet state through that role.
   Require three zeros.
   The three columns are run leases, action leases and other app connections.

   ```bash
   with_tunnel app_sql -At -F $'\t' -c "
     SELECT
       (SELECT count(*) FROM public.agent_run WHERE state = 'LEASED' AND leased_until > clock_timestamp()),
       (SELECT count(*) FROM public.agent_action WHERE state = 'EXECUTING' AND leased_until > clock_timestamp()),
       (SELECT count(*) FROM pg_stat_activity
        WHERE datname = current_database() AND usename = current_user AND pid <> pg_backend_pid())
   " > "$work/quiet.tsv"
   test "$(cat "$work/quiet.tsv")" = $'0\t0\t0'
   ```

3. Record the source inventory before the dump.
   Count the ordinary tables that the full dump includes.
   The count includes partition leaves and extension configuration tables.
   Require a positive count.

   ```bash
   with_tunnel app_sql -At -c "
     SELECT count(*) FROM pg_class c
     JOIN pg_namespace n ON n.oid = c.relnamespace
     WHERE c.relkind = 'r'
       AND (EXISTS (SELECT 1 FROM pg_extension e WHERE c.oid = ANY(e.extconfig))
         OR (n.nspname <> 'information_schema' AND left(n.nspname, 3) <> 'pg_'
           AND NOT EXISTS (
             SELECT 1 FROM pg_depend d
             WHERE d.classid = 'pg_class'::regclass AND d.objid = c.oid
               AND d.refclassid = 'pg_extension'::regclass AND d.deptype = 'e'
           )))
   " > "$work/source-table-data.count"
   test "$(cat "$work/source-table-data.count")" -gt 0
   ```

4. Take the dump as the database admin.
   The app role cannot read every schema.
   Record the receipt after all checks pass.

   ```bash
   (
     set +x
     set -euo pipefail
     umask 077
     cd -- "$work"
     test "$(cat quiet.tsv)" = $'0\t0\t0'
     expected_table_data=$(cat source-table-data.count)
     test "$expected_table_data" -gt 0
     test ! -e final.dump
     cat > row-counts.sql <<'SQL'
   SELECT 'workspace', count(*) FROM public.workspace
   UNION ALL SELECT 'person_data_request', count(*) FROM public.person_data_request
   UNION ALL SELECT 'event_publication', count(*) FROM public.event_publication
   ORDER BY 1;
   SQL
     with_tunnel app_sql -At -F $'\t' -f row-counts.sql > row-counts.tsv
     started=$(date -u +%FT%TZ)
     with_tunnel admin_pg pg_dump "$pg_host dbname=$database" \
       --no-password --format=custom --file=final.dump
     ended=$(date -u +%FT%TZ)
     test -s final.dump
     chmod 600 final.dump
     test "$(stat -c %a final.dump)" = 600
     sha256sum final.dump > final.dump.sha256
     pg_restore --file=/dev/null final.dump
     pg_restore --list final.dump > archive.list
     table_data=$(grep -cE '^[0-9]+; [0-9]+ [0-9]+ TABLE DATA ' archive.list)
     test "$table_data" -eq "$expected_table_data"
     printf 'file=final.dump\nbytes=%s\nstart=%s\nend=%s\nserver_pods=0\nsandbox_workloads=0\n' \
       "$(stat -c %s final.dump)" "$started" "$ended" > receipt.txt
     printf 'run_leases=0\naction_leases=0\napp_connections=0\nsource_TABLE_DATA=%s\nTABLE_DATA=%s\n' \
       "$expected_table_data" "$table_data" >> receipt.txt
     cat final.dump.sha256 row-counts.tsv >> receipt.txt
   )
   ```

5. Require the dump to exit successfully.
   Check that the file is nonempty.
   Check that its mode is 600.
   Require the full archive read to exit successfully.
   Check that the `TABLE DATA` count matches the source inventory.
   Require a complete receipt before you start phase 2.

### Restore the final logical archive

:::caution[CAUTION: Erased data]
Restoring an older archive can bring back erased data.
Select the archive from the final stopped window.
Use the receipt that matches that archive.
:::

Keep the server stopped.
Confirm that the failed migration Job has stopped.

Use the source release's PostgreSQL version, extensions, database roles and encryption keys.
Keep the matching signed release lock.
Before you start, rehearse this procedure on an isolated staging installation.

1. Define the [database tunnel](#open-the-database-tunnel) functions.
   Define `app_sql` as in [Check for erasure requests](#check-for-erasure-requests).
2. Verify the SHA-256.
   Check that the archive names the selected database.
   Do both checks before you change the live database.
   Run the restore as the database admin.

   The block keeps the failed database under another name with connections disabled.
   The exporter can still hold a connection after the server stops.
   The block records its PIDs before it closes them.
   It stops if any other connection remains.

   ```bash
   (
     set +x
     set -euo pipefail
     umask 077
     cd -- "$work"
     sha256sum --check final.dump.sha256
     grep -Fx "$(cat final.dump.sha256)" receipt.txt
     pg_restore --list final.dump > archive.list
     test "$(sed -nE 's/^;[[:space:]]+dbname:[[:space:]]+//p' archive.list)" = "$database"
     pg_restore --file=/dev/null final.dump
     pg_restore --create --list final.dump > database-inventory.list
     awk -v db="$database" '
       function matches_db(value) { return value == db || value == "\"" db "\"" }
       $1 !~ /^[0-9]+;$/ { next }
       $4 == "DATABASE" && $5 == "-" && matches_db($6) { print }
       $4 == "DATABASE" && $5 == "PROPERTIES" && $6 == "-" && matches_db($7) { print }
       $4 ~ /^(ACL|COMMENT)$/ && $5 == "-" && $6 == "DATABASE" && matches_db($7) { print }
       $4 == "SECURITY" && $5 == "LABEL" && $6 == "-" && $7 == "DATABASE" && matches_db($8) { print }
     ' database-inventory.list > database-only.list
     pg_restore --create --use-list=database-only.list --file=database.sql final.dump
     : > database-create.sql
     : > database-properties.sql
     awk '/^\\connect[[:space:]]/ { if (++switches > 2) exit 1; next }
          { print > (switches ? "database-properties.sql" : "database-create.sql") }' database.sql
     grep -qE "^CREATE DATABASE ($database|\"$database\") " database-create.sql
     failed_db="heph_failed_$(date -u +%Y%m%dT%H%M%S)"
     with_tunnel admin_pg psql -X -w -v ON_ERROR_STOP=1 "$pg_host dbname=$maintenance_database" \
       -v "database=$database" -v "failed_db=$failed_db" -f - <<'SQL'
   ALTER DATABASE :"database" WITH ALLOW_CONNECTIONS false;
   SELECT pid AS exporter_pid FROM pg_stat_activity
   WHERE datname = :'database' AND usename = 'hephaestus_monitor';
   SELECT format(
     'SELECT pg_terminate_backend(pid, 5000) FROM pg_stat_activity WHERE pid = %s
      AND datname = %L AND usename = %L', pid, datname, usename
   ) FROM pg_stat_activity
   WHERE datname = :'database' AND usename = 'hephaestus_monitor'
   \gexec
   ALTER DATABASE :"database" RENAME TO :"failed_db";
   SQL
     with_tunnel admin_pg psql -X -w -v ON_ERROR_STOP=1 "$pg_host dbname=$maintenance_database" \
       -f database-create.sql
     with_tunnel admin_pg pg_restore --no-password --exit-on-error --single-transaction \
       --dbname="$pg_host dbname=$database" final.dump
     if [[ -s database-properties.sql ]]; then
       with_tunnel admin_pg psql -X -w -v ON_ERROR_STOP=1 --single-transaction \
         "$pg_host dbname=$database" -f database-properties.sql
     fi
     pg_restore --list final.dump > archive.list
     table_data=$(grep -cE '^[0-9]+; [0-9]+ [0-9]+ TABLE DATA ' archive.list)
     grep -Fx "TABLE_DATA=$table_data" receipt.txt
     with_tunnel app_sql -At -F $'\t' -f row-counts.sql > restored-row-counts.tsv
     grep -E '^(event_publication|person_data_request|workspace)'$'\t' receipt.txt > expected-row-counts.tsv
     cmp expected-row-counts.tsv restored-row-counts.tsv
   )
   ```

   The SQL files keep the database settings and grants in the archive.
   One connection creates the database.
   Another connection applies the archive in a transaction.
   A separate command applies the remaining database grants and settings if the archive has them.
   The split keeps the archive's restriction commands in their original order.
   It removes the reconnect commands so each client starts with a fresh tunnel.

   Require each command to succeed.
   Check that the archive inventory matches the receipt.
   Check that the restored row counts match the receipt.
   On any failure, leave the server stopped.
   Keep the failed database and any partial restore for diagnosis.
3. After verification passes, apply the signed source release with the server stopped and migration enabled.
   The migration Job runs [database role setup](./helm-chart#database-roles) again.
   Wait for the Job to be `Complete`.
   Keep every source server stopped.
   Keep the failed database until the investigation and retention rules permit its removal.

## Change a volume size

A StatefulSet does not allow a change of its `volumeClaimTemplates`.
The PostgreSQL StatefulSet has a volume claim template:

- `<release>-postgresql`, sized by `postgresql.persistence.size`.

If an upgrade changes its size, for example through a new profile, `helm upgrade` fails.
The error says `StatefulSet ... is invalid: spec: Forbidden: updates to statefulset spec for fields other than ...`.
With `--rollback-on-failure`, Helm then returns to the previous revision, and nothing changes.

Kubernetes cannot shrink a volume.
If the new size is smaller, keep the current size in your own values file, as [Storage and retention](./helm-chart#storage-and-retention) says.

If the new size is larger, do these steps for the PostgreSQL StatefulSet.
The volume of PostgreSQL is `data-<release>-postgresql-0`.
Before you start, take a backup ([Backup and restore](./backup-restore#back-up-the-database)).

1. Check that the storage class allows expansion:

   ```bash
   kubectl get storageclass
   ```

   If `ALLOWVOLUMEEXPANSION` is not `true` for the class of the volume, stop.
   Keep the current size in your own values file.

2. Make the volume larger. Use the new size from the chart in place of `<new size>`:

   ```bash
   kubectl --namespace hephaestus patch pvc data-hephaestus-postgresql-0 \
     --patch '{"spec":{"resources":{"requests":{"storage":"<new size>"}}}}'
   ```

3. Wait until `kubectl --namespace hephaestus get pvc` shows the new capacity.
   If the capacity stays at the old size, check the conditions of the volume:

   ```bash
   kubectl --namespace hephaestus get pvc data-hephaestus-postgresql-0 -o jsonpath='{.status.conditions[*].type}'
   ```

   `FileSystemResizePending` means that the storage driver resizes the file system only when the Pod starts again.
   Then continue with steps 4 and 5, and after step 5 delete the Pod: `kubectl --namespace hephaestus delete pod hephaestus-postgresql-0`.
   The StatefulSet starts it again with the larger volume.
4. Delete the StatefulSet and keep its Pods and volumes:

   ```bash
   kubectl --namespace hephaestus delete statefulset hephaestus-postgresql --cascade=orphan
   ```

5. Run the same `helm upgrade` again.
   Helm creates the StatefulSet with the new template.
   The new StatefulSet takes over the Pods and the volumes.
   It restarts a Pod only if the upgrade also changes the Pod template.

## Check that it worked

1. Run `helm history hephaestus --namespace hephaestus`.
   The new revision is `deployed`.
2. Read the log of the migration Job of that revision: `kubectl --namespace hephaestus logs job/hephaestus-migration-<revision>`.
   It logs `Database migration completed`.
3. Run `kubectl --namespace hephaestus get pods`.
   Each Pod of the new revision is ready.
4. Query `application_build_info` in Prometheus, as [Release metric](./metrics#release-metric) shows.
   Each server reports the new `version`.

## If migration fails

:::caution[CAUTION: Failed migration]
Do not clear checksums, edit released changelogs, or mark the changeset as run.
Do not run a release other than the previous one against the partly migrated database. If the migration guide entry of the new release starts with **Stop every role**, do not run the previous one either ([Rollouts and rollback](./runtime-roles#rollouts-and-rollback)).
Do not release a Liquibase lock by hand except as [One migration at a time](./runtime-roles#one-migration-at-a-time) allows.
Removal of a stale lock does not repair a failed migration.
:::

On a pull-based one-host install, follow [Recover a stopped cutover](./pull-based-deployment#recover-a-stopped-cutover) instead.
It adds the steps of the reconciler to this procedure.

1. Keep the server stopped.
2. Wait until the migration Job has stopped.
   `kubectl --namespace hephaestus get job hephaestus-migration-<revision>` shows its `Complete` or `Failed` condition.
   After its 24-hour TTL, an absent Job has stopped only if no migration Pod remains.
3. Save the Job log, the error and the identity of the failed changeset.
4. Save the `databasechangelog` and lock diagnostics and the target image lock.
5. If possible, take a forensic snapshot of the database volume.
6. If Helm reports a `pending-*` status, roll the release back: `helm rollback hephaestus <revision> --namespace hephaestus --wait`.
   After a stopped upgrade, use the phase-1 revision, which runs no server. After a rolling upgrade, use the previous revision.
7. If you took a final logical archive, [restore that archive](#restore-the-final-logical-archive).
   For a target retry, keep the source stopped.
   To return to the source, start it after the restore passes.
   Verify readiness.
   Verify authenticated reads.
   For a repository backup, follow [Recover the live installation](./backup-restore#recover-the-live-installation) to restore the pre-upgrade backup.
   Use the previous chart, signed release lock, PostgreSQL image, extensions and encryption keys.
8. Report the actual recovery point and time, and any lost writes.
9. Keep the failed database until the investigation and your retention rules permit its removal.
10. On a pull-based one-host install: promote the recovered release, with **allow-rollback** if it is older than the failed upgrade.
    Until the channel names it, the next tick can apply the failed upgrade again.
11. On a pull-based one-host install: enable the reconcile timer again when the promotion has published the channel.
    The version check of the promotion passes when the host applies the channel.
    It fails if the timer stays off for 15 minutes.

To rehearse this procedure, cause a controlled migration failure only in a disposable rehearsal.
Restore the old backup and release, and prove the readiness and data integrity of the old release without a provider write.

## Rollback

:::caution[CAUTION: Images alone cannot reverse a schema change]
Reverting images alone is not a rollback.
Never run a release older than the previous one against a newer schema. [Rollouts and rollback](./runtime-roles#rollouts-and-rollback) says when the previous release can run on it.
Never reconstruct an old lock or resolve mutable image tags.
:::

To roll back, follow [If migration fails](#if-migration-fails) to restore the database, secrets and signed lock of the previous release.
