Upgrade a Helm installation to a later release, and recover when its migration fails.
The [compatibility policy](./compatibility-policy#upgrade-guarantee) states which releases you can upgrade from.
Read the release notes and the [migration guide](https://github.com/hephaestus-build/Hephaestus/blob/main/MIGRATION.md) entry of every release between yours and the target.
In-place downgrades are not supported.
For the cutover from a 1.0 release candidate to 1.0.0, follow [Upgrade to 1.0](./upgrade-to-1-0).

Expect a release candidate (`X.Y.Z-rc.N`) before major upgrades, [stopped cutovers](./pull-based-deployment#stopped-major-upgrades) and irreversible migrations.
See the [release policy](../contributor/release-management#release-candidate-policy).

## Choose a rolling or a stopped upgrade

Only the previous release can run on the schema of a new release.
A rolling upgrade keeps a ready server, and a stopped upgrade stops every server before the migration.

| Situation | Upgrade |
| --- | --- |
| The target is the next release on a cluster that is not a one-host installation. No entry between the two releases starts with **Stop every role**. | [Rolling](#upgrade-a-schema-compatible-release) |
| A migration guide entry between the two releases starts with **Stop every role** | [Stopped](#stopped-schema-upgrades) |
| The upgrade skips one or more releases | [Stopped](#stopped-schema-upgrades) |
| A one-host installation. Its installer refuses every other release change. | [Stopped](#stopped-schema-upgrades) |
| A 1.0 release candidate to 1.0.0 | Stopped, as [Upgrade to 1.0](./upgrade-to-1-0) describes |

During a stopped upgrade, no server receives provider deliveries.
[Reception during a restart](./runtime-roles#reception-during-a-restart) says how each provider delivers them again.

## Validate the actual production data

Use a restricted staging copy of production with the access and retention rules of the backup.
Run the target release's [migrate run mode](./runtime-roles#database-migrations) with the production profile against staging.
The update must use that exact release's changelog, contexts, PostgreSQL image and extensions, secrets, and role configuration.

Do these steps:

1. Set an outage budget.
2. Isolate the copy, as the [isolated restore drill](./backup-restore#isolated-restore-drill) describes, **before** you restore secrets or start application code.
   Keep ingress and sandboxes off, and external egress denied, for the whole rehearsal.
3. Check the [database prerequisites](./compatibility-policy#database-baseline-prerequisites) before the candidate starts.
4. If an intermediate release is required, rehearse that upgrade on the same copy first.
5. Run Liquibase **update**, not only `validate` or SQL generation.
   Do not use a test profile, Hibernate `ddl-auto`, or an empty database as this proof.
6. Verify application readiness and authenticated reads.
7. If the rehearsal exceeds the outage budget, stop.
8. After you fix a migration failure, repeat against a fresh copy.

Record these results:

- The migration duration, errors, free disk, WAL growth and locks.
- Before and after checks of representative workspace relationships and of the readability of encrypted credentials.
- Before and after checks of the practice catalog and the ledger row counts.
- The expected target changesets in `databasechangelog`, and a released lock in `databasechangeloglock`.

[CI migration checks](/contributor/database-migration#ci-validation) cover empty and seeded databases,
not your production data. They do not replace this staging update.

## Upgrade the release {/*#upgrade-the-host*/}

Check the [database prerequisites](./compatibility-policy#database-baseline-prerequisites) before you start.

1. On a pull-based one-host install, pause [reconciliation](./pull-based-deployment#operating-it), and wait for its active run to finish.
2. Take a verified [database backup](./backup-restore#back-up-the-database), and complete [Validate the actual production data](#validate-the-actual-production-data).
3. On the running instance, open **Instance administration → Instance settings**.
4. Select **Turn on silent mode…**, enter the upgrade as the reason, and select **Turn on silent mode**.
5. Read it back: the **Silent mode** card shows **On**.
   Do not continue until it does.
6. Read the target release's migration instructions, and update your protected `site.yaml` and Secret as they require.
7. Verify the target release's joint lock, as [Independent verification](./release-image-lock#independent-verification) describes.
8. Do the [rolling](#upgrade-a-schema-compatible-release) or the [stopped](#stopped-schema-upgrades) upgrade that [the table](#choose-a-rolling-or-a-stopped-upgrade) selects.
   During a rolling upgrade, reviews continue, and silent mode withholds their feedback on the work.
9. Check the migration Job and the readiness of the server, as [Check that it worked](#check-that-it-worked) describes.
10. If the migration fails, or Helm times out or reports a pending or failed release, follow [If migration fails](#if-migration-fails).
    A failed Helm status does not prove that the migration Job has stopped.
11. Follow [Prove silence, then turn off silent mode](./silent-deployment).
12. On a pull-based one-host install, make the channel name the installed release before you resume the timer.

## Upgrade a schema-compatible release

[Verify the release chart](./kubernetes#verify-the-release-chart).
Then apply the new chart, its profile, and your own values:

```bash
helm upgrade --install hephaestus "chart-$VERSION/hephaestus" -n hephaestus \
  -f "chart-$VERSION/hephaestus/profiles/small.yaml" -f site.yaml \
  --rollback-on-failure --wait=watcher --wait-for-jobs --timeout 45m
```

The migration Job of the new revision and the new Pods start together.
The new Pods wait up to 10 minutes for the migrated schema, and the previous release serves until they are ready.
`--wait-for-jobs` fails the upgrade when the migration fails, and `--rollback-on-failure` then returns the Deployments to the previous revision.

The server uses a rolling update: its replacement is ready before the old Pod stops serving.
An old server drains for up to `server.drainTimeoutSeconds`: 30 minutes by default, and 10 minutes in the `small` profile.
Any ready server serves the sandbox calls of running reviews. A connection that is open can finish on the old server during the drain.
Ready replacements accept new claims.

The Helm `--timeout` must cover the drain, 2 minutes of shutdown and up to 10 minutes of start.
After the timeout, Helm rolls the release back. If you set a longer drain, set a longer timeout.
Start the next upgrade only after the old server is gone: `kubectl --namespace hephaestus get pods -l app.kubernetes.io/component=server` shows no `Terminating` Pod.

To fix a failed upgrade, roll forward.
`helm rollback` and an older image do not undo a migration: restore the database from the backup taken before the upgrade ([Restore](./backup-restore#restore)).

### Sandbox capacity during upgrade

A rolling upgrade runs a draining server, its replacement, and the migration and stanza Jobs at the same time.
A supplied `sandbox.budget` must hold this peak, as [Sandbox capacity budget](./helm-chart#sandbox-capacity-budget) describes.
Let the review drain finish before the peak.
Do not resume review work while the Jobs or the replacement server still use the budget.
A drain timeout does not prove that the reviews ended: check the remaining runs before you continue.

## Stopped schema upgrades

Use this procedure when [the table](#choose-a-rolling-or-a-stopped-upgrade) selects a stopped upgrade.
Do not use `--rollback-on-failure`: a rollback can start the old server against a changed schema.
Pause deployment automation that can change the release until this procedure is complete.

Before phase 1, record the current chart, profile, site values and `server.replicas`.
Prepare a PostgreSQL backup, verify its restore, and keep the matching signed release lock and encryption keys.
Verify the new release's chart before you use it.
Each phase is a separate `helm upgrade` with that phase's chart, profile and site values:

| Phase | Chart | `migration.enabled` | `server.replicas` | Before the next phase |
| --- | --- | --- | --- | --- |
| 1. Stop the server | Current release | `false` | 0 | Every old server Pod, including terminating Pods, and its sandbox Pods are gone. |
| 2. Migrate | New release | `true` | 0 | The migration Job of this revision completed successfully. |
| 3. Start the server | New release | `true` | Recorded count | Readiness, authenticated reads, a practice review and a conversation pass. |

1. Apply each phase's values after your profile and site values, so that they take precedence.
   Use `--wait=watcher --wait-for-jobs --timeout 45m`, without automatic rollback.
   Keep PostgreSQL running through all phases.
   Use `server.replicas=0`, not `sandbox.enabled=false`, to stop the server.
2. Do phase 1.
   A server can drain for up to its configured timeout. If phase 1 times out, keep the count at zero and wait for every old Pod to stop.
3. Remove the remaining sandbox workloads, as step 4 of [Planned node maintenance](./maintenance#planned-node-maintenance) describes.
4. Take and verify the final restore point while the server is stopped.
5. Do phase 2.
   Find the migration Job of the new Helm revision. For the release `hephaestus`, its name is `hephaestus-migration-<revision>`.
6. Save its log: `kubectl --namespace hephaestus logs job/<migration-job> -c migration > migration.log`.
7. Require its `Complete` condition: `kubectl --namespace hephaestus wait --for=condition=complete job/<migration-job> --timeout=20m`.
   If the Job fails or times out, do not do phase 3.
   Keep the server stopped. Save the log and the failed change set: the chart deletes the Job after 24 hours.
   Then follow [If migration fails](#if-migration-fails).
8. Do phase 3.
   Phase 3 runs another migration Job for the same release, which has no change to apply.
9. Resume deployment automation only after its release and replica counts match the verified installation.
   On one host, keep it paused through the final installer run of [Upgrade the host](./k3s#upgrade-the-host).

A refused migration can follow changesets that it already committed.
An image or Helm rollback does not undo them.
Before you return to the old release, restore the matching pre-upgrade backup.

## Change a volume size

A StatefulSet does not allow a change of its `volumeClaimTemplates`.
The PostgreSQL StatefulSet has a volume claim template:

- `<release>-postgresql`, sized by `postgresql.persistence.size`.

If an upgrade changes its size, for example through a new profile, `helm upgrade` fails.
The error says `StatefulSet ... is invalid: spec: Forbidden: updates to statefulset spec for fields other than ...`.
With `--rollback-on-failure`, Helm then returns to the previous revision, and nothing changes.

Kubernetes cannot shrink a volume.
If the new size is smaller, keep the current size in your own values file, as [Storage and retention](./helm-chart#storage-and-retention) says.

If the new size is larger, do these steps for the PostgreSQL StatefulSet.
The volume of PostgreSQL is `data-<release>-postgresql-0`.
Before you start, take a backup ([Backup and restore](./backup-restore#back-up-the-database)).

1. Check that the storage class allows expansion:

   ```bash
   kubectl get storageclass
   ```

   If `ALLOWVOLUMEEXPANSION` is not `true` for the class of the volume, stop.
   Keep the current size in your own values file.

2. Make the volume larger. Use the new size from the chart in place of `<new size>`:

   ```bash
   kubectl --namespace hephaestus patch pvc data-hephaestus-postgresql-0 \
     --patch '{"spec":{"resources":{"requests":{"storage":"<new size>"}}}}'
   ```

3. Wait until `kubectl --namespace hephaestus get pvc` shows the new capacity.
   If the capacity stays at the old size, check the conditions of the volume:

   ```bash
   kubectl --namespace hephaestus get pvc data-hephaestus-postgresql-0 -o jsonpath='{.status.conditions[*].type}'
   ```

   `FileSystemResizePending` means that the storage driver resizes the file system only when the Pod starts again.
   Then continue with steps 4 and 5, and after step 5 delete the Pod: `kubectl --namespace hephaestus delete pod hephaestus-postgresql-0`.
   The StatefulSet starts it again with the larger volume.
4. Delete the StatefulSet and keep its Pods and volumes:

   ```bash
   kubectl --namespace hephaestus delete statefulset hephaestus-postgresql --cascade=orphan
   ```

5. Run the same `helm upgrade` again.
   Helm creates the StatefulSet with the new template.
   The new StatefulSet takes over the Pods and the volumes.
   It restarts a Pod only if the upgrade also changes the Pod template.

## Check that it worked

1. Run `helm history hephaestus --namespace hephaestus`.
   The new revision is `deployed`.
2. Read the log of the migration Job of that revision: `kubectl --namespace hephaestus logs job/hephaestus-migration-<revision>`.
   It logs `Database migration completed`.
3. Run `kubectl --namespace hephaestus get pods`.
   Each Pod of the new revision is ready.
4. Query `application_build_info` in Prometheus, as [Release metric](./metrics#release-metric) shows.
   Each server reports the new `version`.

## If migration fails

:::caution[CAUTION: Failed migration]
Do not clear checksums, edit released changelogs, or mark the changeset as run.
Do not run a release other than the previous one against the partly migrated database. If the migration guide entry of the new release starts with **Stop every role**, do not run the previous one either ([Rollouts and rollback](./runtime-roles#rollouts-and-rollback)).
Do not release a Liquibase lock by hand except as [One migration at a time](./runtime-roles#one-migration-at-a-time) allows.
Removal of a stale lock does not repair a failed migration.
:::

On a pull-based one-host install, follow [Recover a stopped cutover](./pull-based-deployment#recover-a-stopped-cutover) instead.
It adds the steps of the reconciler to this procedure.

1. Keep the server stopped.
2. Wait until the migration Job has stopped.
   `kubectl --namespace hephaestus get job hephaestus-migration-<revision>` shows its `Complete` or `Failed` condition.
   After its 24-hour TTL, an absent Job has stopped only if no migration Pod remains.
3. Save the Job log, the error and the identity of the failed changeset.
4. Save the `databasechangelog` and lock diagnostics and the target image lock.
5. If possible, take a forensic snapshot of the database volume.
6. If Helm reports a `pending-*` status, roll the release back: `helm rollback hephaestus <revision> --namespace hephaestus --wait`.
   After a stopped upgrade, use the phase-1 revision, which runs no server. After a rolling upgrade, use the previous revision.
7. Restore the pre-upgrade backup, as [Recover the live installation](./backup-restore#recover-the-live-installation) describes.
   Use the chart and the **previous signed release lock** of the previous release.
   Use its PostgreSQL image and extensions, and its encryption keys.
   That procedure starts the server with silent mode on, and ends when you turn silent mode off.
8. Report the actual recovery point and time, and any lost writes.
9. Keep the failed database until the investigation and your retention rules permit its removal.
10. On a pull-based one-host install: promote the recovered release, with **allow-rollback** if it is older than the failed upgrade.
    Until the channel names it, the next tick can apply the failed upgrade again.
11. On a pull-based one-host install: enable the reconcile timer again when the promotion has published the channel.
    The version check of the promotion passes when the host applies the channel.
    It fails if the timer stays off for 15 minutes.

To rehearse this procedure, cause a controlled migration failure only in a disposable rehearsal.
Restore the old backup and release, and prove the readiness and data integrity of the old release without a provider write.

## Rollback

:::caution[CAUTION: Images alone cannot reverse a schema change]
Reverting images alone is not a rollback.
Never run a release older than the previous one against a newer schema. [Rollouts and rollback](./runtime-roles#rollouts-and-rollback) says when the previous release can run on it.
Never reconstruct an old lock or resolve mutable image tags.
:::

To roll back, follow [If migration fails](#if-migration-fails) to restore the database, secrets and signed lock of the previous release.
