Back up the database, the keys and the release identity of an instance, and restore the instance from them.
The chart backs up the bundled PostgreSQL with pgBackRest to an S3-compatible bucket.
Backups are off by default. Turn them on before production: without a backup, the loss of the database volume loses all application data.
Hephaestus states no recovery-point or recovery-time objective. Rehearse a restore to measure your own.

## What to back up

| Data | Recovery requirement |
| --- | --- |
| PostgreSQL | Preserve application state, encrypted provider credentials, JWT signing keys, practice results and delivery history. |
| Encryption keys and configuration | Keep the keys and required Secret values outside the cluster as [Secret custody](./secret-custody#keep-the-required-keys-outside-the-cluster) describes. The database alone cannot recover encrypted values. |
| Signed release lock and site values | Restore the release and configuration that match the database. Verify its chart and image digests. |
| Platform recovery material | Keep the k3s token, datastore, manifests, certificates, and storage configuration as [Platform recovery material](#platform-recovery-material) describes. |

Repository mirrors and the inputs of running reviews are disposable.
The server rebuilds them from PostgreSQL and the provider.
Do not use copied review folders to resume a review.

Keep the database, the keys and the signed release identity together as one recovery set.
Keep the originals until a recovery is verified.

## Back up the database

With `postgresql.backup.enabled=true`, the bundled PostgreSQL archives its WAL to one S3-compatible bucket with pgBackRest.
`BACKUP_CIPHER_PASS` encrypts the repository.
The CronJob `<release>-postgresql-backup-full` takes a full backup each Sunday at 02:15 UTC.
The CronJob `<release>-postgresql-backup-diff` takes a differential backup on the other days at the same time.
`postgresql.backup.schedule.full` and `postgresql.backup.schedule.differential` change these schedules.
Each release runs the Job `<release>-postgresql-backup-stanza-<revision>`, which creates the stanza of the repository, so that the WAL archive works from the install.

The backup Jobs do not mount the PostgreSQL volume.
They read the data directory through the pgBackRest TLS server in the PostgreSQL Pod.
That server admits only a client certificate for the common name `hephaestus-backup` that `ca.crt` signed.

While the bundled PostgreSQL runs without backups, each `helm install` and `helm upgrade` prints a warning that links to this section.
The chart cannot see a backup that you take yourself, for example a volume snapshot. In that case, the warning stays.

1. Create a bucket for this instance alone, and an identity with read, write and delete rights in it.
2. Add `BACKUP_S3_KEY` and `BACKUP_S3_KEY_SECRET` to the release Secret.
3. Run `sh hephaestus-keys.sh --backups` to generate `BACKUP_CIPHER_PASS`, as [Create the Secret](./kubernetes#create-the-secret) describes.
   Keep a copy of the passphrase as [Secret custody](./secret-custody#keep-the-required-keys-outside-the-cluster) describes.
4. Set `postgresql.backup.clientTlsSecret` to a TLS Secret for the common name `hephaestus-backup`.
   It needs `ca.crt`, `tls.crt` and `tls.key`, signed by the PostgreSQL CA.
   The one-host platform issues `hephaestus-postgresql-backup-tls` and sets this value.
5. Set `postgresql.backup.enabled=true` and `postgresql.backup.s3` with the bucket, the endpoint host name and the region.
   Set `cidr` and `port` when the endpoint is in a private address range.
6. Optional: if a private CA signs the certificate of the endpoint, add the CA to the PostgreSQL TLS Secret as `s3-ca.crt`.
   Then set `postgresql.backup.s3.privateCa=true`.
7. Upgrade the release.

A failed WAL archive keeps the WAL on the PostgreSQL volume until the volume is full.
The [alert rules](./alert-rules.md) watch the WAL archive, the age of the latest backup and the free space of the volume.
[Backup bucket credentials](./secret-custody#backup-bucket-credentials) and [Backup cipher passphrase](./secret-custody#backup-cipher-passphrase) give the rotation of these values.

### Backup retention

`postgresql.backup.retentionFull` sets the number of full backup chains to keep, each with its differential backups.
Its default is 2.
This setting is a count, not a time limit.
Erased data can stay in a backup until pgBackRest expires that backup.
Keep the manifest of [Reapply erasures after a restore](./erasure-recovery) as long as any backup that can restore erased data.
This includes backup copies that you keep elsewhere.

## Platform recovery material

The database backup does not contain the Kubernetes datastore or the contents of other volumes.
Keep the k3s configuration, the installed platform manifests, and the storage layout with the recovery record.
Keep the server token outside the host, with restricted access.
The token decrypts confidential data in the k3s datastore.

Follow the [k3s datastore backup procedure](https://docs.k3s.io/datastore/backup-restore) for your datastore type.
SQLite and embedded etcd use different procedures.
A datastore backup does not replace the PostgreSQL recovery set.
Rehearse both on an isolated replacement host before you rely on host recovery.

## Restore

A restore replaces the bundled database with a backup.
It loses every change after the backup or the time that you select.
Only the keys that sealed the values of the restored database can read them.
Keep them as [Secret custody](./secret-custody#keep-the-required-keys-outside-the-cluster) describes.

Choose the procedure for the destination:

- [Isolated restore drill](#isolated-restore-drill): a disposable, isolated clone. It locks down the clone before any migration or server starts.
- [Recover the live installation](#recover-the-live-installation): the production instance. Do not lock down the live database.

Before you set `server.replicas` to 0, record `SHOW max_connections` and set `postgresql.parameters.max_connections` to that value.
Keep this override until WAL replay finishes. Include it in the recovery set for a replacement host.
The chart derives a lower connection limit when fewer servers run, but PostgreSQL refuses recovery below the source setting.
The [PostgreSQL recovery requirements](https://www.postgresql.org/docs/18/hot-standby.html#HOT-STANDBY-ADMIN) describe this constraint.

The restored database has the role passwords that it had at the backup.
The migration Job sets the passwords of `hephaestus_owner` and `hephaestus_app` from the Secret again.
If `DATABASE_ADMIN_PASSWORD` changed after the backup, put the old value back in the Secret before the restored PostgreSQL starts.

### Prepare replacement storage

On a replacement host, restore the release keys, TLS Secrets, verified chart and site values first.
Keep migration disabled and `server.replicas` at 0.
Keep the failed volume until the recovery is verified.

Before you enable the restore, provision an empty claim named `data-<release>-postgresql-0` in the release namespace.
Use the PostgreSQL storage class, access mode and size from the site values.
For node-local storage, bind the new volume to the replacement node.
The restore Job needs this claim before PostgreSQL starts.
Do not initialize a new database in it.

Then follow the isolated or live procedure below.

### Deny external egress

The chart has no switch that turns off external egress.
Narrow the egress range in your site values instead.
With these values, the server can reach no provider, model endpoint or mail server outside the cluster:

```yaml title="values.yaml"
networkPolicy:
  externalEgress:
    cidr: 192.0.2.1/32
    except: []
  modelEndpoints: []
  scmEndpoints: []
  modelGatewayPorts: []
postgresql:
  backup:
    s3:
      cidr: 203.0.113.0/24 # The addresses of your bucket endpoint
```

The range `192.0.2.0/24` is reserved for documentation, so no host answers on `192.0.2.1`.
PostgreSQL, the backup Jobs and the restore Job reach the bucket through `postgresql.backup.s3.cidr`.
Without it, they use `networkPolicy.externalEgress`, and the restore and the WAL archive stop.
Set it to the addresses of your bucket endpoint, and set `postgresql.backup.s3.port` if the endpoint does not use 443.
The narrow range also stops the Alertmanager of the bundled monitoring stack from reaching receivers on the internet.
It has an effect only where the network plugin enforces NetworkPolicies.

To open egress again, upgrade with your site values without these values.

### Isolated restore drill

Do this procedure only on a disposable, isolated clone.
Run the clone on its own host or cluster, with its own database, domain and credentials.
A different release name or namespace alone does not isolate it.
Its lockdown SQL changes the control settings of the clone.

1. Add the values of [Deny external egress](#deny-external-egress) to your site values.
   Keep them for the whole drill.
2. Upgrade the release with `postgresql.backup.restore.enabled=true`.
   Set `postgresql.backup.restore.time` to restore the database as it was at that time, for example `2026-10-24 18:00:00+00`.
   Leave it empty to restore the latest backup and every archived WAL segment.
   While the setting is on, the server and PostgreSQL stop, and the backups pause.
3. Wait for the Job `<release>-postgresql-backup-restore-<revision>` to complete:

   ```bash
   kubectl --namespace hephaestus wait --for=condition=complete \
     job/hephaestus-postgresql-backup-restore-<revision> --timeout=30m
   ```

   The Job retries while PostgreSQL still shuts down.
4. Upgrade with `postgresql.backup.restore.enabled=false`, `migration.enabled=false` and `server.replicas=0`.
   PostgreSQL alone replays the WAL up to the target.
5. Wait until this command prints `f`. Readiness does not prove that the replay finished.

   ```bash
   kubectl -n hephaestus exec hephaestus-postgresql-0 -c postgresql -- \
     sh -c 'exec psql -Atc "SELECT pg_is_in_recovery()" -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
   ```

6. Apply the lockdown SQL from the verified chart, before any migration or server starts:

   ```bash
   kubectl -n hephaestus exec -i hephaestus-postgresql-0 -c postgresql -- \
     sh -c 'exec psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
     < "chart-$VERSION/hephaestus/files/restore-clone-lockdown.sql"
   ```

   It turns on silent mode, pauses feedback and review triggers in each workspace, and turns off each conversation model.
   If it prints `restore clone lockdown did not engage`, stop.
7. Resolve provider write receipts before the server starts.
8. Upgrade with `migration.enabled=true` and `server.replicas=1`. Verify the migration, readiness and authenticated reads.
9. To run test reviews on the clone, use only controlled providers.
   Follow [Prove silence](./silent-deployment#prove-silence) before you open any external destination.

Rehearse a restore on a copy of the instance before you need one.

### Recover the live installation

A restore also reverses account suspensions, session revocations, recipient consent and deletions after the backup.
Sessions issued after the backup must sign in again. Sessions revoked after it can become valid again.
PostgreSQL loses the delivery history after the backup. Thus, the server cannot prevent duplicate external writes.
Scheduled sync cannot recover every event in the gap.

1. Set `server.replicas=0`, remove the sandbox workloads as step 4 of [Planned node maintenance](./maintenance#planned-node-maintenance) describes, and pause reconciliation.
   This stops traffic and provider reception.
2. Keep a copy of the failed data. Record the chosen recovery point and the expected lost writes.
3. Add the values of [Deny external egress](#deny-external-egress) to your site values.
4. Do steps 2 to 5 of the [isolated restore drill](#isolated-restore-drill).
   Do not apply `restore-clone-lockdown.sql` to the live database.
5. Turn on silent mode in the restored database, and read it back.
   The backup keeps the silent mode setting that it had, so it can be off.

   ```bash
   kubectl -n hephaestus exec -i hephaestus-postgresql-0 -c postgresql -- \
     sh -c 'exec psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
   UPDATE instance_settings
   SET silent_mode_engaged = TRUE,
       silent_mode_reason = 'Restore: silent until proved',
       silent_mode_changed_at = now(),
       silent_mode_changed_by_account_id = NULL,
       version = version + 1
   WHERE id = 1;
   SELECT silent_mode_engaged FROM instance_settings WHERE id = 1;
   SQL
   ```

   The last line prints `t`.
   Check the delivery status, the review triggers and the conversation models of each workspace against the intended live settings.
6. Upgrade with `migration.enabled=true` and `server.replicas=0`. Wait until the migration Job of the revision is `Complete`.
7. Reapply the erasures after the recovery point, as [Reapply erasures after a restore](./erasure-recovery) describes.
   Do this also when no erasure occurred: the manifest then declares that no erasure followed the recovery point.
8. Upgrade with your site values, the values of step 3 and the recorded `server.replicas`.
   Verify readiness, authenticated reads and encrypted values.
   If a value cannot be decrypted, keep the signing keys. Diagnose a missing encryption key apart from corrupt signing data.
9. From the restricted incident record, reapply the account suspensions, session revocations and consent withdrawals after the backup.
   Do this before access or delivery resumes.
10. Remove the values of step 3, and upgrade with your site values. Keep silent mode on.
11. Recover the provider writes and deliveries of the gap, as [Reconcile provider writes after a restore](./reconcile-after-restore) describes.
12. Prove silence and turn off silent mode, as [Prove silence, then turn off silent mode](./silent-deployment) describes.
13. Resume reconciliation only after its release and apply mode match the recovered deployment.

Restore with the signed release lock of the backup, then upgrade. Do not restore into an older release.

## Check that it worked

After you turn on backups:

1. Run `kubectl --namespace hephaestus get jobs`.
   The stanza Job and the latest backup Job are `Complete`.
2. Check that `HephaestusBackupStale` does not fire ([Alert rules](./alert-rules)).
3. Restore the latest backup on a clone, as [Isolated restore drill](#isolated-restore-drill) describes.

After a restore:

1. `SELECT pg_is_in_recovery()` prints `f`, as step 5 of the isolated restore drill shows.
2. The migration Job of the revision is `Complete`, and its log has `Database migration completed`.
3. `kubectl --namespace hephaestus get pods` shows each server Pod ready.
4. Sign in to Hephaestus. A sign-in needs the restored JWT signing keys, which only the matching encryption key decrypts.

## Unsupported PostgreSQL versions

Use the PostgreSQL version and image of the verified release.
The [compatibility policy](./compatibility-policy) states the supported versions and upgrade prerequisites.
