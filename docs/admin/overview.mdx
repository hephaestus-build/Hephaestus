This guide is for people who run a Hephaestus deployment.
It has five parts:

- **Deploy** installs the supported stack.
- **Configure** connects providers, AI models, and practices.
- **Operate** covers upgrades, backups, troubleshooting, and incidents.
- **Security and compliance** covers the threat model, keys, release verification, legal pages, and data protection.
- **Reference** lists every setting, the server runtime, network egress, sizing, and what a version number promises.

Developers who use Hephaestus need the [User guide](/user/overview).
People who change the code need the [Contributor guide](/contributor/overview).

## Choose an install path

Each path installs the same signed Helm chart with a different profile.
After the install, each path continues at [First steps § 3. Sign in](./first-steps#3-sign-in).

| Where you install | Install page | Profile |
| --- | --- | --- |
| One Linux host. The installer sets up k3s and the platform for you. | [Install on one host](./k3s) | `small.yaml`. The installer selects it. |
| A cluster on which you are a cluster-admin | [Install on a Kubernetes cluster](./kubernetes) | `small.yaml` for one node. `dev.yaml` for a trial without reviews. |
| A cluster on which you are not a cluster-admin, or a cluster of several nodes | [Install on a managed cluster without cluster-admin](./managed-cluster) | `cluster.yaml` |

[Profiles](./helm-chart#profiles) gives the size and the use of each profile.

## What a deployment consists of

This view shows who uses Hephaestus and which services it connects to.
Each grey dashed box marked `«external»` is a service that you connect.
Each arrow points from the side that starts the exchange. GitHub, GitLab and Slack start some exchanges too: they send work events and questions.
An admin is a workspace admin or an instance admin, as [Two kinds of admin](#two-kinds-of-admin) explains.

GitHub or GitLab is required: it supplies the work and the sign-in.
Slack, Outline and email are optional.
A model provider is required for reviews and conversations. Only Hephaestus holds its key.

One application image runs the server.
PostgreSQL stores the data of the deployment, including the provider events that wait for processing.
A Gateway API controller in front of the release handles TLS.
The server starts a sandboxed container in a separate namespace for each practice review.
It does not keep that container between reviews.
[What the chart runs](./helm-chart#what-the-chart-runs) shows each Pod, its storage and its network policies.

## Two kinds of admin

- **Instance admin** — operates the whole deployment. This includes AI providers, instance-wide settings, and the practice catalog that workspaces can adopt from.
- **Workspace admin** — configures one workspace. This includes its repositories, practices, members, AI model, and cap on AI spend.

A person can be both.
[Instance administration](./instance-admin) covers the operator console.
[Integrations](/user/integrations) covers workspace connections.

## Set it up in this order

1. Install Hephaestus on the [path that fits your platform](#choose-an-install-path).
   Then follow [First steps](./first-steps) for the login provider, the first admin, and the first review.
2. Connect a source of repository activity: [GitHub](./github-integration) or [GitLab](./connect-gitlab).
   [Connect Slack](./connect-slack), [Connect Outline](./connect-outline) and [Set up email](./set-up-email) cover the other integrations.
3. [Connect an AI provider](./ai-providers) with a supported API.
4. [Set a cap on AI spend](./instance-admin#usage) for each workspace.
5. [Choose practices](./practice-catalog) for the instance to include and the workspace to adopt.
   [Practice reviews and feedback mode](/user/practice-reviews) explains how a review runs.
   [Scans](/user/scans) explains default-branch review and SARIF export.
6. [Publish the legal pages](./legal-pages) with imprint and privacy information for your deployment.
   The [data-protection documentation](./dsms) has the GDPR records.

- [Sizing and scaling](./sizing) gives the resource budget.
- The [production operations runbook](./production-operations-runbook) covers incident brakes, silent deployment, PostgreSQL restore, and removal of external feedback.
- [Practice review operations](./practice-review-operations) and
  [webhook ingestion operations](./webhook-ingestion-operations) cover the two pipelines whose failures are most visible.
