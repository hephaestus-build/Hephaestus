# Practice review operations

Use this reference to configure the runtime and monitor a deployed instance. Workspace admins
should start with [Practice Review](./practice-review.mdx).

Public feedback addresses the author’s work.
`PUBLIC_SUBJECT_INELIGIBLE` means the recorded subject or its support does not qualify for that public placement.
Reviewer observations remain recorded for the reviewer.
Private feedback must pass its own evidence, recipient and delivery checks.

## Deployment configuration

Server configuration metadata defines property names, types, and defaults.
The reference Compose files determine which environment variables reach the application.
Agent execution alone does not enable repository collection.
Each workspace enables practice review and selects its own coverage.

1. Enable the agent runtime on both the submitting server and claiming worker.
2. Enable `GIT_CHECKOUT_ENABLED` for repository access.
3. Give every server and worker container its own storage under `HEPHAESTUS_FABRIC_ROOT` for repository mirrors and attempt inputs.
4. Set campaign, request-rate, retry, and retention limits appropriate to the deployment's budget and governance policy.

A review measures one practice group at a time.
By default, groups with more than six practices are split into smaller sets.
Each set has a separate work budget.
Within a set, each practice gets a fresh model session, in order.
Work, not time, bounds the set.

`PRACTICE_REVIEW_PRACTICE_MODEL_CALLS` (default 12) and `PRACTICE_REVIEW_PRACTICE_OUTPUT_TOKENS` (default 16000) determine each set's budget.
Each value is multiplied by the number of practices in the set, with a minimum of three.
A set of five practices can make 60 model calls and write 80,000 output tokens.

The model calls of precompute scripts have their own attempt token limit.
`PRACTICE_REVIEW_PRECOMPUTE_MAX_TOKENS_PER_ATTEMPT` (default 200000) sets it.
See [Cost and limits](./ai-providers.mdx#cost-and-limits).
[Precompute scripts](#precompute-scripts) tells you how to read what each script did.

The defaults cap excessive work at several times a set's normal use.
A review spends what its practices need, and no more.
Each set has its own budget, independent of previous sets' spend.
Near the budget limit, the model receives a request to record its current results.
The set ends after the call that spends the budget.

Each composition pass gets at most one full set's work budget.
All passes share the remaining whole-run safety ceiling.

1. For a model that reasons at length, raise the output tokens.

The timeout of the workspace's **Practice reviews** assignment is the whole-run safety ceiling.
It can stop a productive review and leave later practices `NOT_REACHED`.
Independent set budgets do not reserve time for every set.
If a set has no streamed token or tool progress for five minutes, it stops.
Two consecutive stalls end measurement with its recorded results.

A timeout below 151 seconds runs at 151 seconds.
The precompute scripts run first, inside the same timeout, as the [workspace ABI](/contributor/agent/agent-workspace-abi#precompute-validation-and-limits) describes.

`PRACTICE_REVIEW_SAMPLING_TEMPERATURE` sets the sampling temperature for practice-review model calls, not mentor calls.
If unset, the provider default applies.
A low temperature does not guarantee repeatable judgments.
Do not set `0` for an open model whose vendor advises against greedy decoding.
Such a model can repeat the same tool call until the review stops that practice group.
Use the model's recommended sampling or the provider default.

Before you change an environment variable:

1. Read the [server configuration](https://github.com/hephaestus-build/Hephaestus/blob/main/server/application/src/main/resources/application.yml).
2. Read the [reference Compose files](https://github.com/hephaestus-build/Hephaestus/tree/main/docker).
3. Use a value that the selected model supports.
4. Confirm that the deployment forwards the setting.
5. Evaluate changes against representative cases.

Unknown variables or variables that the deployment does not forward cannot configure the application.
Repository mirrors and attempt folders are disposable container-local storage, not a shared evidence store.
Each container keeps bare mirrors under its own `HEPHAESTUS_FABRIC_ROOT`, which defaults to `/data/git-repos`.
The shipped Compose files mount `git-repos` into the server and `worker-git-repos` into the worker.
A missing mirror is cloned again on the next sync or review.

Git runs in-process through JGit, with no `git` binary or second image.
Commit ingestion uses the server role and its mirrors.
Review preparation uses the worker role and its mirrors.
A server with its worker role enabled uses one root for both.
Attempt folders use the same root.
Sandbox inputs and results pass through the authenticated worker gateway.

PostgreSQL retains admitted observations and their citation verification results.
Delivery does not require the worker's source files.
[ADR 0041](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0041-compose-1x-kubernetes-2.md#evidence-admission-and-deletion) defines the storage and cleanup contract.

Source authorization is not a deployment switch.
The shipped artifact-source contract fixes which governed sources each purpose can use.
Integrations only determine which authorized sources are available.
See [Artifact-source governance](./dsms/artifact-source-governance.md).

### Queue health

The job queue exposes its own signals.
Use them for alerts instead of application logs.

- **`agent.queue.oldest_age_seconds`** — age of the oldest eligible queued job. It is `0` when empty.
  Sustained growth needs an alert.
  Queue depth alone does not distinguish a temporary burst from a persistent backlog.
- **`agent.queue.depth`** — queued jobs eligible to run now.
- **`agent.queue.held`** — jobs held on an exhausted budget.
- **`agent.queue.running`** — jobs active across the fleet.
- **`agent.queue.health.sampler.failures`** — failed samples.
  Gauges keep their last-good value instead of a false empty-queue report.
- **`agent.job.claim.latency`** — time from a job's eligibility to its claim.
- **`agent.job.execution.duration`** — tagged by `jobType` and outcome `status`.
- **`agent.job.delivery.recovered`** — deliveries stopped by an executor crash and successfully retried.
- **`agent.job.retention.stripped`** / **`agent.job.retention.deleted`** — rows pruned by the retention sweep.
- **`llm.budget.exhausted`** / **`llm.budget.blocked`** — a crossed cap and work refused at a cap.
- **`llm.proxy.budget.blocked`** — model calls of a running job that the LLM proxy refused at a cap, tagged by `apiProtocol` and `cap`.
  `instance` names the shared-model budget, and `byo` names the provider cap.
  An admin raises it.
  `precompute_attempt` names the [attempt token limit](./ai-providers.mdx#cost-and-limits).
  An operator raises it with `PRACTICE_REVIEW_PRECOMPUTE_MAX_TOKENS_PER_ATTEMPT`.
- **`practice.review.occasions`** — live issue-update recording attempts, tagged by `signal` and `outcome` (`deferred` or `duplicate`).
  These exclude issue opening and closing.
- **`practice.review.refused`** — refused reviews, tagged by `phase` (`submission` or `execution`) and `reason`.
  Submission reason `coalesced` counts displaced issue-update snapshots, not review failures.
  These counters measure attempts, including rolled-back transactions.
  The occasion trace shows committed outcomes.
- **`practice.feedback.dispatch`** — durable-dispatch outcomes, tagged by bounded `destination` and `state`.
  Sustained `UNCERTAIN` or `FAILED` outcomes need an alert.
  `UNCERTAIN` means delivery is not yet confirmed.
  `FAILED` is terminal after the retry limit or an unrecoverable dispatch record.

1. Query `/actuator/health/readiness` on the [management listener](./observability.mdx#scrape-metrics), or `/readyz` on the application port, for aggregate readiness.

An authorized response includes the **`practiceReview`** component.
An enabled review worker reports `OUT_OF_SERVICE` with `GIT_CHECKOUT_DISABLED` when repository checkout is disabled.
It reports `SOURCE_AUTHORIZATION_EXPIRED` when an automated-review source authorization has expired.

Missing model assignments are workspace-specific.
They stay visible under **Practices → Practice reviews → Work** and in the refusal counter.
They do not remove the worker from service.
Gauges have periodic samples.
Timers and counters record their corresponding events.
Metric names in the instrumented code are authoritative for dashboards and alerts.

### Precompute scripts

A practice's precompute script runs before the review and points it at places to check.
For each review, Hephaestus records what each script did.
Workspace admins see it in two places:

- **The trace line.** Open the work under **Practice reviews → Work**, then **Every practice**.
  The column **What it saw** has one line for each practice with a script.
- **The section Precompute scripts of the review.** Open the review under **Practice reviews → Reviews**, or select **Details** in the trace line.

[Write a precompute script](./precompute-scripts.mdx) tells how to write and try a script.

#### The trace line

The line starts with how the script ended.
If some model calls of the script were not rated, the line adds their count.
An example is `5 calls were not rated.`
Then it has at most one link that fixes the cause, and **Details**.
**Details** opens the review's section **Precompute scripts**.

| The line starts with | What it means | What to do |
| --- | --- | --- |
| **Precompute script found** | The script ran to its end. It gave the review the places that the line counts. | Nothing. If the line links **Check the decision model**, or the model that it names, a model caused calls that were not rated. Open its row and check it. |
| **Precompute script handed the review no places** | The script ran to its end and gave no places, but some of its model calls were not rated. It does not mean that the work has nothing to check. | Select **Details** and read the reasons. If the line links **Check the decision model**, or the model that it names, open its row and check it. |
| **Precompute script did not run** | The review had no model that the script requires. Either no model is assigned for the reviewed developer's AI choice, or the assigned model does not meet the rule in [Privacy](./ai-providers.mdx#privacy). The line names the model, such as `no decision model was set for this review`. The review checked the practice without the script. | Select **Assign a decision model**, or the link for the model that the line names. Assign a model for that tier. If the review ran on an In-house model, assign an In-house model. |
| **Precompute script failed** | The script stopped with an error, returned a result that is not valid, or its process ended without a result. | Select **Edit the script**. The review's section shows the first line of the error. To reproduce it, [run the script on the same change](./precompute-scripts.mdx#run-a-script-on-your-own-change). |
| **Precompute script ran out of time** | The script passed its deadline, or the precompute stage ended before the script started. | If many scripts in one review run out of time, raise the timeout of the **Practice reviews** assignment on **AI models**. Otherwise, make the script faster. |
| **Precompute script did not finish** | The script was staged, but the stage stopped before the script reported a result. | Same as for a script that ran out of time. If it continues, read the container logs that the job record keeps. When the stage fails, they hold the end of the precompute runner's log. |

A script that failed, ran out of time, or did not finish can still have given the review places.
Then the line adds them.
An example is `Precompute script ran out of time but found 3 places to check.`

Some causes have no single fix in the workspace.
For them, the link opens a section of this page:

- A script that ran out of time or did not finish links **Why scripts stop early**.
  It opens [The trace line](#the-trace-line), and the table above tells what to do.
- A script that ran to its end can have calls that were not rated only for such causes.
  These causes are a spent token limit, budget or cap, a slow model, and a call with too many entries.
  Then the script links **Why calls go unrated**.
  It opens [Calls that were not rated](#calls-that-were-not-rated), which tells who fixes each cause, and where.

The stage takes its time from the timeout of the **Practice reviews** assignment.
The [workspace ABI](/contributor/agent/agent-workspace-abi#precompute-validation-and-limits) gives the time limits of the stage and of each script.

#### The review's precompute scripts

A review that ran at least one script has the section **Precompute scripts**.
It is between the review's output and **How this review ran**.
It has one row for each script:

| Column | What it shows |
| --- | --- |
| **Practice** | The practice. It links to the practice. A practice that the workspace no longer has shows its identifier and **Not a current practice**. |
| **Result** | **Found 3 places**, **Found no places**, **Handed the review no places**, **Did not run**, **Failed**, **Ran out of time**, or **Did not finish**. A script that ended early but gave places adds them, such as **Failed, found 2 places**. Below the result is the same fix link as in the trace line. A practice that the workspace no longer has shows no **Edit the script**. For a script that failed, the first line of the error comes last. |
| **Models** | Each decision, embedding or reranking model that the script declared or called. An icon shows the tier of the model that the review had for it. A declared model that the review did not have and that made no calls shows **No model**. The review's own chat model never shows here. |
| **Not rated** | The model calls that were not rated, with one line below for each reason, such as `5 too slow` and `1 wrong format`. [Calls that were not rated](#calls-that-were-not-rated) gives what to do for each reason. |
| **Calls** | The decision, embedding and reranking calls that the proxy recorded for the script. A script that did not run, or that uses no such model, shows a dash. |
| **Time** | How long the script ran, such as `4.2 s` or `2 min 5 s`. A run shorter than 0.1 seconds shows `< 0.1 s`. A script that did not run or did not finish shows a dash. |

A script that gave no places while some of its calls were not rated shows **Handed the review no places**.
It does not mean that the work has nothing to check.

The section shows no cost.
Its note says `Spend is on AI usage.`
**AI usage** shows the cost of precompute models by practice.
The card **How this review ran** shows the review's **Model** with an icon for its tier.
Its **Review model calls** and token counts include the chat calls of the scripts, because those calls use the review's model.
They do not include the decision, embedding and reranking calls.

#### Calls that were not rated

A model call that was not rated has a reason.
The count is model calls, not places.
A reason never means that the script found nothing.
This table is the one list of reasons.
The column **In a script** gives the name that a script and the section that the review reads use.

| Reason | In a script | What it means | What to do |
| --- | --- | --- | --- |
| model missing | `unavailable` | No model of that slot was available to the script. | Assign the model. **Check the decision model**, or the link for the model that the row names, opens its row. |
| limit reached | `budget` | A token limit cannot hold the call, or the shared-model budget or the provider cap is spent. For `agent`, no `submit` call came within `maxSteps`. | Raise the limit that was spent. The list below tells who raises each limit, and where. |
| too slow | `deadline` | The script's deadline passed before the model answered, for example because the model was slow or had to load first. A call that the script aborted also has this reason. | Ask the operator of the model's host to keep the model loaded, or assign a faster model. |
| too large | `too-large` | The call held more entries than one call can send, or the script found an item too large to send. The runner refuses a call with too many entries before it reaches the model. | Ask the script's author to send fewer entries in one call. [Limits](./precompute-scripts.mdx#limits) gives the limits. |
| wrong format | `off-format` | The model's answer did not have the expected shape. In the section that the review reads, a lead that did not resolve also has this reason. | The model is not suitable for this purpose. Choose another model. |
| declined | `refused` | The model declined to answer. The script sets this reason. | Choose another model. |
| failed | `error` | Any other failure, such as an error from the provider or a rate limit. | Check the provider and the connection. |

The column **Not rated** counts only the model calls that the runner could not finish.
Thus, it never shows `refused`.
The `unrated` entries that a script returns reach only the section that the review reads, as [What the review reads](./precompute-scripts.mdx#what-the-review-reads) tells.

A token limit, a budget or a cap stops calls in one of these places:

- **The token limit of the practice**, `meta.tokens`, or the `maxSteps` of `agent`.
  The script's author raises it in the script, or makes the script send less.
  [Limits](./precompute-scripts.mdx#limits) gives the limits.
- **The attempt token limit.**
  An operator raises it with `PRACTICE_REVIEW_PRECOMPUTE_MAX_TOKENS_PER_ATTEMPT`.
  See [Cost and limits](./ai-providers.mdx#cost-and-limits).
- **The shared-model budget.**
  Only an instance admin raises it on **Instance admin → AI usage** with **Change budget**.
- **The provider cap of the workspace's own provider.**
  A workspace admin raises it on **AI usage** with **Change provider cap**.

On **AI usage**, the tile of a purse whose budget or cap is spent shows **Paused**.
A purse with a budget or cap also pauses when some of its usage has no price.
Its tile then shows **No price set**, and an alert gives the number of runs that have usage without a price.

A failed or stopped script never becomes a claim about the developer's work.
The review checks the practice from the sources.

#### Precompute metrics

Two metrics count precompute events on the worker:

- **`agent.review.precompute.scripts`** — one count for each script run that the report of a review attempt records, tagged by `status`: `ok`, `skipped`, `failed`, `timed_out` or `not_finished`.
  A staged script that a complete report does not name counts as `not_finished`.
  A missing report adds no count.
  A truncated report adds no count for the scripts that it does not name.
  An entry that is not valid adds no count.
  It counts when the attempt's results are stored.
  A growing share of `failed`, `timed_out` or `not_finished` needs attention.
  `skipped` usually means a missing assignment.
- **`llm.proxy.precompute.unattributed`** — precompute calls that the proxy refused with HTTP 400, because they named no valid practice.
  It is 0 when the server and the agent image come from the same release.
  A value above 0 means that the agent image does not send the practice of each call.
  Run the agent image of the server's release.

[Queue health](#queue-health) lists `llm.proxy.budget.blocked`, which also counts the precompute calls that a budget, a cap or the attempt token limit refused.

### Issue-update queue

Live issue updates become eligible 30 seconds after the last newly queued snapshot, or when the oldest reaches five minutes.
The server checks every five seconds and processes at most 100 issues per sweep.
Opening and closing are separate occasions and do not wait in this queue.

A return to an already-pending snapshot does not reset eligibility.
Queue load, contention, and failures can delay submission beyond eligibility.
Job-queue gauges exclude these pre-submission occasions.

### Log correlation

The application emits one JSON object per log line.
Worker logs use correlation keys under `mdc`.
The shipped Compose stack already has the necessary filter tools.

1. From your deployment directory, filter the logs:

```bash
# All log lines for one agent job
docker compose logs --no-log-prefix application-worker \
  | jq -cR 'fromjson? | select(.mdc."job.id" == "<job-uuid>")'

# All errors for one workspace
docker compose logs --no-log-prefix application-worker \
  | jq -cR 'fromjson? | select(.mdc."workspace.id" == "<workspace-id>" and .level == "ERROR")'
```

A deployment with its own log collector can use the same `mdc` fields for dashboards and alerts.
The collector's label names are deployment-specific.

**Retention.** The application strips terminal job payloads before it deletes their rows.
A row retention shorter than payload retention is inconsistent, and the application refuses startup.

1. Treat the fabric root as sensitive storage.

Delivery-policy evaluations and dispatch intents follow their review ledger.
Disconnect, person erasure, and workspace purge remove the matching copies.
A sent or withheld dispatch projects into that ledger.
Then its duplicate summary and inline-comment payload is erased.
The destination key and provider references remain as the idempotency record.

A failed dispatch keeps its package because a workspace admin can still retry it.
Selected coverage targets follow their workspace membership or monitored repository.

**Dispatch recovery.** One dispatch owns the exact summary and inline comments in a review.
Each summary comment has a stable marker.
Each inline comment has a recurrence key.
Before summary creation, the dispatch searches the reviewed work's comments for its marker:

- **Found** — it records the comment and never creates it again.
- **Search inconclusive** — it stays `UNCERTAIN` and retries later.
- **Search complete, nothing found** — it creates the summary only if no earlier attempt closed its write fence.

A summary can have no inline comments and exactly match the last recorded summary delivered on the same work for the same person.
In this case, the dispatch withholds it as `REPEATS_DELIVERED_NOTE` instead of creating it.
If the earlier summary has a correction or awaits restoration of its original text, no comparison occurs.
The new summary is then created.

The check uses only the delivered ledger, after delivery policy permits the write.
Two reviews with summaries still in dispatch can each post one on the same work.

**Reviewed work.** Before each new summary or line note, a pull request or merge request package checks its authorized capture.
The captured head, title and description must match the work Hephaestus last synchronized.
An approved package must also match the proposal's recorded commit, when present.
An unchanged commit alone does not establish unchanged words.

The comparison and delivery policy run together while the work is locked.
The write receipt commits before the provider call.
A change that Hephaestus has not synchronized yet does not stop the write.
The reservation also does not order when the provider receives the request.

- **Same captured work** — the create proceeds when delivery policy still permits it.
- **Changed captured work** — nothing more is created.
  An automatic package is withheld as `REVIEWED_REVISION_CHANGED`, an approved one as `APPROVAL_STALE`.
  Comments already posted stay and remain recorded.
- **Comparison unknown** — nothing is created.
  Automatic and approved packages retry without a withholding reason.
  Missing capture or source authorization can prevent comparison even when both commits are known.
- **Delivery policy now refuses** — nothing more is created, with the existing exact policy reason.

Copies an earlier attempt may have posted are still looked up first, against the reviewed commit.
An unconfirmed write is never settled unseen.
The [review pipeline](/contributor/practice-review-pipeline#copies-on-the-reviewed-work-are-immutable) describes the reservation boundary.
Its [observation section](/contributor/practice-review-pipeline#observation) describes how new reviews retain their occasion and prior reviews keep their ordering.

**Where inline comments land.** GitHub inline comments are review comments on the lines.
GitLab inline comments are ordinary merge request comments.

Each starts with a static link to the file and lines at the reviewed commit, built from the workspace's configured GitLab server.
GitLab does not attach them to the lines, so they are not diff notes and are never resolved, edited or deleted by Hephaestus.
The ledger records them as `LOCATION_COMMENT` placements with the proposed file and lines, and the comment's own link.
Diff notes and fallback comments that earlier versions posted are still recognized as copies.
A GitLab anchor on the old side of the diff is not posted, since the reviewed head has no lines to link to.

The write fence closes after delivery policy permits the write and before provider-adapter preparation.
That preparation checks the rate limit and resolves the pull request, merge request, or issue before the create request.

If the adapter fails before the create request, the attempt reopens its own fence while it still holds its lease.
The dispatch becomes `SENT` only after the whole package converges.
A sustained `UNCERTAIN` dispatch has two different explanations:

- **Fence open: no create request has been sent.**
  The last attempt could not complete the marker search or failed before delivery.
  Causes include provider connectivity, credentials, a critical rate limit, or work the provider no longer resolves.
  The dispatch retries with backoff.
  It becomes `FAILED` after its retry budget is spent.
  A review whose target cannot be named at all fails the same way.
- **Fence closed: a create request was sent, or may have been, and its outcome is unknown.**
  Hephaestus never sends that create again.
  Each later attempt searches for the marker.
  A found comment completes the dispatch.
  A search that finds nothing leaves it `UNCERTAIN` with no retry budget.
  Thus, it never reaches `FAILED`, and nothing is automatically resent.

An absent marker now does not prove that feedback was never delivered.
The provider can show the comment later.
A resend requires an operator-approved recovery procedure.
Hephaestus has no action for it.

**CAUTION:** Do not edit a dispatch row to force a resend.
The state, write fence, retry count, and lease jointly prevent a duplicate comment.

1. Deliberately reconcile a fenced dispatch against the provider's own record of the reviewed work and its comments.

## Limits you should know about

Configuration metadata describes deployment settings.
The artifact-source catalog defines capture semantics.
These behaviors matter independently of configured capacity:

- **Background task cadences are fixed in code.**
  Their thresholds can be configurable even if their poll schedules are not.
- **Feedback preparation recovery has a bounded window.**
  The sweeper selects recent completed pull request and issue reviews with missing preparation marks.
  It does not automatically recover older unfinished preparation.
  A successful empty result is complete.
  Recovery does not rerun the model.
- **Retryable occurrences eventually lapse.**
  A misconfigured workspace can accumulate retries and then become quiet when their deadline passes.
- **Nothing is ever deleted from the occurrence ledger**, in any state, including retired rows.
  It records what was *not* done and only grows.
  A busy instance needs storage sized for that growth.
- **Repository capture includes every regular and executable file at the reviewed commit**.
  This includes binary content and large files.
  It includes sanitized Git history reachable from that commit, mirrored branches, and tags.
  Native bash, Git, ripgrep, and file-discovery tools are available.
  File count and content size do not truncate the tree.
  Symbolic links become regular files with the link target, without traversal of the link.
  Submodules are not hydrated.
  Their presence and excluded unsafe paths cause a partial-capture report.
  A snapshot entry that is not a regular file or directory fails capture.
  Capture keeps committed Git LFS pointers instead of downloads.
  Model-facing output limits do not bound capture storage.
  The captured worktree and Git metadata are read-only, with no repository credentials or upstream configuration.
  Reviews use an isolated internal Docker network.
  The authenticated worker gateway must be reachable on it.
- **Repository preparation is bounded per snapshot and per walk.**
  Server and worker roles use JGit for capture.
  This needs no sandbox admission and does not count against `SANDBOX_MAX_CONCURRENT`.
  `GIT_MAX_CONCURRENT_INGESTIONS` (default 2) caps captured commits that a container writes to PostgreSQL simultaneously.
  A checkout plus mirrored history over `GIT_MAX_SNAPSHOT_BYTES` (default 8 GiB) causes refusal of the whole repository.
  Measurement occurs before the snapshot is written.
  Refusal fails the operation and never selects a smaller tree.
  The mirror itself has no measurement against this limit.
  A commit-history walk reads pages of 256 commits.
  It pauses after 32 pages that needed capture.
  Pages whose commits were all previously captured do not count.
  The next sync cycle resumes from captured commits.
- **Linked Outline documents are retrieval-limited, and the mentor and review paths do not agree.**
  A review first resolves documents *linked from* the work, then adds a small number by search.
  The mentor searches the whole corpus and truncates each document.
  Neither path can report that it found everything.
  Neither substitutes for the other in diagnosis of missing context.
- **Work that has been deleted at the provider yields a review with no evidence, not an empty one.**
  After reconciliation finds work missing upstream, evidence capture reports its sources as unavailable.
  The review stops without an observation about that work.
  If the work reappears, the next ordinary sync clears the mark.
  A later review reads the work again.
- **No screen edits what the model is told.**
  Each practice's criteria shape what Hephaestus observes.
  A prompt that ships with the release shapes its text.
  A prompt change is a code change.

1. Provision storage for the mirror, captured content, and per-job staging.
2. For larger monorepos, raise `GIT_MAX_SNAPSHOT_BYTES`.
3. Size the fabric root for the repositories you monitor.
