This page lists what the webhook receiver of the server stores, its answers, its meters and alerts, and the retention of the provider event inbox.
The inbox is a PostgreSQL table that holds each verified delivery until a server handles it.
[Ingest durability](/contributor/ingest-durability#the-database-inbox) explains the design.

## What the receiver stores

The receiver verifies a delivery and stores one event for each workspace whose subscription matches it.
It answers `202` only after PostgreSQL commits the events, and it answers within 2 seconds.
A GitHub App installation event also gets one event with no workspace, because it can create the workspace.

A delivery that arrives again with the same identifier adds no event:

| Provider | Identifier |
| --- | --- |
| GitHub | `X-GitHub-Delivery` |
| Slack | `event_id` |
| GitLab | A hash of the body, the event UUID and the event kind, for each connection |

Each server claims due events from the inbox.
A workspace handles the events of one resource, such as a repository or a Slack channel, one at a time and in arrival order.
`server.inboxClaimers` sets how many events one server handles at once. The default is 8.
[Replay a failed webhook event](./webhook-replay.mdx) gives the retries, the dead letters and their replay.

## Receiver answers

| Answer | Cause | Log record |
| --- | --- | --- |
| `202` | The inbox stored the delivery. A duplicate, or a delivery that no active connection admits, adds no event. | `Stored <kind> webhook`, or `Webhook admission refused` with the reason |
| `503` with the detail `store-failed` | PostgreSQL did not store the delivery in time. | `event.name=webhook.publish.failed`. The message names the exception class. |
| `503` with the detail `gate-unavailable` | The publish gate of the provider could not read the database. | `Publish gate for kind=<kind> unavailable` |
| `503` with the detail `busy` and `Retry-After: 30` | Large deliveries fill the memory that the receiver holds for them. See [Payload size](#payload-size). | None. `webhook.rejected` counts `reason=busy`. |
| `408` with the detail `too-slow` | The body did not arrive within 30 seconds. | None. `webhook.rejected` counts `reason=too-slow`. |

A transaction that commits after a `503` adds no event when the provider sends the delivery again.

## Failed GitHub deliveries

GitHub records a delivery as failed when the receiver answers with an error or takes longer than 10 seconds.
GitHub does not retry a failed delivery.
It keeps deliveries of the past three days, and it can [redeliver](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks) them.

Every 10 minutes, the server reads the GitHub App's recent deliveries from the [GitHub App webhook API](https://docs.github.com/en/rest/apps/webhooks).
For each event with no successful delivery, it asks GitHub to redeliver the latest attempt when the next redelivery is due.
GitHub [recommends](https://docs.github.com/en/webhooks/using-webhooks/automatically-redelivering-failed-deliveries-for-a-github-app-webhook) this procedure.

How far a run reads back:

- A run reads back 2 hours from the start of the previous run.
  It reads further back for an event that it still redelivers.
- A run that cannot read the deliveries changes nothing, so the next run reads the whole gap.
  This also covers a database outage: the run then does not start, because its lock is in the database.
- The first run after a server starts reads back 71 hours.
  GitHub keeps deliveries for 3 days, and a redelivery requested an hour before that limit is still accepted.
  Thus, a server that stops on a Friday evening recovers the deliveries of the weekend when it starts on Monday.
- A run reads at most 10,000 deliveries. Older ones are not redelivered, and the run counts `outcome=truncated`.

How a run redelivers:

- One run at a time works across all server replicas. A run sends requests for at most 5 minutes, and at most 5 each second.
- A run stops after GitHub refuses 5 requests in a row, or after GitHub answers `403` or `429`. The other events wait for the next run, the oldest first.
- If the newest 10 redeliveries all failed, a run sends only 3 redeliveries as probes and counts `outcome=paused`.
- An event whose latest answer was a `4xx` is not redelivered. The receiver refused it on purpose, for example for a bad signature.
- An event gets at most six attempts: the original and five redeliveries.
  The redeliveries are due 0, 10, 20, 40 and 80 minutes after the original.
- A redelivery keeps its `X-GitHub-Delivery` identifier, so a redelivery of a stored delivery adds no event.
- Silent mode does not stop redelivery. A redelivery only asks GitHub to send the event to the receiver again.

The job needs the GitHub App ID and private key.
`github.webhook.unrecovered` counts an event that failed all six attempts, for 2 hours after its last attempt.
Redeliver such an event in the GitHub App settings under **Advanced** → **Recent Deliveries**, within three days.
After three days, only the reconciliation sync recovers its effect.

## Which providers deliver again

| Provider | Delivers a failed event again | What else recovers it |
| --- | --- | --- |
| GitHub | Hephaestus asks GitHub to redeliver, on the schedule above. | Manual redelivery for three days, then reconciliation. |
| GitLab | No. GitLab does not retry a failed webhook. It disables a hook after 4 failures in a row, for 1 minute up to 24 hours, and permanently after 40. See [GitLab webhooks](https://docs.gitlab.com/user/project/integrations/webhooks/). | Reconciliation over `config.sync.timeframeDays` days. |
| Slack | Yes. Slack retries 3 times: at once, after 1 minute and after 5 minutes. With [Delayed Events](https://docs.slack.dev/apis/events-api/) on in the Slack app, it also retries every hour for 24 hours. | Reconciliation of monitored channels. |
| Outline | No. Outline waits 5 seconds and does not retry. It disables a subscription when 80 % of its deliveries in 24 hours fail. | Reconciliation of the Outline connection. |

## What to alert on

The server exports these meters on its private management listener.
[Scrape metrics](./monitoring.md#scrape-metrics) gives the port and the scrape configuration.
[Alert rules](./alert-rules.md) gives the thresholds of the shipped alerts.
[Alert response](./production-operations-runbook#alert-response) gives the action for each alert.

| Meter | Type | What it counts | Shipped alert |
| --- | --- | --- | --- |
| `webhook.publish` | counter | Deliveries that the inbox stored (`outcome=success`) or did not store (`outcome=failure`), by `stream`, which names the provider. | `HephaestusWebhookPublishFailing` |
| `webhook.rejected` | counter | Deliveries that the receiver refused, by `provider` and `reason`, such as `busy`, `too-slow` or `connection-not-active`. | `HephaestusWebhookReceiverBusy` (`reason=busy`) |
| `integration.consumer.oldest.due.seconds` | gauge (s) | Seconds since the oldest due event of a `provider` became due. 0 when none is due. | `HephaestusProviderEventsWaiting` |
| `integration.message.lag` | timer | How long an event waited in the inbox before its first handling, by `kind`. | `HephaestusEventsDelayed` |
| `integration.message.process.duration` | timer | How long the handling of one event took, by `kind` and `outcome`: `completed`, `failed`, `retried`, `dropped` or `timed_out`. | `HephaestusConsumerHandlerTimedOut` (`outcome=timed_out`) |
| `integration.consumer.backlog` | gauge | Events in the inbox, by `provider` and `state`: `QUEUED`, `LEASED` or `DEAD`. | None |
| `integration.consumer.backlog.sampler.failures` | counter | Passes that could not read the backlog. The gauges keep their last values. | `HephaestusProviderEventBacklogUnsampled` |
| `integration.consumer.retry` | counter | Attempts that failed and wait for a retry, by `kind`. | `HephaestusConsumerRetryStalled` |
| `integration.consumer.poison` | counter | Events that became dead letters, by `kind`. | `HephaestusConsumerPoison` |
| `integration.message.dropped` | counter | Attempts that the write fence stopped, by `kind` and `reason`: `erased-during-processing` or `lease-lost`. | None |
| `integration.consumer.inbox.retention.failures` | counter | Retention passes that failed. | `HephaestusInboxRetentionFailing` |
| `github.webhook.redelivery` | counter | Redelivery requests that GitHub accepted (`requested`) or refused (`refused`). Runs that could not read the deliveries (`unavailable`), only probed a failing receiver (`paused`), or stopped listing at a bound (`truncated`). | `HephaestusWebhookRedeliveryNotRunning` (`refused`, `unavailable`), `HephaestusWebhookRedeliveryTruncated` (`truncated`), `HephaestusWebhookRedeliveriesRequested` (`requested`) |
| `github.webhook.unrecovered` | gauge | GitHub events that failed all six attempts, the last one in the past two hours. | `HephaestusWebhookEventsUnrecovered` |

The events of a suspended workspace are not claimed, but they count in `integration.consumer.oldest.due.seconds`.
An `erased-during-processing` drop is the expected result of an erasure while a handler runs. Do not replay it.

## How long the inbox keeps an event

| Event | Kept for |
| --- | --- |
| Handled | 3 days after its handling |
| Dead letter | 30 days after its failure |
| Queued or leased | Until it is handled or becomes a dead letter |

The chart does not change these periods.
The handled events cover the three days in which GitHub can redeliver, so a late redelivery is not handled twice.
Plan PostgreSQL space for 3 days of webhook traffic, plus the dead letters of 30 days.

One server deletes the ended events every hour.
Deleting a workspace deletes its events.
Erasing a person deletes the events that name them. An event that a server handles at that moment stays until its retention removes it.

## Payload size

The receiver accepts deliveries up to 25 MiB, the GitHub delivery cap.
The inbox stores the body as it arrived.

The receiver holds each delivery in its heap until the inbox stores it, and a body costs several times its size.
A delivery of 256 KiB or less never waits.
A larger delivery that does not fit in the heap budget waits for 1.5 seconds, and then gets the `busy` answer.
To hold more at once, raise the memory in `server.resources`.
