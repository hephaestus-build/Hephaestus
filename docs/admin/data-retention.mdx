This page lists what a self-hosted instance stores, where, and for how long.
Each period comes from the code or the shipped configuration.
"No automatic deletion" means that no scheduled job deletes the data.
The **Deleted by** column then names what still removes it.
The [personal-data map](./dsms/personal-data-map.md) describes workspace purge, disconnection, and verified person erasure.
The operator's [record of processing](./dsms/record-of-processing.md) gives the legal basis of each category.

The **Setting** column names the environment variable when the supported stack forwards it from `.env`.
Otherwise, it names the Spring property, and the value is fixed in the supported stack.
The [configuration reference](./configuration-reference) lists the settings that have an environment variable.
The times of the scheduled jobs are in the time zone of the server process.

## Webhook dead letters

Failed events retain only broker coordinates, a subject, timestamps and an error class in PostgreSQL.
No payload, headers, exception text or routing credential is copied into this table.
The original event remains in NATS under the stream retention limits below.
Replay cannot recover an expired event.

Workspace deletion removes that workspace's dead-letter records through the workspace foreign key.
Unassigned installation events have no workspace and remain until the instance is removed.

Replay completion records the requesting account ID and time without deleting the metadata.
Person export includes the replay actor's metadata, without subjects or payloads.
Person erasure clears the actor reference through the integration store contributor.
Account deletion also clears it through the foreign key.

Person erasure does not extend the broker retention period or create another payload copy.
Replay still uses the current adapter admission checks.
Restrict database and backup access as for other provider data.
See [Replay a failed webhook event](./webhook-replay.mdx).

## Worker disk

The worker keeps these files under `/data/worker-git-repos`, on the `worker-git-repos` volume.

| Data | Retention | Setting | Deleted by |
| --- | --- | --- | --- |
| Debug transcript of an agent run | 24 hours. It goes earlier when the job's evidence expires. | None | A worker sweep every minute |
| Inputs of an attempt | Until the result is admitted. Otherwise, 1 hour after the attempt ends. A worker restart deletes them. | None | The same sweep |
| Repository mirrors of the worker, one for each workspace and repository | As [Git repository history and short-lived attempts](./dsms/personal-data-map.md#git-repository-history-and-short-lived-attempts) describes | None | A worker check every minute |

## PostgreSQL

The jobs that delete review job data run only when `AGENT_ENABLED` is `true`.

| Data | Retention | Setting | Deleted by |
| --- | --- | --- | --- |
| Capture and output of a review job | 14 days after the job ends. A job that waits for delivery keeps them. | `hephaestus.agent.payload-retention` | A server job every 6 hours |
| Review job rows, with their script runs and attempt usage | 90 days after the job ends | `hephaestus.agent.row-retention` | The same job |
| Original review inputs (composition basis) | Until they expire. The end of the job also deletes them. | None | The same job |
| Evidence-copy receipts | As long as their review job row. After that, until the worker that held the copy confirms its removal. | `hephaestus.agent.row-retention` | The same job, after the worker confirms. Person erasure and workspace purge clear the identities earlier. |
| Evidence of an item event | Replaced by a marker 30 days after it is recorded | `hephaestus.item-event-ledger.retain-for` | A server job every 15 minutes |
| Item events that nothing references | 30 days after their decision | `hephaestus.item-event-ledger.retain-for` | The same job |
| Item events that stay pending | They expire after 7 days. The expired row goes 30 days later. | `ITEM_EVENT_LEDGER_PENDING_LAPSE_AFTER`, `hephaestus.item-event-ledger.retain-for` | The same job |
| Practice results that no feedback cites, and the raw proof of scans | 400 days | None | A server job at 03:00 every day |
| Feedback and its delivery records | No automatic deletion. Conversation feedback that is never shown is withheld after 14 days and kept. | None | Workspace purge or person erasure |
| LLM usage records | 400 days | `HEPHAESTUS_LLM_USAGE_RETENTION` | A server job at 04:15 every day |
| conversations | No automatic deletion | None | Workspace purge, person erasure, or Slack disconnection |
| Slack messages and threads | 30 days for each connection, at most 180 days. A message deleted in Slack goes earlier, as [Messages deleted or edited in Slack](#messages-deleted-or-edited-in-slack) says. | None | A server job at 03:30 every day |
| Outline documents | No age limit. Document bodies above 200 MB for each workspace are evicted. | `hephaestus.integration.outline.cache.max-size-mb` | Outline sync |
| GitHub and GitLab mirror tables | No age limit while a workspace monitors the repository | None | Repository monitoring |
| Sync job history | The newest 50 runs of each connection | None | Each new sync run |
| Connection audit records | No automatic deletion | None | Workspace purge |
| Authentication events, including sign-ins, user views, IP address, and user agent | 12 months, in monthly partitions | None | Partition maintenance at 00:10 every day |
| Configuration audit events | 365 days | None | A server job at 00:20 every day |
| Issued access tokens | Until they expire. Access tokens last 24 hours. | `hephaestus.auth.access-ttl` | A server job at 03:30 every day |
| Client sessions | At most 7 days. A revoked session goes 1 day after revocation. | `hephaestus.auth.session-max-lifetime` | A server job every hour |
| OAuth state values | 7 days | `hephaestus.integration.oauth-state.nonce-retention` | A server job at 04:00 every day |
| Email notifications waiting for delivery | Deleted when delivered. An account deletion confirmation expires at the purge deadline. Security, alert, and weekly digest mail expires after 24 hours. Product feedback mail expires after 7 days. | None | Delivery and the retry job |
| Self-service account exports | The download goes 48 hours after it is ready. | None | A server job every hour |
| Deleted accounts | Removed 48 hours after the request, by the next hourly sweep | `hephaestus.auth.delete-cooldown` | A server job every hour |
| Product feedback reports, drafts, and choices | No automatic deletion by age | None | Account or person erasure removes account-owned rows. Workspace purge removes reports from that workspace. Both start applicable GitHub cleanup. |
| Product feedback cleanup locators | Until external cleanup completes. After 30 days, incomplete work needs manual action. The locator remains until completion or admin confirmation. | None | Cleanup or confirmed manual completion ([Product feedback](./product-feedback.mdx#handle-erasure)) |
| Research disclosure records | No automatic deletion. The released file is not stored. | None | Closure of the disclosure removes its mapping |

## Messages deleted or edited in Slack

Slack sends an event when a person deletes or edits a message in a monitored channel.
For a deletion, Hephaestus erases the stored text and keeps only an empty marker.
For an edit, it stores the new text.

The event can fail to arrive: Slack stops after its retries, or the event ages out of NATS during a long outage.
The nightly Slack sync then finds the change.
It reads the history of each active monitored channel and compares it with the stored messages:

- A stored message that a complete read no longer returns is erased, as the event would erase it.
- A stored message that Slack shows as edited gets its new text.

A read that stops early removes nothing: an error, a rate limit, a request budget that ran out, a consent change or a cancelled job.

These limits remain:

- The sync reads only active channels.
  In a paused or archived channel, a lost deletion stays until the channel is active again.
  Otherwise, the retention sweep deletes it with its thread.
- The sync compares only messages inside the retention window and from the last 89 days.
  Slack's free plan hides messages older than 90 days from apps, so their absence proves nothing.
  A thread that is still active keeps its older messages until the thread ages out.
- Messages stored in the last 10 minutes are compared on a later night.
- The sync compares a reply only when the reply count of its thread differs from the stored replies.
  It finds the edit of a reply only then.
- `hephaestus.sync.slack.reconcile-request-budget` limits the requests for messages older than the last sync.
  The default is 30 requests for each workspace each night.
  Each request waits `hephaestus.sync.slack.history-request-interval`, 60 seconds by default.
  Thus the check can add 30 minutes to the nightly sync of each workspace.
  At 15 messages a request, the default budget reads about 450 messages of Slack history a night.
  The check continues each channel on the day where it stopped, and the channel checked longest ago goes first.
  A larger workspace thus takes more nights for a full check.
  One day of a channel that needs more than the whole budget is not compared.
- The check keeps up only while one night's budget reads more than one day of the workspace's history.
  At the defaults, that is about 450 messages and replies a day.
  In a busier workspace, the oldest messages leave the 89-day window before the check reaches them.
- The default budgets and interval suit the rate limits of commercially distributed apps outside the Slack Marketplace.
  An app that you create for your own Slack workspace has higher limits.
  For such an app, raise the budgets and shorten the interval.

Direct messages with Hephaestus are not part of this sync.

## NATS JetStream

The `nats-data` volume keeps webhook deliveries.
Each stream deletes its oldest messages first when it reaches its age limit or its size limit.
[Webhook ingestion operations](./webhook-ingestion-operations#how-long-a-delivery-is-actually-kept) gives the limits of each stream and their settings.

## Logs and traces

| Data | Retention | Where to change it |
| --- | --- | --- |
| Container logs       | The kubelet's configured size and file-count limits                    | The node's kubelet configuration |
| Logs shipped to Loki | The retention that you set in Loki | Loki |
| Traces | Off by default. The OTLP recipient keeps them under its own retention. | `TRACING_OTLP_ENABLED` |

No container writes an HTTP access log.

## Backups

| Data | Retention | Where to change it |
| --- | --- | --- |
| pgBackRest backups, when enabled in the chart | Two full backups, with their differential backups and WAL. [Backup and restore on Kubernetes](./kubernetes#backup-and-restore) gives the schedule. | `postgresql.backup.retentionFull` in site values |
| A plain `pg_dump` file | No automatic deletion | Delete the file yourself |

A backup contains the whole database, so it also contains data that the instance deleted later.
Erasure does not reach a backup.
[Backup & restore](./backup-restore) gives the restore procedure.
