The GitHub App gives Hephaestus access to the repositories of an organization.
Hephaestus syncs them, receives their webhooks, and posts feedback with the identity of the App.
Register one App for each instance, such as production and staging, because an App has one webhook URL.
Sign-in with GitHub uses a separate OAuth App, also one for each instance, as [First steps § 1](./first-steps#1-configure-a-login-provider) describes.

## Before you start

- An installed instance that serves its host over HTTPS ([Install on Kubernetes](./kubernetes)).
- The owner role in the GitHub organization that owns the App.
- `kubectl` with access to the release namespace, and `jq`.

The commands use the release namespace `hephaestus` and the release Secret `hephaestus-app`.
Replace these names if your release uses other names.

## Register the GitHub App {/*#github-app-mode*/}

1. Open `https://github.com/organizations/<org>/settings/apps/new`.
2. Set **GitHub App name** to a name for this instance, such as `acme-hephaestus`.
3. Set **Homepage URL** to `https://<host>`.
4. Set **Callback URL** to `https://<host>/api/oauth/callback/github`.
5. Select **Request user authorization (OAuth) during installation**.
6. Under **Webhook**, select **Active**.
7. Set **Webhook URL** to `https://<host>/webhooks/github`.
8. Show the webhook secret of the release:

   ```bash
   kubectl -n hephaestus get secret hephaestus-app -o jsonpath='{.data.WEBHOOK_SECRET}' | base64 -d; echo
   ```

9. Enter that value in **Secret**.
   Do not put the value in a ticket or a log.
10. Set the permissions of [Required permissions](./github-app-permissions#required-permissions) and [Provisioned permissions](./github-app-permissions#provisioned-permissions).
11. Select the events of [Event subscriptions](./github-app-permissions#event-subscriptions).
12. Under **Where can this GitHub App be installed?**, select **Any account**.
13. Select **Create GitHub App**.
14. On the page of the App, copy the **App ID** and the **Client ID**.
15. Select **Generate a new client secret**, and copy the secret.
16. Under **Private keys**, select **Generate a private key**.
    Your browser downloads a `.pem` file.
17. Optional: upload [`external-app-icon-1024.png`](/img/brand/external-app-icon-1024.png) as the display image.

GitHub does not follow a redirect when it delivers an event.
Thus, the **Webhook URL** must reach the server directly, on the host of the instance.

`WEBHOOK_SECRET` also verifies each GitHub webhook that you create by hand.
Thus, use the value that the release Secret holds, and do not make a new one.
If the Secret has no `WEBHOOK_SECRET`, run `hephaestus-keys.sh` again, as [Create the Secret](./kubernetes#create-the-secret) describes.

## Set the Helm values and Secret keys {/*#install-and-configure*/}

1. Type the client secret of the App. The shell does not show it:

   ```bash
   read -rs GH_APP_CLIENT_SECRET && export GH_APP_CLIENT_SECRET
   ```

2. Add the private key and the client secret to the release Secret.
   Replace the file name with the name of your `.pem` file:

   ```bash
   jq -n --rawfile key acme-hephaestus.private-key.pem --arg secret "$GH_APP_CLIENT_SECRET" \
     '{stringData: {GH_APP_PRIVATE_KEY: $key, GH_APP_CLIENT_SECRET: $secret}}' |
     kubectl -n hephaestus patch secret hephaestus-app --type merge --patch-file /dev/stdin
   ```

   `jq` keeps the line breaks of the key.
   Keep the `.pem` file only in your secret store.

3. Add the App to `site.yaml`:

   ```yaml title="values.yaml"
   config:
     github:
       appId: 123456
       appClientId: Iv23liExampleClientId
       appInstallationUrl: https://github.com/apps/acme-hephaestus/installations/new
   ```

   `appInstallationUrl` is the public page of the App, followed by `/installations/new`.
   With it, **Create workspace** offers **GitHub**.

4. Apply `site.yaml`.
   On a cluster, run the `helm upgrade` command of [Install](./kubernetes#install) again.
   On one host, run the installer again ([Run the installer](./k3s#2-run-the-installer)).
   The changed values restart the server, and the new server reads the new keys.

## Install the App

1. Open the address of `appInstallationUrl`.
2. Select the organization.
3. Select all repositories, or only the repositories to monitor.
4. Confirm the installation.
   GitHub returns you to Hephaestus.
5. Select **Continue**.
6. Open **Instance administration → GitHub installations**.
7. Select **Adopt** for the installation.
   Hephaestus creates the workspace with you as its owner, and starts the first sync.

To change the repositories later, change the installation on GitHub.
Hephaestus syncs the repositories that the installation can read.

An installation belongs to one workspace.
Hephaestus refuses to connect it to a second workspace.

When GitHub returns a person with no workspace to connect, Hephaestus shows the setup page of the installation.
The setup page never creates a workspace.
It names an existing workspace only to its members and to instance admins.
It also tells the person when an instance admin declined the installation.

A person who cannot install Apps on the organization sends an installation request to its owners instead.
After an owner approves the request, the person connects GitHub again.

### Who creates the workspace of an installation

`config.workspaceCreationPolicy` sets who creates workspaces:

| Value | A new GitHub App installation | **Create workspace** in Hephaestus |
| --- | --- | --- |
| `ADMIN_ONLY` (default) | Waits until an instance admin adopts it | Instance admins only |
| `SELF_SERVICE` | Creates its own workspace, without approval | Every signed-in user |

Under `ADMIN_ONLY`, **GitHub installations** lists each new installation:

- **Adopt** reads the installation again from GitHub.
  Hephaestus refuses a suspended installation, an installation that GitHub no longer has, and an installation that moved to another account.
- **Decline** keeps the installation in the list.
  An instance admin can adopt it later.

Adopt and decline need a recent sign-in.
The audit log records each decision with the installation ID.
To undo an adoption, delete the workspace.
The installation stays adopted, and a later installation event does not create a workspace for it.
For a personal account, Hephaestus then removes the account's login and id from the record.
To use the account again, uninstall the App on GitHub and install it again.

### Workspaces without the GitHub App

The web app creates a GitHub workspace only from a GitHub App installation.
No supported interface creates a GitHub workspace that syncs with a personal access token.
For an existing token workspace, the web app can replace the token and add repositories.
Its token needs the scopes of [Fine-grained token permissions](./github-app-permissions#fine-grained-token-permissions), or the `repo` and `read:org` scopes of a classic token.
Feedback that Hephaestus posts then shows the person who owns the token.
For webhooks, add an organization webhook with the URL and secret of [Register the GitHub App](./github-integration.mdx#github-app-mode), and with the events that GitHub offers for it.

## Check that it worked

1. Open or update a pull request in a monitored repository.
2. On the page of the App, open **Advanced → Recent deliveries**.
   The delivery shows a `2xx` response.
3. Open the workspace in Hephaestus.
   The change shows without a wait for the scheduled sync.

The first `ping` delivery returns `200` also with a wrong secret.
Thus, check a real event.
If a delivery fails, read [GitHub deliveries return `401`](./troubleshooting#github-deliveries-return-401) and [Failed GitHub deliveries](./webhook-ingestion-operations#failed-github-deliveries).

## Undo

Uninstall the App on GitHub to remove its access.
Hephaestus then purges the workspace of that installation, with the work that it synced.

1. Open the settings of the organization on GitHub, then **GitHub Apps**.
2. Select **Configure** for the App, then **Uninstall**.
3. Remove `config.github.appId`, `config.github.appClientId` and `config.github.appInstallationUrl` from `site.yaml`.
4. Remove the keys from the release Secret:

   ```bash
   kubectl -n hephaestus patch secret hephaestus-app --type json \
     -p '[{"op":"remove","path":"/data/GH_APP_PRIVATE_KEY"},{"op":"remove","path":"/data/GH_APP_CLIENT_SECRET"}]'
   ```

5. Apply `site.yaml` as in [Set the Helm values and Secret keys](./github-integration.mdx#install-and-configure).

[GitHub App keys](./secret-custody#github-app-keys) describes how to replace the private key and the client secret without a gap.

## Transfer the App to another owner

A transfer keeps the App ID, the client credentials, the private keys and, normally, the installations.
Do not delete the App and register it again.

1. Check that **Where can this GitHub App be installed?** is **Any account**.
2. On the page of the App, open **Advanced**, and select **Transfer ownership**.
3. Read each warning before you continue. GitHub warns when a transfer would uninstall the App ([Transferring ownership of a GitHub App](https://docs.github.com/en/apps/maintaining-github-apps/transferring-ownership-of-a-github-app)).
4. After the transfer, check **Where can this GitHub App be installed?** again.
5. Check the installations, their repositories, and a recent delivery.
6. If the previous owner must lose access, replace the private key and the client secret, as [GitHub App keys](./secret-custody#github-app-keys) describes.

A transfer does not revoke the copies of the keys that the previous owner holds.
