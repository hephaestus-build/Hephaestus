The Hephaestus Chrome extension shows the practice review of a pull request, merge request or issue on its provider page.
Your instance accepts a sign-in only from the extension IDs that you allow.
The extension is not in the Chrome Web Store, so you deploy the signed package of each release to your users.
The user guide's [Chrome extension](/user/browser-extension) describes what people see.

## Before you start

- The release version that your server runs.
- `gh` and `cosign`, to verify the package.

## Get the extension package

Take the package of the release that your server runs, with its signature and the release attestation.
Then verify both:

```bash
VERSION=X.Y.Z # the release, without the leading "v"
PACKAGE="hephaestus-chrome-extension-$VERSION.zip"
gh release download "v$VERSION" --repo hephaestus-build/Hephaestus \
  --pattern "$PACKAGE" --pattern "$PACKAGE.sigstore.json" \
  --pattern "release-v$VERSION.intoto.jsonl"
cosign verify-blob \
  --bundle "$PACKAGE.sigstore.json" \
  --certificate-identity \
    'https://github.com/hephaestus-build/Hephaestus/.github/workflows/release.yml@refs/heads/main' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  "$PACKAGE"
gh attestation verify "$PACKAGE" \
  --bundle "release-v$VERSION.intoto.jsonl" \
  --predicate-type https://in-toto.io/attestation/release/v0.1 \
  --repo hephaestus-build/Hephaestus
```

`cosign verify-blob` proves that the release workflow of Hephaestus signed these exact bytes.
`gh attestation verify` proves that the package is a subject of that release.
If either command fails, do not distribute the package.

The package is the ZIP that the Chrome Web Store takes, not a signed `.crx`.
[Release assets](./release-image-lock#release-assets) lists the other assets of a release.

## Allow the extension to sign in

1. Get the ID of each build that you distribute.
   Chrome shows the ID of an unpacked extension on `chrome://extensions`, and each unpacked folder has its own ID.
2. Add the IDs to `site.yaml`:

   ```yaml title="values.yaml"
   config:
     auth:
       browserExtensionIds:
         - abcdefghijklmnopabcdefghijklmnop
   ```

3. Apply `site.yaml`.
   On a cluster, run the `helm upgrade` command of [Install](./kubernetes#install) again.
   On one host, run the installer again ([Run the installer](./k3s#2-run-the-installer)).

The list is empty by default, and then no extension can sign in.
Each ID allows two things:

- The sign-in return address `https://<id>.chromiumapp.org/callback`, which Chrome reserves for that extension.
- API requests from the origin `chrome-extension://<id>`.

A sign-in that names another extension or return address stops on an error page of your instance.

The list controls where a sign-in returns, not which package runs.
Extension IDs and their public keys are public, so anyone can load a changed build with the same ID.
Managed distribution controls which packages your users run.
Do not list the development ID `ijkajblcbajjpjbknfgdiiiljipafiko` on a production instance: every local build of a contributor has it.

The extension uses the sign-in page of your instance, with your login providers.
You register no new OAuth application and add no callback at GitHub or GitLab.

## Deploy it to your users

- **Unmanaged Chrome.** Give users the package that you verified.
  They unzip it and load the folder on `chrome://extensions` with **Developer mode** on, as the user guide's [Install it](/user/browser-extension#install-it) describes.
  The extension does not update itself.
  Each folder has its own ID, so users send you theirs, and you add it to `config.auth.browserExtensionIds`.
  Some organizations turn off developer mode.
- **Managed Chrome.** The [`ExtensionInstallForcelist`](https://chromeenterprise.google/policies/#ExtensionInstallForcelist) policy installs an extension for every managed profile.
  A package outside the store must be a signed `.crx` that you host with an update manifest.
  Pack and sign the `.crx` with your own key, as [Self-host for Linux](https://developer.chrome.com/docs/extensions/how-to/distribute/host-on-linux) describes.
  Chrome force-installs a package outside the store only on a managed browser, such as a domain-joined, MDM-managed or cloud-enrolled one.
- **Limit where it runs.** The `runtime_blocked_hosts` setting of the [`ExtensionSettings`](https://chromeenterprise.google/policies/#ExtensionSettings) policy removes sites from its reach, also with the permission of the user.

The extension reads GitHub.com and GitLab, also a self-managed GitLab.
Users allow each provider site one at a time.
Work on a provider that no workspace connects shows as not available.
GitHub Enterprise Server is not supported.

## Check that it worked

1. Ask your instance whether it accepts an ID:

   ```bash
   curl "https://<host>/api/auth/client/configuration?clientId=<extension id>"
   ```

   `{"registered":true}` means that the ID is in the list.

2. Sign in from the options page of the extension.
3. Open **User settings**.
   The session list shows **Browser extension in Chrome on …**.

## Undo

1. Remove the ID from `config.auth.browserExtensionIds`.
2. Apply `site.yaml`.

A new sign-in from that extension then fails.
To end its sessions that exist, ask each user to end them in **User settings**, or force a sign-out as an instance admin.

## Keep the server current

Chrome can update a managed extension before you upgrade the server.
The extension works with every server that names version 1.0.0 or later in `/.well-known/hephaestus.json`.
On an older server, the extension says that the server is too old and asks users to contact you.
After you upgrade, it works again without a reinstall.

## Sessions and limits

An extension session ends with the web sessions of the account, at the same absolute limit.
[Session deadlines](./configuration-readiness#session-deadlines) gives the limits.
The chart has no value that changes them.

Sign-in starts share a limit of 20 requests a minute for each network address.
Code redemption, session renewal and sign-out share a limit of 30 requests a minute for each address.
The chart has no value that changes these limits.
If many users behind one address get HTTP `429`, spread their sign-ins over several minutes.

The user guide's [Chrome extension privacy](/user/browser-extension-privacy) states what the extension sends to your instance.
