At the end of this tutorial, your instance has a first admin, a workspace with GitHub data, and a first practice review that you approved.
The steps configure the Helm chart on [Kubernetes](./kubernetes).
Stages 1 and 2 set values before the first start, so the install pages link to them.
Stages 3 to 6 follow the first start.

## Before you start

- An instance of the Helm chart. [Install on one host](./k3s) or [on a Kubernetes cluster](./kubernetes) installs it.
- The host name of the instance.
- A GitHub organization in which you can create and install apps.
- An account at an AI provider, with an API key.

This tutorial uses GitHub for sign-in and for repository data.

## 1. Configure a login provider

GitHub login needs a plain **OAuth App**.
This is *not* the GitHub App for data access, which stage 4 creates.
Without a login provider, the instance boots but shows **no sign-in button**.

1. Open [github.com/settings/developers](https://github.com/settings/developers), or your organization's equivalent settings.
2. Select **New OAuth App**.
3. Set **Homepage URL** to `https://<your hostname>`.
4. Set **Authorization callback URL** to `https://<your hostname>/api/login/oauth2/code/github`.
   The string must include `/api` and have no trailing slash.
5. If the GitHub settings page offers an image upload, use [`external-app-icon-1024.png`](/img/brand/external-app-icon-1024.png) as the application logo.
6. Create a client secret.
7. Set the client ID as `config.github.oauthClientId` in `site.yaml`.
8. Put the client secret as `GITHUB_OAUTH_CLIENT_SECRET` in the [Secret](./kubernetes#create-the-secret).

## 2. Name the first admin

The admin UI requires admin access.
The **first instance admin must therefore come from operator config**, not the UI.

1. Before the first start, set the first admin.
   Set `config.auth.bootstrapAdmins: ["github:@your-github-username"]` in `site.yaml`.

   Add one array item for each admin, as `<provider>:@<username>` or `<provider>:<numeric-id>`.
   Promotion occurs **on sign-in**.
   It is idempotent and never demotes.

2. On public github.com, prefer the numeric ID (`github:1234567`, from `https://api.github.com/users/<login>`).
   Others can reclaim abandoned handles.
3. If you omitted the value, add it.
   Then run the install command again: `helm upgrade --install` with your site values.

For the break-glass bootstrap token, see [Instance administration](./instance-admin#bootstrap-and-recovery).

## 3. Sign in

After the first start:

1. Open `https://<your hostname>`.
   The login page should offer **Continue with GitHub**.
2. Sign in as the bootstrap admin.
   You should see instance-admin navigation.
3. Open **Instance administration → Overview**.
4. Read **Configuration readiness**.

   Each item under **Action required** needs a change and links to its section in [Configuration readiness](./configuration-readiness).
   **Not configured** lists optional settings you have not set, such as email.
   The page never shows a setting's value.

5. Leave optional settings until you want them.

## 4. Connect repository data

Login alone syncs nothing.
A **GitHub App** reads the repositories, receives their webhooks, and posts feedback with its own identity.

1. Create the GitHub App, as [GitHub App mode](./github-integration#github-app-mode) describes.
   Its webhook points at `https://<your hostname>/webhooks/github` with your `WEBHOOK_SECRET`.
2. Install the App on your organization, and set its chart values and Secret keys, as [Install and configure](./github-integration#install-and-configure) describes.
3. Open **Instance administration → GitHub installations**.
4. Select **Adopt** for the installation.
   Hephaestus creates the workspace with you as its owner and starts the first sync.

## 5. Connect an AI provider

Practice review needs a running server and a model that the workspace can run on.
The job queue runs on PostgreSQL, so practice review needs no NATS setup.

1. Turn on the server, reviews, and repository checkouts in the [chart values](./helm-chart#integration-values).
   On Kubernetes, the `small.yaml` profile turns on the server.
2. Run the install command again with your site values.
3. Connect the provider, then price, enable, and share a model, as [The staged flow](./ai-providers#1-the-staged-flow-and-why-it-is-staged) describes.
4. As a workspace admin, assign the model to **Practice reviews** on the workspace's **AI models** page.
   The row shows the model and does not read **Not ready**.

## 6. Run the first practice review

A new instance starts in **Silent mode**.
Sync and reviews can run, but outbound feedback is blocked.
The procedure runs one review and lets you read its feedback before anyone else can.

1. Open **Practices → Review settings → How much**.
2. Set the **Workspace default** to **Approve first**.
   Each piece of feedback waits for your approval.
3. Follow [First successful review](./practice-review#first-successful-review).
4. When the review finishes, open **Practices → Practice reviews**.
   Its feedback is listed under **Needs you**, awaiting approval.
   Nothing reaches the pull request before you approve it.
5. Open the feedback.
6. Read it.
7. Read the problems behind it.
8. Open **Instance administration → Instance settings**.
9. Turn silent mode off.
   Turning silent mode off does not replay feedback withheld while it was on.
   [Silent mode](./instance-admin#silent-mode) describes the switch.
10. Approve or reject the feedback.
