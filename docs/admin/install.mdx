This is the **only supported install path**: the Docker Compose stack in
[`docker/self-host/`](https://github.com/hephaestus-build/Hephaestus/tree/main/docker/self-host)
on one Linux host. Other setups (own reverse proxy, external database, Kubernetes, Podman)
can work but are unsupported.

The stack you get:

| Service              | What it is                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------- |
| `reverse-proxy`      | Traefik — TLS through `Let's Encrypt`, routes `/`, `/api`, `/webhooks`                       |
| `webapp`             | React SPA served by nginx                                                                    |
| `application-server` | Spring Boot API                                                                              |
| `application-worker` | Same image, worker profile — runs the AI sandboxes. The only service given the Docker socket |
| `webhook-server`     | Same image, webhook profile — keeps receiving events while the app restarts                  |
| `postgres`           | PostgreSQL 18 + pg_partman (custom image — vanilla `postgres:18` is **not** a drop-in)       |
| `nats-server`        | NATS JetStream event buffer                                                                  |

Docker Compose on one Linux host supports all 1.x releases.
**Hephaestus 2.0 runs on Kubernetes only**.
It includes one Helm chart and removes the Compose stack described here.
The 2.0 release includes a migration guide for your database, event buffer, and secrets.
You lose none of your current configuration.
See
[ADR 0041](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0041-compose-1x-kubernetes-2.md)
for the decision and the conditions that would reverse it.

## Requirements

### Supported host matrix

Hephaestus supports the specified single-host stack on the following native (not emulated) hosts:

| Distribution     | CPU architecture       |
| ---------------- | ---------------------- |
| Ubuntu 24.04 LTS | x86-64 (`amd64`)       |
| Ubuntu 24.04 LTS | ARMv8 64-bit (`arm64`) |

Both require the Docker Engine and Docker Compose versions in [Tested versions](#tested-versions).
Docker supports these hosts according to its [Ubuntu installation requirements](https://docs.docker.com/engine/install/ubuntu/#os-requirements).
Before publication, each release passes qualification on both matrix cells.

Only the listed native hosts and the unmodified self-hosted Compose topology are supported. Other hosts, runtimes, and topologies are outside release qualification.

### Tested versions

This table lists the versions that CI and release qualification actually run.
A version that no job runs is not in the table.

| Component | Version | What tests it |
| --- | --- | --- |

| Docker Compose | 2.24.4 or newer | Release qualification refuses an older Compose and records the version that it ran in the same assets. Every pull request checks that the Compose files render. No job runs version 2.24.4 itself. |
| PostgreSQL | 18, the release image with `pg_partman` | The merge queue runs the integration tests against an image built from the same Dockerfile before every change merges. |
| NATS server | The version that `security/release-images.json` pins | Release qualification boots it. The integration tests use NATS 2.10. |
| Traefik | The version that `security/release-images.json` pins | Release qualification sends a request through it. |
| Java | 21 | CI builds and tests with Java 21. The server image runs the Java 21 runtime of its buildpack. |
| Browsers | Chromium, the build that Playwright 1.63 bundles | The end-to-end, component, and Chrome extension suites run Chromium only. No job runs Firefox or Safari. |
| Chrome extension | Chrome 130 or newer | The extension manifest requires it. No job runs Chrome 130 itself. |
| Node.js, for release-lock verification | The version pinned in `package.json#devEngines.runtime` | CI installs this version through the setup-toolchain action. |
| Cosign, for release-lock verification | 3.1.4 | Release, promotion, and image signing jobs verify with this version. |

To see which Docker Engine and Docker Compose a release ran, download the `host-smoke-*.json` assets of that release from the [releases page](https://github.com/hephaestus-build/Hephaestus/releases).

- The CPU, memory, and disk that [Sizing](./sizing) gives.
- A host in the supported matrix, plus `git` and `openssl`.
- An NTP-synchronized clock. [Clocks](#clocks) explains why.
- A **DNS A record** that points your hostname at the host.
  Ports **80 and 443** must be reachable from the internet for `Let's Encrypt` HTTP-01, OAuth callbacks, and webhooks.
- Outbound HTTPS to the destinations in [Network egress](./network-egress).
- The [Node.js](https://nodejs.org/en/download) version pinned in `package.json#devEngines.runtime`
  and [Cosign](https://docs.sigstore.dev/cosign/system_config/installation/) for release-lock
  verification.

### Clocks

Keep the clock of every host that runs a Hephaestus role or PostgreSQL synchronized by NTP.
Heph turn leases and person erasure compare times that different hosts write.
If Slack does not answer when Heph starts a streamed reply, the server looks for that reply in the thread by time.
Hephaestus assumes that Slack's clock and the server's clock differ by less than 2 seconds.
[Heph runtime § Slack replies](/contributor/unified-pi-runtime#slack-replies) has the rule.

## 1. Get the files

1. Check out the newest version from the [releases page](https://github.com/hephaestus-build/Hephaestus/releases):

```bash
VERSION=0.94.7   # the release you are installing, without the leading "v"
sudo git clone --depth 1 --branch "v$VERSION" \
  https://github.com/hephaestus-build/Hephaestus.git /opt/hephaestus
sudo chown -R "$USER" /opt/hephaestus
cd /opt/hephaestus
cd docker/self-host
./setup.sh
cd ../..
node scripts/prepare-release-lock.ts "v$VERSION"
cd docker/self-host
```

`setup.sh` creates or updates `.env` with mode `0600`.
It generates the database password and master encryption key (`HEPHAESTUS_SECURITY_ENCRYPTION_KEY`).
It copies the master key into an empty `HEPHAESTUS_SECURITY_CREDENTIAL_ENCRYPTION_KEY`.
It also generates these values:

- OAuth state-cookie key.
- Webhook secret.
- Routing secret.
- Message-broker credentials.
- Worker registration token.
  It does not replace non-empty values and never prints a secret.
  Changing either encryption key on an existing installation makes everything encrypted under the old
  one unreadable.

Everything below runs from `/opt/hephaestus/docker/self-host`.
After step 2 supplies the remaining required values, `docker compose --env-file .env --env-file release-lock.env config` renders the effective configuration.
Before then it exits at the first missing required variable, as does every other `docker compose` subcommand in this directory.
See [Troubleshooting](./troubleshooting).

## 2. Configure `.env`

:::caution CAUTION: Back up both encryption keys
`HEPHAESTUS_SECURITY_ENCRYPTION_KEY` protects legacy encrypted values and the JWT signing key.
`HEPHAESTUS_SECURITY_CREDENTIAL_ENCRYPTION_KEY` protects integration credentials. Loss of either key
makes the corresponding database values unreadable. Store both with the database backup. Rotate the
credential key only with the [credential-key rotation procedure](./credential-key-rotation).
:::

`setup.sh` manages the internal secrets listed above.

1. Open `.env`.
2. Fill in the remaining **REQUIRED** values.
3. Do not replace the generated internal secrets manually.

   | Variable                           | What / how                                                                                                                                           |
   | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
   | `APP_HOSTNAME`                     | Your public hostname, for example, `hephaestus.example.com`                                                                                          |
   | `ACME_EMAIL`                       | `Let's Encrypt` expiry notices                                                                                                                       |
   | One login provider                 | GitHub OAuth (`GH_OAUTH_CLIENT_ID` / `_SECRET`) or GitLab OAuth (`GITLAB_OAUTH_CLIENT_ID` / `_SECRET` and its base URL), from step 3. One is enough. |
   | `DOCKER_GROUP_ID`                  | Host group ID that can access `/var/run/docker.sock`. Use the command below. A wrong value prevents every sandbox start.                             |
   | `HEPHAESTUS_AUTH_BOOTSTRAP_ADMINS` | From step 4 — set it **before** first boot                                                                                                           |

4. To find `DOCKER_GROUP_ID`, run:

   ```bash
   stat -c %g /var/run/docker.sock
   ```

   Other generated values also affect the lifecycle:

   - A database password change does not update an initialized PostgreSQL volume.
   - State-cookie key rotation invalidates OAuth flows in progress.
   - Webhook secret rotation requires the same change at each configured provider.
     The GitLab routing secret is never entered anywhere.
     GitLab group hooks stop delivery until registration repeats if you rotate the secret incorrectly.

5. Rotate it as [production setup](./production-setup#gitlab-rollout-bundle) describes.
6. Back up `.env` with the database as [Backup & Restore](./backup-restore) describes.

### Serving more than one hostname

An instance answers on `APP_HOSTNAME`.
It can also answer on other names, such as a domain you are leaving or a `www.` variant.
The reverse proxy reads `APP_HOST_MATCH` as a host matcher.
It **replaces** the default rather than extending it.

1. List all required hostnames in `APP_HOST_MATCH`.
2. Include `APP_HOSTNAME` in the matcher:

   ```ini
   APP_HOST_MATCH=Host(`hephaestus.example.com`) || Host(`old.example.com`)
   ```

   Traefik takes one hostname per `Host()`, joined with `||`. ``Host(`a`,`b`)`` is rejected and the
   router does not load at all.

3. Before deployment, point each name at this host in DNS.

The certificate covers exactly the names in the matcher.
Certificate issuance requires a challenge response on each name.
A name that does not yet resolve here delays the whole certificate.
The first name becomes the certificate's subject.
The other names become its alternative names.

`APP_HOSTNAME` remains the instance's single origin.
The SPA, API, and auth issuer all use it.
**The proxy redirects a browser that opens any other name to `APP_HOSTNAME`.**
The app therefore loads from only one host.
OAuth callback URLs stay on `APP_HOSTNAME`.

The API and webhook endpoints deliberately answer on all names in the matcher.
An open tab and a provider that still posts to the old name continue to work through the move.
The proxy redirects only what a browser loads.

The login callback uses the address where the request arrived.
A sign-in *started* at `/api/login/...` on another name asks the provider to return to that name.
The provider refuses because its only registered callback uses `APP_HOSTNAME`.
Normal access avoids this problem: the proxy redirects the browser before sign-in starts.

1. Register callbacks for `APP_HOSTNAME` only.

A callback for another name would permit a session outside the canonical origin.

The proxy controls both the matcher and the redirect.
A proxy that does not read this stack's routing configuration can send requests for any names.
In that setup, `APP_HOST_MATCH` has no effect.

1. Configure the extra names on that proxy.
2. Configure their certificate there.
3. Configure its redirect to `APP_HOSTNAME`.

## 3. Configure a login provider

One enabled GitHub or GitLab login provider is enough. Slack and Outline are for account linking,
not sign-in. The steps below configure GitHub. For GitLab, use the
[GitLab rollout bundle](./production-setup#gitlab-rollout-bundle).

GitHub login needs a plain **OAuth App**.
This is *not* the GitHub App for data access: see [GitHub integration](./github-integration).
Without a login provider, the instance boots but shows **no sign-in button**.

1. Open [github.com/settings/developers](https://github.com/settings/developers), or your organization's equivalent settings.
2. Select **New OAuth App**.
3. Set **Homepage URL** to `https://<APP_HOSTNAME>`.
4. Set **Authorization callback URL** to `https://<APP_HOSTNAME>/api/login/oauth2/code/github`.
   The string must include `/api` and have no trailing slash.
5. If the GitHub settings page offers an image upload, use [`external-app-icon-1024.png`](/img/brand/external-app-icon-1024.png) as the application logo.
6. Create a client secret.
7. Put both values into `.env` as `GH_OAUTH_CLIENT_ID` / `GH_OAUTH_CLIENT_SECRET`.

GitLab login works the same way and can be used instead of (or next to) GitHub — see the
[GitLab rollout bundle](./production-setup#gitlab-rollout-bundle).

## 4. First admin — before first boot

The admin UI requires admin access.
The **first instance admin must therefore come from operator config**, not the UI.

1. Set this value in `.env`:

   ```bash
   HEPHAESTUS_AUTH_BOOTSTRAP_ADMINS=github:@your-github-username
   ```

   The format is comma-separated `<provider>:@<username>` or `<provider>:<numeric-id>`.
   Promotion occurs **on sign-in**.
   It is idempotent and never demotes.

2. On public github.com, prefer the numeric ID (`github:1234567`, from `https://api.github.com/users/<login>`).
   Others can reclaim abandoned handles.
3. If you omitted the value, add it.
4. If you omitted the value, restart after adding it.

For the break-glass bootstrap token, see [Instance admin](./instance-admin#bootstrap-and-recovery).

## 5. First boot

```bash
docker compose --env-file .env --env-file release-lock.env up -d
docker compose --env-file .env --env-file release-lock.env logs -f database-migration application-server
```

First startup pulls about 2 GB of images, and the one-shot `database-migration` service runs all database migrations.
The application server starts after it completes. A failed migration shows in its log.
It can take a few minutes.

1. Open `https://<APP_HOSTNAME>`.
   The login page should offer **Continue with GitHub**.
2. Sign in as the bootstrap admin.
   You should see instance-admin navigation.
3. Open **Instance administration → Overview**.
4. Read **Configuration readiness**.

   Each item under **Action required** needs a change and links to its section in [Configuration readiness](./configuration-readiness).
   **Not configured** lists optional settings you have not set, such as email.
   The page never shows a setting's value.

5. Leave optional settings until you want them.
6. Create your first workspace.
7. Connect it to GitHub.

## 6. Connect repository data

A new instance starts in **Silent mode**. Sync and reviews can run, but outbound feedback is blocked.
Turning silent mode off does not replay feedback withheld while it was on.
See [Instance admin](./instance-admin#silent-mode).

1. Check the deployment and integrations.
2. Open **Instance admin → Instance settings**.
3. Turn silent mode off.

For GitLab workspaces, use [Integrations](./integrations#gitlab). For GitHub:

Login alone syncs nothing.
Data flow requires two things.
Both have procedures in
[GitHub integration](./github-integration):

1. **Repository access** — use a **PAT** in the workspace UI for the simplest setup.
   A **GitHub App** is necessary to post AI-review feedback to GitHub and offers better rate limits.
2. **Webhooks** — Hephaestus does **not** auto-register GitHub webhooks (unlike GitLab).
   Configure the webhook on your GitHub App **or** create an org/repo webhook manually,
   pointing at `https://<APP_HOSTNAME>/webhooks/github` with your `WEBHOOK_SECRET`. Without
   it the instance only sees changes on the hourly sync poll, and nothing warns you.

## 7. Optional integrations

All optional integrations are off by default.
The Compose file already passes their variables through.
Each has a variable reference in [Integration settings](./production-setup).

1. Enable the desired integrations in `.env`.
2. Run:

   ```bash
   docker compose --env-file .env --env-file release-lock.env up -d
   ```

| Add-on             | What it gives you                                                                                             | Where                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| GitLab             | GitLab login, workspaces, and sync (webhooks auto-register here)                                              | [GitLab bundle](./production-setup#gitlab-rollout-bundle)     |
| Slack              | Heph in Slack DMs, channel ingestion                                                                          | [Slack app setup](./production-setup#slack-app-configuration) |
| Outline            | Wiki as a content source for reviews                                                                          | [Outline integration](./production-setup#outline-integration) |
| AI practice review | Automated PR feedback from the coding agent                                                                   | [Practice review](./practice-review#first-successful-review)               |
| Email              | Optional invitations, summaries, weekly digest notes, and connection alerts. Configure `SPRING_MAIL_*` and `HEPHAESTUS_EMAIL_FROM` | [Email setup](./production-setup#email)                       |
| An AI provider     | The model everything AI runs on — required by the row above                                                   | [Connect an AI Provider](./ai-providers)                      |

AI practice review requires both the environment bundle above and a model that the workspace can run on.
The bundle contains `AGENT_ENABLED` and `GIT_CHECKOUT_ENABLED`.

1. Set them together on each role that submits or claims work.

The job queue runs on PostgreSQL, so this bundle needs no NATS setup.

[Connect an AI Provider](./ai-providers) explains model setup.
It covers provider connection registration, tests, model prices, model shares, and an assignment to the **practice reviews** purpose.
No reviews run until setup is complete.

If the flags are on but no model is assigned, reviews do not run.
Hephaestus records each review opportunity with the reason **No AI model is assigned to practice review.**
The reason is visible under **Practices → Practice reviews → Work**.
A workspace without an assigned model is a normal state.

## 9. First practice review

Before this procedure, GitHub must be connected (step 6).
A model must also be assigned to practice reviews ([Connect an AI
Provider](./ai-providers)).
The procedure runs one review and lets you read its feedback before anyone else can:

1. Open **Practices → Review settings → How much**.
2. Set the **Workspace default** to **Review before sending**.
   Each piece of feedback waits for your approval.
3. Follow [First successful review](./practice-review#first-successful-review).
4. When the review finishes, open **Practices → Practice reviews**. Its feedback is listed under
   **Needs you**, awaiting approval. Nothing reaches the pull or merge request before you approve it.
5. Open the feedback.
6. Read it.
7. Read the problems behind it.
8. Approve or reject the feedback.

9. Once the feedback reads as you want, widen coverage or increase feedback mode as [Practice review](./practice-review) describes.
